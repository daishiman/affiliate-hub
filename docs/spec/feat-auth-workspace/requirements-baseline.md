## この文書が答えるもの / 答えないもの

答えるのは 1 つだけ。**「4 つの受け入れ条件それぞれについて、何が満たされたら合格と言えるのか」**である。

答えないもの（先に書く）:

- 実装方法・ファイル配置・API 形。これは P02（設計）と P05/P06（実装）が持つ。
- 実装済みかどうか。確定済み auth 章の実装状態は `not_started`、検証状態は `unverified` であり、**本文書は目標仕様の写しであって現況報告ではない**。

### AWS-ACC-02 が `403` ではなく `404` である理由

`403` は「在るが見せない」を意味するため、**他所の Workspace にその ID が存在すること自体が漏れる**。存在しない ID と同じ `404` を同じ本文で返すことで、応答から存在を引けなくする。確定済み auth 章の AUTH-ACC-002 が「未存在 ID と同一の `404` 応答・本文で」としてこれを既に確定させている。

AWS-ACC-04 の `403` はこれと矛盾しない。あちらは**自分の Workspace 内**の操作であり、対象の存在は既に本人に見えている。隠すものが無いので `403` でよい。

### 検証不能な形にしないための制約

- 「隠す」で満たさない。AWS-ACC-01 と AWS-ACC-04 は**サーバー側の応答**で判定する。UI から要素を消しただけの実装は、この表の合格判定を満たさない。
- 許可側を同時に見る。拒否だけを見るテストは、全部を拒否する壊れ方に対して緑になる。AWS-ACC-04 は「Analyst の分析閲覧が成功すること」を同じテストの中で見る。
- 全部 404 に倒さない。AWS-ACC-02 は「A の自分のデータが取れること」を同じテストの中で見る。

## `spec-freshness` 門との関係（本文書を足したことの副作用）

`scripts/spec-freshness.mjs` は `docs/spec/**.md` を指紋の材料にするため、**本文書を新設した時点で完全性レポートは STALE になる**。本文書は派生・非規範であり、評価対象（確定済み仕様章と既存 `docs/spec/*.md`）を 1 バイトも変えていない。

再焼き付けの前に、レポートが焼いた 47 件の入力すべてについて現在の sha256 と突き合わせ、**変化 0 件**であることを実測した。焼き直しはこの実測を根拠とし、内容の再評価を省いた鞍替えではない。

この副作用は本文書の欠陥ではなく、指紋の粒度が「評価対象」ではなく「ディレクトリ」で切られていることによる。塞ぐなら指紋の対象から派生文書を外す必要があるが、それは `docs/spec` 直下に規範文書と派生文書が同居している現状を先に整理しないと安全側に倒せないため、**ここでは塞がず、踏んだことを記録する**に留める。
