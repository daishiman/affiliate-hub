# データモデル ギャップ分析

対象: [仕様書 §12 正規データモデル](./ai-first-webmcp.md#12-正規データモデル) ↔ 現在の `src/db/schema.ts`

本書は Phase 0 時点の読者ドメイン差分である。Analytics のフィールドと状態遷移は `03-分析・解析基盤仕様.md` を正本とする。Phase 1 で読者テーブルは追加済みだが、運営者3テーブルとの分離方針は変わらない。
作成日: 2026-08-16

## 結論

**既存3テーブルは、仕様書のどのエンティティにも対応しません。** 移行ではなく新規追加になります。

理由は扱っているドメインが違うためです。

| | 既存実装 | 仕様書 |
| --- | --- | --- |
| 主語 | **運営者** | **読者** |
| 目的 | 自分が受け取る報酬を集計する | 読者が商品を選べるようにする |
| 中心データ | ASP・案件・成果 | 記事・商品・主張・根拠 |
| 読み手 | 運営者本人とその AI | 一般読者・ブラウザーエージェント |
| 公開範囲 | 非公開（認証必須） | 公開 |

同じ「アフィリエイト」という語を使っていますが、**アフィリエイト業務管理ツール**と**アフィリエイト収益型の比較メディア**という別物です。

## 現在のスキーマ

`drizzle/0000_dry_ken_ellis.sql` で作成済み。

| テーブル | 内容 | 仕様書での対応 |
| --- | --- | --- |
| `asps` | A8.net 等の ASP マスタ | **対応なし**（仕様書に ASP の概念が無い） |
| `programs` | 案件。広告主・報酬額・料率・ステータス | **部分的に `Offer` に近い**（後述） |
| `conversions` | 成果1件。発生日・確定状態・報酬額 | **対応なし**（§23 の商業指標に間接的に関係） |

### `programs` と `Offer` の違い

一見似ていますが、決定的に違います。

| 観点 | 既存 `programs` | 仕様書 `Offer` |
| --- | --- | --- |
| 参照先 | ASP（報酬の出どころ） | Product（読者が買う物） |
| 主要フィールド | `rewardAmount` / `rewardRate`（**運営者の取り分**） | `display_price`（**読者が払う額**） |
| 鮮度管理 | なし | `checked_at` / `expires_at` 必須 |
| 在庫 | なし | `availability` |
| 複数販売店 | 想定なし | §17.3 で複数提示が要求される |

**`rewardAmount` / `rewardRate` は仕様書 §4.7 と §17.4 で「ランキングの入力に使ってはならない」と明示されたデータです。** 既存スキーマではこれが案件の中心フィールドになっています。統合するなら、報酬情報と読者向け価格情報をテーブルレベルで分離し、ランキング計算モジュールから報酬テーブルへ到達できない構造にする必要があります。

## 設計上の論点

実装前に決める必要がある事項です。

### 1. 配列フィールドの表現

仕様書は `claim_ids: []` のように配列を多用しますが、D1（SQLite）に配列型はありません。選択肢は3つです。

| 方式 | 利点 | 欠点 |
| --- | --- | --- |
| 中間テーブル | 参照整合性・逆引き・JOIN が可能 | テーブル数が増える（10個以上） |
| JSON カラム | スキーマが単純 | 外部キー制約が効かず、逆引きに全表走査 |
| 混在 | 重要な関連だけ中間テーブル | 判断基準が必要 |

§28 に「正規定義重複ゼロ」「依存循環ゼロ」があり、§4.2 が Single Source of Truth を要求するため、**参照整合性が必要な関連（`Claim`↔`Evidence`、`Article`↔`Product`）は中間テーブル**が妥当です。表示専用の順序情報（`conversation_block_ids` の並び順など）は JSON で足ります。

### 2. 既存3テーブルの扱い

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A: 残す | 運営者向け機能として維持し、公開側と分離 | §23 の商業指標に流用できる。テーブル数は増える |
| B: 削除 | 仕様書に無いので消す | 既存の MCP ツール3個とダッシュボードが動かなくなる |
| C: 縮小 | `conversions` だけ残し §23 の商業指標基盤にする | `programs` の報酬情報の置き場が消える |

**A を推奨します。** §23 が「販売店クリック率」「記事タイプ別成果」「収益」を求めており、成果データの蓄積先が必要だからです。ただし §17.4 の禁止依存を守るため、ランキング計算から報酬テーブルへ到達しないことをテストで担保します（下記 §テスト方針）。

### 3. `Claim.confidence` の意味

仕様書は `confidence: 0.0` とだけ書いており、算出方法が未定義です。誰が・何を根拠に付けるのかを決めないと、実装者ごとに解釈がぶれます。

### 4. `Evidence.integrity_hash` の対象

外部 URL の場合、ページ内容は変わり得ます。取得時点のスナップショットをハッシュするのか、URL 自体をハッシュするのかで意味が変わります。前者なら R2 へのスナップショット保存が必要です。

## テスト方針（§27 の禁止依存を仕組みで担保）

仕様書 §27 の「禁止する依存」は、口約束では守れません。次を自動テストにします。

| 禁止事項 | 検査方法 |
| --- | --- |
| WebMCP 内に独自のランキング式 | ランキング計算モジュールの import 元を検査し、UI/WebMCP 層から直接呼ばれていないこと |
| アフィリエイト成果から評価点を更新 | ランキング計算モジュールが `programs` / `conversions` / `Offer.affiliate_url` を import しないことを静的検査 |
| ベクトルDBを正規データ源として扱う | 正規データの読み出しが必ず D1 経由であること |
| UI からランキング式を直接実装 | 同上（依存方向の検査） |

`RankingModel.affiliate_compensation_is_input: false` は**定数であって設定値ではありません**。true にできる余地を残すと §4.7 が破れるため、型レベルで `false` に固定します。

## 次のアクション

1. 上記「設計上の論点」1〜4 を決める
2. Phase 1 に必要な最小エンティティ（`Article` / `Category` / `Author` / `Disclosure` / `UpdateLog`）から Drizzle スキーマを起こす
