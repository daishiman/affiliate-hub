# 設計レビューの指摘 — ブログごとの管理画面 (feat-blog-scoped-admin-console)

P03 の成果物。実装を読んで見つけた弱点。

直したものと、直さないと決めたものを両方書く。

## F-01 `actions` の 11 本が手書き

`/admin/sites/[site]` のリンク一覧は
route metadata から自動生成していない。

画面を足して `actions` に足し忘れると、
**サイドバーにも出ず、親からも辿れない**。

### 直さない

自動生成すると並び順が `nav.group` の順になる。

いまの並びは
「直す → 書く → 見せる → 出す → 見る → 直しに行く」で、
運営者の作業順である。

分類の順とは別物なので、機械には決められない。

コメント「**足したら同時にここへ出す。**」が防御。

### 残る危険

次に画面を足す人がこのコメントを読まない可能性がある。

P05 のときに実際に起きた
（`appearance` / `placements` の入口が無かった）。

## F-02 `Callout` の数え方が文字列

```ts
const count = (screen.source.match(/<Callout[\s/>]/g) ?? []).length;
```

ソースの正規表現で数えている。

`const Warn = Callout` のように別名を付ければ
上限を超えても検出されない。

### 直さない

AST を解析すれば正確になるが、
**検査の側が壊れたときに気付きにくくなる**。

正規表現なら、外れたときに 0 件になり、
「落とす計画が実施されていない画面」の床
（`toBeGreaterThan(0)`）で止まる。

いまは全画面が直接 `<Callout>` と書いている。
書き方を揃えることで検査を単純に保つ側に倒した。

## F-03 `sites/[site]` に節が 5 つある

1 画面 1 目的だが、この画面には節が並ぶ:

1. このブログは読者に届くか
2. このブログの位置づけ
3. 読者に出ている配色
4. 操作へのリンク（11 本）
5. 削除

目的は「運用を続けるか判断する」1 つで、
5 つとも判断材料ではある。

### 弱点

**説明文 40 字の上限では、この画面の中身を説明しきれない。**

上限が守れているのは、
説明文が中身を説明していないから。

`uiux-screen-single-purpose.test.ts` は
目的が 1 つであることは見るが、
**目的に対して節が多すぎることは見ていない**。

### 直さない

分割すると、判断のたびに 3 画面を開くことになる。

「続けるか判断する」に必要な材料が
3 か所に散るほうが悪い。

## F-04 削除が同じ画面の末尾にある

`DeleteConfirm` が `sites/[site]` の末尾。

「末尾が delete の route が無い」を満たすために
専用画面を作らなかった結果。

### 弱点

**設計図を読みに来ただけの人の画面に、削除がある。**

スクロールの末尾なので誤操作は起きにくいが、
「読むだけの画面」ではなくなっている。

`classification` は `business-mutation`。

### 直さない

削除専用画面のほうが危険。
何を消すのか確かめずに消せる。

## F-05 子 route が `requires` を持たない

```ts
"sites/[site]/audience": child("sites/[site]", "読者の行動"),
```

`child` に `requires` の引数が無い。

権限の判定は開いた先のユースケースが行う。

### 弱点

URL を知っていれば**画面は開ける**（中身は断られる）。

親（`sites`）が `content.read` で消えても、
子の URL は生きている。

### 直さない

権限をナビの表とユースケースの 2 か所に書くと、
片方だけ直した状態が作れる。

**判定は 1 か所（ユースケース）に置く。**
ナビから消すのは見やすさの話で、防御ではない。

## F-06 `entry.ready` の分岐が 5 画面で重複

`domains` / `audience` / `revenue` / `seo` / `aeo` が
それぞれ同じ形の分岐を書いている:

```tsx
const entry = await blogXxxEntry();
if (!entry.ready) { /* 骨格 + 理由 */ }
```

### 直さない

共通化すると、画面ごとに違う「なぜ空か」の文言が
1 つに寄る。

`audience` が空な理由と `revenue` が空な理由は違う。
まとめた瞬間に、どちらにも当てはまる薄い文言になる。

## F-07 `sites` 一覧に数字が無い

`/admin/sites` はブログを選ぶだけで、
PV も収益も出ない。

「どのブログを見るか」を決めるのに、
**全部開かないと分からない**。

### 弱点として記録する

一覧に数字を出すと、
それは「ブログをまたぐ合算画面」に近づく
（`requirements-baseline.md` の作らないもの 2）。

ただし合算ではなく**並列表示**なら、
作らないものには当たらない。

いまは作っていない。
必要になったら判断する。

## F-08 `viewport` の絞り込みが `audience` だけ

幅の切り替えは `audience` にしかない。

`revenue` には無い。

### 弱点

読者の幅は収益にも効く（スマホでは押されにくい、など）。

`revenue` で幅を絞れないので、
**幅ごとの収益差**は見られない。

### 直さない

`revenue` は `Commercial` の印で、
幅は読者の属性（`Editorial`）。

同じ画面に持ち込むと §12.3 の分離が崩れる。

## F-09 `sites/[site]` の目的文が判断で終わる

> 1 ブログの設計図を確かめ、**運用を続けるか判断する**

「判断する」の次の操作が、
この画面には削除しか無い。

「続ける」を選んだ人は何もしない。

### 弱点として記録する

目的文は「次の行動」まで書く規則
（`screen-responsibility-map.md`）だが、
この画面の次の行動は**画面の外**にある。

11 本のリンクがそれを担っている。

規則には従っているが、
他の画面ほど素直に読めない。
