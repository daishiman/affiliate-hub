# 要件の基線 — ブログごとの管理画面 (feat-blog-scoped-admin-console)

P01 の成果物。

## 何を解くか

管理画面が**記事を単位に組み立てられていた**。

記事の一覧、記事の編集、記事の診断。
どれもブログをまたいだ横断の画面で、
「どのブログの話か」は画面の中の選択欄で切り替える形だった。

### それで起きること

**選び忘れたまま別のブログの数字を読める。**

`/admin/analytics` を開いて数字を見る。
選択欄が前回のブログのままだと、
今見ているブログの数字だと思って読む。

画面はどちらの状態でも同じ顔をしている。

## 何をするか

**ブログ 1 本を住所の階層にする。**

```
/admin/sites/[site]/          ← このブログの設計図
/admin/sites/[site]/domains   ← 住所
/admin/sites/[site]/audience  ← 読者の行動
/admin/sites/[site]/revenue   ← 記事ごとの成果
/admin/sites/[site]/seo       ← SEO 診断
/admin/sites/[site]/aeo       ← AEO
```

URL に `site` が入っていれば、**取り違えようがない**。

### `analytics` の下に置かない

横断の分析画面と同じ場所に置くと、
選択欄で切り替える形に戻る。

`admin-route-metadata.ts` にこの判断がコメントで残っている:

```
横断の分析画面と同じ場所に置くと、「どのブログの数字か」を
画面の中の選択欄で切り替えることになり、選び忘れたまま
別のブログの数字を読む形が作れる。住所の下なら取り違えようがない。
```

## 受入条件

1. ブログ 1 本の下に、住所・観測・改善の画面がぶら下がる
2. 各画面に「この画面で何をするか」が 1 つだけ宣言されている
3. 足した画面は必ず `/admin/sites/[site]` から辿れる
4. route・ナビ・パンくず・分類が**同じ 1 つの表**から派生する
5. 動的 route の実 URL・選択中ナビ・パンくずを別々に解決する
6. 根拠が足りない数字には、読み方の代わりに理由を出す
7. 空の表を「出せた」と言わない
8. 押せない要素に `onclick` を付けない
9. 断りの文言は、原因になった入力欄に出る
10. 常時表示の注意書きは 2 個まで

## 作らないもの

### 1. ブログ切り替えの選択欄

**この feature が消したいものである。**

URL が唯一の切り替え手段。

### 2. ブログをまたぐ合算画面

「全ブログの合計 PV」のような画面を作らない。

合算すると、ブログごとに違う目的（`purpose`）を
1 つの数字に潰すことになる。

### 3. 画面ごとの権限の作り分け

権限はユースケースが持つ。画面は結果を出すだけ。

### 4. ブログ専用の画面

「このブログだけ特別扱いする」画面を作らない。

`/admin/sites/[site]` のコメント:

```
「このブログだけ特別扱いする」ための画面ではない。
ここに出ている項目がブログの違いのすべてであり、
足りない項目があれば設計図に欄を足す。画面に分岐を足さない。
```

### 5. 計算

画面で数えない（AD-2）。
読み取りが済んだ値を並べるだけ。

## 上位ゴールとの関係

- **G1**（一つの URL を起点に目的の違うコンテンツを安全に作る）
  → ブログの違いが設計図の項目に集まる
- **G2**（何が成果に効くかを計測・分析・一元管理）
  → ブログ 1 本の下に観測と改善が並ぶ
