## 1. 確定したプロダクト像

> ブログ単体も構築ができて、それらをプラットフォームで管理できる。さまざまなアフィリエイトの内容を合わせて構築できる。

この一文を二層構造として確定する。**どちらか一方へ寄せない。両方が要求されている。**

| 層 | 正本仕様 | 責務 | 成果物 |
| --- | --- | --- | --- |
| プラットフォーム層 | `01-要求仕様書-v1.0.md` | Workspace / Brand / Site 階層、アフィリエイトURL受信箱、商品インテリジェンス、比較エンジン、Persona Studio、AI Content Studio、Site Builder、Distribution Hub、Affiliate Hub、Analytics、権限・コンプライアンス | Content Package と、その配信先の管理 |
| ブログ層 | `ai-first-webmcp.md` | 読者に届く比較メディアそのもの。情報アーキテクチャ、記事構成、文章、会話ブロック、WebMCP 契約、アクセシビリティ | Site の実体（公開される HTML） |

## 2. 統合ルール（5条）

### 2-1. ブログ層はプラットフォーム層の Site の実体である

ブログ層 §7 の18ルートは、プラットフォーム層 §21 の `Site` エンティティ1件が持つ公開面である。ブログ構築は独立機能ではなく、**Content Package の一出力先**として扱う。

```text
Workspace
 └ Brand
    └ Site  ← ブログ層 §7 の18ルートを持つ実体
       └ Publication ← Content Package から生成された各記事の掲載
```

### 2-2. 同じ概念に2つの正規定義を作らない

ブログ層 §12 の8エンティティは、プラットフォーム層 §21 と**同一の正規データ**を指す。別テーブル・別型を作らない。

| ブログ層 §12 | プラットフォーム層 §21 | 正規の所有者 |
| --- | --- | --- |
| Article | ContentVariant / Publication | プラットフォーム層 |
| Product | Product | プラットフォーム層 |
| Claim | Claim | プラットフォーム層 |
| Evidence | Evidence | プラットフォーム層 |
| TestRun | TestRun | プラットフォーム層 |
| RankingModel | RankingModel | プラットフォーム層 |
| Offer | Offer | プラットフォーム層 |
| Disclosure | Disclosure | プラットフォーム層 |

ブログ層はこれらを**読み取り、描画する**。ブログ層側で正規値を再定義・再計算しない。

### 2-3. ドメインサービス層を共有する

ランキング計算、比較候補の分類、公開ゲート判定、広告表記の要否判定は `src/lib/domain/` の純関数1箇所に置き、以下すべてがそこを呼ぶ。

- 管理画面（プラットフォーム層 §22 の8画面群）
- 公開ブログ（ブログ層 §7 の18ルート）
- WebMCP ツール（ブログ層 §14.2 の10種）
- バックエンド MCP（プラットフォーム層 §24.3）

**ランキング式を UI や WebMCP に重複実装することは §27 の禁止依存に該当する。**

### 2-4. 編集評価と報酬データを分離する

プラットフォーム層 §19.4 に従い、Ranking Service は Editorial DB のみを読む。報酬額・成果報酬率・ASP実績は Commercial DB に置き、**推薦スコアの入力にしない**。この境界は二層いずれの経路（管理画面／公開ブログ／WebMCP／MCP）からも迂回できない位置（ドメインサービス層の関数シグネチャ）で担保する。

### 2-5. Phase は別軸として並走させる

プラットフォーム層 §28 の Phase 0〜6 とブログ層 §26 の Phase は別軸である。依存関係を以下に固定する。

| プラットフォーム Phase | ブログ層で同時に必要なもの | 依存の向き |
| --- | --- | --- |
| P0 基盤・認証・テナント | ブログ層 §7 のルート骨格（静的） | ブログ層 → プラットフォーム層 |
| P1 URL受信箱・商品識別 | なし | — |
| P2 比較エンジン・Evidence | ブログ層 §12 の読み取り面 | ブログ層 → プラットフォーム層 |
| P3 Persona / Content Studio | ブログ層 §8〜§11（記事構成・文章・会話） | 相互 |
| P4 Site Builder / Distribution | ブログ層 §7 全ルート、§17 広告表記 | ブログ層 → プラットフォーム層 |
| P5 Analytics / Affiliate Hub | ブログ層 §14 WebMCP、計測 | 相互 |
| P6 権限・監査・スケール | ブログ層 §20 WCAG 2.2 AA、§21 公開ゲート | 相互 |

## 3. WebMCP の確定契約（ブログ層 §14 準拠）

| 項目 | 確定内容 |
| --- | --- |
| 登録先 | **`document.modelContext`**。`navigator.modelContext` は Chrome 150 で非推奨のため legacy fallback 専用（CHG-001） |
| 導入条件 | 機能フラグ配下。能力検出を先に実行し、非対応環境は通常 UI へフォールバック |
| ツール数 | 1ページあたり原則6個以下 |
| 導入順 | 読み取り専用から。状態変更系は確認 UI を伴う場合のみ |
| 宣言型フォーム | `toolname` / `tooldescription` / `toolparamdescription`。状態変更に `toolautosubmit` を使わない |
| オリジン制約 | ブログ層 §14.6。自オリジンの機能だけを公開する |
| エラー形式 | ブログ層 §16.4 |

### 3-1. ツールカタログ10種（ブログ層 §14.2、全定義）

| # | ツール名 | 種別 | 目的 | 主な入力 | 出力 |
| --- | --- | --- | --- | --- | --- |
| 1 | `list_ranking` | 読取 | 現在ページのランキングを構造化して返す | `article_id` | 順位・商品ID・スコア・評価軸 |
| 2 | `get_product` | 読取 | 商品1件の正規情報 | `product_id` | 仕様・価格帯・識別キー |
| 3 | `compare_products` | 読取 | 2件以上の差分表 | `product_ids[]` | 差分項目と値 |
| 4 | `get_evidence` | 読取 | Claim の根拠 | `claim_id` | Evidence 一覧と出典 |
| 5 | `list_test_runs` | 読取 | 実測条件と結果 | `product_id` | TestRun 一覧 |
| 6 | `explain_ranking` | 読取 | 順位の根拠説明 | `article_id` | RankingModel の重みと適用値 |
| 7 | `filter_products` | 読取 | 条件による絞り込み | `criteria` | 該当商品一覧 |
| 8 | `get_disclosure` | 読取 | 広告表記とアフィリエイト関係 | `article_id` | Disclosure 本文と適用範囲 |
| 9 | `find_alternatives` | 読取 | 代替候補 | `product_id` | 4分類つき候補一覧 |
| 10 | `submit_feedback` | 状態変更 | 訂正報告の受付 | `article_id`, `body` | 受付ID。**確認 UI 必須** |

読み取り9種／状態変更1種。1ページ6個以下の制約により、ページ種別ごとに登録するツールを選択する（記事ページ = 1,2,3,4,6,8／比較ページ = 3,4,7,9,10 など）。

## 4. 禁止依存（ブログ層 §27）

| # | 禁止事項 | 検査方法 |
| --- | --- | --- |
| FD-1 | ランキング式を UI 層・WebMCP 層へ重複実装する | `src/lib/domain/ranking.ts` 以外に重み計算が現れないことを grep テストで固定 |
| FD-2 | 報酬データを推薦スコアの入力にする | Ranking Service の入力型に Commercial DB 由来の型が含まれないことを型で担保 |
| FD-3 | 根拠のない主張を公開する | 公開ゲート（`src/lib/content/publish-gate.ts`）で Claim に Evidence が紐づかない場合 BLOCK |
| FD-4 | WebMCP でしか到達できない機能を作る | 全 WebMCP ツールに対応する通常 UI 経路が存在することをトレーサビリティ表で確認 |
| FD-5 | ブログ層で正規データを再定義する | ブログ層のコードが `src/db/schema.ts` 以外のスキーマ定義を持たないこと |

## 6. 品質統制プロセス（ブログ層 付属 §0〜§10 準拠）

本プロジェクトの成果物は以下を満たす。

- 能力検出を先に行う。**実際に並列実行していないなら並列実行したと報告しない。**
- **証拠のない PASS を出さない。** 未検証は `NOT RUN` と書く。
- 最大3回の改善後も条件を満たせない場合、成功を偽装せず未解決事項と必要な判断を出力する。
- 指摘は Issue ID（FND-xxx）で一意化する。
- 仮定台帳・指摘台帳・意思決定記録・変更台帳・要件追跡表を成果物として残す（`docs/product/ledgers.md`、`docs/product/traceability.md`）。
