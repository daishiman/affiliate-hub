# ブログ別コンポーネントの scaffold 契約: feat-uiux-overhaul

- graph node: `SYS-UIUX-OVERHAUL-P02`
- 受入条件: A7 — 新規ブログ構築時にブログ別コンポーネント一式が仕様どおり scaffold される
- 現行の正本: `src/domain/authoring/site-blueprint.ts` (`SiteBlueprint`), `site-routes.ts` (`SITE_ROUTES`, `routesFor`), `site-draft.ts`

## 決めること

ブログを 1 本増やしたとき、**何がデータとして増え、何がファイルとして増えるか**の境界。

A7 の述語は「生成物はデータ (設計図) と、それを読む共通コンポーネントに分かれている」「ブログ本数に比例して増えるファイルは、仕様が列挙したものだけ」を要求する。本書がその列挙を与える。

## 既にある構造

`/admin/sites/new` の 13 の質問は `SiteBlueprint` を組み立てる。

| 設計図の要素 | 型 | 何を決めるか |
|---|---|---|
| `pattern` | `SitePattern` | ブログの型 |
| `purpose` / `genre` | `string` | 何のためのブログか |
| `revenueModel` | `RevenueModel` | どう稼ぐか |
| `pages` | `StandardPage[]` | どのページを置くか |
| `categories` | `CategoryPlan[]` | どんな区分けで書くか |
| `theme` | `ThemeTokens` | 見た目 (配色・書体・角丸・密度・明暗) |
| `differentiation` | `DifferentiationAxes` | **10 軸の違い** — 読者・検索意図・記事の目的・評価軸・利用場面・独自体験・比較範囲・結論の立場・内部リンク・CTA |

`routesFor(blueprint)` が `pages` から route 一式を導き、共通コンポーネント (`SiteShell`, `ArticleView` ほか) がそれを読む。**ブログを増やしてもコードは増えない。**

`differentiation` の 10 軸には `MIN_DIFFERENT_AXES = 3` と `differentiationGap()` があり、既存ブログと似すぎているブログを作れないようになっている。

## 境界: データで表現するもの / ファイルを生成するもの

**原則: データで表現する。ファイル生成は例外とし、条件を満たすときだけ許す。**

理由は、ブログ本数 × ファイル数だけ保守対象が増えるため。10 本のブログにそれぞれ 5 ファイルあると、共通の直し 1 件が 50 か所への追従になる。「同じことを何度も書かない」という要望は、ここでは**ファイルを増やさないこと**として実現される。

### データで表現するもの (ファイルは増えない)

| 差 | 表現方法 |
|---|---|
| 配色・書体・角丸・密度・明暗 | `ThemeTokens` → CSS カスタムプロパティ |
| 置くページの組み合わせ | `pages` → `routesFor()` |
| カテゴリ構成と初期記事型 | `categories` |
| 読者像・切り口・結論の立場 | `differentiation` の 10 軸 |
| 広告表記の文面と置き場 | `revenueModel` + ブランド設定 |
| 記事の節の並び | 記事型 (`ArticleType`) ごとの共通定義 |

**新しい差を足したくなったら、まず設計図に項目を足せないかを試す。** 項目を足すと全ブログがその項目を持ち、`/admin/sites/new` の質問が 1 つ増え、既存ブログには既定値が入る。これで済む限り、ファイルは 1 つも増えない。

### ファイルを生成するもの (例外)

次の**両方**を満たすときだけ、ブログ固有のファイルを生成してよい。

1. **共通コンポーネントの組み合わせでは表現できない構造**である — 節の並び替え・値の差し替え・表示の有無では届かない
2. **他のブログへ広がる見込みが無い** — 広がるなら共通コンポーネントに足す

満たす例: あるブログだけが持つ独自の計算機・診断ツール・特殊な図表。
満たさない例: 「このブログだけカードを 3 列にしたい」(密度で表現できる)、「このブログだけ著者欄を上に出したい」(設計図の項目にできる)。

### 生成されるファイルの一覧 (A7 の「仕様が列挙したもの」)

例外に該当したとき、生成されるのは次だけ。**この一覧に無いものは生成しない。**

```
src/presentation/sites/<site-slug>/
├── index.ts        … このブログ固有の部品の入口。共通からはここ経由でのみ読む
├── sections/       … 独自セクション (0 個でもよい)
└── README.md       … なぜ共通で表現できなかったかの記録 (必須)
```

`README.md` を必須にするのは、**例外が増えすぎたときに気付くため**。理由が書けないなら、それは共通で表現できる差である。

`<site-slug>` は `SiteBlueprint.id` から導く。ディレクトリ名にブログの表示名を使わない (改名でパスが変わる)。

## scaffold の実行

ブログ作成 (`create_site_from_draft`) が成功したとき、生成されるものは次。

| 生成物 | 種別 | ブログ本数に比例するか |
|---|---|---|
| `SiteBlueprint` 1 件 | データ | する (データなので可) |
| route の解決結果 | 導出 | しない (`routesFor()` が都度計算) |
| テーマの CSS カスタムプロパティ | 導出 | しない (`ThemeTokens` から生成) |
| `src/presentation/sites/<slug>/` | ファイル | **既定では生成しない** |

**既定でファイルを生成しない。** 例外に該当したときだけ、後から明示的に足す。作成時に空のディレクトリ一式を作ると、使われない骨組みが本数分たまる。

## 共通コンポーネントの読み方

ブログ固有の部品があるとき、共通コンポーネントはこう読む。

```
SiteShell(blueprint) ─▶ routesFor(blueprint) で route を決める
                     ─▶ 固有部品があれば sites/<slug>/index.ts から読む
                     ─▶ 無ければ共通のまま描く
```

**共通コンポーネント側にブログ名の分岐 (`if (slug === "...")`) を書かない。** 書いた時点でブログを増やすたびに共通側を直すことになり、A7 の「ブログ本数に比例して増えるファイルは列挙したものだけ」が崩れる。

固有部品の有無は、`sites/<slug>/index.ts` が存在するかで決める。存在しないブログでは何も読まない。

## 管理画面側の反映

| 画面 | 反映内容 |
|---|---|
| `/admin/sites/[site]` | 10 軸の違い・テーマ・カテゴリ構成を表示。**固有部品を持つ場合はその旨と理由を表示** |
| `/admin/sites/[site]/edit` | 設計図の項目を直す。10 軸を直すと `differentiationGap()` が再判定される |
| `/admin/sites/new` | 現行の 13 質問を維持 (作成フォームの手本) |

固有部品の存在を管理画面に出すのは、**例外が積み上がっていることに気付ける場所が必要**なため。`README.md` はコードを読む人しか見ない。

## 1 商品 → 複数ブログ (A5 との接続)

`differentiation` の 10 軸が、そのままコンセプト別文章作成の入力になる。

```
商品 1 件 ──▶ 対象ブログを複数選ぶ
            ──▶ ブログごとに differentiation を読む
            ──▶ 「同じ商品を、違う読者へ、違う結論の立場で」書く指示が組み上がる
            ──▶ 生成物はブログ別に区別して一覧に現れる
```

**切り口を人が毎回入力しない。** ブログの設計図が既に持っている。利用者がするのは「どのブログへ出すか」を選ぶことだけで、切り口は設計図から決まる。これが認知負荷を下げる要点で、渡さなくてよい情報 (10 軸の中身) を毎回渡さずに済む。

上書きしたいときだけ、選んだブログの切り口を画面で変えられるようにする。既定は設計図のまま。

## この文書が決めていないこと

- 記事生成エンジン本体 — `feat-ai-content-studio` が所有する (scope_out)
- 固有部品の具体的な実装形 — 例外が実際に発生したときに決める
- 設計図に足す新項目 — 必要になった時点で `/admin/sites/new` の質問と共に足す
