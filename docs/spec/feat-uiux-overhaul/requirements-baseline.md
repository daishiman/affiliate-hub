## この文書の役割

feature の受入条件 10 件は、そのままでは「満たしたかどうか」を機械が言えない。ここでは 10 件それぞれを **観測可能な述語**へ書き下し、判定に使う入力と、判定を実行する phase を固定する。以降の phase (P02 設計〜P10 最終レビュー) は、この表を判断根拠として使う。

## 受入条件の検証可能化

### A1. 各管理画面が単一用途で、1画面に複数の主要タスクが混在しない

- **述語**: `information-priority-map.json` の全 route が `primary_task` をちょうど 1 つ持ち、その画面の主要操作 (submit を伴う操作、または遷移先を変える操作) が全て `primary_task` に属する。属さない操作は別 route へ分離されている。
- **入力**: `information-priority-map.json`, `src/app/admin/**/page.tsx`
- **判定**: P03 (設計レビュー) が分割案を承認、P09 (品質保証) が実装後の route 一覧と map の突合で確認
- **境界**: 「主要タスク」とは、完了すると業務状態が変わる操作を指す。閲覧のための絞り込み・並べ替え・展開は主要タスクに数えない。

### A2. 管理対象 (ブログ・記事・商品・SNS投稿) 全てに一覧・新規作成・編集・削除の操作と対応 API が存在する

- **述語**: 4 つの管理対象 × 4 操作 = **16 の組み合わせすべて**について、(a) 到達可能な画面上の操作が存在し、(b) それを実行する API route が存在し、(c) 権限の要求が宣言されている。
- **入力**: route 一覧、`src/app/api/**`、`ADMIN_NAV` からの到達可能性
- **判定**: P06 (テスト実行) が 16 組の E2E 経路で確認。1 組でも欠ければ FAIL
- **現状**: 層によって充足度が違う。P02 の [`admin-api-contract.md`](./admin-api-contract.md) が両方を数え直した。
  - **画面上の操作**: 一覧 4/4 済み、新規作成 1/4 (ブログのみ)、編集 0/4、削除 0/4 → **12 組が未充足**
  - **API (tool) 層**: SNS 投稿は `schedule_publication` / `reschedule_publication` / `cancel_publication` が作成・更新・削除に相当し既に存在する → **8 組が未充足** (ブログ 2・記事 3・商品 3)
  - 差の 4 組は「API はあるが画面に操作が無い」もの。(a)(b)(c) の 3 つすべてを要求するので、どちらも埋める
- **境界**: 削除は物理削除に限らない。復元可能な取り下げでも、利用者から見て「消える」操作であれば満たす。ただしどちらかを明示すること。

### A3. 各サイト・SNS への投稿状態が管理画面の一覧・詳細に反映される

- **述語**: 記事 (content) の一覧と詳細の両方に、その記事の配信先ごとの状態 (未着手 / 予約済み / 送信中 / 完了 / 失敗) が表示される。失敗時は理由が併記される。
- **入力**: `/admin/content`, `/admin/content/[variant]`, `/admin/distribution`
- **判定**: P06 が各状態のフィクスチャで表示を確認、P07 (受入) が失敗理由の表示を確認
- **境界**: 状態の**取得**は `feat-distribution-hub` の責務 (scope_out)。本 feature は取得済み状態の**表示**に責任を持つ。

### A4. 新しい SNS の追加がプロバイダ実装の追加のみで完了し、既存画面の改修を要しない

- **述語**: 新規 SNS プロバイダを 1 つ追加したとき、変更が必要なファイルが **プロバイダ実装ファイルと、その登録 1 箇所のみ**である。`src/app/admin/**` と `src/presentation/ui/**` の差分が 0 行。
- **入力**: 実際に 1 プロバイダ (例: Facebook) を追加した git diff
- **判定**: P09 が diff のパス集合で機械判定
- **境界**: 「登録 1 箇所」はプロバイダ表 (レジストリ) への 1 エントリ追加を指す。表そのものが SNS ごとの分岐 (switch/if) を持つ実装は本条件を満たさない。

### A5. 1 商品から複数ブログへコンセプト別の文章を作成する導線が動作する

- **述語**: 商品詳細を起点に、対象ブログを複数選択し、ブログごとに異なるコンセプト (切り口) を指定して生成を開始できる。開始後、生成物がブログごとに区別して一覧に現れる。
- **入力**: `/admin/products/[product]`, `/admin/content/matrix`
- **判定**: P06 が 1 商品 → 2 ブログ以上のシナリオで確認
- **境界**: 生成エンジン本体は `feat-ai-content-studio` (scope_out)。本 feature は**指定と起動の導線**、および結果の区別表示に責任を持つ。

### A6. 同等 UI の重複実装が 0 件で、共通部品は共有コンポーネント経由で使用される

- **述語**: `src/app/admin/**` の中に、`src/presentation/ui/**` が提供する部品と同等の JSX 構造を独自に組んだ箇所が 0 件。判定は「同じ役割の要素 3 つ以上を同じ並びで持つ塊が、共有部品を経由せず 2 箇所以上に現れる」で行う。
- **入力**: `src/app/admin/**/*.tsx`
- **判定**: P08 (リファクタリング) が収束させ、P09 が機械検査で 0 件を確認
- **境界**: 1 箇所にしか無い構造は重複ではない。共有部品へ引き上げる判断は P08 が行う。

### A7. 新規ブログ構築時にブログ別コンポーネント一式が仕様どおり scaffold される

- **述語**: ブログを 1 本作ると、そのブログ固有のコンポーネント一式が仕様で定めた構成どおりに生成され、生成物は**データ (設計図) と、それを読む共通コンポーネント**に分かれている。ブログ本数に比例して増えるファイルは、仕様が列挙したものだけである。
- **入力**: `/admin/sites/new` の実行結果、scaffold 仕様書 (P02 が作成)
- **判定**: P06 が 2 本目のブログ作成で生成物の集合を確認
- **境界**: 現行 `/admin/sites/new` の説明文は「増えるのは設計図のデータだけで、画面のコードは共通のまま使います」と述べている。この方針は維持し、**ブログ固有の見た目の差**をデータで表現できる範囲を P02 が確定する。

### A8. カード間隔・文章量・サイドバー構成が規則として文書化され全画面へ適用されている

- **述語**: 次の 3 つが文書に数値で書かれ、かつ全画面がそれに従う。
  1. **カード間隔**: カード内 padding とカード間 gap に使うトークンが、それぞれ 1 つに固定されている (現状は `--space-3/4/5` 混在)
  2. **文章量**: 画面説明文 (`lead`) の上限字数、および常時表示の補足 (`Callout`) の 1 画面あたり上限個数
  3. **サイドバー構成**: 分類の数と、1 分類あたりの項目数の上限
- **入力**: P02 が作成する規則文書、`ui.module.css`、全 page.tsx
- **判定**: P09 が機械検査で違反 0 件を確認
- **境界**: 上限を超える必要がある画面は、超える理由を画面側に書けば違反としない。ただし例外は数えられる形で残す。

### A9. サイドバーの全項目にアイコンが付き、アイコンクリックで折りたたみ/展開が切り替わり、折りたたみ時もアイコンで項目を識別できる

- **述語**:
  1. `ADMIN_NAV` の**全項目**がアイコンを持つ (未設定を型で禁止する)
  2. 折りたたみ操作が存在し、折りたたみ状態が再訪時にも保たれる
  3. 折りたたみ時、各項目はアイコンのみで表示され、読み上げには項目名が残る
  4. 分類の見出しも、折りたたみ時に何らかの形で区別できる
- **入力**: `src/presentation/ui/templates/app-shell.tsx`, `ADMIN_NAV`
- **判定**: P06 が型検査と操作テストで確認、P07 が読み上げでの識別を確認
- **境界**: アイコンだけで意味が伝わらない項目があってもよいが、その場合はホバー/フォーカス時に名前が出ること。**アイコンのみで名前を完全に置き換えない。**

### A10. 各画面の表示情報がタスク遂行に必要な項目のみに絞られ、不要な文章・説明が非表示になっている

- **述語**: 全 route について `information-priority-map.json` に `keep` / `drop` / `transform` の 3 分類が記録され、実装がそれに一致する。加えて次の数値目標を満たす。
  - 常時表示の `Callout` が 1 画面あたり **2 個以下** (現状 総数 79 個 / 上限超過 14 画面 / うち 4 個以上が 8 画面)
  - `lead` が **40 字以下** (現状 平均 46.8 字・最大 70 字・超過 21 画面 / 32)
  - 初期表示で読む必要のある文章の総量が、画面ごとに測定され減少している
- **入力**: `information-priority-map.json`, 全 page.tsx
- **判定**: P09 が機械集計で確認
- **境界**: 「落とす」は削除とは限らない。折りたたみの中へ移す、操作したときだけ出す、も `drop` に含める (初期表示に出さない、が判定基準)。**安全に関わる警告は落とさない** — 金額・鍵・公開操作に関する注意は `keep` 固定とする。
