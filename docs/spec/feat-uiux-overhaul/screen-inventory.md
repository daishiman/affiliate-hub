# 画面棚卸しと単一用途分割案: feat-uiux-overhaul

- graph node: `SYS-UIUX-OVERHAUL-P01`
- 対象: `src/app/admin` 配下 32 画面 (2026-08-21 実測)
- 判定基準: [`requirements-baseline.md`](./requirements-baseline.md) の A1 / A2
- 情報の残す・落とす・加工するの判断: [`information-priority-map.json`](./information-priority-map.json)

## 読み方

- **主要タスク**: 完了すると業務状態が変わる操作。閲覧・絞り込み・並べ替え・展開は数えない
- **混在**: 主要タスクが 2 つ以上ある、または「見る」画面に「決める」操作が同居している状態
- **分割案**: A1 を満たすための最小の分割。分割しないことも案のうち (`維持`)

計測値の凡例: `行` = tsx 行数、`C` = 常時表示 Callout 数、`カード` = Card 数、`F` = フォーム数。

## 全体像

32 画面は 3 つの型に分かれる。

| 型 | 画面数 | 特徴 | 主な課題 |
|---|---|---|---|
| **一覧** | 11 | 対象を探して次へ進む | 新規作成の入口が無い (`sites` を除く) |
| **詳細** | 6 | 1 件の中身を確かめる | 編集・削除が無い。節が多く縦に長い |
| **説明・参照** | 16 | 決めごとや仕組みを読む | 操作が無いのに常時表示の文章が最も多い |

**32 画面のうち業務状態を変えるフォームを持つのは `/admin/sites/new` の 1 つだけ**である。管理画面でありながら、ほぼ全ての画面が読むだけになっている。これが受入条件 A2 (16 組の CRUD) が要求する主要な欠落である。

## 分割・補完の集約

### 分割が要る画面 (6)

| route | 分割後 | 根拠 |
|---|---|---|
| `/admin/settings` | 索引 + 見た目 + 作業場所 + 担当者 + 役割 (4 画面新設) | 6 節が別々の管理対象。459 行は全画面最長 |
| `/admin/products/[product]` | 商品詳細 + 順位の理由 | 「なぜこの順位か」は評価基準の文脈で読む |
| `/admin/content/[variant]` | 本文の確認 + 進行の操作 | 読む目的と決める目的が同居 |
| `/admin/generation` | 渡す項目 + 指示文の組み立て + 人の判断境界 | Callout 6・418 行・8 節 |
| `/admin/rankings` | 評価基準の編集 + 順位の結果 | 基準の編集を足す時点で必須 |
| `/admin/personas` | 書き手 + 読者像 | 別の管理対象が 1 画面に同居 |

### 基本管理機能の不足 (A2 の 16 組)

| 管理対象 | 一覧 | 新規作成 | 編集 | 削除 | 補完先 |
|---|---|---|---|---|---|
| ブログ (site) | ✅ `/admin/sites` | ✅ `/admin/sites/new` | ❌ | ❌ | `/admin/sites/[site]` |
| 記事 (content) | ✅ `/admin/content` | ❌ | ❌ | ❌ | `/admin/content` + `/admin/content/[variant]` |
| 商品 (product) | ✅ `/admin/products` | ❌ | ❌ | ❌ | `/admin/products` + `/admin/products/[product]` |
| SNS 投稿 (publication) | ✅ `/admin/distribution` | ❌ | ❌ | ❌ | `/admin/distribution` + `/admin/distribution/[publication]` |

**充足 4 / 16。未充足 12 組**が P02 の API 契約表と P05 の実装対象になる。

### 文章量の削減が要る画面 (Callout 4 個以上・A10 の上限 2 個)

`/admin/generation` (6)、`/admin/analytics` (5)、`/admin/settings` (5)、`/admin/personas` (4)、`/admin/improvement` (4)、`/admin/inbox` (4)、`/admin/sites` (4)、`/admin/content/[variant]` (4)

ただし次は **keep 固定** (落とさない) とする。金銭・鍵・公開に関する誤解は、直接損害につながる。

- `/admin/affiliate` 「この金額は記事の順位に入りません」
- `/admin/analytics` 「収益の数字は順位に戻せません」
- `/admin/settings/llm` 「鍵の扱い」
- `/admin/settings/integration-access` 「値が表示されるのは 1 回だけ」
- `/admin/improvement` 「数字を良く見せるために判定を緩めません」

## サイドバーの現状と要求

現状 `ADMIN_NAV` は 19 項目 / 6 分類。項目数は分類あたり 2〜4 で偏りは小さい。不足しているのは A9 の 4 点 (アイコン・折りたたみ・折りたたみ時の識別・分類の区別) と、上記の分割で **新設される画面の登録**である。

分割後の項目数は 19 + 4 (設定の分割) + 5 (その他の分割) = 最大 28 になりうる。**これは分類あたり 5 項目に近づく**ため、P02 は「サイドバーに全て載せる」か「設定のように親画面の索引に載せる」かを決める必要がある。棚卸しの結論としては、**分割で生まれた子画面は親の索引に置き、サイドバーは現在の 19 項目を保つ**ことを推奨する。サイドバーが伸びること自体が認知負荷になる。

## この棚卸しが依拠した測定

```bash
# 画面数とフォーム数
find src/app/admin -name page.tsx | wc -l
grep -rlE '<[Ff]orm\b' src/app/admin --include=page.tsx

# 常時表示の Callout 数 (画面別)
for f in $(find src/app/admin -name page.tsx); do echo "$(grep -c '<Callout' $f) $f"; done | sort -rn
```
