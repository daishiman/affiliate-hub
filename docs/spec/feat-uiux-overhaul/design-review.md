## 観点 (a): 認知負荷の低減が画面ごとに具体化されているか

### 重大 1: A8-2 の 2 つの上限が同じ画面で衝突する

`information-priority-map.json` は 32 画面すべてに keep/drop/transform を持つが、**lead の短縮を 1 件も持っていない**。機械的に確かめた。

```
lead 40 字超 21 画面 → transform に lead を扱う項目があるもの: 0 件
```

lead を 40 字にするには 2 文目以降を落とすことになる。ところが現行 lead の 2 文目は、7 画面で safety-critical な断り書き (「請求額とは一致しません」「判定を緩めません」「ここを通るまで記事には出しません」) である。これを Callout へ移すと、上限 2 個を破る。

| 画面 | 現 Callout | drop 後 | lead から 1 件移設 | 上限 2 |
|---|---|---|---|---|
| `/admin/improvement` | 4 | 3 | **4** | ✗ |
| `/admin/inbox` | 4 | 3 | **4** | ✗ |
| `/admin/settings/llm` | 3 | 3 | **4** | ✗ |
| `/admin/affiliate` | 2 | 2 | **3** | ✗ |
| `/admin/improvement/dimensions` | 2 | 2 | **3** | ✗ |
| `/admin/ai-usage` | 1 | 1 | 2 | ✓ |
| `/admin/settings/integration-access` | 1 | 1 | 2 | ✓ |

**5 画面が破る。** A10 は「現状からの変化」で測るので、ここを詰めずに実装へ入ると P09 の機械検査で落ちる。

#### 対応: safety-critical な断り書きは Callout ではなく操作の隣に置く

Callout は**画面全体にかかる注意**にだけ使う。特定の操作・特定の数字にかかる断り書きは、その操作・その数字の隣に置く。

| 断り書き | 現在地 | 移設先 |
|---|---|---|
| 「請求額とは一致しません」 | lead 2 文目 | 費用の数字の脇 (`Field.hint` 相当) |
| 「判定を緩めません」 | lead 3 文目 | 判定基準の表示の脇 |
| 「ここを通るまで記事には出しません」 | lead 3 文目 | 取り込みボタンの脇 |
| 「表示は発行時の 1 回だけ」 | lead 2 文目 | 発行ボタンの脇 |
| 「記事の順位には入りません」 | lead 2 文目 | 成果金額の列見出しの脇 |

これは字数を削る話ではなく、**読む場所を正す**話である。「この画面のどこかに書いてある」より「押す物の隣に書いてある」ほうが、押す前に読まれる。認知負荷を下げるとは、読む量を減らすことと、読む場所を近づけることの両方を指す。

移設先は Callout ではないので、上限 2 個には数えない。7 画面すべてが上限内に収まる。

`information-priority-map.json` は方針を持つが文案を持たない。実装 phase が 21 画面分の文案を都度考えると、判断がばらつく。**本書が全 21 画面の改稿後 lead を確定させる。**

### 要注意 3: `/admin/ui-catalog` が lead 上限の除外に入っていない

`exempt_from` は `["callout_max", "card_max", "line_max"]` で、lead は除外されていない。見本帳だから長くてよいという理由も無いので、**除外を増やさず改稿で対応する** (上表で 21 字)。除外は増やすほど検査が形骸化する。

### 要注意 4: 作成の入口が 2 つある

`create_content_variant` (空枠を作る) と `draft_content_variant` (生成する) が並ぶと、利用者は「どっちで作るのか」を毎回判断させられる。これは認知負荷そのもの。

**対応**: `/admin/content` の主操作は**生成 1 本**にする。空枠作成は主操作にせず、生成せずに枠だけ要る場面 (外部で書いた原稿を貼る) の入口としてのみ置く。`README.md` の作法「主操作は 1 画面 1 つ」に従う。

### 要注意 5: `Section` の開閉を利用者ごとに保持しない

`component-contract.md` は「初期の開閉を指定できる」とだけ書き、利用者が開閉した状態を次回まで持つかを決めていない。

**対応: 保持しない。** 保持すると、次に来たとき何が閉じているか分からず、「無いのか閉じているのか」を確かめる操作が毎回増える。既定の開閉は画面ごとに仕様が決め、常に同じ状態で開く。

サイドバーの折りたたみだけは保持する (`screen-architecture.md` の決定を維持)。あちらは**利用者が選んだ作業の広さ**で、画面の中身とは別の話。

## 観点 (b): 共通部品の境界が重複実装を排除できるか

### 重大 6: A6 の重複判定が実装できる形になっていない

`component-contract.md` の判定規則は「文字列リテラルと変数参照を伏せた形で一致すれば重複」とするが、これには JSX の AST を正規化する道具が要る。P09 までに用意できないと、A6 は「検査していないので 0 件」になる。

**対応: 2 段構えにする。**

| 段 | 検査 | 実現方法 |
|---|---|---|
| 一次 (必須) | 同じ import 群 + 同じ JSX タグ列 (深さ 2 まで) が 2 か所以上 | `tsc` の AST を辿り、タグ名列を文字列化して照合する。属性値は見ない |
| 二次 (任意) | 属性の構造まで含めた一致 | 一次で挙がった候補を人が見る |

一次だけなら 100 行程度の script で書ける。**A6 の合否は一次で判定する。** 二次を必須にすると、道具ができないことが受入条件の未達になる。

### 要注意 7: `RecordForm` の戻り先が直リンク時に決まらない

「戻り先の保持」とあるが、`/admin/products/new` へ URL で直接来たとき、履歴に戻り先が無い。

**対応: 親 route を静的に持つ。** 各作成・編集 route は自分の一覧 route を定数で知っており、履歴が無ければそこへ戻る。履歴に依存すると、共有された URL を開いた人だけ挙動が変わる。

### 要注意 8: `RecordForm` / `RecordList` が templates にあるのは正しいか

判断基準は「仕様を知っているか」。`RecordForm` は保存・やめる・実行中抑止の**並べ方**しか持たず、何のレコードかを知らない。templates で正しい。

ただし `DeleteConfirm` が patterns にあるのは、**関連の件数を出して止める**という事業の決めごとを持つため。境界は妥当。

### 要注意 9: 削除に画面が無いことと `RecordList` の関係

`screen-architecture.md` は「削除は画面を作らない」と決めた。すると `DeleteConfirm` は一覧と詳細の両方から呼ばれる。`RecordList` が `DeleteConfirm` を内側に持つと、詳細画面が同じものを別に持つことになる。

**対応**: `DeleteConfirm` は `RecordList` の内側に埋めず、両方から**同じ部品として呼ぶ**。`RecordList` は「削除の入口を置ける」だけを持ち、確認の中身は持たない。

## 観点 (c): SNS 抽象が既存画面の改修なしに拡張できるか

### 重大 10: `iconName` が A4 の「差分 0 行」を破る

`sns-provider-contract.md` は `ChannelCapability.iconName` を足し、A4 の検証で `src/presentation/ui/**` の差分 0 行を要求する。しかし `Icon` は名前で絵柄を引くので、**絵柄の実体をどこかが持つ**。Facebook を足して `iconName: "facebook"` と書けば、その絵柄を `src/presentation/ui/primitives/` へ足すことになり、差分 0 行が破れる。

これは「データで持つ」と言った値が、実は実体への参照だったという穴である。

**対応: 配信先にブランドロゴを使わない。**

| 表示 | 出どころ | 新プロバイダで増えるか |
|---|---|---|
| 配信先の名前 | `label` | 表の 1 エントリ内 |
| 識別色 | `accentToken` (既存トークン名) | 増えない |
| 投稿方式の絵柄 | `publishMode` に対応する 3 種の汎用アイコン | 増えない |

`iconName` は**プロバイダごとの絵柄ではなく、投稿方式ごとの絵柄**にする。`api_publish` / `api_schedule` / `manual_export` の 3 つだけなので、プロバイダが何個増えても絵柄は増えない。配信先の見分けは `label` + `accentToken` が担う。

ブランドロゴが本当に要るとわかった時点で、`icon-set.ts` をデータとして持つ形に変え、A4 の禁止対象から明示的に外す。今それをやると、要るかどうか分からない仕組みを先に作ることになる。

**`sns-provider-contract.md` の「追加項目」表の `iconName` の説明は、この形に読み替える。**

### 要注意 11: `statusLabels` の網羅を型で強制する

`Record<PublishState, string>` は 5 状態すべてを要求するので、書き漏らすと型検査で止まる。**これは正しく効いている。** `Partial<>` にしない。

### 要注意 12: `basisCheckedAt` に古さの判定が無い

日付を出すだけでは、見た人が古いかどうかを判断することになる。

**対応**: 表示側で経過日数を出す (「最終確認: 2026-08-21 (今日)」「… (183 日前)」)。閾値で警告は出さない — 規約が変わる周期は配信先ごとに違い、一律の閾値は嘘になる。

### 要注意 13: A4 の検証が「送信できるか」を含まないことの明示

`sns-provider-contract.md` のスコープ境界表は正しいが、**P09 の検証シナリオが何を PASS とするかが 1 行足りない**。

**対応**: A4 の PASS 条件は「表に 1 エントリ足すと、画面に選択肢として現れ、制約が正しく表示され、状態欄が描ける」まで。実際に送信できることは PASS 条件に含めない (`feat-distribution-hub` の範囲)。P09 はこの形で判定する。

## 観点をまたぐ指摘

### 重大 14: 削除 tool の承認要求が P06 の検証経路を塞ぐ

`delete_*` 3 件を `requiresHumanApproval: true` にすると、`isToolAllowedForScope` がどのスコープからも false を返す。**P06 が「削除できること」を tool 経由で検証できない。**

**対応**: 削除の検証は 2 層に分ける。

| 層 | 何を確かめるか | どこから呼ぶか |
|---|---|---|
| usecase | 参照が残っていれば拒否し、無ければ消える | usecase を直接呼ぶ |
| 入口 | `requiresHumanApproval` の tool が両スコープから拒否される | `isToolAllowedForScope` を直接呼ぶ |

画面からの削除は E2E で確かめる。**この分割は設計の変更ではなく、検証方法の確定**であり、`requiresHumanApproval: true` の判断は維持する。取り消せない操作を入口から実行できないことのほうが重い。

### 要注意 15: 新設 17 route の到達性

`screen-architecture.md` はサイドバーを 19 項目に留め、新設 route を載せない。すると `/admin/settings/appearance` へ直接来た人は、自分がどこにいるか分からない。「子画面では親項目を現在地にする」だけでは、**画面の中に戻り道が無い**。

**対応**: 新設 17 route すべてに、親への戻り道を画面上部に置く。既存の `Breadcrumb` を使い、新しい部品を作らない。
