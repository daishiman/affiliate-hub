# 崩れてはいけないこと — 読者行動の観測 (feat-reader-behavior-analytics)

P02 の成果物。守るべき性質と、何がそれを守っているか。

「注意して書く」で守るものと、構造で守るものを分ける。
**構造で守れるものは、注意で守らない。**

## 一覧

| # | 崩れてはいけないこと | 何が守るか | 破ったら |
|---|---|---|---|
| I-1 | 同意が無い読者の行が作られない | 送信側の早期 return + 受け口の `decideConsent` | 型は通る。テストが落ちる |
| I-2 | 絶対座標の列が存在しない | 表の列定義 | migration が要る。目に付く |
| I-3 | 生の行を返す読み口が無い | `BlogAudiencePort` の型 | **コンパイルが通らない** |
| I-4 | `session_key` に索引が無い | 索引定義 | 型は通る。性能で気づく |
| I-5 | 実寸ではなく区分を送る | `viewportBandOf()` | 型は通る。テストが落ちる |
| I-6 | 参照元は URL 全体でなく区分 | `segmentOf()` | 同上 |
| I-7 | 離脱が 2 度送られない | `done` フラグ | 型は通る。**平均滞在が半分になる** |

## 型で守れているのは I-3 だけ

`BlogAudiencePort` に生の行を返す関数が無いので、
1 人の行動を並べる画面は**書こうとしても書けない**。

これが条件 4 の実質的な防御である。
他は「テストが落ちる」か「性能で気づく」か「気づかない」。

## 気づかないもの（I-7 / I-14）を doc で補う

### I-7（離脱の二重送信）

裏に回った後そのまま閉じると `visibilitychange` と `pagehide` が
続けて来る。`done` を見ないと滞在も離脱も 2 件になる。

2 件目の滞在は 0 秒なので、**平均滞在がちょうど半分に見える**。
半分という値は「そういうものか」と受け入れられてしまう。

コード内に理由を doc として置いてある。

### I-14（集計と掃除の順序）

先に消すと、まだ集計していない日の観測が集計前に消える。

**型は通る。cron も回る。エラーも出ない。**
気づくのは、数か月後に「この期間だけ数字が薄い」と誰かが言ったとき。

`reader-metrics-scheduler.ts` の冒頭 doc に理由を書いてある。
順序を入れ替えるときに、なぜその順なのかが目に入る。

## 索引を張らないこと（I-4）を性質として書く理由

`session_key` に索引を張れば「この鍵の行を全部」が速く引ける。
それは条件 4 が禁じているクエリそのものである。

索引が無ければ全表走査になるので、実装しようとした人が
**性能で気づく**。気づいて索引を足そうとしたときに、
この文書へ行き当たる。

「張らない」を積極的な設計判断として書いておかないと、
次に見た人が「索引が足りない」と判断して足す。

## 変更するときに読む順序

1. 列を増やす → `privacy-constraints.md` の「持たない列」に当たらないか
2. 読み口を増やす → I-3 が崩れないか（集計しか返さないか）
3. 計測の種別を増やす → `measurement-inventory.md` の指紋性の議論
4. 定期実行を触る → I-14 の順序
