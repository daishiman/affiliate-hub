# 要求の確定 — 読者行動の観測 (feat-reader-behavior-analytics)

P01 の成果物。受入 10 件を検証できる形へ写し、実装との差を先に申告する。

## この feature の目的

読者が記事の**どこで時間を使い、どこを押しているか**を、
**個人を追跡せずに**分布として観測する。

「個人を追跡しない」は、注意書きではなく**構造**として表す。
つまり「持たない列」と「描けない画面」の両方で表す。

## 受入条件

| # | 条件 | 判定できる形 |
|---|---|---|
| 1 | 同意が無い読者の行から `reader_key` が常に null で、個人へ戻せる列が他に無い | 表の列一覧を検査 |
| 2 | 位置が要素相対の比率で、絶対座標の列が存在しない | 同上 |
| 3 | ポインタは全軌跡ではなくクリックと間隔標本だけが記録される | 送信側のイベント種別 |
| 4 | ヒートマップが常に集計分布で、単一 `reader_key` の再生経路が UI にもクエリにも無い | 読み口の型と画面 |
| 5 | `viewport_bucket` を切り替えると同じ記事で別の分布が描かれる | 画面テスト |
| 6 | 離脱時にも計測が欠落せず `sendBeacon` で送出される | 送信側テスト |
| 7 | 同じバッチを二度受け取っても件数が二重にならない | 受け口テスト |
| 8 | 90 日を超えると生イベントが削除され、集計側は残る | 結合テスト |
| 9 | `reader_key` 指定の抽出・削除が Owner だけで実行でき、`audit_logs` に残る | **成立しない。下記** |
| 10 | 計測 script の失敗が読者面の描画を壊さない | 送信側テスト |

## 範囲

### 含む

- `reader_interaction_event` 表
- 読者面の計測（到達・滞在・クリック・離脱）
- 要素相対の比率で位置を持つこと
- `sendBeacon` による束ね送信と、追記専用の受け口
- 同意が無いときの扱い
- 管理画面での画面幅ごとの分布表示
- 90 日削除

### 含まない

| 除いたもの | 誰の責務か |
|---|---|
| 1 読者の行動を時系列で再生する機能 | **作らない**（条件 4 そのもの） |
| 日次ロールアップと収益・PV との突合 | feat-blog-metrics-rollup |
| 行動指標を使った示唆生成と提示順序 | feat-blog-scoped-admin-console |
| 既存の汎用イベント / KPI 基盤 | feat-analytics-insight |

## 仕様と実装の食い違い（先に申告する）

### 名前

| 仕様 | 実装 |
|---|---|
| `reader_interaction_events` | `reader_interaction_event`（単数） |
| `reader_key` | `session_key` |
| `viewport_bucket` | `viewport_band` |
| `element_ref` | `element_key` |
| `kind = scroll_depth\|dwell\|element_click\|pointer_sample` | `kind = view\|scroll\|dwell\|click\|exit` |

名前を変えた理由は `measurement-inventory.md` と `data-model.md` に書いた。
とくに `reader_key` → `session_key` は**意味が違う**改名で、
条件 9 が成立しない理由に直結する。

### 位置の持ち方（条件 2 に関わる）

仕様は `x_ratio` / `y_ratio` の 2 次元、実装は `position_ratio` の**1 次元**。

つまり「記事の上から何割の位置か」だけを持ち、横方向は持たない。
**絶対座標を持たないという条件 2 の要求より、さらに狭い。**
理由は `privacy-constraints.md`。

結果として、描かれるのは 2 次元のヒートマップではなく
**縦方向の到達率の分布**（棒グラフ）になる。

### `pointer_sample`（条件 3 に関わる）

**実装していない。** 記録するのはクリックだけで、間隔標本は取らない。

条件 3 の趣旨は「全軌跡を残さない」ことなので、
クリックだけの実装は**条件を満たす側に外れている**。
判断の理由は `design-review-findings.md` F-03。

### 条件 9 は成立しない（条件 1 と両立しない）

条件 1 は「個人へ戻せる列が他に無い」ことを求める。
条件 9 は「`reader_key` を指定して抽出・削除できる」ことを求める。

**この 2 つは同時には成り立たない。**

実装の `session_key` は `sessionStorage` に置いた使い捨ての UUID で、
タブを閉じれば消える。読者本人がその値を知る手段は無く、
運営者がその値から誰かを特定する手段も無い。

したがって「この `reader_key` の行を出してほしい」という請求は、
**請求してくる主体が自分の鍵を名乗れない**ので実行できない。
実行できる形にすると、鍵を個人へ結びつける経路を作ることになり、
条件 1 が崩れる。

決着は `subject-request-design.md` に書いた。要旨は
**「主体からの請求に応える対象そのものを持たない」**という設計にし、
条件 9 を「請求の受け口を作らない」へ読み替えた。
