# UI 規則（feat-blog-ui-builder）

- 更新日: 2026-08-31（固定文書の現行契約へ同期）
- 正本は実装。**この文書は実装の写しではなく、実装が守っている規則の説明である。**
  値そのもの（テンプレート ID の一覧など）を直すときは実装を直す。ここを直しても何も変わらない。

---

## 0. この文書の使い方

規則は 3 つの層に分かれている。**下に行くほど変えてよい。**

| 層 | 何が書いてあるか | 変えるとき |
| --- | --- | --- |
| **不変** | 変えると既存の記事や読者の入口が壊れるもの | 変えない。変えたいなら仕様から |
| **契約** | 実装が守ることを検査で強制しているもの | 実装と検査を同時に直す |
| **運用** | 人が判断する余地があるもの | 運用手順（`operations.md`）で決める |

---

## 1. テンプレート（6 種）

### 1.1 不変 — テンプレートは「並び方」だけを決める

**テンプレートは記事の中身を知らない。** 決めるのは 4 つだけである。

- トップの区画の並び（`homeSections`）
- 記事のブロックの推奨順（`articleBlockOrder`）
- サイドバーを既定で出すか（`sidebar`）
- 追加で薦める固定ページ（`suggestedPages`）

**「このテンプレートでは図解が使えない」の類を書いてはならない。**
書くと、テンプレートを差し替えた瞬間に既存記事の図解が消える。
受入 A1 の「差し替えても既存記事が壊れない」はこの一点で成り立っている。

並べ替えは `orderBlocksForTemplate()` が行い、
**推奨順に無い種類は末尾へ元の順のまま付ける。1 つも落とさない。**

### 1.2 6 種の選定基準

| ID | 表示名 | 設計図の型 | サイドバー | 選ぶ基準 |
| --- | --- | --- | --- | --- |
| `review_focus` | レビュー特化 | `specialist_review` | あり | 1 製品を深く扱う。読者は「これは買いか」を知りたい |
| `comparison_focus` | 比較特化 | `comparison_lab` | あり | 複数を横に並べる。読者は「どれを選ぶか」を知りたい |
| `howto` | ハウツー | `beginner_guide` | あり | 手順を追う。読者はまだ製品名を知らない |
| `news` | ニュース | `editorial_media` | **なし** | 鮮度が価値。読者は一覧より個別記事から入る |
| `minimal` | ミニマル | `personal_brand` | **なし** | 書き手が主役。区画は「最近の記事」だけ |
| `gadget` | ガジェット寄り | `specialist_review` | あり | 仕様の数字が判断材料。スペック表が先に来る |

**選ぶ順番は「読者が何を知りたいか」→「型」→「テンプレート」である。**
テンプレートから選ぶと、設計図の型と食い違ったときにどちらが正しいか決められなくなる。

`review_focus` と `gadget` は同じ型（`specialist_review`）を指す。
違いは記事のブロック順で、`gadget` はスペック表が図解より先に来る。
**数字で判断する読者と、写真で判断する読者の違いである。**

### 1.3 記事ブロックの順（`articleBlockOrder`）

全テンプレートに共通する骨格がある。

```
[ answer, key_points ]  …  各テンプレート固有の並び  …  [ faq, sources, freshness ]
      AI_FIRST                                              AI_LAST
```

- **先頭 2 つは必ず「結論」「要点」** — AI 検索に引用されるとき、
  先頭が結論でないと途中から切り取られる
- **末尾 3 つは必ず「よくある質問」「出典」「最終更新」** — 読者が
  信頼を確かめる材料は、読み終わったところに置く

`news` だけ `cta`（行動の呼びかけ）が `AI_LAST` の**後ろ**に来る。
ニュースは読んだ直後に買わせる記事ではないためである。

## 2. 表現ブロック（10 種）

### 2.1 契約 — 前半 5 種は AI 検索のための構造

| 種類 | 表示名 | 役割 |
| --- | --- | --- |
| `answer` | 結論（先に答え） | AI 引用の起点 |
| `key_points` | 要点 | 箇条書き。引用の単位 |
| `faq` | よくある質問 | 質問と答えの対 |
| `sources` | 出典 | 確認日つき |
| `freshness` | 最終更新・〜時点 | 鮮度の明示 |

| 種類 | 表示名 | 役割 |
| --- | --- | --- |
| `figure` | 図解 | 視覚 |
| `comparison` | 比較表 | 横並び |
| `cta` | 行動の呼びかけ | 導線 |
| `summary` | まとめ | 読後の整理 |
| `spec_table` | スペック表 | 数字 |

Google の「AI 機能での最適化ガイド」は追加の技術要件を求めていない。
**この 5 種は「引用されやすい構造」として選んだものであり、規格ではない。**
規格だと書くと、ガイドが変わったとき何を直せばよいか分からなくなる。

### 2.2 不変 — スロットは黙って空にしない

`slot` が付いたブロックは、別カテゴリのブログで中身だけ差し替えて再利用できる。
**差し替え先が無いときは `fallback` を `summary` ブロックとして出す。**
空にすると、記事の途中が理由なく飛ぶ。

## 3. 配色の 2 層

### 3.1 不変 — 効くのは 2 層だけで、順番は 1 つ

```
page_theme_override（そのページだけの例外）
        ↓ 無ければ
blog_theme（このブログの既定）
        ↓ 無ければ
site_blueprint.theme（設計図の既定）
```

**読む口は `publicBlogAppearance()` の 1 本だけである。**
公開面も管理画面もここを通る。別の読み方を作ると、
同じブログの配色について 2 つの画面が別の値を出す（2026-08-30 に実際そうなった。
`migration-report.md` §2）。

### 3.2 契約 — 2 層の対象は「配色」だけ

| 項目 | 2 層で上書きできるか |
| --- | --- |
| 色の組み合わせ（`brandTheme`） | ✅ できる |
| 明暗（`colorMode`） | ✅ できる |
| 余白の詰め方（`density`） | ❌ 設計図のみ |
| 角の丸み（`radius`） | ❌ 設計図のみ |

**余白と角丸を 2 層に入れないのは、ページごとに変わると読者が「同じサイトだ」と
思えなくなるためである。** 色は季節や特集で変えてよい。骨格は変えない。

管理画面で余白・角丸を出すときは、値の横に「（設計図）」と出所を書く。
書かないと「配色を変えたのに余白が変わらない」の理由が画面から消える。

### 3.3 契約 — 11 配色 × light/dark はすべて AA を満たす

配色を足すときは `themes.css` に light と dark の両方を書く。
**dark を light の単純反転で済ませてはならない**（`theme-contrast.test.ts` が止める）。
数値上 AA を満たしても、暗所で眩しくなる。

## 4. 固定ページ

### 4.1 現行契約 — 正本は `SiteDocumentKey` 1 系統

- `SITE_ROUTES` から導く `SITE_DOCUMENT_KEYS` 8 種が `legal_page.kind` の正本。
- canonical 管理画面は `/admin/sites/[site]/documents` の 1 画面。
- 保存は published にし、削除済み印を外す。公開取得は owner workspace・published・
  `deleted_at IS NULL` をすべて満たす行だけを返す。
- `/admin/blog/pages` と `/s/[site]/[fixedPage]` は canonical URL へ転送する
  redirect-only adapter。独自の CRUD/read-model を持たない。
- `FixedPageKind` は旧URLを認識する入力語彙に限る。表・管理画面・公開本文の正本ではない。

新しい固定文書は route catalog と名前付き canonical route へ足す。
旧URLも受け続ける要件がある場合だけ legacy redirect 対応を追加する。

### 4.2 歴史 snapshot — 2026-08-30 の統合前

> 当時は `SiteDocumentKey` と `FixedPageKind` が同じ表を別経路で触り、
> 18 経路中 12 件が 404 だった（`evidence/11-a4-a13-http-status.txt`）。
> これは統合前の失敗証跡であり、現行判定ではない。現行判定は
> [`acceptance-report.md`](./acceptance-report.md#2026-08-31-現行判定a1a14-の唯一の正本) を参照する。

### 4.3 不変 — 信頼ページはテンプレートに関係なく必須

`suggestedPages` は**追加で薦める**ページであって、必須ページではない。
運営者情報・プライバシー・特商法表記は、どのテンプレートでも要る。
`minimal` の `suggestedPages` が空なのは「信頼ページが要らない」の意味ではない。

## 5. SEO / AI 標準ブロックの挿入規則

### 5.1 不変 — 画面と機械向け出力は同じ読み取りモデルから作る

画面に出る本文と、機械向け出力（JSON-LD / sitemap / RSS / robots / llms.txt）は
**同じ読み取りモデルから作る。別の組み立てを置かない。**
置くと、記事を直したのに sitemap だけ古い、が起きる。

### 5.2 契約

1. 報酬・運営情報は読者向け読み取りポートを通さない
2. 更新日は JSON-LD の `dateModified` と `<time dateTime>` で**同じ値**を出す
3. 構造化データを HTML に埋めるときは `<` を `<` に逃がしてから埋める
   （逃がさないと、本文に `</script>` を含む記事でスクリプトが途中で閉じる）
4. origin は届いたリクエストの Host から作る。**環境変数に固定しない**
5. `llms.txt` は設計図の任意項目。出さない設定なら 404 を返す（空ファイルを返さない）

### 5.3 挿入の順

標準ブロックは**記事の書き手が置くもので、システムが自動で差し込まない**。
テンプレートは順番だけを決める（§1.3）。
自動挿入にすると、書き手が置いていない「結論」が空で出る。

> **2026-08-30 時点の実測**: 公開記事の本文が 1 文字も出ていない
> （`evidence/README.md` §3.1）。標準ブロックの挿入規則以前に、
> ブロックが載る場所そのものが空である。§5.3 は「あるべき規則」であって、
> 現状の説明ではない。

## 6. 出典レジストリ（`guideline_references`）の 90 日サイクル

### 6.1 契約 — 90 日の判定はドメイン関数だけが行う

**`referenceReviewStatus` だけが日数を数える。画面側で数え直さない。**
2 か所で数えると、時差や境界の扱いが食い違ったとき、
どちらが正しいか決められなくなる。

### 6.2 サイクルの規則

```
登録（確認日 = 今日）
   ↓ 90 日
「再確認」と表示される
   ↓ 原典を読み直す
確認日を今日に更新 → 振り出しへ
```

1. **90 日を超えた行は「再確認」と出る。自動では消えない。**
   消すと、古い指針に基づいた記事が残っていることに気付けなくなる
2. 再確認したら確認日を今日に更新する。**内容が変わっていなくても更新する**
   （「読み直した」という事実に意味がある）
3. **ガイドラインの中身が変わったときは、仕様セルを R4-reopen する。**
   アプリのレジストリを直しただけでは仕様は動かない
4. `/admin/settings/seo` の目的は「出典を登録し、90 日超を再確認する」だけ。
   他の設定を混ぜない

### 6.3 記事公開後の AI 検索点検

**点検は公開の条件ではない。** 足りない項目は直し方（hint）まで出す。
公開の条件にすると、点検を通すために内容を歪める力が働く。

> **2026-08-30 時点の実測**: レジストリの登録は 0 件で、
> コードに書かれた候補 4 件はすべて「原典未取得」である
> （`evidence/README.md` §3.3）。90 日の判定は動くが、判定する対象が無い。

| 変えたいもの | どこを直すか | 検査 |
