## 観点 1: makuring.jp 参照が丸パクリになっていないか

**判定: ✅ 適合。ただし ⚠️ 指摘 1 件。**

### 検証したこと

リポジトリ全体で `makuring` を走査し、参照の性質を確かめた。

| 場所 | 内容 | 判定 |
|---|---|---|
| `src/domain/authoring/site-blueprint.ts:21` | 「参考記事の構成を…」というコメント | ✅ 構成の参照のみ |
| `docs/product/T2-experience-spec.md:5` | 移植したものを 5 項目に限定し明記。「固有の文章・画像・ブランド名・色値は移植しない」 | ✅ 境界が文書化されている |
| `docs/spec/06-サイトブループリント-記事構成テンプレート.md:13` | **参考記事の取得が権限拒否で行えなかった**ことを記録 | ✅ 機械取得していない証跡 |
| `docs/product/ledgers.md:45` | 「参考記事ではなく…」を台帳へ記録 | ✅ 由来が追える |

**構成・配置・表記法の参照に留まっている。**
文章・素材・色値の複製は見つからなかった。
とりわけ、参考記事を**取得できなかった**ことが記録として残っているのは、
複製が構造的に起こりえなかったことの証跡になっている。

### ⚠️ R1-1: テストデータに参考元のブランド名が使われている

```
tests/integration/d1-telemetry.test.ts:63   const SITE = "makuring";
tests/integration/d1-telemetry.test.ts:127  path: "/s/makuring/a/laptop"
```

丸パクリではないが、**実在する第三者のブランド名をテストの識別子にしている。**

問題は 2 つある。

1. テスト出力・失敗ログに第三者の名前が現れる。
2. 「参考にしただけ」という境界が、コードを読む人には見えない。
   `SITE = "makuring"` だけを見た人は、これが取引先か自社サイトかを区別できない。

**対応**: 架空の slug（例 `sample-gear`）へ置き換える。
テストの意味は 1 文字も変わらない。

| 項目 | 内容 |

## 観点 2: 配色 2 層（`blog_theme` / `page_theme_override`）の一貫性

**判定: ✅ 一貫している。⚠️ 指摘 2 件。**

### 検証したこと

`theme-contract.md` §3 の解決順（読者 cookie > ページ上書き > ブログ既定 >
旧正本 > 全体既定）が、既存コードの前提と矛盾しないかを確かめた。

- `src/domain/authoring/appearance.ts` のコメントが既に
  「読者の選択 > ブログ既定 > 全体既定」の 3 段を宣言しており、
  P02 はこの間に**ページ上書きを 1 段挟んだだけ**である。既存の順序を反転していない。✅
- 軸ごとに独立に解決する（§3.2）ため、`BrandTheme` × `ColorMode` の
  掛け合わせが設定値として現れない。`appearance.ts:17-19` の
  「掛け合わせの数だけ設定を持たない」と整合。✅
- 解除を `DELETE` で表す（§3.3）判断は、schema コメント
  （`schema.ts` の `page_theme_override`「行を消すとブログ既定へ戻る」）と一致。✅

### ⚠️ R2-1: 5 段の解決順は、どこで解いても同じにならない

`theme-contract.md` §3 は 5 段の優先順を定めたが、
**この 5 段を解く関数の置き場所が指定されていない。**

段が 5 つあり、出どころが cookie（リクエスト）・DB 2 表・
設計図・定数と**4 種類に散っている**。解く場所が決まっていないと、
公開面のページ・レイアウト・OGP 画像生成でそれぞれ別々に解かれ、
「本文は上書きが効いているが OGP 画像は既定のまま」が起きる。

**対応**: `resolveAppearance(inputs): Appearance` を**純関数 1 本**として
`src/domain/authoring/appearance.ts` に置き、5 段の入力をすべて引数で受ける。
DB も cookie も関数の中で読まない（読むと単体で確かめられなくなる）。

| 項目 | 内容 |
|---|---|
| 対応先 | P06（実装） |
| 検査 | P04 が「5 段を上から順に潰す」境界値テストを持つ |

### ⚠️ R2-2: 静的化ページでの上書きが「運用手順に残す」で止まっている

`theme-contract.md` §5 は、静的化されたページでは
`page_theme_override` が読めないため build 時に解決されるとし、
その旨を P12 の運用手順へ回している。

**これは設計判断であって運用手順ではない。**

利用者から見ると「上書きを保存したのに公開面が変わらないページがある」となり、
その理由は運用手順書を読まないと分からない。
手順書は、変わらないことに気づいた**後**に読むものである。

**対応**: 次のいずれかを P06 が決める。

| 案 | 内容 | 代償 |
|---|---|---|
| A | 上書きのあるページを動的化する | そのページのキャッシュ効果を失う |
| B | 上書き保存時に該当パスを `revalidatePath` する | ISR の設定に依存する |
| C | 上書き一覧の画面で「このページは静的化されており、反映は次回ビルド時」と**表示する** | 実装が最も軽い。利用者が理由を知れる |

**C を推す。** 案 A・B は反映を早くするが、
「なぜ変わらないか」が利用者に見えないという本来の問題は
C でしか解けない。A または B を採る場合も C を併せて行う。

| 項目 | 内容 |
|---|---|
| 対応先 | P06（判断）/ P12（手順） |

## 観点 3: sticky 要素の WCAG 2.2 適合

**判定: ✅ 主要な論点は押さえている。⚠️ 指摘 1 件。**

### 3.1 達成基準 2.4.11 Focus Not Obscured（Minimum）— ✅

`component-contract.md` §2.3 の **S5**（キーボード焦点がヘッダーに隠れないこと、
`scroll-margin-top`）が正面から扱っている。

さらに同§が
「axe-core は通るのにキーボードで使えない画面になる（自動検査で捕まらない種類の破れ）」
と明記しているのは正しい。**axe-core は 2.4.11 を検出しない。**
自動検査の限界を設計文書側で宣言しているのは適切である。

### 3.2 達成基準 1.4.10 Reflow — ✅

**S2**（狭幅で高さを縮める）と **S4**（375px で本文の可読領域 560px 以上）が扱っている。

S4 を**数値**で固定したのは妥当である。
「圧迫しないこと」のような定性的な条件は、後から誰も判定できない。

### 3.3 フッターを sticky にしない判断 — ✅

`component-contract.md` §2.2（Q4 の決着）の 3 つの理由は、いずれも成立している。
特に「375px で両方固定すると本文が 2 段分削れる」は
1.4.10 との衝突を先回りしており、要求文の字面より代償の側から判断している。

### ⚠️ R3-1: 達成基準 2.4.12 と、モーダル・アンカーの検証範囲が抜けている

S5 は**本文中のリンクへ Tab で移動する**場合を扱っているが、
sticky ヘッダーが焦点を隠す経路はもう 2 つある。

| 経路 | 起きること |
|---|---|
| ページ内アンカー（`#section` への遷移） | 見出しがヘッダーの下に潜る |
| ダイアログを閉じた後の焦点復帰 | 復帰先がヘッダーの下 |

前者は `scroll-margin-top` を**見出しにも**与えれば解ける（S5 は「本文の見出し・リンクへ」
と書いているので実質カバーされているが、アンカー遷移という**経路**としては書かれていない）。
後者は `scroll-margin-top` では解けない。

**対応**: P04 の検査 Y2 を、次の 3 経路すべてで見る。

1. Tab による順送り
2. ページ内アンカー遷移
3. ダイアログを閉じた後の焦点復帰

| 項目 | 内容 |
|---|---|
| 対応先 | P04（検査範囲）/ P06（実装） |

## 観点 5: JSON-LD 自動生成と SSR 出力の整合（A10）

**判定: ✅ 妥当。⚠️ 指摘 1 件。**

### 検証したこと

- 生成関数を再利用し、**2 つ目の生成経路を作らない**（§1.1）判断は正しい。
  schema.org の仕様が変わったとき片方だけ直る事故を防ぐ。✅
- 「同じ 1 つの値から可視テキストと JSON-LD の両方を出す」（§3.2）は、
  構造化データと本文の食い違いを**構造で**防いでいる。
  検査（`dateModified` と可視日付の一致）まで指定されている。✅
- `FAQPage` を「`faq` ブロックが 1 件以上あるときだけ」に限る判断は、
  `structured-data.ts:173` の既存方針と一致。✅
- `canonical` を絶対 URL に限る（§2）のは、配信元が変わったときの自己参照崩れを防ぐ。✅

### ⚠️ R5-1: SSR 出力に JSON-LD が「載っている」ことの検査が指定されていない

§3.2 は **JSON-LD の中身**の検査（`dateModified` の一致）を指定したが、
**JSON-LD が実際に HTML に出ているか**の検査が無い。

これは別の失敗である。生成関数が正しく動いても、

- コンポーネントが `<script type="application/ld+json">` を出し忘れる
- 動的インポートの境界で client component 側に落ち、SSR の HTML に載らない

と、関数の単体テストは緑のまま HTML には何も無い。
**A10 は「記事ページの HTML に…」と書いており、関数の出力ではなく HTML が対象である。**

**対応**: P04 は**実応答の HTML 文字列**に対する検査を持つ。

```
GET /s/<site>/blog/<article> の応答 HTML に
  <script type="application/ld+json"> が 2 個以上（BlogPosting + BreadcrumbList）
  <link rel="canonical"> が 1 個、絶対 URL
```

| 項目 | 内容 |
|---|---|
| 対応先 | P04 |
| 種別 | 契約テスト（純関数の単体では代替できない） |

## 観点 6: IndexNow 鍵のリポジトリ非保存ポリシー（A13）

**判定: ✅ 適合を実測で確認。⚠️ 指摘 1 件。**

### 検証したこと（実測）

リポジトリ全体で `INDEXNOW_KEY` を走査した。**鍵の実値は 1 件も無い。**

| 出現 | 内容 | 判定 |
|---|---|---|
| `src/app/indexnow.txt/route.ts:20` | `env["INDEXNOW_KEY"]` の読み取り | ✅ 変数名のみ |
| `src/infrastructure/indexnow/indexnow-client.ts:40` | 同上 | ✅ |
| テスト 5 箇所 | 擬装した env に注入 | ✅ 値はテスト内の固定文字列 |
| 文書 6 箇所 | 変数名の説明 | ✅ |

- `.dev.vars` は `.gitignore:21` で除外されている。✅
- `.dev.vars.example` に鍵の実値は無い（`MCP_TOKEN=""` 等、空値のみ）。✅
- `wrangler` 設定に鍵の記載は無い。✅

`seo-ai-search-contract.md` §5.1 の K1〜K5 は、この実測状態を正しく写している。

とくに **K3 を「期待」ではなく「手当て」で守る**という書き方は正しい。
`indexnow-client.ts` のコメントが記録している 2026-08-25 の修正
（例外メッセージをそのまま戻り値に入れていた）は、

### ⚠️ R6-1: `.dev.vars.example` に `INDEXNOW_KEY` の行が無い

`.dev.vars.example` は `MCP_TOKEN` / `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET` を
列挙しているが、**`INDEXNOW_KEY` が載っていない。**

鍵をリポジトリに置かないことと、**鍵の存在をリポジトリに書かないこと**は別である。
example ファイルの役割は、必要な環境変数の**一覧を示すこと**にある。
載っていないと、新しく環境を立てる人は IndexNow が使えることに気づけず、
「通知が飛ばない」を故障として調べ始める。

**対応**: `.dev.vars.example` に空値で 1 行足す。

```
# IndexNow の鍵（任意）。未設定なら通知は skip され、公開自体は通る。
# 実値はここに書かず、`npx wrangler secret put INDEXNOW_KEY` で登録する。
INDEXNOW_KEY=""
```

| 項目 | 内容 |
|---|---|
| 対応先 | P06 または P12 |
| 難度 | 低 |
| 注意 | **実値は利用者が別途登録する。** 本作業で値を書き込まない |

### ✅ R6-2: Q5 の決着（`console.info` 継続）は妥当

`seo-ai-search-contract.md` §5.3 の 3 つの理由は成立している。
特に 3 番目（「鍵が未設定であることは状態として見えるべきで、

## 観点 7: `guideline_references` の 90 日再確認設計（A14）

**判定: ✅ 妥当。指摘なし。**

### 検証したこと

- **G3**（期限切れを自動で消さない・自動で更新しない、表示するだけ）が本質を捉えている。
  自動更新すると「誰も読んでいないのに確認日が新しい行」ができ、
  確認日が指す事実（**人が原典を読んだ**）が失われる。✅
- **G4**（境界は「90 日超」、ちょうど 90 日は対象外）は、境界値が明示されている。
  P04 が 89 / 90 / 91 日で検査できる。✅
- 「要旨を読んだ」と「原典を取得した」の区別（§6.2）を
  `note`（人が読む文）ではなく**列**で持たせている。
  「但し書きに書いても機械は判定に使えない」という理由が正しい。✅
- **再取得と再評価を分ける**（§6.3）設計は、
  取得を繰り返すだけで警告を消せる経路を塞いでいる。✅
- 「前回の指紋を別の表に置かない」（同）は、
  2 つの指紋が同じ行に並んでいることが変化検出の唯一の担保である、という理解に基づく。✅
- 出典の本文を保存しない（§6.4）。古くなった写しを正本の顔で残さない。✅

この観点は**設計として隙が無い**。指摘を作るために何かを挙げる必要はない。
