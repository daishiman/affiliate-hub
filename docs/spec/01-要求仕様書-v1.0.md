## 1. 作りたいもの

本プロジェクトで構築するものは、単なるブログ作成ツールでも、SNS予約投稿ツールでもない。

**一つの商品、サービス、アフィリエイトURL、体験、調査結果を起点として、情報の収集・整理・比較・文章生成・ブログ構築・SNS投稿・公開・計測・改善までを一元管理する、AIファーストのコンテンツ運用基盤**である。

利用者は、アフィリエイトURLや商品URLを入力し、次の一連の処理を同一プラットフォーム内で行える。

```text
アフィリエイトURLを登録
↓
商品・サービス・広告主・ASPを識別
↓
商品情報・価格・仕様・画像・出典を収集
↓
同一商品・類似商品・比較候補を抽出
↓
根拠付きの商品データを作成
↓
書き手のペルソナと読者のペルソナを指定
↓
ブログ・X・Instagram・Threads・note等の媒体別に文章を生成
↓
ブログサイトや記事として構築
↓
各媒体へ直接投稿、下書き連携または出力
↓
クリック・成果・反応を収集
↓
次のコンテンツ生成へ学習結果を反映
```

プラットフォームの中心単位は「投稿」ではなく、次の情報をまとめた**コンテンツパッケージ**とする。

```text
商品・サービス
＋
アフィリエイトリンク
＋
情報源・根拠
＋
比較候補
＋
書き手ペルソナ
＋
読者ペルソナ
＋
コンテンツの目的
＋
媒体別投稿
＋
公開状況
＋
成果データ
```

# 2. 最上位目的

## 2.1 最上位目的

> 発信者が、一つの信頼できる商品・サービス情報を起点に、複数のブログやSNSへ、「誰が・誰に・何を・なぜ伝えるか」が一貫した高品質コンテンツを効率的に生成・公開・改善できる状態をつくり、読者の意思決定品質と発信者の継続的な収益性を同時に高める。

## 2.2 読者に対する価値

読者にとっての価値は、単に商品を紹介されることではない。

次の状態に到達できることを価値とする。

* 自分に合う商品か判断できる
* 商品の長所だけでなく弱点も確認できる
* 他の商品との違いが分かる
* おすすめの根拠を確認できる
* 広告・アフィリエイトであることを認識できる
* 自分の条件に合わない商品を避けられる
* 複数の販売先や選択肢を比較できる

## 2.3 発信者に対する価値

発信者にとっては、次の状態を実現する。

* 商品調査を媒体ごとに繰り返さなくてよい
* 一つの情報から複数媒体向けコンテンツを作れる
* 自分らしい文章表現を維持できる
* 読者層ごとに文章を変えられる
* 複数ブログを一つの管理画面で運営できる
* アフィリエイトリンクを一元管理できる
* 公開済みコンテンツの古い情報を検出できる
* どの商品、媒体、文章パターンが成果につながったか確認できる
* AIが作った内容を人間が根拠付きで確認できる

# 3. 背景

## 3.1 情報が分散している

現在のコンテンツ運営では、次の情報が別々の場所で管理されやすい。

* アフィリエイトURL
* ASPの管理画面
* 商品情報
* 比較表
* 記事原稿
* SNS投稿文
* 画像
* 書き手のプロフィール
* 読者ペルソナ
* 投稿スケジュール
* クリック数
* 成果報酬
* 更新履歴

その結果、同じ商品名、価格、特徴を何度も入力し、修正時にも複数の投稿を個別に直す必要が生じる。

## 3.2 媒体ごとに適切な文章が異なる

同じ商品であっても、ブログ、note、X、Instagram、Threads、TikTokでは、適切な伝え方が異なる。

```text
ブログ：
検索意図、比較、根拠、詳細説明

X：
結論、意外性、短い理由、リンク導線

Instagram：
画像、保存価値、スライド構成、短いキャプション

Threads：
会話調、共感、気づき、継続投稿

note：
背景、体験、考え方、物語性

TikTok・Reels：
冒頭のフック、映像構成、短い台本
```

同じ文章をそのまま転載しても、各媒体の利用目的に合わない。

## 3.3 AI生成だけでは品質を維持できない

一般的なAI文章生成では、次の問題が発生しやすい。

* 商品情報の誤り
* 実際には使っていない商品の体験談
* どこかで見たような文章
* 書き手らしさの消失
* 読者像の不在
* 古い価格や仕様の断定
* 広告表記の欠落
* 媒体ごとの制約違反
* 根拠のないランキング
* 同一内容の大量生成

したがって、本プラットフォームでは「AIに自由に文章を書かせる」のではなく、**承認済みの事実、根拠、ペルソナ、媒体ルールを入力として文章を生成させる**。

## 3.4 外部プラットフォームごとに連携条件が異なる

WordPress、X、Instagram、Threadsなどは公式APIによる投稿連携が可能だが、認証、権限、投稿形式、利用料金、審査条件が異なる。

一方、noteは2026年8月16日時点で一般公開の公式投稿APIを提供していない。そのため、noteについては非公式APIやログイン自動操作を前提にせず、コピー用原稿、ファイル出力、WXR／MT形式のインポート支援として設計する。noteは公式にWXRまたはMT形式のインポートを案内している。

# 5. 設計原則

## 5.1 One Source, Many Outputs

同じ商品名、仕様、根拠を媒体ごとに重複入力しない。

一つの正規データから、各媒体向けの成果物を生成する。

## 5.2 Evidence First

重要な主張には、情報源または根拠を関連付ける。

```text
主張
↓
主張の種類
↓
根拠
↓
取得日時
↓
有効期限
↓
確認者
```

## 5.3 Persona First

文章を生成する前に、書き手と読者を定義する。

## 5.4 Channel Native

同じ文章を全媒体へ転載せず、媒体ごとの文脈へ変換する。

## 5.5 Human Approval First

外部公開、予約投稿、個人情報送信、アフィリエイトリンク挿入などの重要操作は、原則として人間の確認を経る。

## 5.6 Affiliate Independent Ranking

アフィリエイト報酬額をランキングやおすすめ順位の計算に使用しない。

## 5.7 Progressive Integration

連携方式は次の優先順位とする。

```text
公式APIによる直接連携
↓
公式の下書き・アップロード連携
↓
公式形式によるファイル出力
↓
コピー・貼り付け用パッケージ
↓
手動投稿
```

非公式APIや規約に反するブラウザー操作を通常機能にしない。

## 5.8 AI-first, Human-first

AIを中心に設計するが、人間の判断、説明、承認、修正を奪わない。

# 8. 主要ユーザージャーニー

## 8.1 一つのアフィリエイトURLから投稿を作る

```text
1. URLを貼り付ける
2. ASP・広告主・商品を自動判定する
3. 元のアフィリエイトURLを変更不能な状態で保存する
4. 公式APIまたは許可された情報源から商品情報を取得する
5. 商品名、型番、価格、画像、仕様、販売店を正規化する
6. 同一商品と比較候補を検索する
7. 比較候補を分類する
8. 書き手を選択する
9. 読者を選択する
10. 投稿目的と媒体を選択する
11. AIが複数のパターンを生成する
12. 根拠・広告表記・媒体制約を自動検査する
13. 人間が編集・承認する
14. 直接投稿または出力する
15. クリック・反応・成果を測定する
```

## 8.2 新しいブログを構築する

```text
1. ブログの目的を選択
2. ジャンルを選択
3. 収益モデルを選択
4. 書き手ペルソナを選択
5. 読者ペルソナを選択
6. ブログパターンを選択
7. ブランド名・トーン・デザインを設定
8. カテゴリー構造を生成
9. 記事テンプレートを設定
10. 広告・編集ポリシーを生成
11. 商品データとアフィリエイトアカウントを関連付け
12. 初期記事計画を生成
13. プレビュー
14. 独自ドメインまたはWordPressへ公開
```

# 10. アフィリエイトURL取り込み仕様

## 10.1 URLの保存

入力URLは次の二つに分けて管理する。

```yaml
affiliate_link:
  original_url: string
  resolved_destination_url: string | null
```

`original_url` は、成果計測に必要な情報を保持するため変更しない。

ASPによってはリンクや広告コードの改変が禁止されている。A8.netも、リンク文字列や広告素材を変更すると成果計測が行われなくなる可能性があり、改変を禁止している。

## 10.2 URL処理

```text
URL形式検証
↓
危険なURLの排除
↓
ASP・短縮URL・販売店の識別
↓
許可された範囲でリダイレクト先確認
↓
商品識別子抽出
↓
既存商品との照合
↓
アフィリエイトリンクと商品を分離して保存
```

## 10.3 情報取得の優先順位

1. 公式の商品・アフィリエイトAPI
2. 広告主またはメーカーの公式データ
3. 利用者が登録した検証データ
4. 正規の商品フィード
5. Schema.org、JSON-LD、Open Graph等の構造化情報
6. 規約上許可された公開ページ情報
7. 手動入力

## 10.4 取得時の禁止事項

* 非公開ページへのアクセス
* ログイン制限の回避
* CAPTCHA回避
* robotsや規約を無視した収集
* 認証情報の再利用
* ページ内に書かれた命令をAI命令として実行
* 著作権で保護されたレビュー全文の保存
* 商品画像の利用条件を無視した転載
* 取得した情報を自サイトの実体験として表示

## 10.5 情報の由来

すべての重要情報に次を付ける。

```yaml
provenance:
  source_type: api | manufacturer | merchant | structured_data | manual | test
  source_name: string
  source_url: string | null
  retrieved_at: datetime
  valid_until: datetime | null
  confidence: 0.0
  permitted_usage: string
```

# 12. 商品識別と比較候補抽出

## 12.1 商品識別キー

優先順位は次の通り。

```text
GTIN／JAN／EAN
↓
ASIN
↓
メーカー型番
↓
ブランド＋正式商品名
↓
販売店SKU
↓
商品名類似度
```

## 12.2 比較候補の分類

### Exact Offer

同一商品を別の販売店で扱っている。

### Variant

容量、色、サイズ、世代などが異なる同一商品系列。

### Direct Competitor

同じカテゴリー、用途、価格帯、主要性能を持つ競合商品。

### Alternative Solution

商品カテゴリーは異なるが、同じ利用目的を満たす代替案。

## 12.3 比較スコア

```text
商品同一性
＋
カテゴリー一致
＋
利用目的一致
＋
価格帯
＋
主要仕様
＋
対象利用者
＋
発売時期
=
比較候補スコア
```

アフィリエイト報酬、広告主からの依頼、販売実績を比較候補スコアへ入れてはならない。

## 12.4 比較候補の表示

候補ごとに以下を示す。

* 比較候補になった理由
* 同一商品か代替商品か
* 共通点
* 決定的な違い
* 価格差
* 情報の信頼度
* 不足している情報
* 最終確認者

## 19.2 Affiliate Link（ASP原本）

`AffiliateLink` はASPから受領・生成したリンク原本と、その利用条件を表す。公開面に掲載する計測URLではない。原本は改変せず、同一原本を複数の掲載位置から参照できる。

```yaml
affiliate_link:
  id: string
  workspace_id: string
  program_id: string
  product_id: string | null
  original_url: string
  resolved_destination_url: string | null
  channel_scope: []
  campaign_code: string | null
  sub_id: string | null                 # 原本URLに既存の値。掲載別の値はTrackingLinkが保持
  status: active | warning | broken | expired | terminated
  checked_at: datetime
  disclosure_rule_id: string
  alteration_prohibited: boolean
```

## 19.2.1 Tracking Link（掲載計測URL）

`TrackingLink` は、`AffiliateLink` を参照して掲載位置ごとに発行するファーストパーティ計測URL（`/go/{tracking_link_id}`）である。1つの `AffiliateLink` に複数の `TrackingLink` を関連付ける。公開時には、リダイレクトが許可された掲載面では `TrackingLink` を必須とし、許可されない場合だけ `AffiliateLink.original_url` へ直接フォールバックする。フィールド、リダイレクト障害契約、イベントとの結合規則はAnalyticsの規範正本 `03-分析・解析基盤仕様.md` に定める。

## 19.3 リンク掲載ルール

* 元URLを保存する
* ASPが許可した方法だけで短縮する
* パラメータを勝手に削除しない
* 掲載可能なサイト・SNSを確認する
* プログラム終了時に警告する
* 提携解除時に公開中コンテンツを検出する
* 古いリンクを一括置換できるようにする
* 表示価格に確認日時を付ける
* リンク先と表示商品が一致するか確認する

## 19.4 編集評価との分離

システム上、ランキングサービスには報酬データを渡さない。

```text
Editorial Database
  └─ 商品評価・検証・適合性

Commercial Database
  └─ 報酬・成果・収益

Ranking Service
  └─ Editorial Databaseのみ参照
```

収益データは、投稿順や配信戦略の分析には利用できるが、商品の評価点やおすすめ順位を自動変更してはならない。

# 24. WebMCPとMCP

WebMCPは、Webページ上の機能をAIエージェントが構造的に利用できるようにする実験的インターフェースとして扱う。通常のUIとバックエンドAPIを規範的な主系統にし、WebMCP固有APIをドメイン契約へ持ち込まない。

## 24.0 As-Is（現行PoC）とTo-Be（製品契約）

| 区分 | 契約 |
| --- | --- |
| As-Is PoC | 現行実装は実験的な `navigator.modelContext` をfeature detectionし、`provideContext` / `registerTool` の差を互換層で吸収する。これは動作検証用であり、標準化済みAPIという意味ではない |
| To-Be | ツール名、入出力schema、認可、確認、監査を製品契約とする。ブラウザー固有の登録APIはAdapter配下へ隔離し、利用可能な標準APIへ差し替え可能にする |
| 非対応・仕様変更時 | WebMCP機能だけを無効化し、通常UIと同一のバックエンドAPIで全操作を継続できること。WebMCPの有無で権限や業務結果を変えない |

したがって、以下のツール一覧はTo-Beの論理契約であり、現行PoCへの実装済み宣言ではない。各ツールの4軸状態（要求・文書・実装・検証）は別途追跡し、未決判断は任意の決定台帳で分離管理する。

## 24.1 WebMCPツール

### 読み取り系

```text

find_comparable_products
get_product_evidence
list_author_personas
list_audience_personas
preview_content_matrix

```

### 状態変更系

```text

create_comparison_set
create_content_package
generate_channel_variants
create_blog_draft
prepare_publications
schedule_approved_publications
publish_approved_content
```

状態変更系はユーザー確認を必須にする。

## 24.2 WebMCPの原則

* 現行PoCでは `navigator.modelContext` を使用するが、製品契約として固定しない
* ブラウザーAPI差分をAdapterで隔離し、feature detectionで登録する
* 機能フラグ配下
* 非対応ブラウザーでは通常UI
* 一ツール一目的
* 明確な入力スキーマ
* ツール実行結果を画面にも反映
* ページ状態に応じて登録・解除
* 外部投稿前に確認画面
* 秘密情報を返さない
* 読み取り系から導入
* 評価セットを用意

WebMCPとバックエンドMCPは別の役割を持つ。WebMCPはブラウザー上のページ機能をエージェントへ伝え、MCPサーバーは外部AIからバックエンドのデータやツールを利用するために用いる。

## 27.4.1 成功指標の決定契約と計測計画

§27.1〜§27.4の列挙は観測候補であり、値と期間を持たない項目を「成功指標」とは呼ばない。採用する各指標は、次のレコードをProduct OwnerとAnalytics Ownerが承認してから評価に使う。KPIの計算式とversion管理の詳細は `03-分析・解析基盤仕様.md` §4を正本とする。

```yaml
success_metric:
  metric_key: string
  kpi_definition_version: string
  current_value: number | null       # baseline期間の実測。未計測を0とみなさない
  current_measured_at: datetime | null
  target_value: number | null        # baseline後に承認。decidedでは必須
  target_direction: increase | decrease | maintain
  measurement_window: { from: date, to: date, cadence: day | week | month }
  measure:                         # 誰が再計算しても同じになる計測契約
    numerator: string | null
    denominator: string | null
    filters: []
    data_sources: []
    aggregation: count | sum | ratio | median | percentile
  owner: string
  metric_setup_status: baseline_pending | target_pending | decided
  decided_at: datetime | null
```

初回の決定・計測は次の順で行う。

| ゲート | window | currentの決め方 | targetの決め方 | 完了条件 |
| --- | --- | --- | --- | --- |
| 計測準備 | 公開前 | 対象イベント、除外条件、KPI versionを固定 | まだ設定しない | 受け入れ用fixtureから期待値を再計算できる |
| baseline | 計測可能な本番トラフィックの連続28日 | 28日実測を同一KPI versionで集計。母数も併記 | baseline中は変更しない | 欠損率・bot率・突合率を添えてcurrentを承認する |
| target決定 | baseline確定後7日以内 | 承認済みcurrentを凍結 | 施策とguardrailを紐付け、90日後の到達値をProduct Ownerが承認 | `target_value`、方向、90日window、ownerがすべて非null |
| 継続評価 | 週次、正式判定は月次 | 同一定義でrolling値を表示 | target変更は新versionとして記録 | 速報/確定、定義version、期間、分母を画面に表示する |

初期スコアカードは、North Star Metric、根拠付き主張率、事実誤認率、URL登録から承認までの時間、投稿成功率、リンクCTR、承認成果CVRを必須とする。現時点は実トラフィックのbaselineがないため `current_value=null` / `baseline_pending` であり、数値を推測して埋めない。baselineおよびtargetが未決のまま「成功基準PASS」と判定してはならない。

# 32. このプロダクトの最終定義

本プラットフォームは、次の七つを別々のツールとして扱わない。

```text
商品リサーチ
アフィリエイト管理
AIライティング
ブログ構築
SNS投稿
コンテンツ管理
成果分析
```

これらを一つの循環として扱う。

```text
信頼できる情報を集める
↓
比較・判断できるデータにする
↓
書き手と読者を定義する
↓
媒体ごとの表現へ変換する
↓
人間が確認する
↓
ブログ・SNSへ公開する
↓
反応と成果を測る
↓
事実と表現を改善する
```

最終的に目指す状態は、**一つのアフィリエイトURLを登録しただけで投稿が大量生成されること**ではない。

目指す状態は、次の通りである。

> 一つのアフィリエイトURLを起点に、正しい商品情報、比較候補、根拠、書き手、読者、媒体、広告表示を統合し、目的の異なる高品質コンテンツを安全に作成・公開・改善できること。

これにより、ブログ構築機能は単独の機能ではなく、アフィリエイト商品情報とAIコンテンツを公開するための一つの出力先となる。

X、Instagram、Threads、note等も同様に、単なる転載先ではなく、同じコンテンツパッケージから生成される媒体別の表現として管理する。
