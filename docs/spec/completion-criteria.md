仕様書の完了条件は抽象的な文のままでは検証できないため、**誰が何を実行すれば真偽が判定できるか**まで落としています。「検証方法」が空欄の項目は、その定義自体が未決であることを示します。

凡例: `☐` 未達成 / `☑` 達成 / `—` 該当フェーズ未着手

## A. 機能

| # | 完了条件 | 検証方法 | 担保フェーズ | 状態 |
| --- | --- | --- | --- | --- |
| A1 | 通常 UI だけで主要タスクを完了できる | JavaScript 無効のブラウザで「検索 → 比較 → 販売店選択」を完走する手動テスト | 1 | ☐ |
| A2 | AI だけでなく記事本文から同じ根拠を確認できる | AI 回答が返した `claim_id` に対応する記述が、記事ページの HTML 内に存在することの自動検査 | 3 | ☐ |
| A3 | WebMCP 非対応環境で機能低下が限定的 | `document.modelContext` を削除した環境で A1 と同じ手動テストを完走 | 4 | ☐ |
| A4 | 商品比較結果が UI・AI・WebMCP で一致する | 同一入力を3経路へ渡し、比較結果の差分がゼロであることの自動テスト | 4 | ☐ |
| A5 | 広告関係が記事・AI・WebMCP で一貫する | `Disclosure` を1か所から取得していることの静的検査＋3経路の出力比較 | 4 | ☐ |

**A4・A5 は「同じ計算を3回書かない」ことでしか達成できません。** 仕様書 §27 の禁止依存（WebMCP 内に独自のランキング式を実装しない）と同じ要求です。既存の `src/lib/mcp/specs.ts` がツール定義を1か所に集約している設計を、Comparison / Disclosure Service にも適用します。

## D. ローンチ基準（§24）

数値目標のため、評価セット実装（Phase 3）まで測定できません。

### WebMCP

| 指標 | 基準 | 状態 |
| --- | --- | --- |
| 正しいツール選択率 | ≥ 95% | — |
| 読み取り専用タスクの完了率 | ≥ 95% | — |
| 不正引数からの回復率 | ≥ 90% | — |
| 未承認の状態変更 | 0 | — |
| 無断のアフィリエイト遷移 | 0 | — |
| クロスオリジンのデータ漏洩 | 0 | — |
| UI 状態の同期 | リリーステストセットで 100% | — |

### AI

| 指標 | 基準 | 状態 |
| --- | --- | --- |
| 事実回答への引用付与率 | 100% | — |
| 引用が主張を支持する率 | ≥ 98% | — |
| 重大なハルシネーション | 0 | — |
| 一次体験の捏造 | 0 | — |
| 報酬に影響されたランキング | 0 | — |
| 不明時の適切な応答率 | ≥ 95% | — |

**「0 でなければならない」指標（未承認の状態変更、無断遷移、報酬影響ランキング）は、測定で担保するものではありません。** 統計的に 0 を目指すのではなく、構造的に発生し得ない設計にしたうえで、テストは回帰検出に使います。具体的には仕様書 §14.5 の「エージェント呼び出しだけで確定させない」処理順序と、§27 の禁止依存の静的検査です。
