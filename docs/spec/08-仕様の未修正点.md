そのため、ここに挙げる 4 件は「書き忘れ」ではなく、**生成の側の課題**である。
手で直すと次の生成で消え、しかも生成側の不具合が見えなくなる。
だから直さずに、**何が起きているか・何が困るか・どうすれば解けるか**を記録する。

## ① `system-spec/backend.md` の記法崩れ（medium・**未解消**）

**何が起きているか**（2026-08-17 に確認）

- 90 行目と 259 行目にコードフェンス（```` ``` ````）があるが、**2 本とも閉じ側**で、開き側が無い。
- 75〜89 行目の図が、フェンスの外に裸で置かれている。
- 同じ本文（計測の 5 層の図と設計原則）が **239〜266 行目にまるごと重複**している。

**何が困るか**: Markdown として描画すると図がずれ、以降の本文がコードとして表示されうる。
仕様を読む人が、どこまでが図でどこからが本文か判別できない。

**原因**: 質疑録（`qa_log`）の回答本文を章へ取り込むとき、
回答の中にあるフェンスをそのまま貼っているため、対が壊れる。

**解除条件**: `run-system-spec-compile`（C03）で、
質疑録の取り込み時にフェンスを退避するか引用ブロックへ変換したうえで再生成する。
あわせて「確定内容（質疑録）」と「本章での適用」の本文重複を解消する。

## ② 上流指針（doctrine）が要件文につながっていない（medium・**未解消**）

**何が起きているか**: 各章に「上流指針」の表があり、
Apple HIG / Clean Architecture / OWASP ASVS / Google SRE が挙げてある。
ところが「本章での適用」の出典は社内文書（`docs/spec/01`〜`03`）だけで、
**挙げた指針の具体的な条項が 1 件も引かれていない**。

**何が困るか**: 名前だけ挙がっている状態は、
「権威ある指針に従っている」ように見えて、実際には何も拘束していない。
判定を通すためだけの記載になり、指標が目的化する。

**解除条件**: C03 の章生成で、確定セルの要件文へ指針の該当節を**最低 1 件**引く。
例: `security.md` の SSRF 要件へ ASVS の該当章、
`maintenance-ops.md` の SLO へ SRE workbook の該当章。

## ③ 技術選定の記録が 1 件しかない（medium・**未解消**）

**何が起きているか**: `spec-state.json` の `decisions[]` は
`decision-auth-method`（Better Auth / IDaaS / Cloudflare Access の 3 案比較）**1 件のみ**。
費用・囲い込み・運用の手間に効く次の選定に、比較の記録が無い。

- Editorial / Commercial の D1 二系統分離
- Redirect Resolver への Queue / Cron 追加
- AI 生成に使う提供元（LLM プロバイダ）

**何が困るか**: あとで「なぜこれにしたのか」を再構成できない。
乗り換えを検討するときに、当時の前提と却下理由が残っていないため、
同じ比較を最初からやり直すことになる。

**解除条件**: `run-system-spec-elicit`（C01）の R5-decision-guide で、
各選定を 2〜3 案の比較（費用・囲い込み・運用負荷・目的適合）として追記し、
**利用者本人の確定**を得る。AI の推奨だけで確定にしない。

ではない。**語で数えると、違う文が同じ語を持っていたときに区別が付かない。**

**確認方法**（語ではなく、探している文そのもので数える）:

```bash
for f in system-spec/*.md; do
  printf '%s ' "$f"; grep -c '実装根拠に使用不可' "$f"
```

つまり ④ は「直ったあとで戻った」のではなく、**最初から直っていなかった**。

## ⑤ 評価が見ていない仕様書が 9 枚ある（2026-08-19 に判明・**未解消**）

**何が起きているか**: 上の 4 件の出所である完全性評価（`completeness-report.json`、判定 `PASS`）は
**2026-08-16 に、`docs/spec/` が 7 枚だった時点**で出されている。
現在の `docs/spec/` は 16 枚で、`04`〜`12` の **9 枚（計 3,012 行）が評価のあとに書かれた**。
`03` も 743 行 → 1,066 行に増えている。

**数え方**（最初 15 枚と書いて 1 枚ずれた。数える対象を先に決めておく）:
数えるのは **`docs/spec/` 直下の `.md` すべて**で、番号付き（`00`〜`12` の 13 枚）と
番号なし（`ai-first-webmcp` / `completion-criteria` / `data-model-gap` の 3 枚）を区別しない。
番号の有無は書かれた順序の名残であって、規範かどうかとは関係がないため。
この数え方は `scripts/spec-freshness.mjs` の指紋の対象と一致しており（`docs/spec` 16 +
`system-spec` 10 + `spec-state.json` 1 = **入力 27 件**）、門の出力と突き合わせて検算できる。
評価当時の 7 枚は `git ls-tree --name-only 4da7c74 docs/spec/` で数えた。7 + 9 = 16。
そして `system-spec/` の 8 章は、この 9 枚を**1 か所も参照していない**
（`grep -o 'docs/spec/NN' system-spec/*.md` が `04`〜`12` について 0 件）。

**何が困るか**: いちばん大きい主張である「仕様を全て満たした」の根拠が、この `PASS` である。
その `PASS` は、いま在る仕様書の **6 割を見ていない**。
古い判定は古く見えないので、放っておくと「満たしている」という読み方だけが残る。

**解除条件**: 完全性評価（C05）を、いまの 15 枚を入力として再実行する。
`scripts/spec-freshness.mjs --write`（指紋の焼き付け）は**その後**に行う。
先に焼くと「いまの仕様書に対する `PASS`」という嘘が 1 コマンドで作れる。

**当座の見張り**: `pnpm run verify` の「仕様レポートの鮮度」を落ちる側にしてある（2026-08-19）。
以前は判定を出したあと捨てて必ず緑を返していたため、この状態が見えなかった。
