### ②-2 この項目は「やり残し」ではなく「やらないと決めたこと」である（2026-08-19・利用者判断）

**この区別を書くために、この節を足した。**②の本文だけを読むと未着手に見えるが、
**着手して、解けないことを確かめて、利用者本人が保留を選んだ**というのが実際である。
仕様書だけを読む人には、この 2 つの区別が付かない。

**決めたこと**: **4 つの authority（Apple HIG / Clean Architecture / OWASP ASVS /
Google SRE）の条項を、外部から取得しない。**取得を伴う作業は行わない。
別の担当・別のセッションに取得を頼む形も取らない
（**手段が変わっても到達点が同じなら迂回にあたる**ため）。

**なぜ解けないか**（難しいからではなく、この作業場所の約束と両立しないため）:

1. 条項を引くには authority の内部位置（節番号・章名）が要る。取得コマンドは権限で断られた。
2. 取得済みの `system-spec/retrieval-evidence/*.json` は `content_sha256` と
   `page_title` しか持たず、**節名を 1 つも持っていない**。
3. ローカルの出典カード（`ref-system-design-knowledge/`）には条項らしき名前が並ぶが、
   `system-spec/security.md` 自身が「**非規範・取得証跡なし・実装根拠に使用不可**」と
   規定している。**そこから借りるのは、この項目が直そうとしている欠陥
   （名前を借りているだけで条項は当たっていない）の再生産にあたる。**
4. `docs/spec/` 側の書面入力にも条項番号は無い（grep 0 件）。

確かめずに条項名を書けば、この項目は「解消」に見え、完全性評価も通るかもしれない。
**それは指標が目的化した状態そのものなので、書いていない。**

**解除条件**: **4 authority の節見出しを、取得証跡つきで持つこと。**
必要なのは「節名を持つ証跡」であって、条項名そのものではない。
名前だけなら確かめずに書けてしまい、それがこの項目の欠陥そのものだからである。

**解除の日に何をするか**（ここまで書いておかないと、次に読む人が保留を解いてよいか判断できない）:
`tests/architecture/doctrine-citation-gap.test.ts`（`REQ-TS13`）が
**赤くなった日が、解除してよい日**である。赤くなる道は 2 つ——
要件文へ引用が現れる／取得証跡が節名を持ち始める。
**そのとき、この検査を消してはならない。向きを反転させて残す**
（「authority を引いている文は 0 文」→「各章が最低 1 件引いていること」）。
消すと、引用が後から抜けても誰も気づかない状態へ戻る。
**穴を見張る検査は、穴が塞がった日に役目を終えるのではない。**

**registry への明示について**: 完全性評価は「registry と章に明示せよ」と指示しているが、
`doctrine-anchor-registry.json` は
`.claude/plugins/system-spec-harness/skills/ref-system-design-knowledge/references/` に
しか無く、**キット配布物なので次の更新で上書きされる**（プロジェクト固有の決定を
キット側へ書かない規約）。章（`system-spec/*.md`）は確定章ガード
（`guard-confirmed-chapter-overwrite.py`）が Edit を遮断する。
**したがって、耐久性のある明示先はこの仕様書だけであり、ここに書いた。**
評価上は「registry に無い」ままなので、この項目は評価器の側では解消しない見込みである。
**それを承知で、消える場所へ書くより残る場所へ書くほうを選んだ。**
