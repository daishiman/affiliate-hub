## 1. クリック計測機構の欠落(移行記録)

### 1.1 問題

v1.0 は「クリック・成果を収集する」と記述するが、**どうやって自サイト経由のクリックを計測するか**が未定義である。ASPの管理画面のクリック数だけでは、「どの記事の・どの位置の・どのリンクが」クリックされたかを特定できず、9.10章・27章の「切り口別成果」「テンプレート別成果」は実現できない。

### 1.2 補充要件の要約

自社ドメイン配下のリダイレクトエンドポイントを設け、リダイレクトが許可された公開面は掲載位置ごとの `TrackingLink` を経由させる。

```text
読者クリック
↓
https://{site_domain}/go/{tracking_link_id}
↓
クリックイベント記録(placement / variant / session 等)
↓
302 リダイレクト → original_url(ASPリンク、改変なし)
```

移行時に維持する境界条件:

* `AffiliateLink` はASPリンク原本、`TrackingLink` は掲載計測URLとし、直接同一視しない
* 公開面に紐付く `TrackingLink` は `workspace_id` を必須とし、`publication_id` も公開時までに必ず非nullにする（下書き段階だけnullを許可）
* 許可された場合も `AffiliateLink.original_url` は改変せず、禁止プログラムは直接リンクへフォールバックする
* 転送先の解決と転送を計測DB書き込みから分離する。計測側が障害中でも、解決済み原本URLへ302転送し、未計測・遅延計測の状態を監視する
* 許可判定、resolver store、Queue非同期配送、SLO、劣化モード、sub_id突合の詳細は `03` §1・§6を正とする

### 1.3 TrackingLink エンティティの追加（移行要約）

`AffiliateLink`(リンク原本)と `TrackingLink`(掲載位置ごとの計測単位)を分離する。同じアフィリエイトリンクでも、記事Aの冒頭CTAと記事Bの比較表では別の TrackingLink を発行する。

本書にあったフィールド一覧は `03` の `tracking_link` 契約へ移行した。公開前不変条件、テナント外部キー、有効期限は `03` だけで定義する。

## 2. 成果データ取り込みとライフサイクル

### 2.1 問題

v1.0 の `Conversion` はエンティティ名のみで、ASP成果の状態遷移(発生→承認→確定/却下)や取り込み方法が未定義。

### 2.2 補充要件の要約

* 取り込みはASP API、CSV、手動登録の三系統を持ち、ASP成果を識別する `source_conversion_id` または安定した代替identityで冪等化する
* `Conversion` は承認軸（`pending / approved / rejected / cancelled`）と支払軸（`not_eligible / unpaid / scheduled / paid / reversed`）を分離し、`paid` を承認状態に混ぜない
* ソース上の状態変更をappend-only履歴として保存し、最新projectionと過去日集計を冪等に再構築できるようにする
* 成果原本はCommercial D1に保存し、Editorial D1へは報酬・EPC・Conversion明細を送らず、配信に必要な非収益性のInsight要約だけを連携できる

成果identity、二軸状態遷移、金額、外部キー、outbox/projectionの詳細は `03` §2.4・§1.3を正とする。

---

## 3. ブログ側行動計測(移行要約)

v1.0 はSNSのInsightsとASP成果に触れるが、**自社ブログの読者行動計測**が未定義。以下を補充する。

ページ表示、スクロール、リンク表示、比較表・FAQ・目次操作を対象とする。GA4等はオプションとし、中核は自前イベント基盤とする。イベントschema、同意なしのnullability、transport冪等と行動上の重複の分離は `03` §2を正とする。

---

## 4. UTM・投稿元識別規約(移行要約)

SNS→ブログ→アフィリエイトリンクの経路を復元するため、自サイトへ誘導するURLには標準UTMを自動付与する。

```text
utm_source   = 媒体 (x / instagram / threads / note / newsletter ...)
utm_medium   = social / email / organic
utm_campaign = campaign_id
utm_content  = publication_id
```

これにより「Xのどの投稿が、どの記事経由で、どの成果につながったか」を publication 単位で追跡できる(30.8章の追跡可能性を計測面で成立させる)。収集時の許可key、個人情報の除去、正規化は `03` §2を正とする。

---

## 5. A/Bテスト(Experiment)の具体化(移行要約)

v1.0 では `Experiment` がエンティティ名のみだったため、hypothesis、variant、traffic allocation、KPI version、guardrail、停止条件、探索率、holdoutを契約化する。フィールドと統計規律の詳細は `03` §7を正とする。

* ブログ記事はタイトル・冒頭・CTA文言・リンク配置のA/Bを配信側で振り分け可能にする
* SNSは同時配信ができないため「逐次比較(時間帯・曜日を揃えた交互投稿)」として別扱いにし、統計的限界を画面に明示する
* 有意差判定前の「勝ち宣言」をUIがさせない(最小サンプル未達では結論ボタンを無効化)

---

## 6. コンプライアンス補充

* **リンク属性**:アフィリエイトリンクには `rel="sponsored nofollow"` を自動付与(検索エンジンガイドライン対応)。v1.0 に記載なし
* **同意管理(CMP)**:クリック・行動計測はCookie等を用いるため、サイトごとに同意バナーとオプトアウトを提供。同意前は匿名集計のみ
* **個人情報**:同意済みクリックのIPアドレスは突合・不正検知用途に限定し、保存時に切り詰め(/24)またはハッシュ化する。同意なしは保存せず、保持期間は`03` §9を正とする
* **薬機法・金融関連**:ジャンル別禁止表現辞書(健康・美容・金融・投資)を PolicyRule に追加。景表法だけでは不足
* **成果報酬の税・通貨**:報酬は税込/税抜と通貨を保持。当面 JPY 固定でもフィールドは用意

## 7. 運用系の補充

| 領域 | 補充内容 |
| --- | --- |
| 通知 | 投稿失敗・リンク切れ・プログラム終了・成果確定をメール/Slack/アプリ内で通知。通知チャネルはWorkspace設定 |
| レート制限 | 各Connectorにレートリミッタとコスト上限(特にX API従量課金)。上限接近で警告、超過で自動停止 |
| バックアップ | Workspace単位のエクスポート(記事・商品・リンク・成果CSV)。退会時データポータビリティ |
| 監査 | AuditLog の必須記録対象を列挙:公開/削除/リンク差し替え/権限変更/成果データ修正/エクスポート |
| 障害時 | リダイレクトはresolver storeで転送先を解決し、計測eventをQueueへ非同期配送する。SLOと劣化モードは`03` §1を正とする |
| 検索 | 記事・商品・リンクの横断全文検索。テナント別インデックス(26.4章と整合) |
