## 2. 数字を偽らないための規律（この章で最も重要）

カバレッジは**目的ではなく、手を抜いていないことの副産物**である。
数字だけを上げる方法はいくらでもあるので、先に禁止事項を決める。

| 禁止 | なぜ禁止か |
| --- | --- |
| アサーションの無いテスト | 実行するだけで「通った」ことになる。壊れても赤くならない |
| スタブを厚くテストして全体を押し上げる | 中身が仮の場所は行数が少なく通しやすい。**最も壊れると痛い場所は覆われないまま数字だけ上がる** |
| 閾値を下げて緑にする | 下げた記録が残らなければ、次の人は「元から 60% だった」と思う |
| 到達しにくい分岐を消して分母を減らす | 異常系を削るのは、異常系を守らないという意思決定である |
| カバレッジのためだけの `if` 展開 | 読みにくくなり、変更容易性を下げる |

### 2-1. スタブの扱い（決定と理由）

**決定: スタブをカバレッジ計算から除外しない。加えて「スタブを除いた実質カバレッジ」を併記する。**

理由:

- スタブは仮の中身だが、**利用者が実際に踏む経路**である（画面に「まだ動きません」を出すのはスタブの仕事）。
  除外すると、その表示が壊れても数字に出ない。
- 一方、除外しないままだと「スタブを厚くテストして数字を作る」ができてしまう。
  そこで**両方の数字を出し、差が開いたら手抜きの合図とする**。

`docs/product/coverage.md` に次の 2 段を必ず並べる。

1. 全体（スタブを含む）
2. **実質**（`src/infrastructure/persistence/sample/` などスタブ実装を除く）

2 が 1 より大きく低い場合、それは「動く場所を覆わずに数字を作った」ことを意味する。

### 2-2. 層別に測る（全体 1 個の数字で判断しない）

全体 80% は、内訳次第で意味が正反対になる。
**domain と application が最も壊れると痛い層**なので、ここには高い水準を要求する。

| 層 | 要求水準の考え方 |
| --- | --- |
| `src/domain/` | 最高水準。業務の決まりごと。ここが壊れると仕様違反が本番に出る |
| `src/application/` | 高水準。ポートを差し替えられるので、厚く書けない言い訳が無い |
| `src/infrastructure/` | 中程度。外部接続はスタブが多く、実接続後に再評価する |
| `src/presentation/` `src/app/` | 中程度。4 状態と孤立ページの検査を優先し、見た目の網羅は追わない |

具体的な数値は `quality-gates.config.mjs`。層ごとの実測は `docs/product/coverage.md`。

## 3. テストの種類（7 種。単体だけでは不可）

各種類は「何を守るためか」を必ず 1 行で持つ。守る対象を書けないテストは消してよい。

| # | 種類 | 守るもの | 置き場所 |
| --- | --- | --- | --- |
| 1 | ドメイン単体 | 業務の不変条件。仕様違反が本番に出ないこと | `tests/domain/` |
| 2 | ユースケース単体 | 手順の正しさ。権限・テナント・失敗時の戻り値 | `tests/application/` |
| 3 | API 単体 | 3 つの入口（REST / WebMCP / バックエンド MCP）が同じ答えを返すこと | `tests/presentation/` |
| 4 | 画面単体 | 4 状態が出ること・操作できること・読み上げられること | `tests/ui/` |
| 5 | 結合 | 層をまたいだ 1 周が実際に通ること | `tests/integration/` |
| 6 | 境界値・異常系 | 端で判断が切り替わること。**数字が嘘をつかないこと** | 各層に併置 |
| 7 | 契約・境界の機械検査 | 設計の約束が破られないこと | `tests/architecture/` |

### 3-1. ドメイン単体（最優先）

最低限、次の不変条件は機械で守る。

- 順位づけに報酬額が入力されない（`affiliate_compensation_is_input: false`）
- Ranking のユースケースに Commercial 側ポートを**注入できない**（型で不可能。
  「型エラーになること」自体を検査する）
- 公開ゲート（ステマ告示に基づく広告表示・開示・`rel="sponsored"`）を飛ばせない
- 改善ループのガードレール（Evidence First / 開示義務 / WCAG 下限 / 報酬額の非入力）が
  最適化の対象として登録できない
- 正のフィードバックループの停止条件と上限が必ず存在する
- テナント境界（他テナントのデータに到達できない）

### 3-2. ユースケース単体

ポートをテストダブルに差し替えて、ユースケース単体で検証する。
**ここを厚く書けるのが、依存性逆転を入れた見返りである。**
厚く書けていないなら、ポートの切り方が間違っている可能性を先に疑う。

### 3-3. API 単体（3 アダプタすべて）

道具は 1 つのカタログ（`src/presentation/tools/catalog.ts`）から生成しているので、
**テストもカタログから反復して作る。手で 1 件ずつ書かない。**
道具を 1 つ足したら、その日から検査対象に入る。

検査項目（各道具について）:

| 項目 | 見るもの |
| --- | --- |
| 正常系 | 期待どおりの形の値が返る |
| 入力検証 | 不正な引数を理由つきで拒否する（例外で落ちない） |
| 認証・認可 | 権限の無い担当者は理由つきで拒否される |
| テナント分離 | 他テナントを指定しても届かない |
| エラー形式 | 失敗の戻り値の形が 3 アダプタで揃っている |
| スタブ | スタブは**失敗を返す**。成功したことにしない |

### 3-4. 画面単体

共通 UI 部品（primitives / patterns / templates）と各画面。

- **4 状態**（読み込み中 / 空 / エラー / 権限なし）が実際に文言として出ること
- 孤立ページが無いこと（既に `tests/presentation/admin-routes.test.ts` / `tests/domain/site-routes.test.ts` が担保）
- フォーム検証、キーボード操作、フォーカス、ARIA
- **アクセシビリティの自動検査**（axe）を、代表画面ではなく**全画面**に当てる
- **全配色 × 明暗のコントラスト検査**（`09-UIテーマ仕様.md` UI-AC-04）

### 3-5. 結合

最低限、次の 1 周が通ること。

```
記事を生成 → 承認 → 公開 → 計測イベント受信 → 分析 → 改善提案 → 承認 → 再生成
```

この 1 周は**層をまたぐ**ため、どこか 1 層の思い込みで通ることがない。
加えて、D1 を実際に使った結合（マイグレーションが適用できること）を含める。

### 3-6. 境界値・異常系

| 対象 | 端 |
| --- | --- |
| 件数 | 0 件 / 1 件 / 上限 / 上限 +1 |
| 文字列 | 空文字 / 最大長 / 最大長 +1 |
| 数値 | 0 / 負値 / 上限 |
| 日付 | 期間の端 / 時間帯（タイムゾーン）の境 |
| ページ送り | 先頭 / 末尾 / 範囲外 |

**とくに統計判定の境界を必ず検査する。**
必要件数の直前・ちょうど・直後で、判定が「まだ判定できません」から正しく切り替わること。
そして **件数が足りないのに「差がある」と言わないこと**。
ここが緩むと、仕組みが嘘をつく。数字を良く見せるために閾値を触らない。

異常系: 外部 API の失敗・応答なし・回数制限・一部だけ成功・やり直し・二重実行の防止。

### 3-7. 契約・境界の機械検査

既にあるもの（維持する）:

- 依存方向（domain が外側を知らない、presentation が domain を直接触らない）
- 生の色コード・生の px をコンポーネントに書けない
- スタブ台帳と実装の一致
- `"use server"` の形
- ツールカタログと仕様の対応

追加するもの:

- 1 概念 1 定義（同じ意味の型が 2 か所に無い）
- 計測イベントの定義と、実際に送っている内容の一致

## 4. 変更しやすいテストにする（テストが変更容易性を殺さないために）

テストは資産にも負債にもなる。負債になるのは次のとき。

| してはいけない | 何が起きるか |
| --- | --- |
| 内部関数名・内部状態をテストする | 名前を変えただけでテストが落ち、リファクタが止まる |
| モックの呼び出し回数を検証する | 実装を 1 行変えるたびにテストを直す |
| 各テストで個別にモックを書く | ポートに項目を 1 つ足すと全テストを書き換える |
| テストデータをテストごとに手で組む | エンティティに項目を 1 つ足すと全テストを書き換える |
| 時刻・乱数・ID を実物のまま使う | たまに落ちるテストになり、やがて無視される |

守ること:

1. **振る舞いをテストする。** 利用者から見える結果だけを見る。
2. **テストデータの生成を一元化する。** ファクトリ（既定値つきビルダー）を 1 か所に置き、
   各テストは「今回関係のある項目だけ」を上書きする。
3. **テストダブルはポート単位で共通化する。** ポート 1 つにつき既定の偽物を 1 つ。
4. **共通のテストユーティリティを用意する。** 描画補助、認証済みの担当者、
   テナント付きの担当者、DB の準備と後始末。
5. **決定的にする。** 時刻・乱数・ID は注入可能にし、固定する。
6. **1 テスト 1 意図。** 落ちたときに名前だけで何が壊れたか分かること。

### 4-1. 変更容易性シナリオでテストがどう壊れるかを見る

「配色を 1 つ足したら既存テストが大量に落ちる」なら、テストが構造に密結合している。
`docs/architecture/changeability-scenarios.md` の各シナリオを実行したとき、
**落ちるテストの数と理由**も記録する。増えるのは良い（検査対象が増えた）。
既存が落ちるのは悪い（書き直しの強制）。

## 5. テストを書く時点（後付けにしない）

**新しく作る機能には、その機能と同じ変更の中でテストを付ける。**
全部作ってから一括でテストを書く進め方をしない。後付けは高くつくうえ、
「動いているのだからテストは形式」という順番になり、テストが実装の写経になる。

バグを直すときは、**先に再現テストを書いて赤くしてから直す**。
テストを直して逃げない（テスト自体が誤っている場合を除く）。

## 7. ビジュアルリグレッションの判断

**決定: たたき台では導入しない。**

理由と代替:

- 配色 5 系統 × 明暗 2 通り = 10 通りを目視で確認するのは現実的に破綻するが、
  スクリーンショット比較は**画面がまだ動くたびに全件差分が出る**段階では維持費が上回る。
- 代替として、目視でしか捕まえられない部分を機械が捕まえられる形に置き換える。
  - 色: **全配色 × 明暗のコントラスト比を計算で検査**（目視より厳密）
  - 崩れ: 生の px を書けない機械検査 + 折り返し位置がトークンの写しであることの検査
  - 抜け: 4 状態が文言として出ることの検査（無言の画面を禁止）
- 画面の形が落ち着いた段階で再評価する。残課題に登録済み。

## 9. カバレッジが答えていないこと（§10〜§12 の前提）

現在の実測は行 90.37% / 分岐 80.03%（2026-08-17、`docs/product/coverage.md`）。
この数字が言っているのは**「そのコードが実行された」ことだけ**である。

言っていないことが 3 つある。

| 答えていない問い | なぜ答えられないか |
| --- | --- |
| その行は**正しい**か | 実行と正しさは別物。誤った実装でも行は通る |
| **仕様**を覆えているか | 目盛りがコードの側にある。書かれていない仕様は分母に入らない |
| テストが**確かめて**いるか | `expect` が 1 つも無くても、実行すれば 100% に届く |

とくに 3 つ目は、**実装をハードコードしてテストを通す**という壊し方を
まったく検出できない。`return 42` と書き、テストが `expect(f()).toBe(42)` なら、
カバレッジは 100%、テストは緑、仕様は 1 ミリも満たされていない。

したがってカバレッジは**下限**であって目標ではない。
80% を「品質の証明」として読まない。読ませないために、この節を置く。

外から確かめる手段は 2 つある。

- **§10 ミューテーション**: 実装を機械が壊し、テストが気づくかを見る
- **§11 プロパティベース**: 例ではなく**成り立つべき性質**を書き、機械に反例を探させる

## 10. ミューテーションテスト（実装を壊してテストを試す）

### 10-1. 何をするか

実装を機械が少しだけ書き換え（変異）、**テストが赤くなるか**を見る。
赤くなれば、そのテストは本当にその判断を見ている。
緑のままなら、その判断は誰も見ていない（＝**生き残った変異**）。

見る変異は最低限これだけ入れる。ここに挙げたものは、
いずれも**実際に業務の判断を反転させる**ものである。

| 変異 | 具体例 | これが生き残ると何が起きるか |
| --- | --- | --- |
| 比較演算子 | `>` → `>=` | 必要件数「ちょうど」で判定が変わる。統計判定が嘘をつく |
| 論理演算子 | `&&` → `\|\|` | 開示と広告表示の両方が必要なゲートが、片方で通る |
| 定数の戻り値 | `return x` → `return 0` / `""` / `true` | 計算がまるごと働いていなくても通る |
| 条件の反転 | `if (a)` → `if (!a)` | 権限が無い人だけが通る、という反転が検出されない |
| 境界の ±1 | `n` → `n + 1` | 上限ちょうどの扱いが誰にも見られていない |
| 例外の握り潰し | `throw` の削除 | 失敗が成功として返る |

### 10-2. どこに必須で当てるか

**`src/domain` と `src/application` は必須。**
この 2 層はポートで外界から切れており、単体で速く回せる。
そして**壊れたときの被害が最も大きい**（業務の決まりごとと手順そのもの）。

`src/infrastructure` はスタブが多く、変異させても意味のある判断が少ない。
`src/presentation` `src/app` は描画が主で、実行が重い。
**この 2 つは当面「対象外」とし、対象外であることを書く**（§13 の現況表）。

覆っている層と覆っていない層の一覧は `docs/product/coverage.md` の隣に置く。
「ミューテーションを入れた」とだけ書くと、
読んだ人は全体に当たっていると受け取る。それは事実ではない。

### 10-3. スコアの扱い

```
ミューテーションスコア = 殺した変異 ÷ （殺した + 生き残った）
```

- 下限は `quality-gates.config.mjs` に置く（数値をこの文書に書き写さない）
- **下限をゼロにしない。** ゼロの門は門ではない
- **低くても、実測値をそのまま出す。** 低いと分かること自体が目的である
- 生き残った変異は「テストを足す」で直す。**下限を下げて直さない**

### 10-4. 実行段

重いので**毎 push では回さない**（§16）。

- 2 段（PR）: **変更されたファイルだけ**を対象にする
- 3 段（夜間・週次）: 全体

2 段には**変更ファイル数の上限**を置く（数値は `quality-gates.config.mjs` の
`MUTATION_MAX_CHANGED_FILES`）。全体の実測が 12〜35 分かかるため、
広い変更をそのまま 2 段に置くと、目標 15 分の門が毎回それを超える。
超え続ける門は、やがて門ごと外される。

**上限を超えた PR では、2 段で測らずに 3 段の全体実測へ回す。**
検査が消えるのではなく、**測る場所が変わるだけ**である（§16 と同じ考え方）。
見送ったことは必ず出力し、黙って緑にしない。

機械の上で比較元が取れない場合は**失敗させる**。
比較元が無いと変更範囲が計算できず、「走らなかったのに緑」になる。
これは検査が無い状態と同じで、最も気づきにくい壊れ方である。

## 11. プロパティベーステスト（例ではなく性質を書く）

### 11-1. 何をするか

「この入力ならこの出力」ではなく、
「**どんな入力でも成り立つべきこと**」を書き、機械に反例を探させる。

例を手で書くとき、人は自分が思いつく入力しか書かない。
**思いつかなかった入力こそが壊れる場所**である。

### 11-2. 必ず書く性質

| # | 性質 | 破れると何が起きるか |
| --- | --- | --- |
| 1 | 順位づけは報酬額を変えても**変わらない** | 報酬で順位が動く。仕組みの前提が崩れる |
| 2 | 採点の順序が安定している（同点の並びが実行ごとに変わらない） | 同じ入力で違う順位が出る |
| 3 | 採点が単調である（評価軸の値を上げて順位が下がらない） | 良くしたのに順位が落ちる |
| 4 | テナント分離（他テナントの ID をどう混ぜても届かない） | 他人のデータが見える |
| 5 | 公開ゲート（開示が無ければ、どう組んでも公開できない） | 法令に反する記事が出る |
| 6 | Variant Spec の描画（どの指定でも、規定の枠から外れない） | 改善ループが画面を壊す |
| 7 | 直列化と復元の往復（`parse(serialize(x))` が `x` と等しい） | 保存して読み直すと値が変わる |
| 8 | 正規化・重複排除の冪等性（2 回かけても 1 回と同じ） | 取り込むたびに件数が増減する |

### 11-3. 反例の扱い

見つかった反例は**最小化してから、通常の回帰テストとして残す**。
性質テストだけに任せると、乱数の種が変わったときに同じ壊れ方を
二度と再現できなくなる。**再現できない検出は、直したことを確かめられない。**

## 12. テストの誠実さを機械で見る

§2 の禁止事項は、人の意思ではなく機械で守る。

| # | 検出するもの | 現況（2026-08-17） |
| --- | --- | --- |
| 1 | アサーションの無いテスト | **実装済み** `tests/architecture/test-honesty.test.ts` |
| 2 | 中身が空のテスト | **実装済み** 同上 |
| 3 | 呼ばれた回数だけを見るテスト | **実装済み** 同上 |
| 4 | 常に真になるアサーション（`expect(true).toBe(true)` ほか） | **実装済み** 同上 |
| 5 | `.skip` / `.only` / コメントアウトされたテスト | **実装済み** 同上（3 件に分けて検出） |
| 6 | 無条件のスナップショット更新 | **実装済み** 同上（`vitest.config.mts` と `package.json` の両方を見る） |
| 7 | カバレッジ除外プラグマの濫用 | **実装済み** 同上（`exclude` は理由必須、`v8 ignore` は 0 件） |

検出器はどれも**見落とす方向に倒してある**。
誤って赤くする検査は、そのうち検査ごと外されるためで、
これは意図した設計であって手抜きではない。たとえば
`toBeDefined()` だけのテストは落とさない（実際に当てたところ 4 件中 3 件が
正しい確認だった）。弱い確認は §10 のミューテーションが生き残った変異として拾う。

### 12-1. 除外には理由を書く

カバレッジ除外（`/* v8 ignore */` の類）と `vitest.config.mts` の `exclude` は、
**書かれた理由を伴わなければ置けない**。
理由の無い除外は「測らないことにした」という決定であり、
決定は記録されなければ次の人には見えない。

現在の除外は 2 つで、どちらも理由がある。

| 除外 | 理由 |
| --- | --- |
| `src/**/*.d.ts` | 実行されるコードではない |
| `src/**/*.css` | v8 が解析できず PARSE_ERROR が並ぶ。**数字は変わらない** |

### 12-2. テストは仕様から書く（実装をなぞらない）

**実装を見てから期待値を書いたテストは、実装が間違っていても緑になる。**
「そう動いているから、そう書いた」という循環で、検査に見えて何も検査していない。
これは §2 の「テスト側の期待値を実装に合わせて書き換えるのは禁止」と同じ話で、
書く順番の問題である。

機械で見られるのは意図ではなく**由来**なので、由来を要求する。
テストファイルは、自分が確かめている要件 ID をヘッダに 1 行書く。

```ts
/** @tier 1 @req REQ-P04, REQ-B03 */
```

`node scripts/traceability.mjs` が両方向を突き合わせ、`docs/product/test-traceability.md`
（テスト → 要件）を生成する。要件 → テストの正本は `docs/product/traceability.md` のまま。

落とす条件は 3 つ。

| 条件 | なぜ落とすか |
| --- | --- |
| 要件表に無い ID が印に書かれている | 打ち間違いか、要件表への追記漏れ |
| 要件表に、**実在しないテスト**が書かれている | 表の上だけで PASS に見える |
| **由来不明のテストが増えた** | 実装をなぞって書いたテストが増えた疑い |

由来不明の上限は `quality-gates.config.mjs` の `TRACEABILITY_MAX_UNLINKED` が正本で、
**2026-08-17 の実測 37 件 / 115 件**を起点に置いてある（起点は 39 件。
§14 の必須種別を宣言するために 7 ファイルへ印を足し、実測が下がったので追随させた）。
起点に置く（0 にしない）のは、既存分へ機械的に印を付ける作業が
「印を付けるための印」になりやすいためで、由来を確かめずに書いた `@req` は
この検査を無意味にする。**上げて緑にすることを禁じる。** 減らすのは 1 件ずつ行う。

上限を実測より 1 小さくすると終了コード 1、実測どおりなら 0 になることを 2026-08-17 に確認した。

**2026-08-21 追記（`ah-8jh`）**: 起点の 37 件から残っていた 28 件を 1 件ずつ中身を読み、
**26 件へ `@req` を書いて上限を 2 まで下げた**。残した 2 件
（`tests/architecture/guard-inline-python-hole.test.ts` /
`tests/architecture/spec-freshness.test.ts`）は**当たる要件行が要件表に無い**もので、
近い要件へ寄せると「印を付けるための印」になるため結んでいない。**要件側の欠落**として扱う。
壊して測った 3 通りは 3/3 赤（①上限を 1 下げる ②印を 1 つ外す → そのファイルが名指しで出る
③要件表に無い ID を書く → 別の条件で落ちる）。

## 14. 要件ごとの必須種別

要件 1 つずつに、**満たすべきテスト種別**を決める。
決めない場合、テストは「書きやすいところから書かれる」ため、
難しい種別（権限のできてはいけない側、禁止された遷移）が永久に残る。

| 要件の性質 | 必須の種別 |
| --- | --- |
| 入力欄がある | 等価分割 + 境界値（**全欄**） |
| 状態が遷移する | 状態遷移（許可 + **禁止**） |
| 権限で分かれる | 権限マトリクス（**できてはいけない側**） |
| テナントを持つ | テナント越境 |
| 外部と通信する | 障害注入 + 冪等性 |
| 画面がある | 4 状態 + axe + キーボード |
| 業務計算を含む | ミューテーション + 境界値 |
| AI が読む文字を含む | プロンプトインジェクション |

除外するときは**理由を書く**。理由の無い除外は認めない。

**新しい要件に必須種別が欠けていたら CI が落ちる。**
これが無ければ、この表は読まれない。

### 14-1. 機械が見る形（実装）

| もの | 場所 |
| --- | --- |
| 性質 → 必須種別 | `quality-gates.config.mjs` `REQUIRED_TEST_TYPES`（上の表の機械可読版） |
| 種別の名前（語彙） | 同 `TEST_TYPES`。ここに無い名前を印に書くと落ちる |
| 要件ごとの性質と除外理由 | `docs/product/required-test-types.md`（宣言表） |
| 充足の証拠 | テストの `@types` 印。`@req` と対で書く |
| 判定 | `node scripts/required-test-types.mjs` → `docs/product/required-test-types-report.md` |

```ts
/** @tier 1 @req REQ-P01, REQ-API02 @types property, tenant-isolation, permission-matrix */
```

**充足を宣言表に書かない。** 書くと自己申告になる。
宣言表が持つのは「何が必要か」と「なぜ書けないか」だけで、
「書いたかどうか」はテスト側の印から機械が数える。

例外は `mutation` で、これは印ではなく実測（`src/domain` と `src/application` が対象）
から導く。印で自己申告させると、印を書くだけで満たしたことになるためである。

#### 落とす条件

| 条件 | なぜ落とすか |
| --- | --- |
| 必須種別が欠けていて、除外理由も無い | §14 の表が読まれていない |
| 除外に理由が無い / 空 | 「理由を書く」を形だけ通している |
| 除外した種別に、実は印が付いている | 宣言表と実態がずれている |
| 語彙に無い種別名 | 表記ゆれで別種別に見える |
| `@types` だけ書いて `@req` が無い | どの要件の充足か決まらない |
| 未宣言の要件が増えた | 新しい要件が検査の外で増えている |
| **理由つき除外が増えた** | 除外は逃げ道になり得る（§14-2） |

#### 実測（2026-08-17）

| | 件数 |
| --- | --- |
| 要件表の要件 | 240 |
| 性質を宣言済 | **12** |
| 未宣言（`TEST_TYPES_MAX_UNDECLARED`） | **228** |
| 理由つき除外（`TEST_TYPES_MAX_EXCLUSIONS`） | **13** |

**宣言済は 12 件しかない。** 240 件すべてに宣言を書き切るまで検査を入れない、
という順にすると検査は永久に入らないので、未宣言の実測を上限に置き、
**新しい要件には最初から宣言を要求する**形にした。
上限を上げて緑にすることを禁じる。

門が落ちることは 3 通りで確認した（2026-08-17）。
必須種別の印を 1 つ外す → `REQ-API02: tenant-isolation` で終了コード 1。
未宣言の上限を 227 にする → 終了コード 1。除外の上限を 12 にする → 終了コード 1。

### 14-2. 除外という逃げ道

理由を書けば通るなら、**全部を除外にすれば緑になる**。
だから理由の質（人が読む）と件数（機械が数える）の両方で縛る。

除外理由に使ってよいのは 2 つだけである。

1. **対象が存在しない**（端の無い入力に境界値、スタブしかない外部に障害注入）
2. **未実施であることと、いつ書くかが残課題として起票されている**

「重要度が低い」「時間が無い」は理由にしない。
それはこの表が防ごうとしている「書きやすいところから書く」そのものである。

## 15. 変更容易性シナリオごとに「落ちるべきテスト」

`docs/architecture/changeability-scenarios.md` の各シナリオについて、
変更したときに**落ちるべきテスト**と**落ちてはいけないテスト**を決める。

- 落ちるべきものが落ちない → その変更を誰も見張っていない
- 落ちてはいけないものが落ちる → テストが構造に密結合している

機能を足すときのチェックリストもここに置く（§14 の必須種別を機械が確認する）。

### 15-1. シナリオ別（①〜⑲）

「落ちてはいけない」は、その変更で**振る舞いが変わらないはずの範囲**である。
ここが落ちたら、テストが構造（クラス名・呼び出し順・内部の形）に
くっついている合図で、テスト側を直す。

| シナリオ | 落ちるべきテスト | 落ちてはいけないテスト |
| --- | --- | --- |
| ① ASP を 1 つ追加 | ASP 一覧の網羅、正規化 URL の性質テスト | ランキング、公開ゲート、画面 |
| ② LLM 提供元の差し替え | 提供元の登録表、切替の既定値 | 生成結果を使う側（差し替えで文面は変わらない） |
| ③ ブログを 1 つ追加 | サイト一覧、テナント分離 | 他サイトの画面・記事 |
| ④ SNS チャネル追加 | 配信先の境界値・禁止された状態遷移 | 記事の生成・公開ゲート |
| ⑤ 評価軸を 1 つ追加 | ランキングの性質テスト（順序の安定） | 既存記事の描画（軸が増えても壊れない） |
| ⑥ 保存先を D1 へ | リポジトリの契約テスト、マイグレーション往復 | ドメイン・ユースケース（**1 件も落ちてはいけない**） |
| ⑦ 認証の差し替え | 権限マトリクス、テナント越境 | 画面、ドメイン |
| ⑧ ブランドの色・追加 | 配色の対比（`theme-contrast`） | 画面の役割・文言 |
| ⑨ 比較表の列追加 | 表の描画、空欄の意味 | ランキング、公開ゲート |
| ⑩ 広告表記の変更 | 公開ゲート（表記が無いと公開できない） | 記事本文の生成 |
| ⑪ ブログ追加（実測） | ③ と同じ | ③ と同じ |
| ⑫ 配色を 1 つ増やす | 配色の対比、見た目の回帰 | 画面の状態（空・劣化） |
| ⑬ 計測を 1 つ増やす | 計測の記録先、種別の語彙 | 計測される側の振る舞い |
| ⑭ 改善の軸を 1 つ増やす | 軸の登録表、改善ループの入口 | 既存の軸の判定 |
| ⑮ ループの種類を増やす | ループの登録表、状態遷移 | 既存ループ |
| ⑯ 自動検査を 1 つ増やす | `quality-gates.config.mjs` の検査一覧 | アプリのテスト全部 |
| ⑰ 改善要望の種類を増やす | 種別の語彙、受付の入力検査 | 既存種別の受付 |
| ⑱ 指示文の文面を直す | プロンプトインジェクション | 生成の骨格 |
| ⑲ 収集する技術情報を増やす | 取り込みの等価分割・境界値 | 既存の取り込み |

**⑥ が最も重要である。** 保存先を替えてドメインのテストが落ちるなら、
層が分かれていない。層分けが効いているかは、この 1 行で分かる。

未実測は ⑮ ⑯ ⑱ ⑲ の 4 つで、上の表は**設計上の想定**である。
実測したものと想定を同じ表に並べているので、この段落を消さない。

### 15-2. 機能を足すときのチェックリスト

1. 要件表（`docs/product/requirements.md`）に REQ を足す
2. `docs/product/required-test-types.md` に**性質**を書く（`has-input` など）
3. §14 の必須種別のテストを書き、`@req` と `@types` を付ける
4. 書けないものは**除外理由**を書く（§14-2 の 2 種類のみ）
5. §15-1 に行を足す（落ちるべき／落ちてはいけない）
6. `pnpm run verify` が緑になることを確認する

**2 と 3 を飛ばすと 6 で落ちる。** これが §14 の機械化の目的である。

一点、実測で分かった副作用を書いておく。ある要件に `@req` の印を新しく付けると、
**その要件を表（`docs/product/traceability.md`）経由で参照していたテストが
「由来不明」に戻る**（印が付いた時点で、その要件の対応先は印の側になるため）。
2026-08-17 に `REQ-R11` へ印を付けたところ、表で結びついていた 2 ファイルが外れ、
由来不明が 37 → 39 に増えて検査が落ちた。上限は上げず、その 2 ファイルにも
印を付けて 37 へ戻した。**印を付けるときは、同じ要件を表で参照しているテストにも
印を付ける。**
上限（`TEST_TYPES_MAX_UNDECLARED`）を上げて緑にすることは禁止する。

## 16. 実行段（どこで走らせるか）

テストを**消す・skip する・閾値を下げる**代わりに、**実行する場所を変える**。
段の定義と実行場所は `docs/spec/11-CI-CD・品質ゲート仕様.md` §8 が正本で、
数値と設定は `quality-gates.config.mjs` にある。

- 各テストファイルは**段の印だけ**を持つ（実行場所は書かない）
- 段 → 実行場所（`ci` / `local` / `manual`）の対応は設定 1 か所で切り替える
- **段の印が無いテストファイルがあれば CI が落ちる**

段の印を持たせる理由は、将来このリポジトリを非公開にしたときに、
**テストを消すのではなく移せるようにする**ためである。
消す判断は戻せないが、移す判断は戻せる。
