# 運用手順: 点検履歴と定期再点検

- 対象 feature: `feat-seo-aeo-gap-closure`
- 所有 phase: `SYS-SEO-AEO-GAP-CLOSURE-P12`
- 状態: 確定 (P12 成果物)
- 読んだもの: [final-review.md](./final-review.md) / [evidence.md](./evidence.md) / [retention-policy.md](./retention-policy.md) / [migration-compatibility.md](./migration-compatibility.md)
- 作成日: 2026-09-04

## 0. この仕組みが解いている問題

記事の「いつの情報か」は、日が経つほど古くなる。
公開したときにしか点検しないと、**公開日は通っていた記事が半年後に落ちても、
誰にも見えない。**

そこで 2 つを足した。

1. 点検の結果を**履歴として残す**（公開のたびに 1 行）
2. 最終点検から 7 日以上経った記事を**1 日 1 回、自動で点検し直す**

再点検は人が起動しない。だから**落ちたことに気づく経路が管理画面の一覧しかない。**
その一覧を誰がいつ見るのかが決まっていないと、仕組みだけあって使われない状態になる。
本文書はそこを決める。

## 1. 誰が、いつ、どこを見るか

| | 内容 |
|---|---|
| **誰が** | サイトの運営者（`owner` 権限を持つ人） |
| **いつ** | 週 1 回。記事を公開した直後は、その日にもう一度 |
| **どこを** | 管理画面 → 公開記事 → **「定期再点検」**と**「AI 検索の点検」**の 2 節 |
| **URL** | `/admin/content/published` |

### 週 1 回でよい理由

再点検は 1 日 1 回、最終点検から **7 日**以上経った記事を拾う。
つまり記事 1 本が落ちる可能性のある間隔は最短で 7 日。
毎日見ても、たいていの日は前日と同じ表を見ることになる。

### 公開直後にもう一度見る理由

公開の瞬間にも点検が走り、その場で履歴に 1 行入る。
**公開したばかりの記事が落ちていたら、その日のうちに直せる。**
7 日待つ必要はない。

## 2. 一覧の読み方

節には 4 列の表が出る。

| 列 | 中身 |
|---|---|
| 記事 | 記事のタイトルと、どのサイトのものか |
| **直すところ** | 落ちた項目ごとの**直し方**。項目名（内部の識別子）ではない |
| 点検日 | いつの点検の結果か |
| 操作 | その記事の編集画面へ |

「直すところ」に出るのは、たとえばこういう文である。

> 一文の結論（summary）を書く。AI は冒頭から答えを拾う。結論を最後に置くと引用されない。

**読んだだけで次にやることが分かる形にしてある。**
落ちた項目が複数あれば、複数行が並ぶ。通った項目は出ない（直す手がかりにならない）。

### 記事の点検結果は 4 つに分ける

| 見えるもの | 意味 | やること |
|---|---|---|
| 「未点検」 | 公開中だが履歴の無い記事がある | 次回の定期点検後に確認する |
| 「全合格」 | 公開中の点検済み記事はすべて通っている | 何もしない |
| 「要修正」と記事が並ぶ | その記事の最新結果が落ちている | 「直すところ」に従って直し、次回の点検後に確認する |
| 「取得不能」 | 点検履歴自体を読み取れない | 時間をおいて画面を開き直す |

記事の履歴が取れたかと、夜間の定期再点検が実際に走ったかは別の事実である。
そのため管理画面は、上の 4 状態とは別に定期再点検の最新状態を常に出す。

| 定期再点検の表示 | 意味 |
|---|---|
| 未実行 | 0045 適用後にまだ cron の最終結果が無い |
| 成功 | 対象取得と、この回に選ばれた全対象の保存が終わった。**対象 0 件の成功もここに含む** |
| 一部失敗 | 対象は取得できたが、一部の記事を保存できなかった |
| 失敗 | 対象の取得など、再点検全体が完了しなかった |

いずれも開始時刻と最終完了時刻を作業場所ごとに読む。
隣の作業場所の状態や件数は混ぜない。

## 3. 異常の見分け方

**この仕組みは、落ちても読者の画面に何も起きない。**
だから「壊れている」と「順調」は、放っておくと同じに見える。
見分けるための材料を 3 つ置いてある。

### 3-1. 定期再点検が「未実行」または「失敗」になる

最終完了時刻を見て、想定する毎日の起動が更新されているか確認する。
この回の対象が 0 件でも、正常に起動した回は「成功」と時刻が残るので、
「修正対象が無い」と「起動していない」を区別できる。

**運用開始直後は別**。0044 を当てた直後は既存の公開記事がすべて履歴 0 件で、
一覧は 0 件から始まる。1 日 50 件ずつ埋まっていくので、
記事が 50 本以下なら翌日に、500 本あれば 10 日かけて一覧が埋まる
（[migration-compatibility.md](./migration-compatibility.md) 2.4）。

この期間、記事の節は「未点検」、定期再点検の節は直近回の成否をそれぞれ示す。
まだ点検していない記事を「全部問題ない」と扱わない。

### 3-2. Workers のログを見る

Cloudflare のダッシュボード（Workers → Logs）に、1 日 1 回この 3 種のどれかが出る。

| ログ | 意味 |
|---|---|
| `[ai-search-reaudit] 記事を再点検しました { scanned, recorded, failed }` | **正常**。`scanned` が拾った件数、`recorded` が履歴に書けた件数 |
| `[ai-search-reaudit] 保存先がつながっていないので、再点検を行いませんでした` | D1 の結び付けが外れている。設定の問題 |
| `[ai-search-reaudit] 再点検に失敗しました` | 実行中に落ちた。次の日が拾う |

**どれも出ていない**なら、cron 自体が起動していない（4 節）。

### 3-3. `scanned` と `recorded` がずれる

`scanned` は拾った件数、`recorded` は履歴に書けた件数。
**ふつうは一致する。**ずれるなら記事ごとの書き込みが個別に失敗している。
ログの `failed` に件数が出る。

## 4. 落ちたときの対応

### ケース A: ログが 1 つも出ていない

cron が起動していない。

1. `wrangler.jsonc` の `crons` を確認する。`["0 17 * * *"]` が
   **トップレベル・dev・production の 3 か所すべて**にあること。
   1 か所だけ直しても、その環境でしか効かない。
2. Cloudflare のダッシュボードで Cron Triggers が登録されているか確認する。
   デプロイが通っていても cron の登録だけ落ちていることがある。

**`0 17 * * *` は UTC の 17:00 = 日本時間の翌 02:00 である。**
「夕方に走る」と読まないこと。夜のうちに走って、朝には結果が出ている。

### ケース B: 「保存先がつながっていない」が出る

D1 の binding（`DB`）が外れている。`wrangler.jsonc` の `d1_databases` を確認する。

**これは再点検だけの問題ではない。**同じ binding を使う機能が他にもあるので、
公開や記事の読み込みも同時に壊れているはず。まずそちらを確認する。

### ケース C: 「再点検に失敗しました」が出る

エラーの中身による。ただし**その日は何もしなくてよい。**
再点検は「最終点検から 7 日以上経った記事」を拾うので、
失敗した日の対象は次の日にそのまま残っている。次の回が拾う。

**2 日以上続いたら**調べる。1 日だけなら一時的な問題として扱ってよい。

### ケース D: 落ちている記事が多すぎて手が回らない

一覧は最新の点検で落ちている記事を**点検日の新しい順**に並べる。
上から順に直し、次の定期点検後に判定を確認する。
編集しただけで一覧から即時に消えるとは保証しない。

**上限を上げないこと。**一度に見られる量を増やしても、直せる量は増えない。

## 5. 記事が増えたときに来る限界

現状の設計は **1 日 1 回・1 回 50 件**である。
「7 日以内に全記事を再点検する」を満たせるのは **350 本（= 50 × 7）まで**。

公開記事がこれを超えたら、**1 回の件数を増やすのではなく cron の頻度を上げる。**

理由は、1 回の処理量を増やすと Workers の実行時間上限に当たるためである。
上限に当たると**途中で切れた回が黙って部分適用になる**——
何件処理できたのか誰にも分からない状態が生まれる。
頻度を上げれば、1 回あたりは軽いまま総量だけが増える。

たとえば 1 日 2 回（`["0 17 * * *", "0 5 * * *"]`）にすれば 700 本まで届く。

## 6. 履歴そのものの扱い

- 記事 1 本につき**最新 30 件**まで。31 件目が入ると最古の 1 件が落ちる。
- 消す処理は追記と**同じトランザクション**に入っている。
  「追記されたが古い分が残っている」状態は観測できない。
- 記事を取り下げても、**その記事の履歴は消えない**。
  取り下げた理由を後から辿るために残してある。

したがって履歴の総量は「記事数 × 30 行 × 約 1.5KB」で頭打ちになる。
100 本で約 4.5MB、1,000 本で約 45MB。
**運用年数が延びても総量は増えない**（増え方が記事数にだけ比例する）。

手で消す運用は要らない。

## 7. この手順で消せない不安

| | 状況 | 現状 |
|---|---|---|
| 実 D1 での 1 回の所要時間 | 50 件の処理に実際どれだけかかるか | 未測定。リリース後に Workers のログで初めて分かる |
| 記事 350 本超 | 7 日以内の全件再点検が破綻する | 現規模から遠い。超える前に 5 節の対処を入れる |

いずれも [final-review.md](./final-review.md) の R1・R3 として follow-up に置いてある。
