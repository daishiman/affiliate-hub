## 1. 全体アーキテクチャ

```text
[収集層]
  ClickEvent(リダイレクトサービス)
  BehaviorEvent(ブログ計測タグ)
  Channel Insights(SNS API)
  Conversion(ASP API / CSV)
      ↓
[正規化層]
  bot除外・重複排除・セッション化・ディメンション付与
      ↓
[集計層]
  MetricRollup(日次 × ディメンション組み合わせ)
      ↓
[分析層]
  KPIディクショナリ / Attribution / Experiment / Insight Engine
      ↓
[活用層]
  Analyticsダッシュボード / InsightReport / 生成時の推奨(Brief への提案)
```

設計原則:

* **イベントは不変(append-only)**。修正は打ち消しイベントで行う
* **集計は再計算可能**。生イベントから任意時点のロールアップを再構築できる
* **転送と計測の障害分離**。計測系障害単独を理由に、既知の有効なresolver entryの転送を止めない。適用範囲と許容値は§1.2のSLO・劣化契約を正とする
* **Editorial / Commercial 分離**(v1.0 19.4章)。Insight Engine は配信戦略・表現の学習にのみ収益データを使い、商品評価・ランキングへは出力しない

### 1.1 TrackingLinkと公開前不変条件

`AffiliateLink` はASPリンク原本、`TrackingLink` は掲載位置ごとの計測URLである。

```yaml
tracking_link:
  id: string                         # 推測困難なID。/go/{id}に使用
  workspace_id: string
  affiliate_link_id: string
  publication_id: string | null      # draftのみnull可
  content_variant_id: string | null  # publicationから導出できない場合の明示値
  placement: hero_cta | inline | comparison_table | product_card | footer_cta | profile | story | other
  position_index: number | null
  channel: string
  redirect_mode: redirect | direct_only
  sub_id_value: string | null
  lifecycle_status: draft | activating | active | direct_only | disabled | expired
  resolver_version: integer | null
  activated_at: datetime | null
  expires_at: datetime | null
  created_at: datetime
  updated_at: datetime
```

公開時は次をトランザクション境界で検査する。

* `workspace_id` は必須。`AffiliateLink`、`Publication`、`ContentVariant` は同一Workspaceに属する
* `publication_id` は下書きだけnull可とし、`active` / `direct_only` への遷移とPublicationの公開は非nullかつ参照先有効を条件とする
* `redirect_mode=redirect` はASP・プログラム・channelの全てが許可し、resolver storeへの同期ackを得たときだけ `active` にできる
* `redirect_mode=direct_only` は公開HTMLに `AffiliateLink.original_url` を改変せず出力し、自前クリック計測不可をUIに表示する
* 転送先原本は不変とする。差し替え時は既存 `TrackingLink` を上書きせず新規発行する

### 1.2 Redirect Resolver、Queue、SLO、劣化モード

`GET /go/{tracking_link_id}` はリクエスト時にAnalytics D1へ同期問い合わせしない。有効なTrackingLinkを、読み取り最適化したresolver storeへ事前投影する。

```yaml
redirect_resolution:
  tracking_link_id: string
  workspace_id: string
  original_url: string               # httpsの登録済みASP原本のみ
  state: active | disabled | expired
  resolver_version: integer
  valid_from: datetime
  expires_at: datetime | null
  checksum: string
  consent_state: not_required
  schema_version: string
```

リクエストフローは「IDをresolver storeで解決 → URL scheme・state・期限を検査 → 302応答を確定 → ClickEventをCloudflare Queueへ非同期送信」とする。Queue consumerがtransport冪等化後にAnalytics D1へappendする。

| 状態 | 利用者向け応答 | 計測側の動作 |
| --- | --- | --- |
| resolver hit / Queue正常 | 302転送 | Queueへ送信 |
| resolver hit / Queue送信失敗 | **302転送を維持** | `measurement_delivery_failed` をログ・警報。欠損数を別メトリクで表示 |
| resolver origin障害 / edge cache hit | 302転送 | stale上限5分の有効entryを使用し、劣化中を記録 |
| resolver miss / 破損 | 404（未知）または410（停止・期限切れ） | 転送先を推測しない。オープンリダイレクトにしない |
| Analytics D1障害 | 302転送を維持 | Queueがバッファし、回復後に再送／DLQを再処理 |

初期SLO（28日間rolling、bot・未知IDを除外）は、有効resolver entryへの302成功率≥99.95%、edge処理時間p95≤150ms、ClickEventのリクエストからAnalytics D1永続化までのp99≤5分、日次欠損推定率<0.1%とする。初回28日の実測後はSLO versionを上げて変更し、過去判定を書き換えない。

302成功率は `valid resolver entryへの302応答数 / valid resolver entryへの全要求数`、日次欠損推定率は `max(0, 302応答数 - D1永続化済みunique event_id数) / 302応答数` とする。edgeの独立counterとD1のunique event数をUTC日単位で24時間の遅着許容後に突合し、分母0はnullとする。

### 1.3 2つのD1とoutbox/projection

| 物理store | 正本データ | 禁止 |
| --- | --- | --- |
| Editorial D1 | Workspace、商品評価、Claim/Evidence、ContentVariant、Publication | 報酬金額、Conversion原本、収益ランキングを格納しない |
| Analytics D1（Commercial） | AffiliateLink、TrackingLink、イベント、Conversion、KPI、Rollup、Attribution、Insight | Ranking Serviceから直接参照させない |

D1間に分散transactionを作らない。正本の更新transactionで同じD1内の `outbox_event` を追記し、dispatcherがQueueへ配送、consumerが `event_id` と `source_version` で冪等にprojectionをupsertする。Publication・ContentVariantの分析dimensionはEditorial→Analytics、配信に必要な非収益性のInsight要約だけをAnalytics→Editorialへ投影できる。報酬、EPC、Conversion明細はEditorialへ投影しない。

```yaml
outbox_event:
  event_id: string
  workspace_id: string
  aggregate_type: string
  aggregate_id: string
  source_version: integer
  event_type: string
  schema_version: string
  consent_state: not_required
  occurred_at: datetime
  payload: object
  dispatched_at: datetime | null
```

Queueは少なくとも1回配送とし、consumerの冪等性を必須とする。連続失敗はDLQへ移し、Workspace、aggregate、versionを指定して再処理できること。projection lagのSLOはp99≤5分、DLQの未解決最長24時間とする。

### 1.4 時刻とbusiness date

* すべての `datetime` はUTCのRFC 3339 instantで保存する
* WorkspaceはIANA形式の `business_timezone`（例: `Asia/Tokyo`）を必須とする
* 日次集計は `occurred_at` を集計時に有効な `business_timezone` で `business_date` へ変換し、そのtimezoneとversionをRollupに固定する
* timezone変更は発効日を持つ新versionとし、過去Rollupを暗黙に再区分しない。再集計は明示ジョブと監査ログを必須とする
* アトリビューション時間窓はUTC instant間のdurationで評価し、カレンダー日で計算しない

## 2. イベントモデル

### 2.0 共通envelopeと冪等性

すべての生イベント、スナップショット、集計、投影レコードは `workspace_id`、`consent_state`、`schema_version` を必須とする。外部接続・システム処理で訪問者同意の対象外となるデータも省略せず `consent_state=not_required` を記録する。

```yaml
event_envelope:
  event_id: string                   # producerが発行するULID/UUID。transport冪等キー
  workspace_id: string
  occurred_at: datetime              # UTC、発生時刻
  received_at: datetime              # UTC、受信時刻
  consent_state: granted | denied | unknown | not_required
  schema_version: string
```

`event_id` は送信再試行・Queue再配送で同一payloadを二重挿入しないための**transport冪等キー**である。別の `event_id` を持つ人間の反復操作は生イベントとして両方保存し、正規化後の `behavioral_dedup_key` でKPI算入可否を決める。両者を同じ「dedup」として削除しない。

### 2.1 ClickEvent(アフィリエイトクリック)

```yaml
click_event:

  session_id: string | null        # 同意済みのみ
  referrer_type: article | sns_post | email | direct | unknown

```

### 2.4 Conversion（成果原本と最新projection）

ASP成果のidentityと状態履歴を分ける。`source_conversion_id` がある場合は `(workspace_id, affiliate_account_id, source_conversion_id)` を一意とする。ない場合はConnector versionごとに定義した安定フィールドの正規化値から `source_identity_hash` を作り、使用フィールドと欠損衝突を監査できるようにする。CSV行全体のhashは内容変更で値が変わるため、成果identityに使わない。

```yaml
conversion:
  id: string
  workspace_id: string
  affiliate_account_id: string
  program_id: string
  source_conversion_id: string | null
  source_identity_hash: string
  affiliate_link_id: string | null
  tracking_link_id: string | null
  occurred_at: datetime
  approval_status: pending | approved | rejected | cancelled
  payment_status: not_eligible | unpaid | scheduled | paid | reversed
  approval_status_updated_at: datetime
  payment_status_updated_at: datetime
  approved_at: datetime | null
  paid_at: datetime | null
  order_amount: decimal | null
  commission_amount_pending: decimal | null
  commission_amount_approved: decimal | null
  commission_amount_paid: decimal | null
  currency: string
  tax_treatment: inclusive | exclusive | unknown
  click_ref: string | null
  import_source: api | csv | manual
  source_record_hash: string         # 同一version内の内容変化検出用
  source_updated_at: datetime | null
  projection_version: integer
  consent_state: not_required
  schema_version: string
  created_at: datetime
  updated_at: datetime
```

`approval_status` と `payment_status` は別軸とし、`paid` を承認状態に入れない。初期状態は `pending + not_eligible`、承認時は `approved + unpaid`、支払確定は `approved + paid`とする。`scheduled/paid` は `approval_status=approved` のときだけ許可する。支払後の取消は `cancelled + reversed` とし、元レコードを削除しない。

```yaml
conversion_status_event:
  event_id: string
  workspace_id: string
  conversion_id: string
  occurred_at: datetime
  received_at: datetime
  approval_status: pending | approved | rejected | cancelled
  payment_status: not_eligible | unpaid | scheduled | paid | reversed
  source_record_hash: string
  import_run_id: string
  source_updated_at: datetime | null
  consent_state: not_required
  schema_version: string
```

status eventをappend-only保存し、`(conversion_id, projection_version)` の最新projectionを冪等に更新する。遅着・逆順イベントは `source_updated_at`、Connectorの状態優先順位、受信順の順で決定し、自動解決できない競合をquarantineへ送る。

### 2.5 正規化、行動重複、同意ルール

* bot判定:UA辞書 + 行動パターン(滞在0秒で全リンク踏破等)+ 既知データセンターIP。`is_bot=true` は既定でKPIから除外(切替可能)
* transport冪等:`(workspace_id, event_id)` のunique constraintで再送を同一イベントとしてackする。payloadが異なる同一IDは受理せずquarantineへ送る
* 行動重複: 同意済みクリックは `workspace + session + tracking_link + 60秒窓`、BehaviorEventは `workspace + session + event_type + target + イベント別窓`を正規化した `behavioral_dedup_key` で判定する。生イベントは残し、`is_behavioral_duplicate=true` を既定KPIから除外する
* セッション: `consent_state=granted` のみ、ファーストパーティ匿名IDを30分無操作で分割する
* UTM: `source / medium / campaign / content` だけを許可し、email、電話、氏名等の個人情報パターンを受信前に除去する

同意なしの契約:

| フィールド | `denied` / `unknown` 時 |
| --- | --- |
| `session_id` | null |
| `ip_hash` / `user_agent_hash` | null（生IPは永続化前に破棄） |
| `behavioral_dedup_key` | null（個人横断の指紋を作らない） |
| `utm` | 許可keyと個人情報除去後の値だけ。安全に正規化できなければnull |
| `device` / `os_family` / `country` | リクエスト中で計算した粗い分類のみ。生値は保存せず、不要ならnull |

同意なしのイベントは単発カウントとしてのみ集計でき、セッションファネル、マルチタッチ、安定割当が必要な実験に使用しない。

## 3. ディメンションモデル(何で切って分析できるか)

すべての集計・分析は次のディメンションの組み合わせで行えることを要件とする。これが「どういう情報がクリック率が高いか」を答えるための軸である。

| 分類 | ディメンション |
| --- | --- |
| コンテンツ | content_package / content_variant / angle(切り口) / format / 長さ帯 / funnel_stage / CTAタイプ / タイトルパターン |
| ペルソナ | author_persona / audience_persona / knowledge_level |
| 商品 | product / カテゴリー / 価格帯 / ブランド / comparison_set |
| 媒体 | channel / channel_account / site / 記事テンプレート / ブログパターン |
| 配置 | placement(冒頭CTA・本文・比較表・商品カード…) / position_index / スクロール深度帯 |
| 商流 | ASP / advertiser / program / merchant_offer |
| 時間 | 投稿曜日 / 投稿時間帯 / 公開からの経過日数 / 季節 |
| 読者環境 | device / 流入元(検索・SNS・メール・直接) |
| 生成条件 | generation_prompt_version / model_id / experiment variant |

`ContentVariant` が angle・persona・prompt_version を保持している(v1.0 21.2章)ため、クリック・成果を variant まで結合できれば全ディメンションが導出できる。正規の連鎖は **Event → TrackingLink → Publication → ContentVariant → ContentPackage** とする。公開時は `TrackingLink.publication_id`を必須とし、projection consumerがWorkspace一致と参照完全性を検証する。連携遅延中のイベントは破棄せず `dimension_pending` とし、projection同期後に再処理する。直接リンク等で追跡不能な値は `unknown`と明示し、他Workspaceや他Publicationへ推定結合しない。

## 4. KPIディクショナリ

指標は名前・定義式・分母分子・除外条件を辞書として一元管理し、画面・API・レポートで同一定義versionを使う。

```yaml
kpi_definition:
  workspace_id: string              # system既定は専用system workspaceに属する
  metric_key: string
  version: string                   # immutable semver
  display_name: string
  formula: string                   # 機械評価可能なDSL/ASTの参照
  numerator: string | null
  denominator: string | null
  filters: []
  minimum_denominator: number | null
  aggregation: count | distinct_count | sum | ratio | median | percentile
  effective_from: datetime
  retired_at: datetime | null
  consent_state: not_required
  schema_version: string
```

公開済みversionは上書き不可とし、定義変更は新versionを発行する。Rollup、Insight、Experiment、成功指標は使用した `kpi_definition_version`を必ず保持する。異なるversionの値を一つの時系列として接続する場合は、新versionで全期間を再集計したときに限る。

| KPI | 定義 | 備考 |
| --- | --- | --- |
| PV | page_view 数 | bot除外後 |
| リンク表示数 | link_impression 数 | 画面内に入った回数 |
| リンクCTR | クリック ÷ リンク表示数 | **配置の良し悪しはこれで測る** |
| ページCTR | distinct(クリックセッション) ÷ distinct(ページ閲覧セッション) | consent=grantedの同一記事セッションのみ |
| SNS CTR | link_clicks ÷ impressions | 媒体API提供時のみ |
| 発生CVR | unique conversion identity数 ÷ アトリビューション対象クリック数 | approval=pendingを含む。突合methodを分離表示 |
| 承認CVR | approval=approvedのunique conversion identity数 ÷ 対象クリック数 | 支払済みとは別 |
| 承認率 | approved ÷ (approved + rejected) | 承認判定済みだけが分母。cancelledは別表示 |
| 承認EPC | `commission_amount_approved` の合計 ÷ 対象クリック数 | 通貨ごとに計算。為替換算は別KPI |
| 支払EPC | `commission_amount_paid` の合計 ÷ 対象クリック数 | payment=paidのみ |
| 承認RPM | 承認報酬 ÷ PV × 1000 | 演算順は `(revenue / pv) * 1000` |
| 読了率 | scroll_100 ÷ page_view | |
| 保存率 | saves ÷ reach | Instagram等 |
| 成果リードタイム | click → conversion の中央値 | 再投稿タイミング設計に使用 |

規則:

* `minimum_denominator` 未満のセルは「データ不足」と表示し、率だけを見せない。初期値はクリック分母30、impression分母1000だが、KPIごとの辞書versionに固定する
* 発生、承認、支払を常に区別し、「確定報酬」の曖昧な表示名を使わない
* 分母0の率は0ではなくnullとし、UIは「算出不可」と表示する
* 各値にperiod、business timezone、consent segment、bot除外、attribution method、KPI versionを併記する

## 5. 集計層(MetricRollup)

```yaml
metric_rollup:
  id: string
  workspace_id: string
  business_date: date
  business_timezone: string
  timezone_version: integer
  grain: day
  consent_state: granted | denied | unknown | mixed | not_required
  schema_version: string
  kpi_definition_versions: {}
  dimension_set_version: string
  source_watermark: datetime
  projection_version: integer
  dimensions:                       # §3 の組み合わせ(正規化キー)
    channel: string | null
    angle: string | null
    placement: string | null
    audience_persona_id: string | null
    # ... 任意の組み合わせ
  measures:
    impressions: number
    link_impressions: number
    clicks: number
    conversions_pending: number
    conversions_approved: number
    conversions_rejected: number
    payments_paid: number
    revenue_pending: decimal
    revenue_approved: decimal
    revenue_paid: decimal
    pv: number
    read_through: number
```

* 一意キーは `(workspace_id, business_date, grain, consent_state, dimension_set_version, dimension_hash, projection_version)` とする
* 日次バッチ + 直近分の準リアルタイムprojectionを持つ。UIはwatermarkを見て「速報」「確定」「遅延」を表示する
* 成果状態の変化は `occurred_at`の発生日と、承認・支払日の状態変化ロールアップを別々再計算する。「発生日別の最終状態」と「当日の承認/支払フロー」を混ぜない
* 処理済みoutbox/event watermarkをcheckpointとし、同一範囲の再実行で同じprojectionになること
* 高カーディナリティ組み合わせは事前集計せず、Workspaceと期間の上限付きアドホック集計で対応する（集計セット定義はversion管理）

## 6. アトリビューション(クリック↔成果の突合)

### 6.1 突合手段(優先順)

```text
1. sub_id 完全一致(対応ASP): tracking_link_id を SID に埋めて成果レポートと突合
2. ASPクリックID一致(APIが提供する場合)
3. 推定突合: program × 時間窓(クリック後 Cookie 期間内)× クリック実績の按分
4. 突合不能: プログラム単位の集計値としてのみ計上
```

```yaml
attribution_record:
  id: string
  workspace_id: string
  conversion_id: string
  tracking_link_id: string | null
  method: sub_id | click_ref | estimated | unattributed
  model: last-click | first-click | linear
  model_version: string
  is_primary: boolean
  credit: decimal                     # 0.0〜1.0。1 conversion内の合計1.0
  confidence: decimal                 # 0.0〜1.0。methodごとの既定値はversion化
  attribution_window_seconds: integer
  attributed_at: datetime
  consent_state: granted | not_required
  schema_version: string
```

* 画面では突合方法を必ず表示し、推定値と実測値を混ぜて見せない
* 突合率(sub_id一致の割合)自体を運用KPIとし、sub_id非対応プログラムには「詳細分析不可」バッジを付ける
* `estimated` は個別Conversionの事実ではなく、プログラムの集計値を同一窓のクリックへ按分した参考projectionとする。個別成果の追跡成功と表示しない
* `consent_state=not_required` はsub_idやASP click_refだけで突合し、ブラウザー識別子を使わない場合に使用する。セッション経路に依存する場合はgrantedだけを対象とする

### 6.2 マルチタッチ

同一セッションが複数コンテンツを経由した場合の貢献配分は、規範的な既定値を **`last-click`** とする。参考値として `first-click` と `linear` を併記できるが、`is_primary=false` として主表示・意思決定値に混ぜない。Workspaceが規範モデルを変更する場合は `model_version` と発効日を新規発行し、過去レポートを暗黙に書き換えない。

## 7. Insight Engine(何が効くかの分析)

### 7.1 目的

蓄積されたロールアップから「クリック率・成果に効いている要因」を定期的に抽出し、人間が読めるレポートと、次回生成時の推奨(Brief への提案)として出力する。

### 7.2 分析ジョブ

| ジョブ | 内容 | 出力例 |
| --- | --- | --- |
| ディメンション比較 | 同一商品・同一媒体内で angle / placement / CTA / 長さ / 投稿時間帯別の CTR・EPC を比較。サンプル不足セルは除外 | 「比較表内リンクは本文リンクよりCTRが2.1倍(n=4,300)」 |
| ペルソナ適合 | audience_persona × angle の成果マトリクス | 「初心者ペルソナには『デメリット重視』が最もCVRが高い」 |
| 時系列検知 | CTR・CVRの急落検知(リンク切れ・価格改定・アルゴリズム変動の兆候) | 「記事XのCTRが7日間で60%低下。価格改定日と一致」 |
| 減衰分析 | 公開からの経過日数と成果の減衰曲線 → リフレッシュ推奨時期 | 「このジャンルは公開90日でEPC半減。REFRESH_DUE の閾値に反映」 |
| タイトル・冒頭分析 | 高CTR variant のタイトルパターン(数字・疑問形・年号等)の傾向 | 「数字入りタイトルはCTR+18%(信頼区間付き)」 |
| 実験集計 | 事前登録した解析法によるExperiment判定 | 「A/B: 固定horizonと多重比較補正後にBの95% CIが最小効果を上回り、guardrail低下なし」 |

### 7.3 統計的規律

* 比較は同一条件セル同士のみ(媒体・商品カテゴリーを跨ぐ単純比較を出さない)
* 多重比較補正を行い、偶然の差を「発見」としない
* すべての発見に n(サンプル数)と期間を併記し、閾値未満は出力しない
* 相関を因果として断定表現しない(レポート文言規則:「〜の傾向」「〜と関連」)
* 開始前にprimary metricとそのKPI version、検出したい最小効果、有意水準、検出力、予定標本数、固定期間、除外条件を凍結する
* 固定horizon実験の途中で通常のp値を繰り返し見て早期終了しない。逐次検定は手法と停止境界を事前登録したExperimentだけで許可する
* 統計的有意差だけでなく、最小効果、信頼区間、guardrail、holdoutとの差を併記する

### 7.5 生成へのフィードバック(適用範囲の制限)

Insight は次にのみ自動反映できる(v1.0 27.5章と整合):

* Brief 作成時の推奨(angle・長さ・CTA・投稿時刻・媒体の提案として表示。強制しない)
* Content Matrix のセル並び順(「過去成果が高い組み合わせ」バッジ)
* リフレッシュ期限(REFRESH_DUE)の閾値

自動反映してはならないもの:

* 商品の編集評価・おすすめ順位
* 比較スコア
* 根拠(Claim/Evidence)の内容

### 7.6 インサイト優先度スコア

大量の発見から画面上位に出すものを決めるスコア。各要素を0〜1へ正規化し、次の加重和とする。

```yaml
# src/lib/insight/priority.ts に実装予定の重み定義。
# 各重みは 0.0〜1.0、合計 1.0。Workspace 設定で変更可能とし、以下を既定値とする。
insight_priority_weights:
  revenue_impact: 0.35      # 推定収益インパクト(EPC×対象トラフィック)
  confidence: 0.30          # 統計的確度(n・信頼区間の狭さ)
  actionability: 0.25       # 推奨アクションの実行しやすさ(ワンクリック再生成=高)
  freshness: 0.10           # 発見の新しさ(既知の再確認=低)
```

```text
priority_score
= 0.35 * revenue_impact
+ 0.30 * confidence
+ 0.25 * actionability
+ 0.10 * freshness
```

正規化関数、外れ値の上限、重みは `priority_model_version` として固定する。加重和は要素間の積と同値ではない。confidenceの下限ゲートで不確実な発見を先に除外した上で、残った候補だけをこの式で順位付ける。

既定値の根拠:

* `revenue_impact` を最大にしつつ `confidence` をほぼ同格に置き、confidenceの下限ゲートと併用して「サンプル不足の派手な数字」を上位に出さない
* 個人〜小規模チーム運用を想定し、すぐ実行できる提案(`actionability`)を3番手に厚く配分。改善サイクルの回転を優先する
* `freshness` は同じ発見の再表示を抑える程度に留める(新奇性を上げすぎると偶然の変動を追いかけてしまう)

```yaml
# 補足: スコア計算時、confidence が閾値未満(n不足)の発見は
# 重み付け以前に表示対象から除外する(§7.3 の規律が優先)。
```

### 7.7 Experiment、探索、holdout

```yaml
experiment:
  id: string
  workspace_id: string
  scope: article | tracking_link | publication_series
  hypothesis: string
  variants:
    - variant_key: string
      content_variant_id: string
      allocation_weight: decimal
  primary_metric_key: string
  kpi_definition_version: string
  guardrail_metric_keys: []
  analysis_plan: fixed_horizon | preregistered_sequential
  alpha: decimal
  power: decimal
  minimum_detectable_effect: decimal
  planned_sample_size: integer
  exploration_rate: decimal           # 初期0.10、適格な非leader案に配分
  holdout_rate: decimal               # 初期0.10、Insight推奨を適用しない対照
  allocation_version: string
  starts_at: datetime
  planned_ends_at: datetime
  status: draft | running | stopped | concluded | invalidated
  consent_state: granted
  schema_version: string
```

`exploration_rate` は現在のleader以外の適格variantへ分散し、新しい勝ち筋の検証機会を残す。`holdout_rate` はInsightや動的最適化を適用しない固定controlに割り当て、増分効果を測る。初期はそれぞれ10%とし、変更は新しい `allocation_version` と監査ログを必須とする。holdoutへの割当後に別variantへ再割当しない。

stable assignmentに匿名セッションが必要なため、実験対象は `consent_state=granted` に限る。`denied/unknown` には事前に定めたcontrolを表示し、実験標本に含めない。投稿時間の逐次比較は無作為割当ではないため、A/Bと同じ因果推論バッジを付けず「観察的比較」と表示する。

## 9. プライバシー・保持期間

| データ | 保持期間 | 備考 |
| --- | --- | --- |
| ClickEvent / BehaviorEvent(生) | 13ヶ月 | ip_hash は90日で削除 |
| MetricRollup | 無期限 | 個人性なし |
| ChannelMetricSnapshot | 無期限 | |
| Conversion | 法定帳簿要件に準拠(7年目安) | 金額データのため |
| ConversionStatusEvent | Conversionと同期間 | 二軸の履歴と再構築に使用 |

* WebMCP・外部AIへは集計値のみ公開し、生イベント・IP系フィールドは返さない
* 削除jobはWorkspace、データ種別、期間を記録し、対象行数と失敗数を監査する。法的holdがある場合は理由と期限を明示する
