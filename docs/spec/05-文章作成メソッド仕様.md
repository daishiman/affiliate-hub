## 1. 文章作成メソッド

### 1-1. すべての記事に共通する執筆順序

ブログ層 §10.1 の基本順序を、**節（セクション）単位で必ず1周させる**。記事全体で1回ではない。

```text
結論 → 理由 → 根拠 → 具体例 → 例外 → 読者にとっての意味 → 次の行動
```

| 段 | 何を書くか | 分量の目安 | 省略可否 |
| --- | --- | --- | --- |
| 結論 | その節で言いたいことを1文で | 1文 | 不可 |
| 理由 | なぜそう言えるかを1〜2文 | 1〜2文 | 不可 |
| 根拠 | Evidence / TestRun への具体的参照 | 1〜3文 | **不可**（根拠のない主張は公開不可） |
| 具体例 | 実際の場面・数値 | 1〜3文 | 可（ただし節の3つに1つ以上は必要） |
| 例外 | 当てはまらない条件 | 1〜2文 | 可 |
| 読者にとっての意味 | 読者の判断にどう効くか | 1文 | 不可 |
| 次の行動 | 次に読む／確認する／申し込む | 1文 | 節末のみ |

### 1-2. 記事タイプ別の順序・粒度

#### ランキング記事（ブログ層 §9.1）

| 順 | セクション | 執筆メソッド | 粒度 |
| --- | --- | --- | --- |
| 1 | 一文結論 | 「◯◯を重視するなら A、△△なら B」の二択以上で書く。1位だけを断定しない | 1文・60字以内 |
| 2 | 用途別ベスト | 用途3〜5個。各1行「用途 → 推奨品 → 理由1句」 | 各1行 |
| 3 | 比較表 | 数値列は単位と測定条件を列ヘッダに書く | 列5〜8 |
| 4 | 評価基準 | 重み（RankingModel）を数値で明示。「総合的に判断」と書かない | 軸4〜6 |
| 5 | 検証条件 | いつ・どこで・何台・どの設定 | 箇条書き5項目以上 |
| 6 | ランキング | 各順位に「結論→理由→根拠→例外」を1周 | 各300〜600字 |
| 7 | 各商品カード | 実測値・向く人・向かない人・価格・購入先 | 各1画面に収める |
| 8 | 選外商品 | 「なぜ選外か」を必ず書く。列挙だけにしない | 各2〜3文 |
| 9 | FAQ | 検索実需のある疑問のみ。水増ししない | 5〜8問 |
| 10 | 最終結論 | 冒頭の一文結論と矛盾しないこと（自動検査対象） | 3〜5文 |
| 11 | 方法論 | 評価方法ページへのリンクと差分だけ | 2〜3文 |

#### 個別レビュー（ブログ層 §9.2）

粒度の要点: **実測値のない項目は書かない**。外観・操作は写真の代替テキストで内容が伝わること。長期使用は使用期間と使用時間を明記する。

#### 比較記事（ブログ層 §9.3）

粒度の要点: 「Aが向く人／Bが向く人」を**先に**書き、差分表を後に置く。差分表は「差がある項目」だけを載せ、同じ項目は「同等」の1行にまとめる。

#### ハウツー記事（ブログ層 §9.4）

粒度の要点: 各ステップに**完了状態**（何が見えたら次へ進めるか）を必ず書く。所要時間と費用を冒頭に置く。エラー対処は「症状 → 原因 → 対処」の3点セット。

### 1-3. 段落構成

- 一段落一論点。原則1〜3文（ブログ層 §10.3）。
- 4文以上になったら段落を割るか、箇条書きへ変換する。
- 段落の先頭文が、その段落の要約になっていること。
- 連続する3段落が同じ構文（例: すべて「〜です。〜だからです。」）にならないこと。

### 1-4. 見出しの立て方

| 規則 | 良い例 | 悪い例 |
| --- | --- | --- |
| 見出しだけで結論が分かる | 「4K編集なら M4 Pro / メモリ24GB以上が下限」 | 「スペックについて」 |
| 疑問形は答えを含める | 「メモリは何GB必要か → 4Kなら24GB」 | 「メモリは何GB必要?」 |
| 数値は単位つき | 「連続書き出し45分での温度」 | 「発熱」 |
| H2 は5〜9個 | — | H2 が2個、または15個 |
| H3 は同一 H2 内で2個以上 | — | H3 が1個だけぶら下がる |

### 1-5. リード文（記事冒頭）

構成を固定する。

```text
1文目: 読者の状況の言い当て（「〜で迷っている方へ」）
2文目: この記事で分かること（箇条書き3点でも可）
3文目: 結論の先出し（一文結論と同一内容）
4文目: 根拠の所在（「◯台を◯条件で実測した結果に基づく」）
```

**禁止**: 「いかがでしょうか」「結論から言うと…（そのあと結論が来ない）」「本記事では〜について解説します」だけで終わる導入。

### 1-6. 結論の置き方

- 記事の**先頭**（一文結論）と**末尾**（最終結論）の2箇所に置く。
- 両者は同じ推奨を指すこと。異なる場合は公開ゲートで BLOCK（自動検査 QC-09）。
- 末尾の結論には「読者タイプ別」の分岐を必ず含める（最低2分岐）。

### 1-7. 根拠の示し方

| 主張の種類 | 必要な根拠 | 文中の書き方 |
| --- | --- | --- |
| 性能が高い | TestRun 1件以上 | 「当サイトの測定では〜（測定日・条件）」 |
| 仕様がこうである | 公式情報 Evidence 1件 | 「メーカー公称値では〜（出典リンク）」 |
| 使いやすい | 使用感 + 使用期間 | 「テスターの主観として、3週間使った範囲では〜」 |
| 他より優れている | 比較可能な TestRun が両方に存在 | 「同一条件で比較すると〜」 |
| 今後こうなる | 推論であることの明示 | 「以上から当サイトでは〜と判断している」 |

**根拠が1件もない主張は文ごと削除する。** 表現を弱めて残すことはしない。

### 1-8. 比較の書き分け

| 比較候補の分類（プラットフォーム層 §12.2） | 書き方 |
| --- | --- |
| Exact Offer（同一商品の別販売経路） | 価格・保証・納期だけを比較。性能比較を書かない |
| Variant（同一シリーズの別構成） | 差分のある仕様だけを表にする。共通仕様は「共通」1行 |
| Direct Competitor（直接競合） | 評価軸をそろえた実測比較。片方だけ未測定の軸は「未測定」と書く |
| Alternative Solution（代替手段） | そもそも別カテゴリであることを先に書く。数値比較を並べない |

### 1-9. CTA 配置

| 位置 | 置いてよい CTA | 条件 |
| --- | --- | --- |
| リード文直後 | 不可 | 判断材料の提示前（ブログ層 §10.3） |
| 各商品カード末尾 | 購入リンク | その商品の実測値とデメリットを提示済みであること |
| 用途別ベストの各行 | 該当商品への内部リンク | 購入リンクは不可 |
| 最終結論の直後 | 購入リンク（複数販売店） | 最有力1件に絞らず、選択肢を並べる |
| FAQ内 | 不可 | — |

すべての購入リンクに `rel="sponsored"`（ブログ層 §17.2）と広告表記が適用されていること。

## 2. 文体規則

| 項目 | 規則 |
| --- | --- |
| 敬体／常体 | **敬体（です・ます）で統一**。表内・箇条書きの断片は体言止め可。1記事内で混在させない |
| 一人称 | 「当サイト」。個人ブランド型パターンのみ「筆者」を許可。「私たち」「弊社」は使わない |
| 読者呼称 | 「あなた」を基本とし、多用しない（1記事5回以内）。「皆さん」「読者の方」は使わない |
| 一文の長さ | 原則60字以内、最大80字。80字超は自動検査で指摘（QC-03） |
| 一段落 | 1〜3文 |
| 専門用語 | 初出時に括弧で1文説明。同一記事内で2回目以降は説明しない |
| 数値 | 必ず単位と測定条件を添える。「速い」ではなく「書き出し12分30秒（4K/10分素材/H.264）」 |
| 日付 | `2026年8月16日` の絶対表記。「先日」「最近」「現在」単独は禁止 |
| 価格 | 「2026年8月16日時点、税込」を必ず併記。価格そのものは動的取得値を優先 |
| 箇条書き | 3項目以上で使う。2項目なら文にする |
| 記号 | 「!」は使わない。「?」は見出し以外で使わない |

### 2-1. 禁止表現

以下は**根拠なしでの使用を禁止**する。自動検査 QC-05 が検出し、Evidence の紐づけがなければ公開ゲートで BLOCK。

| 表現 | 使用条件 |
| --- | --- |
| 絶対 | 例外がないことを示す出典がある場合のみ |
| 完全 | 対象範囲を限定した上で、その範囲の網羅性を示せる場合のみ |
| 最強・最高 | 使用禁止（比較範囲を明示した「本記事の比較対象8機種中では最速」に書き換える） |
| 最安 | 調査対象販売店と調査日時を併記できる場合のみ |
| 誰でも・必ず・確実に | 使用禁止 |
| 業界No.1・圧倒的 | 第三者調査の出典がある場合のみ |
| 永久・半永久 | 使用禁止 |

薬機法・景表法に触れる表現（効果効能の断定、優良誤認、有利誤認）は別途コンプライアンス検査（QC-15〜17）で扱う。

## 3. セクション別の雛形

### 3-1. 一文結論

```text
【型】{読者条件}なら{推奨品}。{別の読者条件}なら{別の推奨品}。
【良い例】4K動画を日常的に編集するなら MacBook Pro 14インチ(M4 Pro/24GB)。予算15万円以内なら {別機種}。
【悪い例】動画編集におすすめのノートパソコンをご紹介します。  ← 結論がない
【悪い例】結論、これ一択です。  ← 条件がない・根拠がない
```

### 3-2. リード文

```text
【型】
{読者の状況の言い当て}。
この記事では{分かること1}・{分かること2}・{分かること3}が分かります。
結論は{一文結論と同一内容}です。
{台数}台を{条件}で実測した結果に基づきます（測定日: {YYYY年M月D日}）。

【悪い例】
動画編集用のノートパソコン選びは難しいですよね。本記事では、そんなあなたのために
おすすめのモデルを徹底解説していきます。ぜひ最後までご覧ください。
  ← 結論なし・根拠なし・「ぜひ最後まで」は読者価値ゼロ
```

### 3-3. 評価基準

```text
【型】
本記事は次の{n}軸で評価しました。重みは合計100です。
- {軸名}（重み{x}）: {測定方法}。{なぜこの重みか}
...
重みは{読者タイプ}を想定して設定しています。別の用途では順位が変わります。

【悪い例】性能・価格・使いやすさを総合的に評価しました。 ← 重みも測定方法もない
```

### 3-4. 商品カード

```text
【型】
### {順位}位 {商品名}（{一言の位置づけ}）
{結論1文}
- 向いている人: {条件}
- 向いていない人: {条件}
- 実測: {項目}={値}（{条件}・{測定日}）
- 価格: {価格}（{販売店}・{取得日時}時点）
{デメリット1〜2文。影響を受ける人と回避策を必ず添える}
{購入リンク（rel="sponsored"）}
```

### 3-5. デメリット記述

```text
【型】{欠点}。{誰に影響するか}には{どう影響するか}。{回避策または許容条件}。
【良い例】重量は2.1kgあります。毎日持ち歩く人には負担ですが、据え置き中心なら問題になりません。
【悪い例】少し重いのが残念なポイントです。 ← 影響対象も回避策もない
```

### 3-6. FAQ

```text
【型】
#### {読者が実際に検索する形の疑問文}
{結論1文}。{理由1文}。{根拠または参照先1文}。
【悪い例】Q. この商品はおすすめですか? A. はい、おすすめです。 ← 検索実需がない・根拠がない
```

### 3-7. 最終結論

```text
【型】
{用途A}なら{商品X}。{理由を1句}。
{用途B}なら{商品Y}。{理由を1句}。
{どちらでもない場合の指針}。
{次の行動: 詳細ページ／比較記事／購入先一覧}
```

## 4. 事実と推論の書き分け

ブログ層 §10.2 の6分類を、**文中表示・データ属性・視覚表現**の3面で実装する。

| 分類 | 文中の表記例 | データ属性 | 視覚表現 |
| --- | --- | --- | --- |
| 公式情報 | 「メーカー公称値では{値}です（{出典名} {取得日}）」 | `data-fact-type="official"` | 出典リンクを文末に付与 |
| 実測 | 「当サイトの測定では{値}でした（{条件}・{測定日}）」 | `data-fact-type="measured"` | 測定条件を展開できる注記 |
| 使用感 | 「テスターの主観として、{期間}使った範囲では{所感}と感じました」 | `data-fact-type="experience"` | テスター名の表示 |
| 推論 | 「以上から当サイトでは{判断}と考えています」 | `data-fact-type="inference"` | 「当サイトの判断」ラベル |
| 外部評価 | 「{媒体名}の利用者レビューでは{傾向}という声が見られます（{件数}件・{取得日}）」 | `data-fact-type="external"` | 件数と取得日の併記 |
| 広告情報 | 「販売店提供情報によると{内容}です」 | `data-fact-type="commercial"` | 広告情報である旨の明示 |

### 4-1. 混同の禁止

**1つの文に2つの分類を入れない。**

```text
【違反】公称値は12分ですが、実際にはもっと速く感じました。
        ← official と experience が同一文に混在
【修正】公称値は12分です。当サイトの測定では11分42秒でした（4K/10分素材・2026年8月10日）。
        体感としても待ち時間の短さを感じました（テスターの主観）。
```

### 4-2. 検査仕様

- 各段落の `data-fact-type` が付与されていること（未分類 = QC-06 FAIL）。
- `inference` の段落の直前または直後に、`measured` または `official` の段落が存在すること（根拠なし推論の検出）。
- `commercial` の段落がランキング根拠セクション内に存在しないこと（§19.4 違反）。

## 5. ペルソナ差分の作り方

プラットフォーム層 §13（書き手ペルソナ）・§14（読者ペルソナ）に基づき、**同じ事実から複数の記事バリアントを作る**。

### 5-1. 変えてよいもの

| 要素 | 変え方の例 |
| --- | --- |
| 語彙 | 初心者向け=「書き出し（動画ファイルにする処理）」／上級者向け=「エンコード」 |
| 詳しさ | 初心者向け=結論と3軸／上級者向け=全8軸＋測定生データへのリンク |
| 例示 | 学生向け=卒業制作／業務向け=クライアント納品 |
| CTA | 初心者向け=「選び方ガイドを読む」／購入意欲高=「価格を確認する」 |
| 見出しの言い回し | 同じ内容を別の言い回しにする |
| 会話ブロックの話者構成 | 初心者向けは ReaderQuestion 多め／上級者向けは ExpertCaution 中心 |

### 5-2. 変えてはいけないもの（事実境界・§13.3）

| 要素 | 理由 |
| --- | --- |
| 数値 | 同じ TestRun から出る値は全バリアントで同一 |
| 事実の分類 | measured が別バリアントで official になることはない |
| 根拠（Evidence の紐づけ） | Claim–Evidence 関係はバリアント非依存 |
| 順位と評価軸の重み | RankingModel が同一なら順位も同一 |
| 広告表記 | Disclosure はバリアント非依存で全面適用 |
| デメリットの有無 | 特定バリアントでデメリットを省略しない |

**書き手ペルソナは「語り口」であって「事実の出所」ではない。** 架空の専門家を作らない、資格を騙らない（ブログ層 §11.2）。

### 5-3. 実装契約

`generated_variant` の生成時、`persona_id` が変わっても以下のハッシュが不変であることを検査する（QC-11）。

```text
fact_fingerprint = sha256(
  sorted(claim_ids) + sorted(evidence_ids) + sorted(test_run_ids)
  + ranking_model_id + sorted(disclosure_ids)
)
```

## 6. マルチサイト差別化の書き分け

プラットフォーム層 §16.6 を文章レベルまで落とす。**言い換え記事にしない実務ルール。**

### 6-1. 差別化の10軸と、文章での現れ方

| 軸 | 文章でどう変わるか | 検査 |
| --- | --- | --- |
| 対象読者 | リード文1文目の状況設定が別物になる | リード文の類似度 < 0.5 |
| 検索意図 | H1 と一文結論の焦点が変わる（「選び方」か「◯◯と△△どっち」か） | H1 完全一致を禁止 |
| 記事の目的 | 到達させたい行動が変わる（比較検討 → 購入／認知 → 比較） | CTA 種別が異なる |
| 評価軸 | RankingModel の重みが異なる → **順位が実際に変わる** | 同一 RankingModel の使い回しを禁止 |
| 使用場面 | 具体例セクションが全面的に別 | 具体例の重複0 |
| 独自の体験 | サイト固有の TestRun / テスターを使う | TestRun ID の重複率 < 0.5 |
| 比較対象 | 選ぶ商品集合が異なる | 商品集合の Jaccard 係数 < 0.7 |
| 結論 | 推奨品が異なるか、同じでも推奨条件が異なる | 一文結論の完全一致を禁止 |
| 内部リンク | サイト内の別記事へ向く | クロスサイトの内部リンク0 |
| CTA | 文言と配置が異なる | — |

### 6-2. 実務ルール

1. **同じ RankingModel を2サイトで使わない。** 重みが同じなら順位も同じになり、それは言い換え記事である。
2. **本文の連続40字以上の一致を0にする。** 自動検査 QC-12 が全サイト横断で検出する。
3. **同一 Claim を引用してよいが、引用の文は書き下ろす。** Claim は正規データであり共有するが、文章は共有しない。
4. **1商品につき、サイトを跨いで同じ「向いている人」を書かない。** 読者ペルソナが違えば向き不向きの記述も変わるはずである。
5. 上記を満たせない場合は**記事を作らない**。カニバリを承知で量産しない。

## 7. 品質チェックリスト（実行可能な検査仕様）

プラットフォーム層 §15.6 の自動品質確認17項目を、実行可能な検査へ変換する。すべて `src/lib/domain/content-quality.ts` の純関数として実装し、公開ゲート（`src/lib/content/publish-gate.ts`）から呼ぶ。

| ID | 検査内容 | 入力 | 判定 | 失敗時 |
| --- | --- | --- | --- | --- |
| QC-01 | 必須セクションの存在 | セクションID一覧 | ブログ層 §8 の必須項目がすべて存在 | BLOCK |
| QC-02 | 一段落の文数 | 段落配列 | 全段落 ≤3文 | WARN |
| QC-03 | 一文の長さ | 文配列 | 全文 ≤80字 | WARN |
| QC-04 | 見出しだけで結論が分かる | 見出し配列 | 動詞または数値を含む見出しが80%以上 | WARN |
| QC-05 | 禁止表現 | 本文 | §2-1 の語が Evidence 紐づけなしで出現しない | BLOCK |
| QC-06 | 事実分類の付与 | 段落 + `data-fact-type` | 未分類段落0 | BLOCK |
| QC-07 | 根拠のない主張 | Claim–Evidence 関係 | Evidence 0件の Claim が0 | BLOCK |
| QC-08 | 数値の単位・条件 | 数値トークン | 単位なし数値が0（順位・個数を除く） | WARN |
| QC-09 | 冒頭結論と最終結論の一致 | 一文結論 / 最終結論 | 推奨 product_id 集合が一致 | BLOCK |

| QC-11 | ペルソナ差分の事実境界 | `fact_fingerprint` | 全バリアントで一致 | BLOCK |
| QC-12 | マルチサイト重複 | 全サイト本文 | 連続40字以上の一致0 | BLOCK |
| QC-13 | 広告表記 | Disclosure / リンク属性 | 全アフィリエイトリンクに `rel="sponsored"` と表記 | BLOCK |

### 7-1. 判定の扱い

- **BLOCK が1件でもあれば公開できない。** 公開ゲートが `blocked` を返す。

- 各検査は結果を `quality_report` として保存し、記事ページの「品質」タブから参照できるようにする（証拠のない PASS を出さないため）。
