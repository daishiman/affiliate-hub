# 設計の見直しで出たこと — SEO の診断と反映 (feat-seo-assessment-reflection)

P03 の成果物。実装を読み直して見つけたこと。
**未達を含む。緑に見せるための書き換えはしていない。**

## F-01 公開のたびに診断が回る配線が無い（受入条件 1・未達）

`createManageSeoAssessmentUseCase` は
`src/application/composition.ts` からしか呼ばれていない。

`publish-article.ts` に診断を呼ぶ経路が無い。

つまり**記事を公開しても診断は自動で回らない**。
管理画面から `assess` を押したときだけ回る。

### なぜそのままにしたか

公開処理の中で診断を回すと、
**診断器が落ちた日に記事が公開できなくなる**。

公開は読者に届ける行為で、診断は後から直すための材料である。
後者の失敗で前者を止めるのは順序が逆になる。

正しい配線は「公開の後に、公開処理とは別に回す」であり、
それには公開イベントを受ける口が要る。
この feature はその口を作っていない。

**未達として記録する。** 条件 1 は満たしていない。

## F-02 月次の再診断が無い（受入条件 2・未達）

`wrangler.jsonc` の `triggers.crons` は `"0 17 * * *"` の 1 本だけで、
これは日次ロールアップ用である。

SEO 診断用の scheduler は
`src/infrastructure/platform/` に存在しない。

条件 2 の「月次で全公開記事の診断が更新される」は満たしていない。

### 難しさ

月次で全記事を回すと、記事数に比例して 1 回の実行が伸びる。
Workers の実行時間の上限に当たる可能性がある。

分割して回すなら、どこまで回したかを持つ表が要る
（reader-behavior-analytics の `REBUILD_SCAN_LIMIT` と同じ問題）。
この feature はそれを設計していない。

## F-03 クローラ拒否を robots.txt に出さない（受入条件 8・意図的に未達）

`buildRobotsTxt` は許可行だけを出す。

```ts
export const AI_CRAWLERS = ["GPTBot","ClaudeBot","PerplexityBot","Google-Extended"] as const;
// 遮断の行はこの関数からは出さない（遮断はこのプロダクトの方針の外）。
```

条件 8 は「ブログごとにクローラを拒否でき、robots.txt に反映される」だが、
**拒否を出さないと決めてある**。

### なぜ

このプロダクトは AEO（回答エンジン最適化）を別 feature で持つ。
そこでは AI クローラに**読ませたい**。

同じ製品の中に「読ませる仕組み」と「読ませない仕組み」を両方置くと、
どちらが効いているのか運用者が追えなくなる。

**条件 8 は満たさない。設計としてそう決めた。**
必要になったら方針の側から決め直すべきで、
関数に枝を足して済ませる話ではない。

## F-04 `image-alt` と `canonical` が常に 0 件

`article-seo-analyzer.ts` はこの 2 観点を 1 件も出さない。

観点の一覧には残っている。

これは意図した設計で、理由は `assessment-catalog.md` に書いた。
ただし**画面が「0 件 = 問題なし」と見せると嘘になる**。

提示層でこの 2 観点を「未対応」として区別できるかは、
`feat-blog-scoped-admin-console` の側の宿題である。

## F-05 `dismissed` を戻す口が無い

一度「直さない」と決めた指摘を `open` へ戻す操作が無い。

方針を変えたときに戻せない。

### 今のところ許容している

`dismiss` は `site.manage` が要る重い操作で、頻繁には起きない。
戻す口を足すと、その口にも権限と記録が要る。

**運用で困ったら足す。** 今は口が少ないほうが安全と判断した。

## F-06 診断の実行が同期である

`assess` はブログ全体を対象にできる。

記事が増えると 1 リクエストが長くなる。
`assessedArticles` で件数は返るが、途中で切れる仕組みが無い。

### 今の規模では起きない

seed のブログは記事が 2 桁である。
3 桁になったら分割が要る。

## F-07 `suggestion` が `null` の指摘の割合が不明

下書きを作れない指摘がどれくらいあるかを測っていない。

多いと、運用者は「直せない指摘ばかり並ぶ一覧」を見ることになる。

診断器の実装を読む限り、
`thin-content` と `heading-structure` は具体的な直し方を出しにくい。

**測っていないので、多いとも少ないとも言わない。**

## F-08 指針の出典と診断の観点が繋がっていない

`guideline-reference.ts` は出典を 90 日で見直す仕組みを持つが、
**その出典が どの観点の根拠か** を持っていない。

指針が変わったときに、
どの観点を作り直すべきかが機械には分からない。

人が読んで判断することになる。

## F-09 権限の 3 分割が画面に出ていない

`content.write` しか持たない人が `dismiss` を押せないことは、
使用時に断られて初めて分かる。

画面側でボタンを出し分けるのは提示層の責務で、
この feature の範囲外。
