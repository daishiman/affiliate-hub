# 最後の見直し — SEO の診断と反映 (feat-seo-assessment-reflection)

P11 の成果物。設計判断（AD-1〜5）との照合と、残る弱点。

## AD との照合

| | 内容 | 結果 |
|---|---|---|
| AD-1 | 層は一方向に依存する | **守っている** |
| AD-2 | 提示層で計算しない | **守っている** |
| AD-3 | 改善層は公開面へ書けない | **守っている（型で）** |
| AD-4 | 生イベントは 90 日で捨てる | 該当しない |
| AD-5 | `site_slug` が唯一の結合キー | **守っている** |

### AD-1

改善層は住所層・観測層のどちらも参照していない。

診断は記事の内容だけを見る。
PV も収益も入力にしない。

### AD-2

出す順（`重み × 件数`）は `rankFindings` が計算する。
画面は並べ替えない。

索引は `state` と `severity` までで、
**並べ替えはアプリ側**（`data-model.md`）。

### AD-3

`draftFix` の戻り値が改訂 id だけで、
ポートに公開の口が無い。

**この feature の中核である。**

### AD-4

この feature は生イベントを持たない。
`article_seo_assessment` は記事 × 観点で上限があり、
掃除が要らない。

### AD-5

表は `(workspace_id, site_slug, article_slug, check_kind)` で引く。
サイトの内部 id を持ち込んでいない。

## §12.3 の口の分離

ポート全体が `Editorial` 印で、`BlogRevenuePort` を呼べない。

**「報酬の高い記事から直す」ができない。**

これは制限に見えるが、そうしないと
SEO の指摘が収益の都合で並び替わることになる。
編集判断と商売判断を混ぜないための線である。

## 残る弱点

### 1. 自動で回らない（条件 1・2）

**この feature の一番大きな穴。**

診断の中身は揃っているが、
それが定期的に回る仕組みが無い。

運用者が押さなければ、指摘は古いまま残る。
`assessed_at` を見れば古さは分かるが、
気づくのは人である。

### 2. `dismissed` を戻せない

方針転換に対応できない。
`site.manage` が要る重い操作なので頻度は低いが、
一度押したら終わりである。

### 3. 常に 0 件の観点が 2 つある

`image-alt` と `canonical`。

観点の一覧に載っていて 0 件は、
画面の作り方次第で「問題なし」に読める。

**根拠を持てない観点を出さない**判断は正しいが、
それが伝わるかは提示層に依存している。

### 4. 出典と観点が繋がっていない

指針が変わったときに、
どの観点を作り直すべきかを機械が言えない。

`guideline-reference.ts` は出典の鮮度を管理するが、
`SEO_CHECK_KINDS` との対応表を持たない。

### 5. `suggestion` が `null` の割合を測っていない

下書きを作れない指摘ばかりだと、
一覧が「読むだけのもの」になる。

多いか少ないか分かっていない。

## それでも出せると考える理由

穴 1 を除けば、この feature が主張していることは
**すべて機械が守っている**。

- 根拠のない指摘は表に入らない（型 + NOT NULL）
- 承認なしに公開面は変わらない（ポートに口が無い）
- 「直さない」判断は診断に上書きされない（d1 で固定）
- 90 日の見直しは境界まで確かめてある（14 件）

穴 1 は「回す仕組みが無い」であって、
「回すと間違ったことをする」ではない。

手で押せば正しく動く。
自動化は後から足せる。

## 未達を隠していないこと

`acceptance-report.md` は 10 件中 3 件を「満たさない」と書いた。

条件 8（クローラ拒否）は、
テストで「遮断を 1 行も書かない」と固定してある。
**満たさないことをテストで留めている**ので、
黙って足すと赤くなる。

未達を後から気づかない形にしていない。
