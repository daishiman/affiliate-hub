# 承認の経路 — SEO の診断と反映 (feat-seo-assessment-reflection)

P02 の成果物。指摘が読者へ届くまでに、誰が何を通すか。

## 経路

```
  診断器 (article-seo-analyzer)
      │  記事 1 本を読んで指摘を作る
      ▼
  article_seo_assessment  state=open
      │
      │  運用者が見る (content.read)
      ▼
  ┌────────────┬─────────────┐
  │            │             │
  ▼            ▼             ▼
draft_fix    dismiss      放置
(content.write) (site.manage)  (open のまま)
  │            │
  ▼            ▼
state=drafted  state=dismissed
  │            └─ 次の診断でも復活しない
  ▼
改訂の下書き (draft_revision_id)
  │
  │  ★ ここから先は この feature の外 ★
  ▼
既存の記事編集画面
  │
  ▼
既存の承認経路（レビュー・公開判断）
  │
  ▼
公開  →  state=applied
```

## 星印の意味

**`draftFix` が返すのは改訂 id だけである。**

そこから先へ進めるのは、この feature が作ったものではない
既存の編集・承認の仕組みで、
診断の側からは呼べない（`writeback-constraints.md`）。

自動で公開へ進む枝が図に無いのは、
実装にその枝が無いからである。

## `applied` は誰が付けるか

**この feature は付けない。**

下書きが承認を経て公開されたことは、
既存の公開経路が知っている事実である。
診断の側は、次に診断を回したときに
その観点の指摘が出なくなることで結果を知る。

`state=applied` は記録用の値として持つが、
遷移させるのは公開側の責務であって、
この層が「公開されたはず」と推測して書かない。

## 放置という枝を残した理由

指摘を見て、直しも却下もしないという選択がある。

「全部の指摘に何かしなければならない」形にすると、
運用者は片付けるために `dismiss` を濫用する。
`dismiss` は**次の診断でも復活しない**強い操作なので、
それが安易に押される設計は危ない。

`open` のまま置けることは、逃げ道ではなく安全弁である。

## 権限の境界を図に重ねる

| 段 | 要る権限 |
|---|---|
| 指摘を見る | `content.read` |
| 診断を回す / 下書きを作る | `content.write` |
| 直さないと決める | `site.manage` |
| 編集・承認・公開 | 既存の記事公開権限 |

**一番下の段が、この feature の権限とは別系統である**ことが要点。
診断の権限をいくら持っても、公開はできない。
