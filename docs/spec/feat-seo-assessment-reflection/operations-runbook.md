# 運用手引き — SEO の診断と反映 (feat-seo-assessment-reflection)

P12 の成果物。動かす人が読むもの。

## 今の運用は手動である

**診断は自動で回らない。**

管理画面の「診断する」を押したときだけ回る
（`acceptance-report.md` の条件 1・2）。

自動化が入るまでは、次のどちらかで回す:

- 記事を公開したあと、その記事だけ診断する
- 週に 1 回、ブログ全体を診断する

後者は `articleSlug` を省いて `assess` を呼ぶ。

## 診断を回す

```
action: "assess"
siteSlug: <ブログ>
articleSlug: <記事> または省略（ブログ全体）
```

返る `assessedArticles` を必ず見る。

| 値 | 意味 |
|---|---|
| `null` | 診断していない（`read` / `dismiss` を呼んだ） |
| `0` | 診断したが、公開記事が 1 本も無かった |
| `n > 0` | n 本を見た |

**`0` を「問題なし」と読まない。** 調べる対象が無かっただけである。

## 一覧の読み方

出る順は `重み × 出現件数` で決まる。

重さだけの順ではないので、
**一番上が一番重い指摘とは限らない**。
「10 本の記事すべてでタイトルが長い」が
「1 本だけの致命的な指摘」より上に来ることがある。

これは意図した並びである（`assessment-catalog.md`）。

## 常に 0 件の観点がある

`image-alt` と `canonical` は 1 件も出ない。

**「調べて問題なし」ではなく「調べていない」。**

画面がこれを区別して見せられるかは、
管理画面側の宿題として残っている。
一覧で 0 件を見たら、この 2 つは数えないこと。

## 「直さない」を押すとき

`dismiss` は重い操作である。

- `site.manage` が要る
- **次の診断でも復活しない**
- **戻す口が無い**（`design-review-findings.md` F-05）

方針が変わったときに戻せないので、
迷ったら `open` のまま置く。放置してよい。

理由は必須で、空白だけでは断られる。
半年後に読む人のために書く。

## 下書きを作ったあと

`draftFix` が返すのは改訂の id だけである。

**そこから公開までは、この機能の外**。
既存の記事編集画面で中身を確認し、
既存の承認経路を通す。

下書きを作っただけでは読者には何も出ていない。
`audit_logs` の行にも `published: false` が残る。

## 指針の出典を見直す

90 日で `review_due` になる。

見直しは 2 段階に分かれている:

| することの中身 | どこが動くか |
|---|---|
| 原典の本文を取り直す | `fetchedAt` / `contentSha256` |
| 取り直した本文で仕様章を読み直す | `reEvaluatedAt` / `reEvaluatedSha256` |

**取り直しただけでは警告は消えない。**
読み直して初めて消える。

これは意図した設計で、
「本文が変わった」という警告を確認せずに消せないようにしてある。

## 何かおかしいとき

### 診断を回しても指摘が変わらない

同じ観点は置き換えなので、
**行数が増えないのは正常**である。
`assessed_at` が更新されているかを見る。

### 指摘が消えた

2 通りある:

1. 記事を直したから消えた
2. 診断器を差し替えて観点ごと無くなった

`audit_logs` の `seo_assessment.ran` を見れば
いつ診断が回ったかは分かる。
**診断を回した記録を残しているのはこの区別のため**である。

### 「下書きを作れた」と言われない

記録（`audit_logs`）が書けなかったときは、
下書きができていても失敗として返る。

記録の残らない変更を「できた」と言わない方針で、
これは repo 全体の作法である。

### 診断器が落ちている

`seo_assessment.ran` の行も残らない。

**先に記録を書いてから診断する**設計だと、
落ちた回も「回した」として残ってしまうので、
そうしていない。
