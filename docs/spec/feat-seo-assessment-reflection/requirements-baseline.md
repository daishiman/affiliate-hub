# 要件の確定 — SEO の診断と反映 (feat-seo-assessment-reflection)

P01 の成果物。何を作るのか、何を作らないのか。

## 何を作るのか

公開済みの記事を機械が読んで、**直したほうがよい箇所を指摘**する。
指摘から**下書き**を作る。公開はしない。

## 「SEO 対策」を型にできない

「対策する」を要件にすると、何をもって対策済みと言えるのかが決まらない。

順位が上がれば対策できたのか。上がらなかったら対策が足りないのか。
検索エンジンの順位はこちらの操作の外にあるので、
**達成条件にすると永久に判定できない**。

そこで扱う対象を絞る。

> **機械が現物を見て真偽を判定できる指摘だけを出す。**

- タイトルが 60 文字を超えている → 数えれば分かる
- 見出しの階層が飛んでいる → 構造を見れば分かる
- 本文が 800 文字未満 → 数えれば分かる
- もっと魅力的にする → **判定できない。出さない**

これが `src/domain/seo/assessment.ts` の存在理由であり、
受入条件 9「検証できない指摘（順位予測など）が受入条件にも画面にも現れない」
に対応する。

## 受入条件 10 件

| # | 条件 |
|---|---|
| 1 | 公開・更新のたびに当該記事の診断が生成される |
| 2 | 月次で全公開記事の診断が更新される |
| 3 | 構造化データの妥当性検証が純関数で、外部通信なしにテストできる |
| 4 | 不正な構造化データが指摘として立ち、妥当なものは立たない |
| 5 | 採用した推奨が下書きにだけ書かれ、公開面が承認なしに変わらない |
| 6 | 採用後も既存の承認経路を通らずには公開されない |
| 7 | sitemap.xml と RSS/Atom が公開記事を漏れなく列挙する |
| 8 | ブログごとにクローラを拒否でき、拒否したブログが robots.txt に反映される |
| 9 | 検証できない指摘が受入条件にも画面にも現れない |
| 10 | 指針の出典が 90 日見直しの対象として登録されている |

条件 5 と 6 が本 feature の背骨である。
`architecture/arch-blog-operations-console.md` の **AD-3
（改善層は公開面へ書けない）** をそのまま条件にしたもの。

## 作らないもの

| 作らないもの | 理由 |
|---|---|
| 順位の予測 | 検証できない。条件 9 が禁じている |
| 競合との比較 | 他社サイトを取りに行くことになる。この feature の外 |
| 自動公開 | AD-3。診断器が壊れた日に読者へ出るものが黙って変わる |
| LLM による診断 | 回すたびに答えが変わり、指摘が消えた理由を区別できない |
| キーワードの提案 | 検索ボリュームは外部データで、検証できない |

### LLM を使わない判断

診断は繰り返し回る。同じ記事から**必ず同じ指摘が出る**ことが要る。

回すたびに答えが変わると、前回の指摘が消えたのが
「記事を直したから」なのか「たまたま出なかったから」なのか
区別できない。区別できない一覧は、運用者が信用しなくなる。

決定的であることのほうが、賢いことより価値が高い。

## 上位のゴールとの関係

`system-spec/index.md` の G1（目的の異なる高品質コンテンツを
安全に作成・公開・改善できる）の「改善」にあたる。

「安全に」の中身がここでは AD-3 である。
改善が公開面を勝手に書き換えないことが、安全の定義になる。

## 隣の feature との境界

| feature | 境界 |
|---|---|
| feat-blog-custom-domain | 正規 URL は住所層が決める。この層は決めない |
| feat-reader-behavior-analytics | 観測層。この層は観測結果を入力にできるが、逆は無い |
| feat-aeo-answer-optimization | 同じ改善層。AEO は引用単位を扱い、SEO は記事の作りを扱う |
| 既存の記事編集・承認 | **下書きを渡す先**。この feature は作り直さない |
