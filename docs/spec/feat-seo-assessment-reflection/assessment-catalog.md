# 診断の観点 — SEO の診断と反映 (feat-seo-assessment-reflection)

P02 の成果物。何を見て、何を言うか。
正本は `src/domain/seo/assessment.ts` と
`src/infrastructure/improvement/article-seo-analyzer.ts`。

## 観点は 8 つ

`SEO_CHECK_KINDS`:

| 観点 | 表示名 | 根拠の取り方 |
|---|---|---|
| `title` | タイトル | 文字数を数える（60 文字が目安） |
| `description` | 説明文 | 文字数を数える（20〜120 文字） |
| `heading-structure` | 見出しの階層 | 節の数を数える |
| `internal-link` | サイト内リンク | 記事間の参照を数える |
| `image-alt` | 画像の代替文 | **出していない**（下記） |
| `structured-data` | 構造化データ | 組み立て結果を検証する |
| `canonical` | 正規 URL | **出していない**（下記） |
| `thin-content` | 内容の薄さ | 本文の文字数（800 未満）と節の数（2 未満） |

## 出していない観点が 2 つある

`image-alt` と `canonical` は 1 件も出さない。

| 観点 | 出さない理由 |
|---|---|
| `image-alt` | 公開記事の投影 `PublishedArticle` に画像の欄が無い。**根拠を持てない** |
| `canonical` | 正規 URL は住所層（`site_custom_domain`）が決める。この層の判断ではない |

**一覧に載っているのに 0 件、というのは危うい。**
「調べた結果 問題なし」と読まれるが、実際は調べていない。

だから `article-seo-analyzer.ts` の冒頭 doc に
「根拠を持てない観点は、観点の一覧にあっても出さない」と明記した。
一覧から消さないのは、後で根拠を持てるようになったときに
観点そのものを作り直さずに済むようにするため。

## 重さは 3 段階

`SEO_SEVERITIES`:

| 値 | 表示名 | 重み |
|---|---|---|
| `critical` | 直したほうがよい | 3 |
| `warning` | 気になる | 2 |
| `info` | 参考 | 1 |

## 出す順は重さだけでは決めない

```
score = 重み × その観点の出現件数
```

**重さだけで並べると、めったに起きない致命的な指摘が、
毎日起きる中程度の指摘を覆い隠す。**

10 本の記事すべてでタイトルが長い（warning × 10）ほうが、
1 本だけの重い指摘（critical × 1）より先に手を付けるべき場面がある。

同点のときは記事の URL 名 → 観点名で安定させる。
安定させるのは、同じデータで開き直すたびに順が変わると
運用者が「昨日の続き」を再開できないためである。

## 指摘 1 件が持つもの

```ts
type SeoFinding = {
  id, siteSlug, articleSlug,
  checkKind, severity, state,
  detail,      // 何がどうなっているかを、現物の値で書く
  evidence,    // 機械が確かめた根拠。空は許さない
  suggestion,  // 提案する直し方。下書きの元。null 可
  assessedAt,
};
```

### `evidence` を必須にした

`validateFinding()` が空の根拠を弾く。

根拠を任意にすると、「なんとなく良くなりそう」な指摘が混ざる。
1 件混ざると、運用者はどれを信じてよいか分からなくなり、
**一覧そのものを見なくなる**。

これはこの層の存在理由そのものなので、型ではなく実行時の門にしてある
（外から作った指摘も通す必要があるため）。

## 指摘の扱いは 4 状態

`ASSESSMENT_STATES`:

| 値 | 表示名 | 意味 |
|---|---|---|
| `open` | 未対応 | 出したまま |
| `drafted` | 下書きあり | 下書きを作った |
| `applied` | 反映済み | 承認を経て公開面へ入った |
| `dismissed` | 対応しない | 運用者が直さないと判断した |

### `dismissed` を持つ理由

単に消すと、**次の診断でまた現れる**。

「この記事のタイトルはこれでよい」という判断は診断より強い。
運用者が一度決めたことが毎回流されると、一覧が信用を失う。

`dismissed` は理由が必須で、次の診断でも復活しない。

## 根拠が 3 件に満たない観点

`MIN_EVIDENCE_COUNT = 3`。

1 件だけの観測から「傾向」を語ると、
たまたま起きた 1 回に運用者を振り回すことになる。

提示層はこの数を下回る観点を「傾向」として出さない。
個別の指摘としては出す（それは 1 件でも真だから）。
