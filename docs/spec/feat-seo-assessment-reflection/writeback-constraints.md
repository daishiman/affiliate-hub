# 書き戻しの制約 — SEO の診断と反映 (feat-seo-assessment-reflection)

P02 の成果物。改善層が公開面へ何をしてよいか。

## 一行

> **診断から作れるのは下書きまで。公開面は承認なしに変わらない。**

`architecture/arch-blog-operations-console.md` の AD-3。
受入条件 5・6 がこれをそのまま条件にしている。

## なぜこの線を引くのか

自動反映は速い。だが**診断器が壊れた日に、
読者へ出ているものが黙って変わる**。

診断器は機械であり、間違える。
タイトルの文字数の数え方を 1 か所直しただけで、
翌日には全記事のタイトルが書き換わりうる。

読者に見えるものを機械の判断だけで変えない、という線を引く。

## 線をどこに引いたか

**ポートの形で引いた。**

```ts
draftFix(
  workspaceId: WorkspaceId,
  findingId: string,
): PortResult<{ readonly draftRevisionId: string }>;
```

戻り値は改訂の id だけである。

- 公開する関数が無い
- 記事本文を返す関数も無い
- 公開状態を変える引数も無い

**この口から公開面へ届く経路が存在しない。**
注意書きではなく、型がそうなっている。

呼び出し側はこの id を既存の編集画面へ渡す。
そこから先は、この feature が作ったものではない
既存の記事編集・承認経路が担う。

## 権限を 3 つに分けた

`manage-seo-assessment.ts`:

| 操作 | 要る権限 | 理由 |
|---|---|---|
| 指摘を見る | `content.read` | 記事を書く人が読む物である |
| 診断を回す・下書きを作る | `content.write` | 記事を直す作業の一部 |
| 「直さない」と決める | `site.manage` | 診断より強い判断で、次の診断でも復活しない |

3 つ目が重い。

「これは直さない」は**その指摘を将来にわたって消す**判断で、
記事 1 本を直す権限とは重さが違う。
ブログの運用を預かる人の側へ置いた。

d1 の「記事を書く人は「直さない」と決められない」で固定してある。

## 診断は報酬を入力にしない

ポート全体が `Editorial` 印である。

「報酬の高い記事から直す」は編集判断ではない。
それをこの層に入れると、SEO の指摘が
**収益の都合で並び替わる**ことになる。

§12.3 の口の分離がここにも効いていて、
この層は `BlogRevenuePort` を呼べない。

## 記録に残すもの

| 操作 | `audit_logs` の action |
|---|---|
| 診断を回した | `seo_assessment.ran` |
| 下書きを作った | `seo_finding.drafted` |
| 直さないと決めた | `seo_finding.dismissed` |

診断を回したこと自体を残すのは、
**指摘が消えた理由を区別する**ためである。

記事を直したから消えたのか、
診断器を差し替えて観点ごと無くなったのか、
指摘の行だけを見ても分からない。

`seo_finding.drafted` の記録には `published: false` を残す。
「下書きを作った」が「公開した」と読まれないようにするため。
`manage-blog-improvement` の「下書きを作っても、記録の行に
published: false が残る」で固定してある。

## 記録が書けなかったとき

**「下書きを作れた」と言わない。**

`auditWriteFailure` で失敗として返す。
記録の残らない変更は、後から誰が何をしたか辿れない。

これは repo 全体の書き込み口の作法で、
この feature 固有の判断ではない。
