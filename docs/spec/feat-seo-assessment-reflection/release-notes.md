# できたこと — SEO の診断と反映 (feat-seo-assessment-reflection)

P13 の成果物。

## 中学生にも分かる説明

ブログの記事を書いたあと、
「この記事、検索で見つけてもらいやすい形になってる？」を
機械が代わりに調べてくれる機能です。

調べる項目は 8 つあります。たとえば:

- タイトルが長すぎないか（60 文字が目安）
- 説明文が短すぎ・長すぎないか
- 見出しがちゃんと分かれているか
- 本文が薄すぎないか（800 文字未満は薄い）

見つかったことは「気になるところリスト」に並びます。
重いものから順に、ではなく
**「重さ × 何件あるか」**で並びます。

1 つだけの大問題より、
10 記事ぜんぶで起きている中くらいの問題のほうが
先に手を付けたほうがいいことがあるからです。

### 大事な約束が 3 つあります

**1. 根拠のないことは言いません。**

「なんとなく良くなりそう」は言いません。
機械が実際に数えた結果（「タイトルが 72 文字」など）が
必ずついてきます。

1 つでも根拠なしが混ざると、
その回の結果は**まるごと保存されません**。

**2. 勝手に記事を書き換えません。**

「こう直したら？」の**下書きまで**は作ります。
でも、それを公開するかどうかは人が決めます。

これは注意書きではなく、
**そもそも公開する機能が作られていない**からできません。

機械が間違えた日に、
読者が見ているページが黙って変わってしまうのを防ぐためです。

**3. 「これは直さない」と決めたら、それが残ります。**

人が「この記事のタイトルはこれでいい」と決めたら、
次に診断しても同じことは言われません。

決めたことが毎回ひっくり返されると、
リストそのものを見なくなってしまうからです。

### まだできていないこと

**記事を公開したときに、自動で診断は始まりません。**
今は画面のボタンを押したときだけ動きます。

**月に 1 回まとめて調べ直す仕組みもありません。**

**「このAIには読ませない」という設定もありません。**
このサービスは AI に読んでもらいたい方針なので、
拒否する仕組みをわざと作っていません。

## 専門的な説明

### 位置づけ

4 層のうち**改善層**。
`architecture/arch-blog-operations-console.md` の AD-3
（改善層は公開面へ書けない）を実装で担保する feature。

### 追加したもの

| 種別 | もの |
|---|---|
| 表 | `article_seo_assessment`（索引 2 本） |
| 領域 | `src/domain/seo/assessment.ts`（観点 8・重さ 3・状態 4・`rankFindings`） |
| 領域 | `src/domain/seo/guideline-reference.ts`（90 日見直し・2 段階の確認） |
| ポート | `SeoAssessmentPort`（`Editorial` 印） |
| 応用 | `manage-seo-assessment.ts`（権限 3 分割） |
| 実体 | `article-seo-analyzer.ts`（`SeoAnalyzer` の 1 実装） |
| 応用 | `structured-data.ts`（純関数の JSON-LD 組み立て） |

### AD-3 を型で守る

```ts
draftFix(workspaceId, findingId): PortResult<{ draftRevisionId: string }>;
```

**ポートに公開の口が無い。**
記事本文も返さず、公開状態を変える引数も無い。

自動反映を禁じる注意書きではなく、
その経路が型として存在しない。

### 権限を 3 つに分けた

| 操作 | 権限 |
|---|---|
| 指摘を見る | `content.read` |
| 診断・下書き | `content.write` |
| 「直さない」と決める | `site.manage` |

3 つ目が重いのは、その指摘を将来にわたって消す判断だから。

### 一意制約が設計の中心

```sql
UNIQUE (workspace_id, site_slug, article_slug, check_kind)
```

記事 × 観点 = 行 1 つ。診断は積み増しでなく置き換え。

`dismissed` は置き換えの対象外で、
運用者の判断が診断に上書きされない。

### 根拠を二重に強制

`validateFinding()`（実行時）+ `evidence NOT NULL`（表）。

外部から直接 INSERT しても根拠なしの行は作れない。

### 検証できないことは出さない

`image-alt` と `canonical` は観点の一覧にあるが 1 件も出さない。
`PublishedArticle` に画像の欄が無い（前者）、
正規 URL は住所層が決める（後者）ため、
**根拠を持てないから出さない**。

LLM を診断に使わないのも同じ理由。
同じ記事から違う指摘が出るものは根拠にできない。

### 既知の制限

1. 公開時の自動診断が無い（受入条件 1・未達）
2. 月次の再診断が無い（受入条件 2・未達）
3. クローラ拒否を robots.txt に出さない（受入条件 8・意図的に未達）
4. `dismissed` を `open` へ戻す口が無い
5. 指針の出典と診断の観点が対応表で繋がっていない

1 と 2 は配線が無いだけで、診断の中身は揃っている。
3 は方針として持たないと決めた（AEO と両立しないため）。
