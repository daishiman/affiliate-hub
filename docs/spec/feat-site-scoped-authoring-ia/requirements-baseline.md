# サイト所属型オーサリング IA — 要求ベースライン (P01)

feature: `feat-site-scoped-authoring-ia` / phase: P01 / graph node: `SYS-SITE-SCOPED-AUTHORING-IA-P01`

この文書は、受入 10 件 (A1–A10) を**実装前に一意で検証できる形**へ書き下したものである。
「良くする」「分かりやすくする」のような、後から判定が割れる書き方はここに置かない。

同時に作った機械可読の成果物:

- `route-inventory.json` — 既存 93 ルートの棚卸しと、作業の対象物への束ね直しマッピング
- `redirect-map-draft.json` — 旧 URL から新配置への対応の下書き

---

## 0. いま何が起きているか (現状の実測)

`src/presentation/ui/admin-route-metadata.ts` を機械で読み出した結果:

| 実測項目 | 値 |
|---|---|
| `src/app/admin/` 配下の `page.tsx` | 93 本 |
| サイドバーに出る一段目の入口 | 21 件 (ホームを除く) |
| 一段目をまとめている見出し | 6 件 (素材 / 書く / 出す / 稼ぐ / 見る / 整える) |
| 読者像・書き方の決め事の所属 | ワークスペース直下 (`/admin/personas/*`, `/admin/writing`) |
| ブログ 1 本の下にある画面 | 10 本 (`/admin/sites/[site]/*`) |

一段目の 6 見出しは**動詞**である (素材・書く・出す・稼ぐ・見る・整える)。
動詞で切ると、1 つの対象物についての作業が複数の見出しにまたがる。
たとえば「商品」は *素材*（商品を登録する）と *稼ぐ*（提携と成果）の両方に現れ、
運営者は「商品の話をしたい」と思ったときに 2 か所を見る必要がある。

`/admin/blog/articles` は、画面の中の**ブログ切替ドロップダウン**でどのブログの記事かを選ばせている
(`src/presentation/admin/publish/blog-site-switch.tsx`)。
選び忘れたまま別のブログの記事を読む形が、構造として作れてしまう。

## 1. 用語

| 語 | この文書での意味 |
|---|---|
| **作業の対象物** | 運営者が「これについて作業する」と言える単位。本 feature では **ブログ・記事・読者・商品・配信** の 5 つ。 |
| **一段目の入口** | サイドバーで、その下にさらに項目をぶら下げている見出し。ホームと常設の補助領域 (整える) は入口に数えない。 |
| **所属替え** | 画面の URL 上の住所を `/admin/<機能>` から `/admin/sites/[site]/<機能>` へ移すこと。保存されているデータの持ち主は変えない。 |
| **転送** | 旧 URL へのアクセスを、対応する新 URL へ `redirect()` で送ること。 |
| **ブログを特定できる** | 後述の解決順序 (§3) のいずれかで site の slug が 1 つに決まること。 |

## 2. 受入 A1–A10 の検証可能化

### A1. 読者像・書き方の決め事が `/admin/sites/[site]/` 配下に存在する

**検証方法 (機械)**: `ADMIN_ROUTE_METADATA` に次の 5 つの route id が存在し、
かつ対応する `src/app/admin/sites/[site]/...` の `page.tsx` が実在すること。

| route id | 画面 |
|---|---|
| `sites/[site]/authors` | 書き手 |
| `sites/[site]/authors/new` | 書き手を作る |
| `sites/[site]/audience/personas` | 読者像 |
| `sites/[site]/audience/personas/new` | 読者像を作る |
| `sites/[site]/writing` | 書き方の決め事 |

(route id の正本は `site-scoped-route-contract.md` §1。P02 で
`audience` 配下へ確定した。P05 task spec の produced artifacts と一致する。)

**判定が割れないようにするための断り**: 記事画面が site 配下にあるかは A1 では判定しない
(`feat-blog-scoped-admin-console` の受入)。

**既知の制約 (この phase で確定させる)**: `author_personas` / `audience_personas` は
`workspace_id` で持たれており、ブログ単位の列を持たない (`src/db/schema.ts`)。
本 feature は新しいデータモデルを作らない (P05 の Workstream: Data = N/A) ため、
**所属替えは住所の変更であって、データの持ち主の変更ではない**。
site 配下の画面は「このワークスペースの書き手・読者像を、このブログの文脈で見ている」ことを
画面上に明示する。明示しないと、他ブログの読者像をこのブログ専用のものと読み違える。

### A2. 旧 URL が、ブログを特定できるときは site 配下へ転送される

**検証方法 (機械)**: `redirect-map-draft.json` の `redirects` 全件について、
site を解決できる状態でアクセスすると `redirect()` が発火し、行き先が表の `to` と一致すること。

転送する 7 件と、転送しない 8 件・その理由は `redirect-map-draft.json` に列挙する。
転送しないものを「まだやっていない」ではなく**理由付きで転送しないと決めた**として残すのは、
後から「漏れているのでは」と再調査されないためである。

### A3. ブログを特定できない旧 URL はブログ選択へ送られる

**検証方法 (機械)**: 解決順序 (§3) が rank 5 (unresolved) に落ちたとき、
行き先が `/admin/sites` であること。エラー画面でも 404 でもない。

### A4. site セグメントが解決できないとき `notFound` になり、他ブログの内容が出ない

**検証方法 (機械)**: `/admin/sites/<存在しない slug>/personas` などへアクセスしたとき、
`notFound()` が投げられること。かつ、応答の中に他ブログの名前・slug が 1 件も含まれないこと。

**現状との差**: いまの `/admin/sites/[site]/page.tsx` は解決できなくても `ErrorView` を出して
画面を描いている。これは「ブログ名が出ないだけで骨格は出る」状態で、
URL を打ち間違えた人に「このブログは存在するが読めない」と読ませる。存在しないなら無いと言う。

### A5. 一段目の入口が、作業の対象物の数まで畳まれている

**検証方法 (機械)**: `ADMIN_NAV_GROUPS.length === 5` かつ、その 5 件の id が
`blog` / `article` / `reader` / `product` / `delivery` と一致すること。

**畳み方**: `route-inventory.json` の `work_object` 列が、93 ルート全件の行き先を持つ
(`unassigned_entries` が空)。内訳:

| 対象物 | 一段目に寄せる入口 | ルート数 |
|---|---|---|
| ブログ | `sites`, `site-network`, `blog`, `analytics` | 28 |
| 記事 | `content`, `generation`, `evidence`, `rankings`, `improvement`, `writing`, `personas` (書き手) | 27 |
| 読者 | `contact`, `feedback` | 5 |
| 商品 | `products`, `affiliate`, `inbox` | 11 |
| 配信 | `distribution` | 5 |
| (補助領域) | `settings`, `ai-usage`, `tools`, `ui-catalog` | 16 |
| (ホーム) | `` | 1 |

**補助領域を入口に数えない理由**: 設定・AI の利用と費用・道具・画面部品の見本は、
運営者が「これについて作業する」と言う対象物ではない。
5 つの対象物に無理に混ぜると、たとえば設定を「配信」に置くことになり、
ラベルから中身が言い当てられなくなる (A6 と矛盾する)。
補助領域はサイドバー下部の常設帯として、対象物の群とは別の領域に置く。

### A6. 一段目のラベルから、何ができるかが言い当てられる (正答率 90% 以上)

**検証方法 (機械の部分)**: 5 つのラベルが `feat-reference-blog-admin-ux` の動詞ラベル規則に従うこと。
規則の正本は同 feature にあるので、本 feature は**適用しているか**だけを検査する。

**検証方法 (人の部分)**: 初見の運営者にラベル一覧だけを見せ、各入口でできることを言い当てさせる。
正答率 90% 以上。**これは人を集めないと満たせない。** 集められない場合は
P07 の判定を FAIL ではなく `BLOCKED (外部参加者が必要)` として記録し、
機械で確かめられる部分 (規則への適合) だけを PASS にする。
`feat-reference-blog-admin-ux` が同じ理由で停止しているので、判定の扱いを揃える。

### A7. 書き方の決め事を共通の雛形から複製する経路が存在する

**検証方法 (機械)**: 共通の雛形 (domain の定義) から、ブログ 1 本ぶんの書き方の決め事を作る
純粋関数が存在し、`/admin/sites/[site]/writing` がその出力を描いていること。
かつ、その画面から複製元 (共通の雛形) へ戻る導線があること。

**制約**: `createReadWritingMethodUseCase()` は保存先を持たない読み取り専用で、
書き方の決め事の保存先は存在しない (`src/db/schema.ts` に該当表なし)。
新しいデータモデルを作らない制約下では、複製は**読み出しのたびに雛形から作る**形にする。
ブログごとの上書きを保存する経路は本 feature の対象外とし、P10 の残課題として明記する。

### A8. よく使う画面への近道があり、到達クリック数が畳む前以下

**検証方法 (機械)**: 束ね直しの前後で、`route-inventory.json` に載る全ルートについて
サイドバーからの到達クリック数を数え、後 ≤ 前 であること。

**設計上の担保**: 一段目を 5 群にしても、群の下の項目はこれまで通り**畳まずに全部出す**。
畳んだのは見出しの数であって項目の数ではないので、既存画面の到達クリック数は変わらない。
所属替えで 2 クリックになりうる画面 (site 配下へ移った読者像・書き方の決め事) は、
サイドバーの旧入口を消さずに残し、その行き先を転送の殻にすることで 1 クリックを維持する
(`shortcut-contract.md` §2)。新しい帯は足さない。

### A9. 危険な操作に確認が挟まり、下書きの編集には挟まらない

**検証方法 (機械)**: ブログ設定・ドメイン・公開の各操作が確認を挟む経路を通ること。
下書きの編集は挟まないこと。分岐の規則そのものは `feat-reference-blog-admin-ux` が正本なので、
本 feature は**新設した画面がその規則から外れていないか**だけを検査する。

### A10. 新しい集計表を追加していない

**検証方法 (機械)**: 本 feature が触った範囲に、`site_daily_metrics` / `article_daily_metrics`
以外の集計表への参照が 0 件であること。`drizzle/` 配下に新しい migration が 0 件であること。

## 3. ブログの解決順序 (転送の前提)

旧 URL からブログ 1 本を決める順序。上から順に試し、決まった時点で止める。

| 順 | 根拠 | 決め方 |
|---|---|---|
| 1 | path | 旧 URL 自身が site セグメントを持つならそれ |
| 2 | query | `?site=<slug>` があればそれ |
| 3 | cookie | 直近に開いていたブログ (`ah_last_site`) |
| 4 | 1 本だけ | ワークスペースにブログが 1 本しか無ければそれ |
| 5 | 決まらない | `/admin/sites` (ブログ選択) へ送る = A3 |

**cookie を 3 番目に置く理由**: query より先に見ると、リンクで明示的に指定したブログを
「前に開いていた別のブログ」で上書きしてしまう。明示は常に記憶より強い。

**1 本だけを 4 番目に置く理由**: 2 本目を作った瞬間に挙動が変わる。
それより上に置くと、cookie を持っている人と持っていない人で行き先が食い違う。
