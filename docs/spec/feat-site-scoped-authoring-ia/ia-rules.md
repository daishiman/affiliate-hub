## 0. 何を守るための規則か

畳んだ入口は、放っておくと元に戻る。戻り方はいつも同じで、
**画面を 1 枚足すときに「どこに置くか」を考えず、置きやすい場所に置く**ことによる。
1 枚では誰も困らないが、20 枚で元の 93 本に戻る。

だから規則は「気をつける」ではなく、**外れたら機械が落ちる形**で書く。
以下の各節は、対応する検査を必ず 1 つ持つ。

---

## 1. 一段目は「作業の対象物」であって、機能ではない

一段目の分類は 5 つだけである。

| id | ラベル | 何についての作業か |
|---|---|---|
| `blog` | ブログ | ブログそのもの（版面・つながり・サイト設定） |
| `article` | 記事 | 記事とその材料（根拠・評価基準・書き手・書き方） |
| `reader` | 読者 | 読者（読者像・評価・購読） |
| `product` | 商品 | 商品と提携 |
| `delivery` | 配信 | 配信の経路と実績 |

**正本は `src/presentation/ui/admin-route-metadata.ts` の `ADMIN_NAV_GROUP_LABELS` 1 箇所**である。
サイドバーもホームのボードもパンくずも、この表からの射影で、第 2 の表を持たない。

### 規則 1-a: 動詞で切らない

かつて一段目は「素材 / 書く / 出す / 稼ぐ / 見る / 整える」だった。
このとき **1 つの対象物についての作業が複数の見出しに散った**。
「商品」は *素材*（登録する）と *稼ぐ*（提携と成果）の両方にあり、
運営者はどちらを開くか決められず、結局両方開いた。

対象物で切ると、**「これについて作業する」と言えるものが 1 か所に集まる**。
新しい分類を足したくなったら、まず「それは作業の対象物か」を問う。
「AI の費用」「道具」「画面部品の見本」は対象物ではない。

### 規則 1-b: 5 つに無理に混ぜない — `group: null` を使う

対象物と言えないものは `nav.group` を `null` にして分類の外へ置く。
無理に 5 つのどれかへ入れると、**ラベルから中身が言い当てられなくなる**。
「設定」を「ブログ」に入れると、「ブログ」を開いた人が設定を探すことになる。

### 規則 1-c: 一段目を 6 つ目に増やすときの条件

増やしてよいのは次の 3 つが同時に成り立つときだけである。

1. それが**作業の対象物**である（「〜について作業する」と言える）
2. 既存 5 つのどれに入れても、ラベルから中身が言い当てられない
3. その対象物に属する画面が**2 枚以上**ある（1 枚なら既存の子で足りる）

**検査**: `tests/acceptance/feat-admin-cognitive-load-ui/ledger-contract.test.ts`（情報台帳と route 数の一致）
/ `tests/acceptance/site-scoped-redirect-map.test.ts` A5 群

## 2. ブログに属する画面は `/admin/sites/[site]/` の下に置く

### 規則 2-a: 判定は「ブログを跨いで 1 組か、ブログごとに 1 組か」

- **ブログごとに違ってよいもの** → `/admin/sites/[site]/` 配下
- **全ブログで 1 組しか無いもの** → `/admin/` 直下

書き手・読者像・書き方の決めごとは前者へ移した。
ブログを 5 本運営していて「誰の立場で書くか」が 5 本まとめて 1 つなのは、
運営の実態と合っていなかった。

### 規則 2-b: site を読む**前に**site を確かめる

`/admin/sites/[site]/` 配下の画面は、**中身を読む前に必ず `resolveSiteOrNotFound(site)` を通す**。

```
const { siteSlug, siteName } = await resolveSiteOrNotFound(site);   // 先
const authors = await (await personaUseCases()).listAuthors.execute(actor, {});  // 後
```

順番が逆だと、**存在しないブログの住所でも一覧が出る**。
書き手はワークスペース単位で持っているので、site を確かめない限り
`/admin/sites/no-such-blog/authors` が中身付きで描画されてしまう。

`getSite` が失敗したときは理由を言い分けずに `notFound()` を返す。
「権限がありません」と「ありません」を出し分けると、
**住所を打ち込むだけで他ワークスペースのブログの存否が読み取れる**。

### 規則 2-c: データ層は動かさない

**画面（住所）が site 配下へ移っただけで、データはワークスペース単位のままである。**
書き手も読者像も `workspaceId` で引く。

これは手抜きではなく選択である。データを site 単位へ割り直すと、
既存ブログ全部に移行が要り、新規ブログを足すたびに初期データの作成が要る。
住所だけを移せば、**新しいブログを足した瞬間から書き手も読者像も配下に見える**
（`operations.md` §3 で確認する）。

ブログ固有の書き手が要るという要望が出たときに初めて、データ層を割る。
そのときの決めごとは `final-review.md` §5 に 3 点挙げてある。

**検査**: `tests/presentation/site-scoped-entry.test.ts` / `site-scoped-redirect-map.test.ts` A4 群

## 3. 旧 URL は消さずに転送で受ける

### 規則 3-a: 転送先が**存在してから**転送を置く

`/admin/content/*` をまだ転送していないのはこの規則による。
転送先の `/admin/sites/[site]/articles` が存在しないので、
先に殻を置くと**旧 URL が今より確実に壊れる**。

移設は、受け皿が立ってからでなければ移設ではなく破壊である。

### 規則 3-b: 転送の殻は転送だけをする

殻になった画面は `legacyAdminRedirect` を呼ぶ以外のことをしない。
DOM を持たず、`redirectOnly: true` を立てる。
殻に少しでも表示を残すと、**同じ画面の実装が 2 か所**になり、
片方だけ直された状態が静かに生まれる。

### 規則 3-c: ブログを特定できないときは例外にせずブログ選択へ出す

cookie が無い / 一覧が引けない / `?site=` が配列 / 対応表に無い住所 ——
**どの不調でも `/admin/sites`（ブログ選択）へ出す**。
外の世界が期待どおり返らなかったことを利用者の画面に例外として見せない。

### 規則 3-d: 旧入口をサイドバーから消さない

殻になっても、サイドバーの入口としては残す。
消すと、**旧来 1 クリックで開けていた画面が 2 クリックになる**。
畳み直しは到達クリック数を増やさない範囲でしか正当化できない（A8）。

**検査**: `tests/acceptance/site-scoped-redirect-map.test.ts` A2/A3/A8 群 /
`tests/presentation/site-scoped-redirect.test.ts`

## 4. 書き方の決めごとは「重み」だけをブログごとに変える

`/admin/sites/[site]/writing` が出しているのは、
**共通の雛形を、そのブログの型（比較・順位・レビュー…）で重み付けした複製**である。

**節も文体の決まりも共通のまま**で、変わるのは
「このブログの型で特に外せない節に印が付く」ことだけ。

決めごとを丸ごと複製すると、**10 本のブログで 10 通りの決まり**ができ、
公開前の検査がどれを見るか決まらなくなる。
この画面と公開前の検査は、コードの中の**同じ 1 つの定義**を読んでいる。
手引きを別文書として書けば、どちらかが必ず古くなり、
「手引きどおりに書いたのに検査で落ちる」が起きる。

**規則**: 書き方の決めごとに関する説明を、この画面の外に別文書として書かない。

**検査**: `clone-writing-method-for-site.ts` / `pattern-writing-emphasis.ts`（いずれも被覆 100%）

## 5. 動詞ラベルと危険操作 — 適用する側であることの明示

これら 2 つの**規則そのものの正本は `feat-reference-blog-admin-ux`** であり、
本 feature は適用する側である。ここでは適用時に守ることだけを書く。

### 規則 5-a: ラベルは「何ができるか」を日本語の動詞で言う

`書き手を作る` / `記事を直す` のように、押した結果が言い当てられる形にする。
`管理` `設定` `一覧` のような名詞は、何ができるか分からない。

**1 つのラベルに 2 つの対象物を束ねない。**
「書き手と読者像」というラベルは、開くまで何の画面か分からなかったので
「書き手」に分けた（書き手は読者ではないので `reader` ではなく `article` に置く）。

### 規則 5-b: 危険操作を新設画面に持ち込まない

`deleteSite` / `publishSite` / `updateDomain` / `deleteArticle` は
**取り消せない、または外から見える**操作である。
新しい画面にこれらを足すときは、規則の正本側の確認分岐に従う。

本 feature の新設 5 枚はこれらを 1 つも呼んでいない。
下書きの編集に確認を挟まないのも規則であって、手抜きではない。

**検査**: `tests/acceptance/site-scoped-redirect-map.test.ts` A9 群（母集団の床つき）

## 6. 正本を増やさない（この規則が全体を支えている）

route を 1 本足すと、次の 5 つが同時に整合を要求してくる。

| 表 | 何を持つ |
|---|---|
| `admin-route-metadata.ts` | route の正本（99 本） |
| `ADMIN_NAV_GROUPS` | サイドバー（正本からの射影） |
| `screen-information-ledger.json` | 情報台帳 |
| `admin-disclosure-contract.ts` | 進行開示 |
| `tests/ui/route-cases.ts` | 描画と axe の対象（正本からの射影） |

**これらは手書きの一覧ではなく、正本からの射影である。**
だから「画面は足したが検査の一覧に足し忘れた」という抜け方ができない。

```ts
const ADMIN: readonly RouteCase[] = ADMIN_ROUTE_METADATA.map((route) => { ... });
```

新しい表を作りたくなったら、**まず既存の正本から射影できないかを疑う**。
射影できるものを別表にすると、その日から 2 つの表がずれ始める。

**検査**: `tests/architecture/open-doors.test.ts` / `generated-doc-freshness.test.ts` /
`ledger-contract.test.ts`
