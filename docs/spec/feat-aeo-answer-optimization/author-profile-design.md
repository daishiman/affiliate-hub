# 名乗りの設計 — 回答エンジン最適化 (feat-aeo-answer-optimization)

P02 の成果物。誰が答えているかを機械へ渡す形。

## なぜ名乗りが AEO の話なのか

回答エンジンは、答えを引くときに
**誰が言っているか**を重みにする。

同じ内容でも、名乗る主体が辿れる記事のほうが引かれやすい。
これは E-E-A-T（経験・専門性・権威性・信頼性）の考え方で、
検索でも回答でも同じように効く。

## 出すもの

`buildPerson`（`structured-data.ts`）:

| キー | 中身 |
|---|---|
| `@type` | `Person` |
| `name` | 名前 |
| `url` | `/authors/<slug>` |
| `description` | 読み取りモデルの `bio` |
| `hasCredential` | 資格（**0 件ならキーごと省く**） |

役割は 2 つ:

| 役割 | いつ出るか |
|---|---|
| `author` | 常に |
| `contributor` | 監修者が付いているときだけ |

## `url` を常に出す

```
著者は実在する著者ページの URL を持ち、資格 0 件なら hasCredential を出さない
```

著者ページ `/s/[site]/authors/<slug>` は公開ルートとして常に実在する
（`view-model.ts` の `authorHref` と同じ道）。

**辿れる URL しか出さない。**

```
著者ページを持たないので url を出さない（存在しない住所へ送らない）
```

`ItemList` の商品側にもこの原則がある。
`reviewSlug` を持つ商品だけが URL を持つ。

存在しない URL を出すと、
機械はそこへ行って 404 を受け取る。
名乗りの信頼を下げる方向に効く。

## 資格 0 件でキーごと省く

```ts
...(person.credentials.length === 0
  ? {}
  : { hasCredential: person.credentials.map(...) })
```

`hasCredential: []` は「資格を持っているが、それは空である」と読める。

**「資格の無い資格持ち」という嘘の構造**になる。

資格が無いことは何も悪くない。
悪いのは、資格の欄を持っていて空にすることである。

## `description` は `bio` をそのまま

```
人物の説明文は読み取りモデルの bio をそのまま出す（著者・監修者とも）
```

構造化データ用に別の紹介文を作らない。

作ると、**読者が読む紹介文と機械が読む紹介文が別々に育つ**。
どちらが本当かが分からなくなる。

## 監修者を `contributor` にした

```
監修者が付いていないなら contributor を出さず、付いていれば Person で出す
```

`author` にまとめない。

書いた人と監修した人は役割が違う。
schema.org には両方の型があるので、区別して出す。

区別しないと、
「この人が書いた」と「この人が確認した」が同じに見える。

## ブログ側の名乗り

`SiteAeoProfile.publisherName`。

記事の著者とは別に、**ブログとして名乗る主体**がある。

構造化データの発行元になるので、
表示用の名前ではなく法的・実質的な主体として扱う。

### 記事の著者と分けた理由

著者は記事ごとに変わる。
発行元はブログ全体で 1 つである。

回答エンジンから見ると、
「この記事は誰が書いたか」と
「このブログは誰が出しているか」は別の問いになる。

## 構えの他の欄との関係

| 欄 | 誰への答えか |
|---|---|
| `topicScope` | 「このブログは何に答えるか」 |
| `audience` | 「誰の問いに答えるか」 |
| `publisherName` | 「誰が出しているか」 |

3 つ揃って初めて、
回答エンジンから見て「この領域のこの人たちの答え」になる。

1 つでも空だと、記事がよくても
どの文脈に置いてよいか機械が決められない。

**だから行が無いときに既定値を返さない**（`data-model.md`）。
空の構えを「決まっている」と見せない。
