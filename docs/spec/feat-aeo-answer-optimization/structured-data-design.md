# 構造化データ — 回答エンジン最適化 (feat-aeo-answer-optimization)

P02 の成果物。受入条件 9。
正本は `src/application/seo/structured-data.ts`（295 行・全部純関数）。

## 何を出すか

| 型 | いつ |
|---|---|
| `BlogPosting` | 記事ごとに常に |
| `Person`（author / contributor） | 著者・監修者 |
| `FAQPage` | FAQ が 1 件以上あるとき |
| `ItemList` | 順位表があり順位が 1 件以上あるとき |

## 回答エンジンにとっての意味

`FAQPage` が AEO の中核である。

問いと答えの対を**機械が読める形で**渡すもので、
本文を読ませて推測させるより確実に構造が伝わる。

`article_answer_unit` が持つのと同じ「問いと答え」を、
公開面から機械へ渡す口である。

## 0 件のときは `null` を返す

```
0 件なら null（質問の無い FAQ という嘘の構造を出さない）
ranking が無い・順位 0 件なら null（順位の無い順位表を出さない）
```

**空の構造は嘘である。**

`FAQPage` に `mainEntity: []` を出すと、
「FAQ を持っているが、その中身は空」と読める。
実際は FAQ が無い。

## 資格 0 件のときキーごと省く

```ts
...(person.credentials.length === 0
  ? {}
  : { hasCredential: person.credentials.map(...) })
```

`hasCredential: []` は「資格の無い資格持ち」。

E-E-A-T で誰が言っているかが問われる場面で、
空の資格欄を出すのは名乗りとして悪い。

## `</script>` を閉じさせない

```
値の中の < を < に逃がす（</script> でタグを閉じさせない）
```

JSON-LD は `<script type="application/ld+json">` の中に置く。

記事の本文に `</script>` という文字列が含まれると、
**そこでタグが閉じて、残りが HTML として解釈される**。

JSON としては正しいのに、HTML としては壊れる。
`<` を `<` に逃がすと、
JSON の意味を変えずにこれを防げる。

**この 1 件が安全側の要である。**

## URL を組み立て直さない

記事の URL は `articleHref` から引く。

構造化データの中で組み立て直すと、
画面のリンクと構造化データの URL がずれる。
ずれても画面は正しく見えるので、検索エンジン側でしか気づけない。

## 画面と同じ射影から作る

`expressionBlocksOf(article)` を使う。

`sections[].claims[].evidence` を自前で辿り直すと、
重複のまとめ方や期限切れの扱いが監査と別々に育ち、
公開判定と機械へ渡す出典が食い違う。

## まとめ（`abstract`）の扱い

```
まとめの節があれば abstract に本文をそのまま写す
表現ブロックのまとめは carrier JSON ではなく読者に見える本文を写す
壊れた summary carrier は通常本文へ fallback せず abstract へ出さない
まとめの節が無ければ abstract を出さない
```

`abstract` は回答エンジンが真っ先に読む場所である。

**読者に見えていない文をここに出さない。**
carrier JSON（内部表現）ではなく、
実際に読者が読む本文を写す。

壊れた carrier のときに通常本文へ落とさないのは、
**読者が見ているものと違う要約を機械に渡すことになる**から。
出さないほうがましである。

## 未公開の記事に公開日を出さない

```
まだ公開していない記事に公開日を出さない
```

日付は機械が鮮度の判断に使う。
存在しない公開日を出すと、鮮度の嘘になる。

## `structuredDataEnabled` との関係

ブログの構えに
「回答エンジン向けの構造化データを出すか」の欄がある。

この欄が false のときに `FAQPage` を出さない配線は、
**公開面（`src/app/s/[site]/`）の責務**である。

改善層は構えを保存するところまでで、
公開面へは書けない（AD-3）。
