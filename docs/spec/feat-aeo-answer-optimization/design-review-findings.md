# 設計の見直しで出たこと — 回答エンジン最適化 (feat-aeo-answer-optimization)

P03 の成果物。実装を読み直して見つけたこと。

## F-01 引用されたかを測っていない

**この feature は成果を測れない。**

抽出した単位が実際に回答エンジンに引かれたかどうかを
知る手段が無い。

### なぜ測らないか

回答エンジンによっては引用元を示さない。
示す場合も、アクセスは読者の User-Agent で来る。

**測れないものに数字を出すと、
その数字を根拠に判断が行われる。**
測っていないより悪い。

`requirements-baseline.md` に「作らないもの」として書いた。

### 何を代わりに見るか

隙間（`gaps`）の件数である。

「引かれやすい形になっているか」は測れる。
「引かれたか」は測れない。

前者だけを扱う。

## F-02 指示語の判定が荒い

```ts
if (/^(これ|それ|あれ|この|その|あの|こう|そう)/.test(unit.answer.trim())) {
  gaps.push("ambiguous-subject");
}
```

- 偽陽性: 「これから説明します」は曖昧ではない
- 偽陰性: 「同社は」で始まる答えは曖昧だが引っかからない

### 許容している

指摘であって禁止ではない。
運用者が見て「これは大丈夫」と判断できる。

指示語で始まる文が単体で引用されると
**高確率で意味が壊れる**ので、
偽陽性のほうが偽陰性より安い。

ただし**偽陽性が多いと一覧が信用を失う**というのは
SEO 側と同じ危険で、割合を測っていない。

## F-03 隙間 6 種のうち 2 種を `detectGaps` が出さない

| 隙間 | `detectGaps` |
|---|---|
| `answer-too-long` | 出す |
| `buried-answer` | 出す |
| `unsourced-claim` | 出す |
| `ambiguous-subject` | 出す |
| `no-direct-answer` | **出さない** |
| `missing-qa-markup` | **出さない** |

理由は `answer-unit-catalog.md`。
どちらも単位 1 つを見ても判定できない。

`no-direct-answer` は「単位が 0 件」という記事全体の事実。
`missing-qa-markup` はブログの構えの `structuredDataEnabled` で決まる。

**一覧の値としては存在するのに、誰も出さない。**

画面側でこの 2 つを組み立てられるかは
管理画面の側の宿題である。

## F-04 出典が消えた履歴を持たない

抽出は置き換えなので、
`sourceRef` が `null` に変わっても行の差分に残らない。

監査に残るのは件数だけ。

**根拠のあった断定から根拠が消えたことに気づけない。**

`citation-ledger-design.md` の末尾に書いた。

## F-05 抽出が公開済み記事しか見ない

```ts
if (row === undefined) return [];
```

取り下げた記事・未公開の記事からは 1 件も取らない。

0 件は失敗ではなく「引用できる形になっていない」という結果である。

### 副作用

**記事を取り下げると、次の抽出でその記事の単位が全部消える。**

これは正しい（公開していないものが引用されてはいけない）が、
再公開したときに抽出をやり直す必要がある。
自動ではやり直されない。

## F-06 抽出が自動で回らない

SEO 側と同じ問題である。

`extract` は管理画面から押したときだけ回る。
記事を公開しても自動では回らない。

**古い引用単位が残り続ける。**

`extracted_at` を見れば古さは分かるが、気づくのは人である。

## F-07 位置の比率が節の番号でしか決まらない

```ts
const ratio = total <= 1 ? 0 : index / (total - 1);
```

節が 3 つなら 0 / 0.5 / 1。

**節の長さを見ていない。**

短い節が 10 個並ぶ記事と、
長い節が 3 個の記事で、同じ比率が別の意味になる。

### FAQ と一文の結論は 0 を入れている

```
FAQ と一文の結論は 0 を入れる。どちらも記事の後ろに描かれるが、
構造化データとして単体で名指しできる塊なので、
本文の奥にある段落とは事情が違う。
```

**ここを節と同じ扱いにすると、
正しく作った FAQ が毎回「埋もれている」と指摘され、
本当に埋もれている答えが埋もれる。**

この例外は正しいが、
「位置比が何を意味するか」が種類によって違うことになる。
一覧で並べたときに比べられない。

## F-08 同じ問いの重複解決が「先勝ち」

```ts
const seen = new Set<string>();
return units.filter((unit) => { ... });
```

一文の結論（記事タイトルを問いとする）が最初に来るので、
**タイトルと同じ問いの FAQ があると FAQ 側が捨てられる**。

記事の前のほうを優先する方針としては一貫しているが、
FAQ のほうが答えとして良く書かれていることが多い。

### 測っていない

実際にこの衝突が起きる頻度を測っていない。

## F-09 構えが 1 つでも空だと機能しないが、空を止めていない

`topicScope` / `audience` / `publisherName` の 3 つが
揃って初めて意味を持つ（`author-profile-design.md`）。

`save_profile` は前後の空白を落とすが、
**空文字での保存を拒んでいない**。

行が無い（`null`）と、行があって全部空、が別の状態になる。
画面から見ると前者は「決めていない」、後者は「決めた（空で）」。
