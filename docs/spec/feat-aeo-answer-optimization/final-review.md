# 最終確認 — 回答エンジン最適化 (feat-aeo-answer-optimization)

P11 の成果物。

## アーキテクチャ決定との照合

正本は `architecture/arch-blog-operations-console.md`。

### AD-1 一方向依存（住所 → 観測 → 改善 → 提示）

守っている。

`article_answer_unit` は記事（公開面）を読むだけで、
観測層（`site_daily_metric` など）も改善層の他の表も参照しない。

`site_aeo_profile` はどこも参照しない。

### AD-2 提示層で計算しない

守っている。

`detectGaps` を呼ぶのはユースケース
（`manage-aeo-answers.ts`）であって画面ではない。

画面（`/admin/sites/[site]/aeo`）は
`AEO_GAP_LABEL` で名前に置き換えるだけ。

usecase「長すぎる答えと埋もれた答えを、画面に代わって数える」が
この境界をテストで固定している。

### AD-3 改善層は公開面へ書けない

守っている。

抽出しても記事は変わらない。
`FAQPage` は公開面が記事から独自に組み立てる
（`delivery-path-diagram.md` の「2 本の線が交わらない」）。

**同じ FAQ から 2 つの写しを作っている**が、
片方を他方から作らないことでこの境界を保っている。

### AD-4 生イベントは 90 日で捨てる

この feature は生イベントを持たない。該当しない。

`article_answer_unit` は抽出のたびに置き換わるので、
時間による掃除が要らない（`migration-notes.md`）。

### AD-5 `site_slug` が唯一の結合キー

守っている。

両表とも `(workspace_id, site_slug)` を持ち、
数値 ID による結合を持ち込んでいない。

## §12.3 の口の分離との照合

`BlogAudiencePort`（`Editorial` 印）/
`BlogRevenuePort`（`Commercial` 印）。

AEO は `Editorial` 側にある。

**収益を入力にしていない。**

「売れている記事を優先して抽出する」ような配線を作っていない。
引用されやすさは収益とは別の軸である。

## それでも出せる理由

### 弱点 1 は設計上の判断である

測れないものを測ったふりをしない、というのは
この製品の他の場所でも通している方針
（「空文字 200 を返さない」と同じ性質）。

**測っていないことを文書に書いた**ので、
数字が無いことを誰かが「まだ実装されていない」と
読み違えることはない。

### 弱点 2 は運用で埋まる

`operations-runbook.md` に
「記事を公開したら抽出を押す」と書いた。

自動化されていないことを知っていれば運用できる。
知らないまま古い単位が残るのが危ない。

### 弱点 3 は受入条件で「一部」と申告した

隙間の一覧に載っているのに一度も出ない値があることを
達成と書かなかった。

### 弱点 6 はこの feature が作ったものではない

上限を上げれば緑になるが、上げていない。
原因（隣の feature の除外追加）を `quality-report.md` に書いた。
