# 足りない数字の扱い — 日次集計 (feat-blog-metrics-rollup)

P02 の成果物。受入条件 7「集計元の件数が閾値未満の日に、示唆に足りないことを示す列が立つ」の設計。

## 3 つの「無い」を区別する

運営者が画面で数字を見るとき、値が小さいことには 3 通りの理由がある。

| 状態 | 意味 | 画面での見え方 |
|---|---|---|
| 集計行が無い | まだ集計していない / 観測が 1 件も無かった | 行が出ない |
| 集計行があり `sample_count` が小さい | 観測はあるが少ない | 数字は出る・解釈は伏せる |
| 集計行があり値が 0 | 観測はあったが、その種類が無かった | 0 と出る |

この 3 つが混ざると、運営者は**計測の故障に気づけなくなる**。
「数字が出ない」を全部同じ見た目にすると、cron が 3 日止まっていても
「今週は誰も来なかったのだな」としか読めない。

## 観測が無い日に 0 の行を書かない

`pendingDays()` は生イベントの側から対象を数え上げる。
観測が 0 件の (ブログ, 日) は返らないので、集計行も作られない。

ブログ一覧から回して全ブログ × 全日を 0 で埋める案は採らなかった。
0 の行を書くと、上の表の 1 行目と 3 行目が区別できなくなる。

## 少なすぎる日の判定

`sample_count` を持ち、`evidenceVerdict(rows, minimum)` が判定する。

```ts
export const MIN_EVIDENCE_SAMPLES = 30;
```

30 は「割合の推定が使い物になり始める」目安として広く使われる値で、
厳密な検定の閾値ではなく**足切り**として使う。

5 件の観測から「この置き場所のクリック率が高い」と言うと、
運営者は 1 人の読者の偶然を仕様だと思って版面を作り替えてしまう。

## 数字は出す。伏せるのは解釈だけ

`evidenceVerdict` の doc に書いた判断:

```
数字そのものは足りなくても出す。伏せるのは解釈の側だけである。
数字ごと隠すと、運営者は「観測が動いていない」のか「まだ少ない」
のかを区別できず、計測の故障に気づけなくなる。
```

返り値は 3 つ組:

```ts
{ sufficient: boolean, sampleCount: number, reason: string | null }
```

`reason` は足りないときだけ入る:

> 観測が 12 件しかありません（示唆を出すには 30 件が要ります）。

**件数を文面に含めている**のが要点で、「足りません」だけだと、
あと 1 件なのか 29 件足りないのかが分からない。運営者は
「もう少し待てば見えるのか、そもそも人が来ていないのか」を判断できない。

## 期間で足す

`evidenceVerdict` は行の配列を受け取り `sample_count` を合計する。
1 日では 30 件に届かなくても、7 日ぶんで届けば示唆は出せる。

日ごとに判定すると、小さいブログではどの日も足りず、
示唆が永久に出ないことになる。

## 0 除算の扱い

`clickThroughRate` / `revenuePerView` は `views === 0` のとき 0 を返す。

`null` にしない理由は並べ替えである。`null` を混ぜると、表の並べ替えで
「まだ誰も見ていない記事」が最上位にも最下位にも来うる。

ただし **0 の率と「率が計算できない」は意味が違う**。
この区別は `sample_count` と `views` を画面が併記することで担保する。
提示層（feat-blog-scoped-admin-console）の責務として引き渡した。

## `computed_at` を併記する

集計行は `computed_at` を持つ。画面がこれを出すことで、
「数字が古い」と「動きが無い」を運用者が区別できる。

出さないと、cron が止まったことに誰も気づかない。
