# 設計レビューの指摘 — 日次集計 (feat-blog-metrics-rollup)

P03 の成果物。P02 の設計に対して見つけた問題と、どう決着したか。

## F-01: 受入条件 3・4 が実装では成り立たない（重大・仕様側を訂正）

**指摘**: 「記事の売上合計がブログの売上合計と一致する」は、記事に紐づかない
閲覧（トップ・一覧・タグページ）が存在する限り成り立たない。

**検討した案**:

| 案 | 却下の理由 |
|---|---|
| 記事外の閲覧をどれかの記事へ割り当てる | 読まれていない記事が読まれたことになる。数字が嘘になる |
| 記事外の閲覧を集計しない | 「トップに人は来ているが記事に流れていない」が見えなくなる。運営判断の主要な材料が消える |
| `article_slug = ''` の擬似記事を置く | 一覧に空の記事が出る。表示側で毎回除外が要り、除外し忘れが必ず起きる |

**決着**: 不等号（`Σ記事 ≤ ブログ`）を正しい関係とし、受入条件の記述不足として
`requirements-baseline.md` に申告した。テストは等号ではなく不等号を検証する。

## F-02: DELETE + INSERT だと売上が消える（重大・実装を変更）

**指摘**: 仕様書は「対象日の行を DELETE してから INSERT」と書いていたが、
`revenue_minor` / `conversions` は観測イベントから出ず、報酬側が別経路で
同じ行へ書く。DELETE すると再集計のたびに報酬の記録が消える。

**決着**: upsert にし、`set` から売上と成果を除外した。
理由をコード内コメントとして残した（消されると気づけないため）。
詳細は `idempotency-contract.md`。

## F-03: DELETE の直後に行が無い瞬間がある（重大・F-02 と同じ変更で解消）

D1 は単一 Worker 実行内でしか transaction を張れない。DELETE 直後に画面が
読むと、その日の数字が 0 として表示される。upsert なら行は常に存在する。

## F-04: 平均に `else 0` を書くと値が壊れる（重大・実装で対処）

**指摘**: `avg(case when kind='dwell' then dwell_seconds else 0 end)` と書くと、
表示イベントの 0 が分母に入り、平均滞在秒数が常に実際より小さくなる。

**決着**: `else` を書かない（`NULL` は `avg` が数えない）。
`coalesce(..., 0)` で「その種類が 1 件も無い日」だけ 0 にする。
`input-mapping.md` に理由を書いた。

## F-05: 掃除を集計より先にやると観測が消える（重大・順序を固定）

**指摘**: 保持期限の掃除と日次集計を同じ回で行うが、順序が指定されていなかった。
先に消すと、まだ集計していない日の観測が集計前に消える。

**決着**: 集計 → 掃除の順に固定し、`reader-metrics-scheduler.ts` の
冒頭 doc に理由を書いた。**順序を逆にしても型は通り cron も回るので、
壊れたことに気づくのは数か月後になる。**だから doc に残した。

## F-06: 定時実行にブログ一覧を引かせると重くなる（中・設計を変更）

**指摘**: 「全ブログ × 直近 2 日」で回す設計だと、観測が 1 件も無いブログにも
毎日 SQL を撃つ。さらに一覧を引くために公開面の組み立てを cron が引き込む。

**決着**: `pendingDays()` を追加し、**生イベントの側から対象を数え上げる**形にした。
定時実行に「どのブログがあるか」を知らせない。
`worker-entry.js` から `createDeps()` を呼ばない制約も同じ理由で、
`tests/architecture/worker-entry-weight.test.ts` が引き込みの増加を見張る。

## F-07: `article_slug` を nullable にすると重複行が作れる（中・NOT NULL に）

**指摘**: 記事外の閲覧を `article_slug = null` の行として持つ案では、
SQLite の PK が `NULL` を重複扱いしないため、同じ日に `null` の行が
何本でも作れる。受入条件 2 が構造で守れない。

**決着**: `NOT NULL` にし、記事外の閲覧は `site_daily_metric` にだけ乗せた。
F-01 の不等号はこの判断の帰結である。

## F-08: 「足りない」を数字ごと隠すと故障に気づけない（中・方針を明文化）

**指摘**: 示唆が出せない日を空欄にすると、cron が止まっていても
「今週は誰も来なかった」としか読めない。

**決着**: 数字は出し、解釈だけ伏せる。`reason` に件数を含める。
`missing-data-policy.md` に方針として書いた。

## F-09: 再実行に範囲指定を許すか（小・許さない）

**指摘**: 「先月ぶんを全部やり直したい」場面がありうる。

**決着**: 1 日ずつに限定した。範囲を許すと「どこから壊れているか分からないので
全部やり直す」が常態になり、`sample_count` の意味が薄れる。
複数日が必要なら、日を変えて複数回押せばよい。

## F-10: 再実行の記録を組ごとに書くと監査記録が埋もれる（小・1 件にまとめた）

**決着**: 結果が出てから 1 件だけ `audit_logs` へ書く。
`{ day, rebuilt, failed }` を `after` に入れる。

## F-11: 読者の自動計測を監査記録に入れるか（小・入れない）

**指摘**: `createRecordReaderInteractionsUseCase` は 1 人が 1 記事を読むだけで
数十件届く。監査記録に入れると承認や公開の行が埋もれる。

**決着**: 記録しない。`docs/product/port-wiring.md` の除外表へ理由付きで登録した。
残すのは**やり直し（`metrics_rollup.rebuilt`）の側**で、そちらは人が
「この日が壊れている」と判断して呼んだ回だけが行になる。
