# 要求の基準線 — 日次集計 (feat-blog-metrics-rollup)

P01 の成果物。以降の phase はこの文書の受入条件を動かさずに参照する。

## 何を解く機能か

読者の行動は 1 件ずつの観測として届く。1 人が 1 記事を読むだけで数十件になる。
このまま画面に出すと、1 画面を開くたびに数千行を走査することになり、しかも
**同じ数字が画面ごとに違う値になる**（どこまでを 1 日とするか、どの区切りで
足すかが画面ごとに決まってしまうため）。

そこで、生の観測と画面のあいだに **1 日 1 行の集計** を挟む。
画面はこの行だけを読む。数字の定義は集計側に 1 つだけ置く。

## 上位ゴールへの接続

- **G2**（どういう情報・切り口・配置がクリック率と成果に有効かを計測・分析し一元管理できる）
  — 本 feature はその「計測結果を運営判断に使える形へ束ねる」層を担う。
- アーキテクチャ上の位置は `architecture/arch-blog-operations-console.md` の **観測層**。
  住所層（feat-blog-custom-domain）・改善層（SEO/AEO）・提示層（管理画面）とは
  AD-1 の一方向依存で結ばれ、本 feature はどの層にも依存しない最下層に置く。

## 範囲に入るもの

1. 日次集計テーブル（日付 × ブログ (× 記事) を一意軸とする）
2. 対象日の生データを読み、当日ぶんを丸ごと置き換える冪等な集計
3. 記事ごとのトータル売上と PV、およびブログ単位での合算
4. 滞在・スクロール到達・要素クリック率を記事指標として同じ行へ載せる
5. 定時実行の配線と、失敗時に対象日を指定して再実行できる入口
6. 件数が少なすぎる日を「示唆に足りない」と機械的に判定できる件数列

### 受入条件 3・4 についての、実装との差の申告

条件 3・4 は「記事の合計 = ブログの合計」と読める。**実装ではこれは常には成り立たない。**

`articleSlug` が `null` の観測（記事に紐づかない閲覧 — 一覧ページ、トップ、
タグページなど）が存在し、それは `site_daily_metric` にだけ乗って
`article_daily_metric` には乗らない。したがって

```
Σ article_daily_metric.views  ≤  site_daily_metric.views
```

が正しい関係であり、等号は「記事外の閲覧が 0 件の日」にだけ成り立つ。

これは実装の誤りではなく **受入条件の書き方が不足していた**ものと判断した。
一覧ページの閲覧を記事のどれかに割り振れば等号は作れるが、それは
「読まれていない記事が読まれたことになる」ので、数字としては嘘になる。
判断の根拠と、テストがこの不等号をどう検証しているかは
`metric-definitions.md` の「合算の恒等式」節に書いた。

## 前提として動かさないもの

- **AD-2**: 提示層で計算しない。画面は集計行をそのまま読む。
- **AD-4**: 生イベントは 90 日で捨てる。集計は消さない。
- **AD-5**: `site_slug` が層をまたぐ唯一の結合キー。
- **§12.3**: 表は 1 つ、読み口は 2 つ。編集判断へ売上を渡さない。
