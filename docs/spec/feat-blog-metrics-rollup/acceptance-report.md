# 受入判定 — 日次集計 (feat-blog-metrics-rollup)

P06 の成果物。受入条件 9 件それぞれについて、満たしたと言える根拠。

## 判定表

| # | 受入条件 | 判定 | 根拠 |
|---|---|---|---|
| 1 | 同じ日を二度集計しても値が変わらない | ○ | 結合テスト「2 回集計しても数字が二重にならない」 |
| 2 | 同じ (ブログ, 日, 記事) の行が重複して作れない | ○ | 主キー。結合テストが PK 違反を期待する |
| 3 | 記事ごとの売上合計 ≤ ブログの売上合計 | **△（条件を訂正）** | 下記「条件 3・4 について」 |

| 5 | 生イベント削除後も集計は 90 日より前まで残る | ○ | 結合テスト「期限を過ぎた生イベントは捨て、集計は残す」 |

## 条件 3・4 について（仕様側の記述不足として訂正）

原文は「一致する」だったが、**実装でも設計でも一致しない**。

記事に紐づかない閲覧（トップ・一覧・タグページ）が存在する限り、
ブログ全体の PV は記事の合計より必ず大きくなる。

```
Σ 記事の PV  ≤  ブログの PV
```

一致させる案は 3 つとも却下した（`design-review-findings.md` F-01）。
どれも「数字を嘘にする」か「見えるべきものを消す」ことになる。

**正しい関係は不等号**であり、テストも不等号を検証している。
条件の文面が実態を写していなかった、という扱いにした。

差の意味は「記事以外の場所が読まれた回数」で、これは
運営者にとって捨ててよい情報ではない。トップに人が来ているのに
記事へ流れていない、が見える唯一の手がかりである。

## 条件 9 について（半分だけ）

「失敗が運用から見える」側は満たした。集計の失敗件数が返り、
`failed > 0` なら操作全体が失敗として返る。監査記録にも
`{ day, rebuilt, failed }` が残る。

**「定時に起動する」側は、こちらのテストでは確かめていない。**

Cloudflare の cron trigger が実際に発火することは、手元でも CI でも
再現できない。確かめられるのは「発火したら何が起きるか」までである。

起動の確認は運用手順（`operations-runbook.md`）に落とした。
`computed_at` を画面に出しているので、止まれば運営者が気づける。

### port-wiring が赤である件（上限を上げていない）

```
書き込みなのに記録へ届いていない入口
  届いていない    0（上限 0）
  理由つき除外    6（上限 5）
NG 書き込み側の除外が上限を 1 件超えました。
```

本 feature が `createRecordReaderInteractionsUseCase` を追加し、
除外表が 5 → 6 件になった。理由は既存の 2 分類のうち「自動の計測」で、
新しい理由の分類は増やしていない。

登録簿は「移した分だけ `PORT_WIRING_MAX_UNRECORDED` を下げる」と
指示しているが、**その値は既に 0 で、下げる余地が無い**。
したがって合計が 1 件増える。

`PORT_WIRING_MAX_WRITE_EXCLUSIONS` を 6 へ上げれば緑になるが、
**上限を上げて緑にすることは禁じられているので、上げていない。**
赤のまま残し、ここに事実として記録する。

判断が要るのは「新しい入口が実体として増えたぶんの件数更新を
認めるか」であり、これは実装側では決められない。
