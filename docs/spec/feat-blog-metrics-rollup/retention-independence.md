# 保持期限からの独立 — 日次集計 (feat-blog-metrics-rollup)

P02 の成果物。受入条件 5「生イベントが 90 日で消えた後もロールアップ済みの日は残る」の設計。

## AD-4 の要求

> 生イベントは 90 日で捨てる。

読者 1 人が 1 記事を読むだけで数十件の行が増える。1 年ぶんを持ち続けると、
D1 の容量とクエリ時間の両方が現実的でなくなる。加えて、個々の読者の
動きをいつまでも保持する必要が運営上どこにも無い。

一方で、**集計は消してはいけない**。去年の同じ月と比べる、という運営判断は
1 年前の集計を必要とする。

## 独立させる仕組み

集計行は生イベントを参照しない。外部キーも無い。
`site_daily_metric` / `article_daily_metric` は生イベントから**作られる**が、
作られた後は独立して存在する。

生イベントを消しても集計行は残る。これは「消し忘れ」ではなく設計である。

## 消す順序（実装の核心）

`reader-metrics-scheduler.ts` は、1 回の定時実行で

1. 集計する（`rollupDay`）
2. **そのあとで**消す（`purgeExpiredEvents`）

の順に行う。この順序は入れ替えられない。

```
掃除は生イベントを消す。集計より先に消すと、まだ集計していない日の
観測が、集計される前に消える。集計を先にすれば、消えるのは既に
日次の行になった観測だけになる。
```

順序を逆にしても型は通り、cron も回り、テストの多くも通る。
壊れるのは「90 日前の日がちょうど未集計だったとき」だけなので、
**壊れたことに気づくのは数か月後**になる。だから doc に理由を残した。

## 消える境界

```ts
const before = new Date(at.getTime() - RAW_EVENT_RETENTION_DAYS * 24 * 60 * 60 * 1000);
```

`RAW_EVENT_RETENTION_DAYS = 90`。`occurred_at < before` の生イベントを消す。

集計の窓（`ROLLUP_DAYS = 2`）が保持期限（90 日）よりはるかに狭いので、
通常運転では「集計されないまま消える観測」は存在しない。

**例外は、定時実行が 88 日以上止まった場合**である。そのときは古い日から
順に、集計されないまま保持期限を迎える。これを検知する手段は
`operations-runbook.md` の監視項目に書いた。

## やり直しの入口にも同じ境界が効く

`validateRollupTargetDay` が保持期限を過ぎた日を拒む。

拒まないと、運営者が「3 か月前の数字がおかしい」と思ってやり直したときに、
**生イベントがもう無いので集計が 0 で上書きされる**。おかしかった数字が、
確実に 0 という間違った数字になる。

これは「取り返しがつく操作」であることの前提でもある
（`tests/architecture/open-doors.test.ts` の `rebuildDailyMetricsAction`）。
保持期限内の日しか指定できないから、同じ日をもう一度回せば同じ値に戻る。

## 集計側に消す仕組みを持たない

集計行の削除経路は実装に無い。ブログを消したときの後始末も含めて、
現時点では集計行は残る。

これは意図した保留である。ブログを消した後も「先月まではこれだけ稼いでいた」
を見たい場面があり、消すべきかどうかは運営の判断による。
判断が要る削除を、機械が黙って行わないようにしてある。
