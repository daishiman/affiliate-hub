# 移行メモ — 住所層

## スキーマ移行

`drizzle/0044_funny_groot.sql` が `site_custom_domain` 表と 3 つの索引を作る。

- **新しい表だけを足す。** 既存の表の列を変えていない。したがって前方互換であり、
  古いコードが動いたままこの移行を当てられる。
- **戻す手順**: 表を落とすだけ。既定住所は住所表に依存しないので、落としても
  ブログは `/s/<URL名>` で読める。これが「住所表の行が無いことが既定住所」という
  設計を選んだことの実利である。

## データ移行

**無い。** 既存のブログは 1 件も独自ドメインを持っていない。既定住所しかない状態が
そのまま初期状態として正しい。

## 重複の解消

この feature を作る前、住所らしきものは次の 2 か所にあった。

| 既存 | 扱い |
|---|---|
| `src/domain/authoring/site-hostname.ts` の `siteSlugFromHost` (基底ドメインのサブドメイン) | **残す。** 別の feature (`feat-blog-subdomain-routing`) の責務。住所表とは独立に動く |
| `src/presentation/site/site-metadata.ts` の `siteMetadataUrl` (要求 host から絶対 URL) | **作り替えた。** 組み立てを純関数 `siteCanonicalUrl` へ出し、正本は 独自ドメイン → 既定サブドメイン → path 形 の順で選ぶ。要求 host に依存する形は canonical の役目を果たしていなかった (FIND-2) |

**住所の解決は入口で 1 本になった。** `decideHostRouting` が基底ドメイン経路を判断し、
そこで `pass` になった要求だけが住所表を引き、引けたら `routeResolvedSite` で
サブドメイン経路と**同じ判断**へ合流する。判断が 1 本なので、「片方の経路にだけ
抜け道がある」形は作れない。

## 環境変数

Cloudflare for SaaS の鍵が未設定でも動く。未設定なら `register` は D1 への保存まで済ませ、
「外部への申し込みができていません」を `notice` で返す。鍵を入れてから行の
「状態を確認」を押せば申し込みからやり直す。**あとで連携する運用を壊さない。**
