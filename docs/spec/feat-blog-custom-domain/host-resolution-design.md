# ホスト解決の設計

## 2 つの解決経路

| 経路 | 実装 | 入力 | 状態 |
|---|---|---|---|
| 基底ドメインのサブドメイン | `src/domain/authoring/site-host-routing.ts` → `src/middleware.ts` | `<URL名>.<基底ドメイン>` | **配線済み** |
| 独自ドメイン | `src/infrastructure/domains/resolve-custom-host.ts` → `src/middleware.ts` (照会は `custom-domain-repository.ts` の `resolveSiteSlugByHost`) | 任意のホスト名 | **配線済み** |

## 基底ドメイン経路

`decideHostRouting({ host, pathname, baseDomain })` は文字列だけを触り、次を返す。

- `pass` — 本体の画面 (管理画面・サインイン)。基底ドメインが未設定の環境では常にこれ。
  「住所が未設定」と「住所が間違っている」を混同して全部 404 にすると、設定を入れる前の
  環境が丸ごと死ぬ。
- `rewrite` — `/s/<URL名><元の path>` へ**差し替える** (転送しない)。読者のアドレス欄は
  独自の住所のままにする。
- `not-found` — ブログの住所から `/admin` `/api` `/signin` `/mcp` および `/s/...` を開こうと
  した場合。**転送せず 404 を返す**のは、転送先の存在を教えないため。

判断を入口 (`middleware.ts`) から切り離しているのは、入口の中に書くと画面を丸ごと
起動しないと確かめられなくなるためである。

ホスト解決は**認証より先**に行う。後にすると、ブログの住所で開いた読者向けページが
管理画面の門の判定を通ることになる。

## 独自ドメイン経路

```ts
resolveSiteSlugByHost(db, hostname): Promise<string | null>
```

`status = 'active'` かつ論理削除されていない行だけを引き、URL 名を返す。検証状態や
証明書は公開側の判断材料にならないので返さない。ホスト名の形が不正なら `null`
(失敗を返すと公開側が 500 を出す)。

ポートを経由しないのは、この経路が要求ごとに必ず 1 回走るためで、組み立ての層を
挟まずに引けるようにしてある。

### 入口への配線

判断は純関数のまま、照会だけを入口側に置いた。

```
middleware(request)
  ├─ decideHostRouting({host, pathname, baseDomain})     ← 文字列だけ
  │    └─ pass / rewrite / not-found
  ├─ pass かつ isAlwaysPassPath(pathname) が偽 のときだけ:
  │    └─ resolveCustomHostSlug(host, lookupCustomHostInD1)  ← 写し付きの D1 照会
  │         └─ 引けたら routeResolvedSite(slug, pathname)    ← 文字列だけ
  └─ 以降は今までどおり (管理画面の門)
```

**なぜ `decideHostRouting` の中で引かないのか。** あれは文字列しか触らない純関数で、
そこに D1 を入れると、住所の判断を確かめるのに D1 が要るようになる。判断は純関数のまま
増やし (`routeResolvedSite` / `isAlwaysPassPath` を切り出した)、照会は入口に置く。

**なぜ `routeResolvedSite` を共有するのか。** サブドメイン経路と独自ドメイン経路は
「ブログを特定するまでの引き方が違うだけで、特定したあとの扱いは同じ」である。ここを
1 本にしていないと、「サブドメインからは管理画面を開けないが、独自ドメインからなら
開ける」という抜け道を片方にだけ作れてしまう。

**なぜ画面の部品を先に落とすのか。** `/_next/` や `/cdn-cgi/` は 1 ページ表示のたびに
何十件も届く。ここで住所表を引くと往復が跳ね上がる。住所に関係なく同じものを返す入口
なので、引く前に落として問題ない。

### 写しの規則と、その代償

`src/infrastructure/domains/resolve-custom-host.ts`:

| 項目 | 値 | 理由 |
|---|---|---|
| 寿命 | 60 秒 | 短くするほど D1 への往復が増え、長くするほど取り下げが遅れる。取り下げの理由はたいてい「間違えて繋いだ」で、1 分の遅れは許容できる |
| 上限 | 512 件 | Host ヘッダは要求側が自由に付けられる。上限が無いと、存在しないホスト名で叩き続けるだけで写しを際限なく太らせられる。溢れたら古いものから捨てる |
| 見つからなかった場合 | **写す** | 写さないと、独自ドメインを 1 件も使っていない環境で毎要求 D1 を引くことになり、写しの意味が消える |
| 照会が投げた場合 | **写さない** | 写すと、D1 が一瞬落ちただけで生きている住所が寿命ぶん「見つからない」に固定される |

**引き受けた代償: 取り下げが効くまで最大 60 秒。** 取り下げた住所を踏んだ読者が、その間は
まだブログに着く。運用手順書の「切り離しの反映」に、確認前に 1 分待つことを書いた。

写しは module 直下の `Map` なので、ワーカーの隔離が入れ替われば空になる。これは弱点では
なく、古い写しが延々と残らないことの保証でもある。逆に、この写しを正本として当てにしては
いけない。配信してよいかの判断は `status = 'active'` を述語に持つ照会そのものが決める。

### 引けないときは本体の画面へ倒す

住所表が読めないとき、入口は `null` を返して本体の画面として扱う。

**通行証 (`entry-gate`) とは向きが逆である。** 通行証は「確かめられない＝通さない」で
よい。住所は「引けない＝いつもの画面」でなければ、D1 が一瞬落ちただけで管理画面まで
404 になる。ここを揃えると、可用性の落ち方を間違える。

## 正本の住所 (canonical) の組み立て

入口とは**逆向き**の照会が要る。「この住所はどのブログか」ではなく「このブログの住所は
どれか」である。

```ts
resolveCanonicalHostBySiteSlug(db, siteSlug): Promise<string | null>
```

同じ記事に、住所の付け方だけが違う URL が最大 3 通りできる。

1. 独自ドメイン `https://blog.example.jp/guides/x`
2. 既定のサブドメイン `https://gadget.example.com/guides/x`
3. path 形 `https://example.com/s/gadget/guides/x`

`siteCanonicalUrl` (`src/domain/authoring/site-public-url.ts`) がこの順で正本を選ぶ。

- **独自ドメインが最優先**。運用者が「この住所で読ませたい」と明示的に立てた印だから。
- **次が既定のサブドメイン**。基底ドメインが設定された環境では、入口が `/s/<URL名>` を
  外から開けない形にしている。そこを canonical に書くと**自分で 404 を指す**。
- **path 形は基底ドメインが未設定の環境だけ**。その環境では `/s/<URL名>` が唯一の開き方。

引けないときは既定の住所へ倒す。既定の住所は正しい答えなので、canonical ごと落とす
必要がない (ここも「引けない＝安全側」の向きが上と揃っている)。
