**自動検査と公開の規範**をここに置く。
非エンジニア向けの運用手順（落ちたときどう直すか）は `docs/product/ci-cd-guide.md`、

## 1. 要求（利用者の言葉）

> それを CI/CD が通るようにしておいてください。
> CI/CD もこちらで管理できるようにしておいてほしいです。

「こちらで管理できる」を、次の 4 つに分解して満たす。

| 分解 | 満たし方 |
| --- | --- |
| 手元で同じことを確かめられる | `pnpm verify` 1 コマンドで CI と同じ検査（§2） |
| 何をしているか読める | 非エンジニア向けの説明を `docs/product/ci-cd-guide.md` に置く。設定ファイルのコメントで済ませない |
| 設定を変えられる | 閾値と検査の一覧を **1 ファイル**に集約（§3） |
| 増やし方・減らし方が分かる | 追加手順を文書化し、変更容易性シナリオ ⑯ で実測する |

---

## 2. 手元と CI を同じにする

```
pnpm verify   = 型検査 → 静的検査 → テスト（カバレッジ閾値つき）→ 契約検査
```

CI はこの 1 コマンドを呼ぶ。**CI 側にだけ追加の検査を書かない。**
書いた瞬間に「CI でしか落ちない状態」が生まれ、それは手元で直せない状態と同じになる。

ビルドとデプロイは `verify` に含めない（遅く、壊すものが違うため。§4）。

---

## 3. 閾値と検査の一覧は 1 か所

**正本: `quality-gates.config.mjs`（リポジトリ直下）**

ここに置くもの:

- カバレッジ閾値（全体・層別）
- カバレッジの対象と除外
- 「スタブ実装」と見なすパスの定義（`10-テスト戦略仕様.md` §2-1 の実質カバレッジ用）
- `pnpm verify` が回す検査の一覧

読む側:

- `vitest.config.mts`（閾値をそのまま使う）
- `scripts/verify.mjs`（検査の一覧をそのまま回す）
- `scripts/coverage-report.mjs`（層別の集計と `docs/product/coverage.md` の生成）
- `tests/architecture/quality-gates.test.ts`（**文書と設定がずれていないこと**を確かめる）

散らさない理由は単純で、**閾値が 2 か所にあると、低い方が実効値になる**からである。

## 4. ワークフローは壊すものの重さで分ける

当初は 3 本（検査 / 公開 / 構造変更）だった。§8 の段を入れた時点で 5 本、
2026-08-21 に枝の順番を足して 6 本になっている。
増やしたのは**壊すものが違うから**であって、種類を増やしたかったからではない。

| ファイル | 引き金 | 壊すもの |
| --- | --- | --- |
| `ci.yml` | push / PR | **なし**（検査だけ） |
| `branch-flow.yml` | main への PR | **なし**（比較元の枝を見るだけ） |
| `deploy.yml` | main への push | 本番アプリ |
| `migrate.yml` | 手動起動 + `APPLY` | **本番データ** |
| `nightly.yml` | **手動のみ**（定例なし・§8-2） | なし（マージも止めない） |
| `ai-eval.yml` | 手動起動 + `RUN` | **お金**（唯一の従量課金） |

`branch-flow.yml` を `ci.yml` に混ぜなかった理由は、見ているものが違うからである。
`ci.yml` は**中身が正しいか**を、`branch-flow.yml` は**どこから来たか**を見る。
混ぜると、枝の順番だけを守らせたい場面で検査一式が動く。

これ以上増やさない。増やすほど、どれがいつ走るのか本人にも分からなくなる。


壊せるものの重さが 3 段階で違うので、起動条件も 3 段階にする。

| ファイル | いつ走るか | 何をするか | 壊すもの |
| --- | --- | --- | --- |
| `ci.yml` | PR の作成・更新 | `pnpm verify` + ビルド + マイグレーション未生成の検出 | **なし**（検査だけ） |
| `deploy.yml` | `dev` / `main` への push | ビルド → 公開 → スモークテスト（間隔を空けて 2 回） | 本番アプリ |
| `migrate.yml` | **手動起動のみ** | バックアップ → DB の構造変更を適用 | **本番データ** |

### 4-1. マイグレーションを自動化しない

DB の構造変更は元に戻せない（列を消したら中身も消える）。
公開に混ぜると、PR をマージした瞬間に本番データの構造が変わる。

- `migrate.yml` は手動起動のみとし、**確認文字列 `APPLY` の入力を必須**にする
- 適用順序は **マイグレーション → コードのデプロイ** で固定する
  （逆にすると、新しいコードが存在しない列を読んで本番が全面エラーになる）
- 列を削除する場合は 2 段階に分ける（誰も読まない状態にしてから消す）

### 4-2. 公開の承認

- 本番は GitHub の Environment（`production`）を通す。承認レビュアーを設定できるプランでは
  ここで人の承認を挟む。**設定できないプランでは、承認は「PR のマージ」が担う**。
  どちらであるかを `docs/product/ci-cd-guide.md` に明記する（できないことを、
  できるように書かない）。
- 先に `dev` 環境へ出して確認できる（プレビュー相当）。

### 4-3. 公開後は必ず確かめる

「デプロイ成功」はファイルが届いたことしか意味しない。

- スモークテストを **30 秒待つ → 1 回目 → 90 秒待つ → 2 回目** の二段構えで実行する。
  Cloudflare Workers は旧版の実行環境を数十秒〜1〜2 分保持するため、
  1 回だけの確認では反映を判定できない（直っているのに落ちる／壊れているのに通る、が両方起こる）。
- スモークテストが落ちたらワークフローを失敗させる。
  **「デプロイは成功したがアプリは壊れている」を緑で通さない。**
- 戻し方は `wrangler rollback`。手順を運用文書に書く。

## 5. 秘密情報

- API キー・トークンは **GitHub Secrets と Cloudflare の環境変数**で管理する。
- **リポジトリのファイル、コマンドライン、AI が読める場所に置かない。**
  登録は利用者本人が、ブラウザまたは本人のターミナルで行う。代行しない。
- `.dev.vars.example` は値を含まない見本のまま維持する。
- ログに秘密情報を出さない（`echo ${{ secrets.X }}` を書かない）。
- API トークンの権限は最小にする（Workers Scripts 編集 / D1 編集 / R2 編集のうち必要なものだけ、
  対象アカウントは 1 つに限定）。

## 6. 品質ゲート（何を満たせば「できた」と言えるか）

リリース可否は次の 2 つだけで判定する。**これ以外の指摘でリリースを止めない**
（残りは `docs/product/backlog.md` へ）。

| ゲート | 条件 |
| --- | --- |
| A. 機能 | 業務に必要な機能一式が動く。追跡表に「未着手」が無い。画面のない要件が無い |
| B. 安全 | セキュリティ監査で CRITICAL がゼロ |

そのうえで、**マージの可否**は CI が判定する（こちらは毎回の門番）。

| 検査 | 落ちたらマージしない |
| --- | --- |
| 型検査 | する |
| 静的検査（依存方向・トークン直書きを含む） | する |
| テスト（7 種） | する |
| カバレッジ閾値（全体・層別） | する |
| 契約検査（スタブ台帳・カタログ・1 概念 1 定義） | する |
| 本番ビルド | する |
| 依存の脆弱性 | **警告どまり**（上流待ちで作業が止まるのを防ぐ） |

CI が赤いままマージしない。1 回許すと、次から誰も見なくなる。
やむを得ず回避した場合は理由を記録する。

## 8. 検査の段

重いテスト（ミューテーション・負荷・見た目の回帰）を足す前に、**置き場所を先に作る**。
順序を逆にすると、CI が回らなくなってから「重いテストを消す」判断に流れる。
ここでやることは 1 つだけ、**実行する場所を変える**ことである。
テストを消す・skip する・閾値を下げるのは、いずれもこの設計の目的に反する。

### 8-1. 費用の前提（2026-08-17 実測）

| | 実測 | 費用 |
| --- | --- | --- |
| このリポジトリの公開設定 | **public** | GitHub Actions の標準ランナーは無料・無制限 |
| 直近の CI 実行時間 | 40〜70 秒 | 0 円 |
| `pnpm verify`（1 段 + 2 段） | 37 秒 | 0 円 |
| AI 評価セット | 51 件 | **ここだけが従量課金** |

**実行時間は費用の要因ではない。** したがって「時間を減らすために CI からテストを外す」判断はしない。
単体テストは CI に置き続ける（手元で流し忘れた場合と、手元だけで通る場合を捕まえるため）。

### 8-2. 3 つの段

| 段 | 引き金 | 目標時間 | マージ | 中身 |
| --- | --- | --- | --- | --- |
| 1 速い門 | push / PR | 5 分 | **止める** | 型検査 / 書き方 / 段の指定漏れ / 単体・契約検査 |
| 2 広い門 | PR | 15 分 | **止める** | 結合 / API 契約 / 画面 / 読み上げ / 境界値 / カバレッジ閾値 / 変更範囲だけのミューテーション |
| 3 深い門 | **手動のみ**（定例なし。打つ場面は下） | 40 分（実測 27 分） | 止めない | 全体ミューテーション / 負荷 / 見た目の回帰 / 脆弱性の深掘り |

3 段がマージを止めない理由: 止めると、手が止まる人が出て、
やがて**赤を消すために 3 段そのものが外される**。
外された検査は、落ちる検査より悪い（あると思われているのに無い）。

3 段から **AI 評価セットを外した**。生成物の内容判定は **2026-08-17 に「作らない」と決めた**
（`ah-gzq` / REQ-CI13）。判定するにはもう一度 AI を呼ぶことになり、
**判定する側が正しいかを確かめる手段が無いまま従量課金だけが発生する**ためである。
未実装ではなく意図的な対象外であり、`.github/workflows/ai-eval.yml` は
手動起動のみ・**必ず落ちる**状態で、費用の見張りの枠としてのみ残してある（§8-4）。

**3 段の定例は 2026-08-18 に廃止した。** 以前は毎日 18:00 UTC の `cron` で走り、
非公開になったら週 1 回へ落とす「予算の門」（`PRIVATE_RUN_DOW`・公開状態の判定 8 通り）を
持っていた。`cron` と一緒にその仕掛けも消した。**どの曜日に走らせるかを決めるためだけの
仕掛けなので、定例が無くなれば守るものが無い。動かないまま残る仕掛けは、
あとから読む人に「まだ走っている」と読まれる。**

**廃止の理由は重さではない。** 実測 27 分 0 秒（2026-08-17・同時実行 4）で、
毎日でも枠に収まる程度に軽かった。それでも要らないと判断した。
3 段が答えるのは「**いま公開してよいか**」であって「昨夜の時点でどうだったか」ではない。
**誰も見ない緑が毎晩 1 つ増えるだけなら、それは記録であって門ではない。**

**定例をやめると、3 段は「誰も打たなければ一度も走らない検査」になる。**
`llm-live-proof.mjs --check` で一度踏んだ形と同じである（名前だけがあって、
打つ場面が書かれていなかった）。**場面を書かずに定例だけ外すのは、検査を消したのと同じ。**
だから打つ場面を人の手順として定める。

| いつ | 誰が | なぜ |
| --- | --- | --- |
| **本番へ公開すると判断する日**（必須） | 公開を決める人 | `docs/product/open-doors.md` を見る回と**同じ回**に含める。判断に要るものを 1 回で揃える |
| domain / application のテストを大きく足した・消した直後 | 動かした本人 | 3 段はテストが書き換えに気づくかを見るので、テストの側が動いた回にしか差が出ない |
| 3 段のテストを新しく足した回（いまは 0 件） | 足した本人 | 打たないと、0 件のまま通っていた頃と区別が付かない |

回数が決まっていないので、月あたりの見積りは置かない
（非公開の月 2,000 分に対し、打った回数 × 27 分だけが乗る）。

目標時間は**目標であって落とす条件ではない**。超えたら `scripts/verify.mjs` が警告を出す。
時間で赤くすると、時間を守るためにテストを削る力が働く。

### 8-3. 段の印と、指定漏れのゲート

テストファイルが持つのは **`@tier <番号>`** の 1 行だけで、実行場所（機械 / 手元 / 手動）は書かない。
実行場所は `quality-gates.config.mjs` の `TIERS[].runOn` が 1 か所で決める。
将来このリポジトリを非公開にしたとき、**テストを消すのではなく移せる**ようにするための分離である。
ファイル側に実行場所を書くと、移すたびに全テストを触ることになり、そのとき人は「移す」より「消す」を選ぶ。

**ディレクトリごとの既定を作らない。** 既定があると新しいテストが黙って段を持ち、
「段の指定漏れで CI を落とす」ゲートが永久に発火しない。

| 検出するもの | 判定 |
| --- | --- |
| 印が無い | 落とす |
| 知らない段の番号 | 落とす |
| 印が 2 つ以上ある | 落とす |
| 段に属するテストが 0 件（1・2 段） | 落とす（印の書き間違いで無言の空回りになるため） |
| 段に属するテストが 0 件（3 段） | 通す（これから足す置き場所） |

検査は `scripts/tier-audit.mjs`。**テストを走らせる前**に置く（`CHECKS` の並びで固定し、
`tests/architecture/quality-gates.test.ts` がその並びを見張る）。

### 8-4. カバレッジ閾値をどの集合で測るか

カバレッジは**走らせたテストの集合に対してしか測れない**。
1 段だけで 80% を要求すると、達成する手段は「閾値を下げる」しか無くなる。
それは禁じているので、閾値は `runOn: "ci"` の段をまとめて走らせたとき
——つまり毎 PR、マージを止める場所——でだけ判定する。
段を絞って走らせたときは、閾値を**下げるのではなく測らない**（`VITEST_TIER_PARTIAL`）。

### 8-5. AI 評価セットの費用

| 決めごと | 理由 |
| --- | --- |
| `workflow_dispatch` のみ | 定期実行に載せると、誰も見ていない時間に費用が出続ける |
| 確認文字列 `RUN` を必須 | 誤って起動したときの唯一の安全弁 |
| 上限は**途中で止まる** | 走り終えてから知らせる作りでは、費用は防げず後から分かるだけになる |
| 見積りと実測の両方を出す | 実測だけでは「思っていたより高い」に気づけず、見積りだけでは合っていたか分からない |

上限の正本は `AI_EVAL_BUDGET`（51 件 / 400,000 トークン）。
実装は `scripts/ai-eval-budget.mjs`、入口は `scripts/ai-eval.mjs`。

**現況: 提供元へ問い合わせる部分は未実装**（残課題 `ah-gzq`）。
いまあるのは見積りと見張りだけで、実行すると 0 件・0 円で終わる。
見張りを先に作ったのは順序の問題で、問い合わせを先に作ると上限が無いまま 1 回目が走る。

### 8-6. 現況（2026-08-17 実測）

| 段 | テスト件数 | 実測時間 |
| --- | --- | --- |
| 1 | 74 ファイル | 22 秒（型検査・書き方・段の指定漏れ・テスト） |
| 2 | 35 ファイル | 1 段と合わせて 37 秒 |
| 3 | **0 ファイル** | 対象 0 件（中身はこれから足す） |

3 段が 0 件であることを「通った」と書かない。`scripts/run-tests.mjs` は件数を必ず表示する。
