## 0. この章の位置づけ

**自動検査と公開の規範**をここに置く。
非エンジニア向けの運用手順（落ちたときどう直すか）は `docs/product/ci-cd-guide.md`、
ワークフローの中身は `.github/workflows/` が実体である。

---

## 1. 要求（利用者の言葉）

> それを CI/CD が通るようにしておいてください。
> CI/CD もこちらで管理できるようにしておいてほしいです。

「こちらで管理できる」を、次の 4 つに分解して満たす。

| 分解 | 満たし方 |
| --- | --- |
| 手元で同じことを確かめられる | `pnpm verify` 1 コマンドで CI と同じ検査（§2） |
| 何をしているか読める | 非エンジニア向けの説明を `docs/product/ci-cd-guide.md` に置く。設定ファイルのコメントで済ませない |
| 設定を変えられる | 閾値と検査の一覧を **1 ファイル**に集約（§3） |
| 増やし方・減らし方が分かる | 追加手順を文書化し、変更容易性シナリオ ⑯ で実測する |

---

## 2. 手元と CI を同じにする

```
pnpm verify   = 型検査 → 静的検査 → テスト（カバレッジ閾値つき）→ 契約検査
```

CI はこの 1 コマンドを呼ぶ。**CI 側にだけ追加の検査を書かない。**
書いた瞬間に「CI でしか落ちない状態」が生まれ、それは手元で直せない状態と同じになる。

ビルドとデプロイは `verify` に含めない（遅く、壊すものが違うため。§4）。

---

## 3. 閾値と検査の一覧は 1 か所

**正本: `quality-gates.config.mjs`（リポジトリ直下）**

ここに置くもの:

- カバレッジ閾値（全体・層別）
- カバレッジの対象と除外
- 「スタブ実装」と見なすパスの定義（`10-テスト戦略仕様.md` §2-1 の実質カバレッジ用）
- `pnpm verify` が回す検査の一覧

読む側:

- `vitest.config.mts`（閾値をそのまま使う）
- `scripts/verify.mjs`（検査の一覧をそのまま回す）
- `scripts/coverage-report.mjs`（層別の集計と `docs/product/coverage.md` の生成）
- `tests/architecture/quality-gates.test.ts`（**文書と設定がずれていないこと**を確かめる）

散らさない理由は単純で、**閾値が 2 か所にあると、低い方が実効値になる**からである。

## 4. ワークフローは 3 本だけ

壊せるものの重さが 3 段階で違うので、起動条件も 3 段階にする。

| ファイル | いつ走るか | 何をするか | 壊すもの |
| --- | --- | --- | --- |
| `ci.yml` | PR の作成・更新 | `pnpm verify` + ビルド + マイグレーション未生成の検出 | **なし**（検査だけ） |
| `deploy.yml` | `dev` / `main` への push | ビルド → 公開 → スモークテスト（間隔を空けて 2 回） | 本番アプリ |
| `migrate.yml` | **手動起動のみ** | バックアップ → DB の構造変更を適用 | **本番データ** |

### 4-1. マイグレーションを自動化しない

DB の構造変更は元に戻せない（列を消したら中身も消える）。
公開に混ぜると、PR をマージした瞬間に本番データの構造が変わる。

- `migrate.yml` は手動起動のみとし、**確認文字列 `APPLY` の入力を必須**にする
- 適用順序は **マイグレーション → コードのデプロイ** で固定する
  （逆にすると、新しいコードが存在しない列を読んで本番が全面エラーになる）
- 列を削除する場合は 2 段階に分ける（誰も読まない状態にしてから消す）

### 4-2. 公開の承認

- 本番は GitHub の Environment（`production`）を通す。承認レビュアーを設定できるプランでは
  ここで人の承認を挟む。**設定できないプランでは、承認は「PR のマージ」が担う**。
  どちらであるかを `docs/product/ci-cd-guide.md` に明記する（できないことを、
  できるように書かない）。
- 先に `dev` 環境へ出して確認できる（プレビュー相当）。

### 4-3. 公開後は必ず確かめる

「デプロイ成功」はファイルが届いたことしか意味しない。

- スモークテストを **30 秒待つ → 1 回目 → 90 秒待つ → 2 回目** の二段構えで実行する。
  Cloudflare Workers は旧版の実行環境を数十秒〜1〜2 分保持するため、
  1 回だけの確認では反映を判定できない（直っているのに落ちる／壊れているのに通る、が両方起こる）。
- スモークテストが落ちたらワークフローを失敗させる。
  **「デプロイは成功したがアプリは壊れている」を緑で通さない。**
- 戻し方は `wrangler rollback`。手順を運用文書に書く。

## 5. 秘密情報

- API キー・トークンは **GitHub Secrets と Cloudflare の環境変数**で管理する。
- **リポジトリのファイル、コマンドライン、AI が読める場所に置かない。**
  登録は利用者本人が、ブラウザまたは本人のターミナルで行う。代行しない。
- `.dev.vars.example` は値を含まない見本のまま維持する。
- ログに秘密情報を出さない（`echo ${{ secrets.X }}` を書かない）。
- API トークンの権限は最小にする（Workers Scripts 編集 / D1 編集 / R2 編集のうち必要なものだけ、
  対象アカウントは 1 つに限定）。

## 6. 品質ゲート（何を満たせば「できた」と言えるか）

リリース可否は次の 2 つだけで判定する。**これ以外の指摘でリリースを止めない**
（残りは `docs/product/backlog.md` へ）。

| ゲート | 条件 |
| --- | --- |
| A. 機能 | 業務に必要な機能一式が動く。追跡表に「未着手」が無い。画面のない要件が無い |
| B. 安全 | セキュリティ監査で CRITICAL がゼロ |

そのうえで、**マージの可否**は CI が判定する（こちらは毎回の門番）。

| 検査 | 落ちたらマージしない |
| --- | --- |
| 型検査 | する |
| 静的検査（依存方向・トークン直書きを含む） | する |
| テスト（7 種） | する |
| カバレッジ閾値（全体・層別） | する |
| 契約検査（スタブ台帳・カタログ・1 概念 1 定義） | する |
| 本番ビルド | する |
| 依存の脆弱性 | **警告どまり**（上流待ちで作業が止まるのを防ぐ） |

CI が赤いままマージしない。1 回許すと、次から誰も見なくなる。
やむを得ず回避した場合は理由を記録する。
