## 1. 受入条件の検証可能化

### A1 — 記法の生テキストが編集面に現れない

- REQ-ID: `FRONT-REQ-005-A1`
- 検証: 編集面の DOM に、断片の表示要素として `` ``` `` / `**` / 表のパイプ `|` が
  **記法として**現れないこと。利用者が本文として打ち込んだ文字は対象外。
- 判定単位: 19 種すべて。各 1 件の挿入直後の描画を見る。
- 反例 (FAIL とする): コードブロックの中身を `` ```ts `` 込みの 1 枚の textarea で編集させる。

### A2 — 見出しレベルが動かない

- REQ-ID: `FRONT-REQ-005-A2`
- 検証: 節 (`ArticleBlock`) の見出しは常に `h2`。断片 (`ProseNode`) の見出しは `h3` か `h4` のみ。
  挿入・移動・削除・貼り付けの 4 操作すべての後で、この不変条件が保たれること。
- 判定単位: 4 操作 × (節 / 断片) の 8 通り。
- 根拠: 見出しレベルは読者の目次と AI 検索の構造抽出が読む。編集操作で動くと、
  記事の意味構造が編集の副作用で書き換わる。

### A3 — 19 種すべてが挿入・編集・公開できる

- REQ-ID: `FRONT-REQ-005-A3`
- 検証: `/` メニューから 19 種すべてを挿入でき、挿入後に編集でき、本文プレビューと
  公開ページが同じ`ProseBody`を通って描画されること。入力欄のDOMまで読者表示と同じにする要件ではない。
  コンポーネントの接続検査に加え、内容保持と実操作を確認する。
- 判定単位: 19 種 × (挿入 / 編集 / 公開描画)。

### A4 — 商品カードは検索選択のみ

- REQ-ID: `FRONT-REQ-005-A4` / `UIUX-ACC-008`
- 検証 (肯定): 商品カード断片を挿入するとき、検索語を打つと候補が出て、
  候補を選ぶと `productId` が確定する。
- 検証 (否定): 商品カード断片の編集 UI に、`productId` を直接受け取る
  text 入力要素が**存在しない**。
- 根拠: 商品 id は人が覚えて打つ値ではない。手入力欄があると、存在しない id を
  持つ記事が保存でき、公開時に初めて壊れる。

### A5 — ファイル選択で画像を入れ、URLを手入力しない（Worker経由を承認済み）

- REQ-ID: `FRONT-REQ-005-A5` / `UIUX-ACC-008`
- 検証 (肯定): 画像断片の挿入時、ファイルを選ぶと送信され、確定した参照が断片に入る。
- 検証 (否定): 画像断片の編集 UI に、画像 URL を受け取る text 入力要素が**存在しない**。
- `dec-article-image-upload-path`の現行決定は`opt-worker-proxy-upload`。2026-09-06の本人回答「ok」を根拠に、Workerで認可・容量・形式を検査して保存する方式へ統一した。
  旧直接PUTの承認は履歴に保持する。方式承認とUI受入・実環境への適用は別に判定する。
  承認根拠と正規仕様への反映は[image-upload-decisions.md](./image-upload-decisions.md)を参照。

### A6 — 公開描画が許可リストで絞られる

- REQ-ID: `SEC-REQ-XSS` / `FRONT-REQ-005-A6`
- 検証: 公開ページの出力に、許可リスト外の断片・属性・スタイルが 1 つも現れないこと。
  許可リストは「載せてよいものを数え上げる」形 (allowlist) で書き、
  「危ないものを除く」形 (denylist) では書かない。
- 判定単位: 許可外を混ぜた入力に対する出力の検査。

### A7 — 既存 10 種の記事が壊れない

- REQ-ID: `FRONT-REQ-005-A7`
- 要求: 既存10種の記事を何も編集せず再保存した際に、保存文字列がバイト単位で一致すること。
- 今回の検証範囲: 既存の正規保存fixtureで一致を確認。不正記法・新しい境界エスケープ・複合装飾では、
  内容を失わない往復を別に検査する。未収集の全既存記事に対するバイト一致は未検証であり、
  fixtureの成功だけでA7全体のPASSを宣言しない。
- 根拠: 保存形式を拡張するとき、いちばん静かに壊れるのがこれ。
  「読めるが書き戻すと変わる」は、利用者が気づかないまま全記事を書き換える。

## 4. ブログ編集の機能範囲（2026-09-06 再検証）

本節は今回のUI/UX・API・公開表示を通した機能一覧の正本。過去のフェーズ別PASSは今回の実機検証の代わりにしない。検証結果と未了は [elegant-review.md](./elegant-review.md) に集約する。

### 設計判断

- 中心対象は「記事」。タイトル・書き出し・本文を主領域、章立て・版面検査・カテゴリ・タグ・公開状態を補助領域にする。
- 内側の19種は本文ブロック、外側の15種は記事の章、ExpressionBlockは構造化された結論・FAQ等。型と保存契約を混ぜず、編集・公開の境界で接続する。
- 主操作は「記事を保存」1つ。未保存・保存中・競合・失敗・保存済みを文字で示す。編集用の操作枠と公開本文の見た目を同一視せず、本文プレビューを公開用ProseBodyへ通す。
- 幅が狭い画面では一列、広い画面では本文と設定の二列。表は自身の枠で横スクロールし、ページ全体を押し広げない。
- 任意HTML、任意CSS、任意iframe、商品IDや画像URLの手入力は追加しない。

### 本文ブロック19種と必要な操作

| ブロック | 入力・編集 | 読者表示 |
| --- | --- | --- |
| 段落 | 文章・改行・Enterで分割 | 段落、行内装飾 |
| 小見出し | h3/h4、文字 | 章h2配下の見出し |
| 箇条書き | 項目の追加・削除 | ul |
| 番号付き | 項目の追加・削除 | ol |
| 引用 | 引用文 | blockquote |
| 注意書き | 種類・題・文章 | 意味別の囲み |
| 商品カード | 商品名検索から選択 | 同じworkspaceの実商品、挿入した位置に表示 |
| 比較表 | 見出し・行列・セル | 共通表枠、横スクロール |
| 画像 | ファイル・代替文 | 認可された画像、代替文 |
| 区切り線 | 挿入・移動 | 意味上の区切り |
| コード | 言語名・コード | 空白と改行を保持するコード枠 |
| 表 | 見出し・行列・セル | 共通表枠 |
| 画像の横並び | 2〜4枚・各代替文 | レスポンシブ画像群 |
| 折りたたみ | 題・補足 | details/summary |
| チェックリスト | 項目・完了状態 | 状態付き一覧 |
| 埋め込み | 許可ホストURL・題 | sandbox付きの許可先のみ |
| CTAボタン | 表示文・相対/HTTP(S)行き先・意味色 | 安全な行き先へのボタン型リンク |
| リンクカード | 題・要約・URL | 安全なリンクと説明 |
| 2段組み | 左右の文章 | 広い画面で並列、狭い画面で縦積み |

全ブロックに追加・移動・削除・複製・Undo/Redo・本文プレビューを提供する。変換は文字を保てる組合せだけに絞る。行内操作は太字・斜体・打消し・コード・リンク・名前付き文字色/背景色。任意の深い入れ子は現保存形式の契約に含めない。

### Notion相当の範囲を誤認させないための区別

今回整えるのは文書をブロックで直感的に書く操作と、ブログとして保存・公開する接続。Notion全製品の同等実装を意味しない。共同編集/CRDT、コメントとメンション、無制限の入れ子、DBビュー、サーバー版履歴、予約公開、リッチHTML/Notionインポートは新しい保存・権限・競合契約が必要で、現実装の完了には数えない。導入時は別要件として方向性を確認する。
