## 目的と到達状態

- 目的: SEO/AEOを自前の観測で理解し、記事のどこを改善するか判断できるようにする。
- 到達状態: 3データ源の観測をページ別の課題・実績推移へ結び付け、記事と差分を確認して承認した変更だけを安全に保存する。夜間処理は観測のみとし、改稿を起動しない。
- 反映後は変更前後・時刻・根拠を同じ履歴から辿れる。保存失敗・同時編集・取消前の追加編集があっても、既存内容を壊さない。

## 3 データ源の分離原則

3 系統は再現性が異なるため、収集・保持・表示・反映根拠のすべての層で分けて持つ。同じ「分析結果」として混ぜない (`backend` 確定内容 qa-answer-aeo-feasibility-v6)。3 系統はいずれも自前実装とし、第三者 SEO SaaS へ依存しない (`backend` 確定内容 qa-decision-aeo-data-sources-v5)。

| 系統 | 入力 | 外部依存 | 再現性 | 承認差分の生成根拠 | 想定間隔 |
|---|---|---|---|---|---|
| ① サイト内静的解析 | 自サイトの公開 HTML | なし | 同一入力に同一結果 | 使える | 日次・有限巡回（下記実装契約） |
| ② Search Console | Search Analytics API | 資格情報が要る | 外部集計に依存 | 使えない | 日次 |

系統②③は反映後に何が動いたかを見る材料に留める。承認済みであっても再現性の低い観測から機械的に改稿しない。この限定は生成経路の型でも保持する (`backend` 現行契約 qa-seo-approved-diff-20260906)。1 系統が失敗しても他系統の結果を失わせない。

## 系統① サイト内静的解析

公開 HTML から次を自前で抽出し、規則違反をページ単位の課題として記録する。抽出は公開された HTML そのものを入力とし、記事データからの数え直しを正としない。

| 抽出項目 | 課題として記録する規則違反の例 |
|---|---|
| title | 欠落、重複、極端に短い/長い |
| meta description | 欠落、薄い、重複 |
| canonical | 欠落、自己参照でない、到達不能 |
| OGP | 必須プロパティの欠落 |
| JSON-LD | 欠落、必須プロパティ欠落、`dateModified` と `<time dateTime>` の不一致 |
| 見出し階層 | H1 の欠落/複数、階層の飛び |
| 内部リンク | 被リンク 0 の孤立ページ |
| 画像 alt と寸法 | alt 欠落、寸法未指定 |
| llms.txt の有無 | 出す設定なのに 404、出さない設定なのに空ファイル |

`llms.txt` は設計図の任意項目で、出さない設定なら空ファイルではなく 404 を返す (`frontend` 章の注記 §3.2)。生成そのものは feat-blog-ui-builder の責務であり、本 feature は「出ているか」を見る側に立つ。

### 公開ページ全体の静的監査の実装契約（A2・A7・A8、2026-09-07）

backend/databaseの正規注記「サイト内の全公開ページ監査（2026-09-07実装確認）」と「静的監査の上限時の継続補足（2026-09-08）」を現行契約とする。公開対象と容量結果は最新の「静的監査の公開境界と容量結果の訂正（2026-09-08）」を優先する。旧詳細残差#3を以下の対象・規則・有限巡回へ接続した。過去注記の「#3が残る」は当時の記録として保持し、この局所実装をfeature全受入や全163仕様の完全性PASSへ置き換えない。

- 比較集合は同じworkspaceの同じ公開ブログ。公開readerと同じく対象workspaceのsite_blueprintsが存在し、site_retirementsに無いことを確認する。site_network_nodeの有無やactive等の状態は公開資格に使わず、対象列挙・Cron・coverageをこの境界に揃える。設計図と公開記事正本から共通ルートで列挙する。トップ、索引、カテゴリー、著者/監修者、固定文書、記事、実在する30件単位の一覧paginationを対象にし、記事0件の公開ブログも開始できる。固定文書は同じworkspace/ブログのlegal_pageでstatus=publishedかつ未削除のものを対象とし、blueprint.pagesに無くても公開readerが返す文書を共通ルートで列挙する。検索・保存一覧・旧redirectは独立canonicalページに数えない。`page=N`（N>1）は保持し、追跡queryやfragmentは同一性の根拠にしない。
- 本物のHTMLRewriterで配信HTMLから抽出する。titleは10〜60文字、descriptionは50〜160文字を判定範囲とし、非空値の前後空白を除いた完全一致で重複を検出する。内部被リンク0は全成功集合内の別ページからのリンクで判定し、自己リンク、目次fragment、同hostの別ブログを根拠にしない。出リンク0と被リンク0を混同しない。
- canonicalの欠落/非自己参照と、全成功の公開集合に行き先がない状態を分ける。`canonical_target_unreachable` は後者の意味であり、任意外部URLへ追加通信した疎通結果ではない。OGPはtitle/description/type/urlと本文の対応を確認し、画像を持たない公開面でog:imageの欠落だけを違反にしない。
- JSON-LDの必須項目は実装が扱うBlogPosting・BreadcrumbList・ItemList・FAQPage・WebSiteに限定する。壊れたJSONや必要項目欠落を検出し、datePublished/dateModifiedと可視`time[datetime]`を日付部分で照合する。全schemaの完全検証や時分秒・記事内の意味まで同一とする照合ではない。既存の見出し・画像alt/寸法の規則も同じHTML観測から判定する。
- llms.txtはHTMLと別に取得し、設定有効で404/空なら所見、無効で404なら正常、無効で空/内容ありなら所見とする。通信・5xx等の取得失敗を404や所見0へ変換しない。全体公開の前にこの設定照合も成功していることを要求する。
- workspace×ブログの現行世代と対象別の試行/成功/失敗を保存し、対象hash変更で新世代へ切り替える。同じURLの過去成功時刻は鮮度判断に保持しても、新世代の全体判定には再取得を必要とする。25件以下・10分leaseで処理権を取得し、観測保存と継続位置を同じ確定単位で更新する。失敗ページも一巡内の位置を進め、先頭の恒久失敗だけで後続を塞がない。
- 対象上限は1,000ページ。公開記事読取はLIMIT 1001で、1,001件返れば正確な全件数を求めず、下限total=1001・targets空・complete=falseを非エラーで返す。limited世代を保持して取得と所見更新を見送り、正確な全件数や未開始に見せない。他ページを加えた列挙上限超過も全体完了にしない。1応答は10秒・1,000,000 bytes、内部リンク先は500件、保存観測JSONは128 KiB、全体判定候補は8 MiBを上限とする。単体128 KiB超はresource_limitとして記録し、一巡内の後続確認を続ける。stageはresourceLimitFailuresを返し、収集側は失敗件数へ加算・pagesExaminedから減算して、同じ実行の再試行理由と系統の失敗記録へ返す。合計8 MiB超は最終HTML batchのstage直後にも判定する。外部取得枠を使い切っていても判定を後回しにせず、limitedへ移して旧所見を保持する。loadCompleteCandidateのlimitedReasonを同じ実行のskippedReasonと系統の失敗記録へ返し、記録失敗も成功にしない。同じinventoryHashでは容量超過時刻から14日以降の次回実行で新世代を開始する。hash変更時は14日を待たず新世代にする。保存対象は抽出事実と身元で、HTML本文・秘密・自由な応答内容を複製しない。
- 全対象の成功観測とllms照合を揃えたready世代のみ、唯一の`markPublished`で所見を公開する。runId/revision/leaseなしと所見snapshotのCAS、対象ブログの旧static所見置換、成功観測stamp、系統成功時刻と失敗解除、世代完了を同D1 batchで確定する。途中失敗・旧lease・遅い旧世代・古い観測では前回の所見を維持し、他workspace/ブログ/系統を変更しない。added/resolvedは同pageKey+code集合の差で数え、途中取得では解消を確定しない。

巡回は開始から完了までの観測をまとめたもので、全ページの同時刻snapshotや現在のSEO効果を証明しない。旧表の「記事保存時」起動は今回未実装で、現行の自動実行は日次Cronの継続処理である。任意外部canonicalの疎通・全JSON-LD schema検証・時刻の完全一致は上記の実装範囲と区別する。

## 系統② Google Search Console 連携

- Search Analytics API から クエリ・ページ・表示回数・クリック・平均掲載順位 を取得して保存する。
- ページ全体の実績は `date/page`、検索語別の内訳は `date/page/query` で別々に取得・保存する。匿名検索語が内訳から除外されるため、検索語別の値を加算してページ全体の表示回数・クリック・平均掲載順位を作らない。ここで保存するのはSearch Console由来の集計済み検索語であり、読者のサイト内自由検索語を新規収集しないtelemetry契約とは別のデータ源である。
- 両取得を日単位で `startRow` によりページングする。1日・検索種別・プロパティあたり50,000行の公開上限へ到達した場合は「API公開範囲」として扱い、匿名検索語を含む実際の全検索・全ページを取得済みとはしない。公開上限で返らなかったページの所見を解消済みにしない。
- 検索語の取得行数は定期実行全体で40,000行の共有上限を持つ。日付・次の `startRow`・版を永続化して次回に継続し、予算による未完了とAPI公開上限での完了を区別する。取得行数と選択ブログに保存した行数を分け、未完了・上限到達の理由を実行結果へ返す。
- 検索語はworkspace・ブログ・ページ・日・検索語に紐付ける。準備中の取得runと直前の完了runを分け、その日の取得完了時だけ読取対象を切り替える。行保存と参照先の版比較を同じD1 batchで確定し、途中失敗や遅延・同時実行で前回完了分を壊さない。
- 資格情報はサーバー環境変数からのみ読む。リポジトリ・環境変数ファイル・コマンド引数・管理画面・ログ・エラーメッセージのいずれにも保存も出力もしない。機械の側から鍵を書き出す経路を持たない。
- 鍵は運営者が Cloudflare の画面または wrangler から登録する。本リポジトリに鍵を置く手順を作らない。IndexNow の鍵が環境変数 1 本に確定している前例と同じ形を取る (`frontend` 章の注記 §3.3)。
- 鍵が未登録でも系統①の所見提示と承認差分の反映は成立する。鍵の欠落を機能全体の停止として現さない。
- 資格情報が上記のどこにも現れないことを機械検査で確認できるようにする (A3)。検査は CI で走る形にする。

### 検索語内訳の管理画面表示（A5、2026-09-08）

- 公開済み記事一覧から、所見や差分候補がない記事を含め、選択した1記事の既存SEO画面へ直接移動できる。検索語は同じ記事の「この記事の観測値」内で段階的に開き、新しい一覧画面や操作を増やさない。
- 検索語内訳は選択workspace・ブログ・ページと両端を含む直近28日へ束縛する。日付の新しい順、同日は表示回数の多い順で最大100件を表示し、100件を超える場合は続きがあることを明示する。
- 行と全28日分の同期状態は同じD1読取snapshotで返す。各日の直前に完了した参照先・API公開上限到達の有無・完了時刻を、再取得中のrunと分離する。再取得中に直前の完了分があればその行を保ち、初回の未完了を空の完了と扱わない。
- 表示は、Search Console未設定、ページ観測との未結合、未取得、初回取得未完了、直前の完了分を表示しながら更新未完了、完了した範囲の検索語0件、読取失敗、API公開上限、100件の表示打切りを区別する。読取失敗は検索語区画に閉じ、差分・ページ実績・ダッシュボード全体を失敗させない。
- 検索語内訳は匿名化された検索語を含まず、1日・検索種別・プロパティあたり50,000行のAPI公開上限と最大100件の表示打切りがある。日別行を合算せず、ページ全体の実績や実際の全検索を表す値として表示しない。未取得を0件へ変換しない。
- この表示は読取専用であり、外部API取得、記事改稿、承認token、既存の反映・取消操作を起動も変更もしない。

## 系統③ AI 検索での被引用チェック

- 自前の質問セットを AI 検索へ投げ、自サイトが引用されたか・どの URL が引用されたかを記録する。
- 費用は検索回数の従量とトークン課金が別建てで、モデルを小さくしても検索 1,000 件あたりの課金は下がらない。費用の主たる量は検索回数である (`backend` 章の注記「被引用チェックの費用が比例する量」)。
- 実効的な制御点は 1 リクエストあたりの検索回数上限であり、実装はこの上限を必ず指定する。
- 会話を継続させず 1 回の問い合わせで完結させる。検索結果は以後の会話ターンでも入力トークンに数え続けられるためである。判定は「自サイトの URL が引用一覧に含まれるか」の照合であり、問い直しを要さない。
- 運営者へ見せる上限の単位は「月あたりの検索回数」とする。金額を単位にすると問い合わせ先を替えたときに設定値の意味が変わる。
- 上限に達したら記録して停止する。記録には上限に達したかどうかを併記し、取りこぼしを「引用されていない」と読み違えさせない。

### 月次検索枠の実装契約（A4・NFR9、2026-09-07）

backend/databaseの正規注記「AI被引用チェックの月次検索枠（2026-09-07実装確認）」を現行契約とする。2026-09-06時点で未達とした月次累積予算は以下の範囲で解消した。旧QAと公開packageの原文はその時点の記録として保つ。

- 月次上限はworkspaceの全ブログで共有するUTC暦月のWeb検索回数。初期値NULLは未設定で停止し、0による明示的な停止と区別する。設定は0〜100,000回の整数で、未設定を無制限や実測0に変えない。資格情報なし・1実行上限0・月次枠不足も別の理由を返し、外部通信前に止める。
- 1問い合わせは最大3検索、1収集は既定50記事。月次検索回数と記事数を混ぜず、予約で得た残量に応じて `max_uses` を減らす。月次枠は検索回数の上限であり、トークン料金や請求額全体の上限ではない。
- `used` は提供元usageで確認できた検索数、`unconfirmed` は送信後に使用数が不明で再利用しない枠、`reserved` は実行中の予約。`remaining` は月次上限から3値を引いて0以上にした値で、上限未設定ならNULL。上限変更で過去の使用・未確認数を消さず、確保済みの実行は確定を続ける。
- 外部送信前のD1条件付き更新でworkspace総枠・ブログ割当・現在設定・同一ブログの実行中予約を照合する。古い設定による予約を拒否し、予約IDに束縛した精算と記事の試行時刻を同batchで保存する。二重確定・別workspace・途中失敗を成功にしない。使用数を確認できた分だけ確定し、未使用予約を返す。1時間を経た未確定予約は不明枠として保ち、期限切れを理由に再利用しない。
- 月はUTCの `YYYY-MM` で区切る。遅い精算は予約月へ適用し、翌月の残量へ混ぜない。送信直前に実時計で月替りを確認し、旧月予約で次の問い合わせを始めず、未使用分を返して次回へ回す。
- 実行時の公開ブログ間で均等配分し、割り切れない回数を受け取る順番は月ごとにずらす。記事は未試行→最古試行で巡回し、失敗記事だけで枠を使い続けない。予算はworkspace×月×ブログの1行、試行はworkspace×ブログ×記事の最新1行で保持し、所見・成功観測・本文を複製しない。
- HTTP 200でもツールエラー、1問い合わせの検索上限到達、未完了、検索未実行、usage不明は確認失敗。実検索が確認できた完了応答の本文citationと対象URLで引用を判定し、検索結果に出ただけのURLを引用ありにしない。失敗時も既知の検索数は計上し、不明なら当該問い合わせの予約枠を未確認数へ計上する。確認失敗を引用なしや新しい成功観測に変えない。
- 既存 `/admin/seo` の補助区画で全ブログ共通・UTC月・残り・確認済み・実行中確保・使用数未確認を近接表示する。人かつ `site.manage` 権限で月次上限を保存し、0では新規AIチェックだけを止める。サイト内解析・Search Consoleは続ける。既存のAIトークン概算や生成回数の台帳を月次検索枠の正本へ流用しない。

## 同一ページ識別子への突合と履歴

- 3系統の結果を同じworkspace・ブログ・ページに突合し、系統と観測日時を保つ。選択した記事の所見・反映履歴と同じページの実績へ到達できるようにする。
- 実績は明示したfrom/toの期間で絞り込み、表示された期間と取得範囲を一致させる。最新N件の上限がある場合は上限を明示し、件数だけの上限を「直近N日」と呼ばない。
- 未観測と実測0を区別する。Search ConsoleやAI被引用には遅延・外部変動があり、観測の変化だけで施策の因果効果や成果を断定しない。
- 履歴は系統別の保持期間を持つ。保持日数は既存の運用契約に従い、今回の表示接続で新しい保持基盤を作らない。
- D1の読取・書込はworkspaceと選択ブログを隔離し、別ブログの同じ記事名・所見・実績を混ぜない。
- 検索語内訳の読取口は選択ブログ・ページ・from/to両端を含む期間で絞り、最新日付から1〜100件を返す。行と各日の完了参照先・上限状態・再取得状態を同じ読取snapshotで返し、選択した記事の既存観測区画に日別内訳として表示する。これはページ全体の実績とは独立した内訳であり、件数制限付きの内訳を全体実績に置き換えない。

## 反映契約 (2026-09-10 改定)

現行契約は**機械が反映し、事後に通知する**。反映前の関門は置かない。
これを許すのは、上位制約 `constraints[4]` の免除条件——変更前後の差分を記録として残し、
1 操作で反映前へ戻せ、反映と同じ確定単位で運営者へ通知する——を 3 つとも満たす場合に限る。
どれか 1 つでも欠く実装は契約の外にある。旧名称auto-applyが残る内部モジュールも、この契約に従う。

**2026-09-06 の「承認した差分だけを反映する」は現行契約ではない。**独立監査 C06 が、その裏付け
`qa-seo-approved-diff-20260906` を 5 論点を 1 問へ束ねた誘導質問と判定したため、2026-09-10 に
論点ごとへ問い直して差し替えた (`qa-seo-apply-*-20260910` / `qa-seo-performance-presentation-20260910`)。

1. **事後通知**: 反映のたびに対象記事、根拠の所見、変更前後を記録し、反映と同じ確定単位で
   運営者へ通知する。通知を遅延させたり、複数の反映をまとめて 1 通にしたりしない。
2. **一括確定**: 記事更新・変更前後の履歴・所見の反映済み状態を同じD1の確定単位に置く。途中失敗時は全体を変更しない。履歴を先に別保存してから記事だけ変える経路も、記事だけ先に変える経路も持たない。反映は記事 1 件を単位とし、複数記事の一括反映は記事ごとに独立した確定単位とする。
3. **同時編集保護**: 保存時に、読み出した版と現在版が一致することを確認する。違えば書かずに止め、運営者へ知らせる。止めた反映は保留として扱い、反映済みの印を立てない。通常の記事公開・編集も共通の正本と版保護を使う。
4. **安全な取消**: 現在版が当該反映後の版と一致する場合だけ戻す。1 操作で反映前へ戻せることが免除の条件なので、この経路は必須である。反映後の追加編集を保護し、記事復元と取消記録を同じ確定単位で保存する。失敗や競合を成功履歴にしない。
5. **対象範囲**: 作成日時を問わず全ての記事を対象とする。作成日時が不明な記事も対象に含める。範囲で守らないぶん、2 と 3 (確定単位と版の一致) はどれか 1 つでも欠ければ反映を成立させない必須条件になる。
6. **夜間と根拠の境界**: Cronは観測・所見提示のみ。夜間収集から改稿を起動しない。差分の生成根拠は系統①の静的所見に限定し、系統②③は実績理解の材料にする。反映を停止しても観測を続ける。
7. **免除の及ばない範囲**: 免除は既に公開済みの記事本文への反映だけに及ぶ。**新規記事の外部公開と
   予約投稿は対象外で、従来どおり人間の承認を要する。**

反映の時刻・変更前後・根拠を履歴に残し、次回の静的解析で公開結果を確認する。反映記録だけを公開反映の証明にしない。観測比較の保留期間や同一記事の反映間隔は既存ポリシーを維持する。

## 定期実行と停止の検出

- Cron Triggerは系統ごとの観測・所見提示だけを実行する。夜間収集から改稿や一括反映を起動しない。
- 失敗した回と理由、系統別最終収集時刻を保持し、他系統の結果と次回の実行を失わせない。未収集と実測0を区別する。
- 想定間隔を超えて更新されない系統を名指しし、収集停止を検出する。未承認の所見があること自体を反映処理の故障とは扱わない。
- ジョブの冪等性・再試行上限・費用上限を既存運用契約に従って保持する。停止/再開・反映/取消は監査記録を残す。
- 静的監査は1回のCron全体でHTMLとllms.txtを合わせた外部取得25回の共有枠とし、公開ブログの開始順をUTC日ごとに交替する。記事0件の公開ブログも列挙する。HTMLで枠を使い切ればready世代を保持し、llms.txtは次回に確認する。通常の途中状態はcheckpointから再開し、上限によるlimitedは上記の条件に従う。全体確認完了時のみ成功時刻を進める。他2系統の共有取得枠やAI月次検索枠とは別に制御する。

## データ/API 境界

- 所見・差分・反映履歴・現在版を既存の永続化正本へ結び付ける。記事更新・履歴・所見状態を同じ確定単位で扱い、取消も記事復元と取消記録を一括確定する。
- 静的巡回のportは`SeoStaticAuditPort`、D1正本は`seo_static_audit_scan`と`seo_static_audit_target`（migration 0053）。scanはworkspace×ブログの1行、対象はrunId×pageKeyで一意とし、所見・成功観測・系統状態は既存表へ同batchで接続する。静的監査はページ別`replaceForPages`を併用せず、全体完了writerに所見の公開/解消責任を集約する。
- 収集器・突合エンジン・所見エンジン・承認差分の反映処理・停止制御・停止検出をコンポーネントとして分け、反映エンジンが系統②③の所見を受け取れない型にする。
- 資格情報は infrastructure 層の 1 か所からのみ環境変数として読み、domain / application / presentation へ値として渡さない。
- 記事の更新は既存の blog-ops の書き込み経路を通し、並行する正本を作らない。Workspace 境界、role authorization、audit event、optimistic concurrency を全 mutation に適用する。
- 検索は D1 の FTS5 全文検索を前提とする (`backend` 確定内容 qa-neutral-search-method-v6)。AI 向け表現物は llms-full.txt と WebMCP の両方であり (同 qa-neutral-ai-surface-v6)、本 feature はその出力の有無を計測する。
