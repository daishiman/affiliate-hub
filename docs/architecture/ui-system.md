# UI / UX の一元管理

**同じ見た目・同じ操作感を、画面の数だけ書き直さないための決まり。**

UI を共通化しないと、次の 3 つが必ず起きる。

1. 広告表示（ステマ規制対応）の実装が画面ごとに違い、法改正のとき直し漏れる
2. ブログを 1 つ足すたびに、色とレイアウトの分岐がコードに増える
3. 「読み込み中」「空」「失敗」の見せ方が画面ごとに違い、利用者が学び直す

ここはその決まりの**正本**。ずらしたくなったら、先にこの文書を直す。

---

## 1. 全体の形

```
src/presentation/ui/
├── tokens/            見た目の値の正本（3 段）
│   ├── primitives.css   1 段目: 生の値。色階調・寸法・時間
│   ├── semantic.css     2 段目: 意味。部品が読んでよいのはここだけ
│   └── themes.css       3 段目: ブランドごとの差し替え
├── copy.ts            画面に出す言葉の正本
├── primitives/        土台の部品（意味を持たない）
├── patterns/          仕様固有の部品（意味を持つ）
└── templates/         画面の骨格
```

依存の向きは **primitives ← patterns ← templates** の一方向。
逆流すると「順位表を直したらボタンが壊れる」状態になる。
機械チェック: `tests/ui/ui-layers.test.ts`

部品はすべて**表示だけ**を行う。データ取得も業務判断も持たない。
持たせた瞬間、その部品は 1 画面でしか使えなくなる。

## 2. 見た目の値（デザイントークン）

### 2-1. 3 段にする理由

| 段 | 名前の付け方 | 例 | 誰が読んでよいか |
| --- | --- | --- | --- |
| 1 段目 | 何色か・いくつか | `--neutral-750`, `--size-3` | 2 段目だけ |
| 2 段目 | 何に使うか | `--color-text-default`, `--space-3` | 部品・画面 |
| 3 段目 | ブランドごとの差し替え | `[data-brand-theme="indigo-teal"]` | （上書きのみ） |

1 段目を部品から直接読むと、ブランドを増やしたときに全部品を触ることになる。
2 段目を挟むことで、**差し替えの対象が 2 段目のトークン 10 個だけ**に閉じる。

### 2-2. 明暗の切り替え

`light-dark()` を使い、1 トークンにつき定義は 1 行。

```css
--color-surface-default: light-dark(var(--neutral-0), var(--neutral-950));
```

明暗で 2 ブロック書くと、片方だけ直して色がずれる事故が必ず起きる。
切り替えは `color-scheme` を変えるだけ（`[data-color-mode="light"|"dark"]`）。
**部品に明暗の分岐を書かない。**

高コントラスト（`prefers-contrast: more`）も、別配色を作らず
境界と文字を強くするだけにする。配色を増やすと AA 検証がその数だけ増える。

### 2-3. ブランドテーマ

ブランドごとの違いは **2 段目のトークン 10 個の値の差**だけ。

```
--color-action-default / hover / active / subtle
--color-text-on-action
--color-accent-default / hover / subtle / border
--color-text-on-accent
```

サイトブループリントがテーマ名を持ち、`<html data-brand-theme="...">` に出る。
テーマが上書きする範囲が揃っていることは
`tests/ui/design-tokens.test.ts` が確認する（一部だけ上書きすると、
そのテーマにだけ既定色が混ざる）。

### 2-4. 折り返し位置だけは例外

CSS の `@media` と Tailwind の設定は `var()` を受け取れない。
ここだけは数値を直接書く。ただし**どのトークンの写しかを注記させ、
値が一致していることをテストで確認する**。

```css
@media (width < 48rem) { /* --breakpoint-md */ }
```

「単一の正本がある」と言えない箇所を、言えないまま安全にする方法がこれ。

## 3. 言葉

`src/presentation/ui/copy.ts` が画面に出る言葉の正本。

- `TERMS` … 概念の呼び名。`docs/architecture/ubiquitous-language.md` と 1 対 1
- `UI_COPY` … 状態・操作・確認など、画面固有の言い回し

**JSX に日本語を直接書かない。** 書き始めると、
言い換えのときに画面の数だけ探し回ることになる。
多言語化の口（`Locale`）も最初から開けてある。

機械チェック: `tests/ui/copy-dictionary.test.ts`
辞書とずれた呼び名、禁止した言い換え、空の文言を落とす。
このチェックは導入直後に、ドメイン層の言い回しのゆれを 5 件見つけた。

## 4. 仕様固有の部品（patterns）

**画面ごとに書き起こさせないもの。** ここが要件の中心。

| 部品 | 何を守るか |
| --- | --- |
| `DisclosureNotice` | 景品表示法のステマ告示（2023-10-01 施行）への対応表示 |
| `AffiliateLink` | `rel="sponsored"` の付与と、ASP 発行 URL の**無改変** |
| `RankingTable` / `CriteriaDisclosure` | 順位は採点表から機械的に決まる。並べ替え関数を持たない。報酬額の欄を型に持たない |
| `ComparisonTable` | 列を配列で受け取る。列追加で JSX を書き足さない |
| `FactualityBadge` / `ClaimStatement` | 事実・推測・意見の区別。`kind` 必須で書き忘れをコンパイルで止める |
| `EvidenceList` / `ProvenanceNote` | 出典と確認日。**0 件のときに黙らない** |
| `ApprovalFlow` | 承認の現在地。人の承認が必要であることの明示 |
| `StubNotice` / `StubLabel` | 見本であることを隠さない。使えるようになる条件を必須にする |

画面がこれらを自前で書いていないことは `tests/ui/ui-layers.test.ts` が確認する
（`rel="sponsored"` の直書き、開示文言の直書き、`data-stub` の直書きを検出）。

出力の中身は `tests/ui/patterns-render.test.tsx` が見る。
型が通ることと、法令要件を満たす HTML が出ることは別。
`rel="sponsored"` が消えていても型は通る。

## 5. 操作の作法（UX パターン正本）

画面ごとに変えない。ここに書いてあるものだけを使う。

### 5-1. 状態は 4 つ、必ず全部作る

| 状態 | 出すもの | 部品 |
| --- | --- | --- |
| 読み込み中 | 何を読んでいるか。読み上げにも届ける | `LoadingView` |
| 空 | **なぜ空か** + 次にできること | `EmptyView` |
| 失敗 | 何が起きたか + 復帰の導線 | `ErrorView` |
| 操作できない | **なぜできないか** + 解決先 | `Callout` |

`title` と `body` を必須にしてあるので、書き忘れはコンパイルで止まる。
**編集できない一覧・ゼロが並ぶ表示には、理由を 1 行必ず出す。**
無言で止めると、利用者は「壊れている」と受け取る。

### 5-2. 入力

作法は 1 組だけ。タブや手順ごとに分岐させない。

1. 空欄の意味は「未入力」。0 と読み替えない
2. 自動計算値は**欄の中に初期値として**入れる。由来を必ず添える。手で書き換えたら「自動の値に戻す」が出る
3. Enter は「次の欄へ」。フォームの送信はしない
4. 「任意」だけ印を付ける。「必須」とは書かない（ほとんどが必須なので印の意味が消える）
5. エラーは欄の直下。直せる言葉で書く（「invalid」ではなく「半角数字で入力してください」）

### 5-3. 取り消せない操作

`UI_COPY.confirm` の文言で、毎回同じ形で聞く。
文言を操作ごとに変えると、利用者は読まなくなる。

### 5-4. 楽観的更新

すぐ反映して、失敗したら**元に戻して理由を出す**。
戻したことを黙っていると、利用者は成功したと思ったまま次へ進む。

### 5-5. 時間のかかる処理

秒数ではなく「何件終わって何件残っているか」を出す（`UI_COPY.progress.stepFormat`）。
中止できるものは中止できると書く。

### 5-6. 通知

消えてよいものだけトーストにする。**失敗は画面に残す。**
消えるもので失敗を伝えると、見逃した人には何も起きていないのと同じになる。

### 5-7. 動き

因果の説明にだけ使う。入場は全体 300ms 以内、最大 6 要素。
`prefers-reduced-motion` ですべて止めてよい作りにする
（動かないと分からない情報を作らない）。

## 6. 画面の並び（情報設計）

階層は **ワークスペース → ブランド → サイト → コンテンツパッケージ**。
この 4 段をナビゲーションとパンくずの両方で同じ順に出す。
場所によって並びを変えると、利用者は毎回考え直すことになる。

- 現在地（どの階層のどこか）と退避先（保存・戻る）は固定表示する
- 固定表示しない画面がある場合、その理由をこの文書に残す
- 定義は `templates/app-shell.tsx` の `ADMIN_NAV` 1 箇所

## 7. アクセシビリティ（WCAG 2.2 AA）

**部品側で担保する。** 画面ごとの努力目標にしない。

| 項目 | どう守るか |
| --- | --- |
| 文字と背景のコントラスト | 2 段目のトークンに実測値を注記。AA を割る値を作らない |
| 焦点の見え方 | `:focus-visible` を共通指定。部品で上書きしない |
| 触れる大きさ | `--tap-target-min: 44px` |
| 色だけに頼らない | 事実区分は記号 + 文字を併記 |
| 見出しと表の構造 | 表は `<caption>` と `scope` 付きの見出しセルを必ず持つ |
| 読み上げ | 状態表示は `aria-live`、失敗は `role="alert"`、手順は `aria-current="step"` |
| 動きを減らす設定 | `prefers-reduced-motion` に対応 |

---

## 8. 新しいブログを足すとき

**コードを書かない。** サイトブループリント + 設定値 + テーマ名だけで増やす。

1. ブランドテーマを `themes.css` に 1 ブロック足す（既存と同じ 10 トークンを上書き）
2. サイトブループリントに設定値を書く
3. 以上

画面のコードにブログ名の分岐が入ったら、それは設計の失敗。
検証は `docs/architecture/changeability-scenarios.md` に実測で記録する。
