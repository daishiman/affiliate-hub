# 自動チェックと公開の運用ガイド

このページは**専門用語なしで**読めるように書いています。
「何を自動で見ているのか」「赤くなったらどうするか」「どうやって本番に出すのか」の 3 点です。

規範（なぜそうするか）は `docs/spec/11-CI-CD・品質ゲート仕様.md`、
設定の中身は `.github/workflows/` にあります。

---

## 1. ひとことで言うと

変更を出すたびに、**機械が 5 種類の確認を自動で行います。**
どれか 1 つでも引っかかると赤くなり、本番には出せません。

「テストしました」という報告は、人が言うと外れることがあります。
機械が実際に走らせて記録を残す形にしてあるので、**言ったことと起きたことがずれません。**

日常的に使う主な経路は **3 つ**です。このほかに枝の順番・深い検査・AI 評価・Actions 使用量の
読み取り中心の仕組みがありますが、アプリや D1 を変更する経路は下の表に集約しています。

| 名前 | いつ動くか | 何をするか | 壊れうるもの |
| --- | --- | --- | --- |
| **検査** | 確認をお願いした時（PR） | 下の 5 種類をまとめて実行 | **なし**（見るだけ） |
| **公開** | `dev` / `main` に反映された時（**本番は承認してから**） | 検査 → 控え → 未適用の形を自動適用 → 台帳と実際の形を確認 → 公開 → 動作確認 | アプリと**データの形** |
| **データの形の変更** | 人が手で起動した時だけ（公開と分けた明示適用・修復） | 控え → 前方移行 → 台帳と実際の形を確認 | **データ**（元に戻せない） |

壊れうるものの重さが 3 段階なので、動き出す条件も 3 段階にしてあります。

## 2. 自動で見ていること

| 見ているもの | かみ砕くと | 落ちたら何が起きていたか |
| --- | --- | --- |
| 型検査 | 部品どうしの噛み合わせ | 動かすと落ちる組み合わせが混ざっている |
| 書き方の検査 | 決めごとを破っていないか | 画面に色を直書きした、層をまたいで呼んだ、など |
| テスト | 実際に動かして答え合わせ（設計の約束の検査もここに含みます。例: 順位づけに報酬額が入り込んでいないか） | 前は動いていた何かが壊れた |
| 覆えている割合 | テストが届いていない場所の量 | 手を抜いた場所が増えた |
| 部品の弱点調べ | 使っている外部部品に既知の弱点がないか | 直せない事情もあるため、これだけは**赤にせず警告どまり** |

このほかに、検査の最後で「**保存するデータの形を変えたのに、変更手順を作り忘れていないか**」を見ています。
忘れたまま公開すると、新しいアプリが「まだ無い列」を読んで本番が止まります。

**本番の組み立て（ビルド）は検査では行いません。**
噛み合わせの確認に必要なところまでは型検査で済んでおり、組み立ては公開のときに 1 回やれば足ります。
毎回 5 分以上かかる処理を、同じ結果のために 2 回走らせないためです。

## 3. 手元で同じことを確かめる

ターミナルで次の 1 つを実行すると、**機械が見ているのとまったく同じ確認**が走ります。

```
pnpm verify
```

「機械の上でだけ落ちる」状態を作らないために、CI 側に別の確認を足さない決まりにしています。
機械の上でしか試せない状態は、直せない状態と同じだからです。

## 4. 赤くなったときの直し方

| 出てくる言葉 | 意味 | まずやること |
| --- | --- | --- |
| `Typecheck` が失敗 | 噛み合わせが合っていない | エラーに出ているファイルの行を直す |
| `Lint` が失敗 | 決めごとを破った | メッセージにどの決めごとかが出ます |
| `Tests` が失敗 | 動かした結果が期待と違う | 失敗したテストの名前が「何が壊れたか」を表しています |
| `Coverage` が失敗 | テストが届いていない場所が増えた | **閾値を下げて緑にしないこと。** 足りない場所にテストを足します |
| `マイグレーション未生成` | データの形を変えたのに手順を作っていない | `pnpm db:generate` を実行して、できたファイルも一緒に保存します |
| `データの形が移行ファイルと違います` | 台帳の名前は揃っていても、実際の表・索引・トリガーに不足・余り・同名異所属/異定義がある | 出力の `missing`（不足）/ `extra`（余り）/ `changed`（定義差）の名前を控え、§6 の「ずれを直す」へ進みます |
| 「公開」の中で失敗 | 組み立てか、公開後の動作確認で落ちた | 本番はまだ古い版のままです。落ちた段階の記録を見て直します |

**閾値を下げて緑にするのは禁止です。** 下げた記録は残らないので、
次に見る人は「元からこの水準だった」と思ってしまいます。

## 5. 本番へ出す流れ

```
   作業する
      ↓
   確認をお願いする（この時点で自動チェックが走る）
      ↓  ← ここが緑でないと先へ進めません
   試し場（dev）へ反映 → ご自身で触って確かめる
      ↓
   本番（main）へ反映
      ↓  ← ここで「承認しますか」と止まります（下の設定をした場合）
   ご自身が承認する
      ↓
   公開 → 30 秒待って 1 回目の確認 → 90 秒待って 2 回目の確認 → 目印を付ける
```

出し先は反映先で自動的に決まります。`dev` なら試し場、`main` なら本番です。

### 「承認しないと本番へ出ない」ようにする設定（ご本人が 1 回だけ行います）

これを設定すると、**うっかり本番へ反映してしまっても、承認するまで公開されません。**
このリポジトリは公開設定のため、この機能が使えます。

1. GitHub のリポジトリ画面 → `Settings` → `Environments`
2. `New environment` を押し、名前に **`production`** と入力して作成
3. `Required reviewers` にチェックを入れ、**ご自身を選ぶ** → `Save protection rules`
4. 同じ画面の `Environment variables` に `APP_URL`（本番 URL）を追加
5. もう一度 `New environment` で **`dev`** を作り、`Environment variables` に `PREVIEW_URL`（試し場の URL）を追加
   （`dev` には承認者を付けません。試し場は気軽に出せる場所にしておくためです）

設定すると、本番へ出るたびに GitHub から通知が届き、画面上の `Review deployments` を押すまで止まります。

### 元に戻す目印

本番へ公開できるたびに `v1`、`v2`… と番号の目印が付きます。
「1 つ前に戻したい」ときは、この番号を指して戻します（§7）。

### なぜ 2 回確認するのか

Cloudflare は、新しい版を出したあとも**古い版をしばらく動かし続けます**（数十秒〜1〜2 分）。
1 回だけ見ると、次の 2 つが**両方**起こり得ます。

- 直っているのに「直っていない」と見えてしまう
- 壊れているのに、古い正常な応答を見て「大丈夫」と思ってしまう

だから間隔を空けて 2 回見ます。

## 6. データの形を変えるとき（いちばん慎重にやること）

保存しているデータの**形**（列を足す・消すなど）を変える操作は、**元に戻せません**。
列を消すと中身も消えます。

だから「公開」は、**戻る先を用意できたときだけ**形を変えます。
dev でも本番でも、順番は同じです。

1. 中身の控えを取ります
2. **控えが空でないことを確かめます。空だったら、そこで止まります**（形は変わりません）
3. 控えをその実行の記録に 30 日間残します
   （実行画面の下の方に、ダウンロードできるファイルとして出ます）
4. 形を変えます
5. 台帳に未適用が 0 件になったことを確かめます
6. 実際の表・索引・トリガーに不足・余り・同名の定義差がないことを確かめます

2 がいちばん大事なところです。ここが通らなければ 4 は起きません。

- 順番は必ず **データの形を変える → アプリを出す**
  （逆にすると、新しいアプリが「まだ無い列」を読んで、本番が全面的に止まります）
- 列を消すときは 2 段階に分けます（誰も読まない状態にしてから消す）

**普通の公開では、手動の「データの形の変更」を先に走らせる必要はありません。**
「公開」自身が 1〜6 を実行したあとでアプリを出します。手動経路は、公開と分けて
形だけ先に適用するとき、またはずれを前方修復するときだけに使います。

同じ dev / 本番に対する「公開」と「データの形の変更」は同時に走りません。
先に始まったほうが終わるまでもう一方が待つため、台帳を見た直後に別の実行が形を変える競合を防ぎます。

### あなたが判断する場所は、その手前です

**本番へ出すときは、承認するまで「公開」そのものが始まりません**（§5 の Environment）。
判断してほしいのは「出してよいか」であって、「控えを取ったか」ではありません。
後者は毎回まったく同じ手順なので、覚えておくより機械に順番で守らせるほうが、
うっかり飛ばすことが起きません。

以前は本番だけ手で起動する決まりにしていましたが、そのせいで 2 つのことが起きていました。
ひとつは、dev で形の変更を含む変更が
「公開がいったん失敗する → 手で形を変える → 公開をやり直す」を毎回たどっていたこと。
失敗が普通のことになると、赤い印を見ても「またこれか」と思うようになり、
**本当に何かおかしいときに気づけなくなります**。
もうひとつは、手で流すとき控えを取るかどうかが、その人の記憶次第だったことです。

### 公開と分けて明示適用・修復するとき

「データの形の変更」は、先に形だけ整える明示適用と、新しい番号の
修復手順を流すために残してあります。

- GitHub のリポジトリ画面 → `Actions` → 左の一覧から「データの形の変更」→ `Run workflow`
- どちらの環境か選び、確認欄に **`APPLY`** と入力しないと動きません

### ずれを直す

1. `missing`（不足）/ `extra`（余り）/ `changed`（同名異所属・異定義）に出た名前を記録し、公開の再実行を止めます
2. 控えを取り、新しい番号の前方修復ファイルで形を正本へ寄せます
3. ローカルで適用と形の検査を通し、上の手動経路を `APPLY` 付きで実行します
4. 不足・余り・定義差がすべて 0 になったことを確かめ、公開を再開します

適用済みの移行ファイルは書き換えず、`d1_migrations` の行を直接追加・更新・削除して緑にしません。
台帳が壊れて前方修復を適用できない場合は通常修復ではないため、所有者承認と復旧点を用意した
別の事故対応に切り替えます。事故の背景と機械が見る範囲は
[`11-CI-CD・品質ゲート仕様.md` §4-1-2](../spec/11-CI-CD・品質ゲート仕様.md#4-1-2-形のずれ) を見てください。

## 7. 元に戻したいとき

- 直前の版へ戻す: `wrangler rollback`
- もっと前へ戻す: `/undo-app`（変更を打ち消す形で戻します。履歴は消しません）

**データの形の変更は、この方法では戻りません。** アプリだけが戻ります。
形の変更を戻したいときは、§6 で取った控えを使います。だから控えを先に取っています。

## 8. 鍵とパスワードの扱い

- API キーなどは、**この仕組みの中に置きません。**
  GitHub と Cloudflare の「秘密の保管場所」に、**ご本人が**登録します。
- こちらでは代行しません。AI が読める場所に秘密を置かないためです。
- 登録は、ブラウザの管理画面か、ご自身のターミナルで行ってください。

登録が必要なもの:

| 名前 | 秘密か | どこで取るか | どこへ入れるか |
| --- | --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | **秘密** | Cloudflare の管理画面 → 右上のアイコン → プロフィール → API トークン | GitHub の `Settings` → `Secrets and variables` → `Actions` → `Secrets` |
| `CLOUDFLARE_ACCOUNT_ID` | **秘密扱い** | Cloudflare の管理画面の URL に出ています | 同上 |
| `APP_URL` | 秘密ではない | 公開後の本番 URL | `production` 環境の `Environment variables`（§5） |
| `PREVIEW_URL` | 秘密ではない | 試し場の URL | `dev` 環境の `Environment variables`（§5） |
| `MCP_TOKEN` | **秘密** | ご自身で決めた長い文字列 | **Cloudflare 側**（ターミナルで `wrangler secret put MCP_TOKEN --env production`） |

`MCP_TOKEN` は AI から操作するときの合言葉です。**未登録のうちは、そこだけ閉じた状態**になり、
公開後の動作確認が「503」で赤くなります。壊れているのではなく、まだ鍵が無い状態です。

キーの権限は**必要な分だけ**にしてください。
「Workers Scripts: 編集」と「D1: 編集」の 2 つで足ります。対象は**ご自身のアカウント 1 つ**に絞ってください。

ターミナルで登録する場合は、**値をコマンドに書かずに**次のように打つと、あとから入力を求められます。

```
gh secret set CLOUDFLARE_API_TOKEN
gh secret set CLOUDFLARE_ACCOUNT_ID
gh secret list
```

値を直接コマンドに書くと、打った内容の履歴として端末に残ります。

## 9. 費用について

このリポジトリは**公開設定**のため、自動チェックの実行時間は**無料・無制限**です。
それでも次を守っています。非公開に切り替えた瞬間に上限（月 2,000 分）が効き始めるためです。

- 動かす機械は Linux のみ（他は 2〜10 倍の消費）
- 新しい変更を出したら、古い検査は打ち切る（公開は打ち切りません。どの版が出たか分からなくなるため）
- すべての処理に時間の上限を付ける
  （これは節約ではなく**安全弁**です。上限が無いと、暴走した処理が 6 時間走り続けます）
- 検査では本番の組み立てを行わない（§2）

**Cloudflare 側の Git 連携は使いません。** 両方を有効にすると二重に公開が走り、
どちらの成果物が本番なのか分からなくなります。公開は GitHub 側に寄せています。

### 何が無料で、何にお金がかかるか

| やっていること | 費用 | なぜ |
| --- | --- | --- |
| 自動チェック（型・書き方・テスト・カバレッジ） | **0 円** | 公開設定のリポジトリでは、検査に使う機械が無料・無制限だからです |
| 深い門（人が打ったとき） | **0 円** | 同じ理由です。長く回しても費用は変わりません |
| 本番への公開 | **0 円** | 同上です |
| **AI に文章の良し悪しを採点させる検査** | **お金がかかります** | 外部の AI サービスへ問い合わせるためです。1 回まわして概算 1,000 円弱を見込んでいます |

**お金がかかるのは最後の 1 つだけです。** そのため、この検査だけは

- 自動では**絶対に走りません**（決まった時刻の実行も、変更を出したときの実行もしません）
- 走らせるにはご本人が画面から起動し、確認用に `RUN` と入力する必要があります
- 走っている最中に上限に達したら、**そこで止まります**（最後まで走ってから「超えました」とは言いません）
- 走らせる前の見込み額と、走らせた後の実際の額を、両方表示します

裏を返すと、**検査の実行時間を減らすためにテストを削る理由はありません。**
「時間がかかるからテストを減らす」という判断は、この構成では 1 度も必要になりません。

なお、この AI 採点は**作らないと決めました**（2026-08-17）。作りかけで放置しているのではありません。
文章の良し悪しを機械で採点しようとすると、結局もう一度 AI に聞くことになり、
**採点する側が正しいかを確かめる手段が無いまま、お金だけがかかります**。
たたき台の段階では割に合わないという判断です。
いま起動すると 0 件で**赤くなって止まります**。0 件・0 円で緑にすると、
押した方が「採点を通った」と受け取ってしまうためです。**赤いのが正しい状態**です。
（AI を使わない検査 ── 採点項目の定義が仕様を覆っているかを見るもの ── は無料で動いています。）

### 深い門は「定例」をやめました（2026-08-18）

以前は毎晩 3:00（日本時間）に自動で走らせていました。**やめました。**
いまは**人が打ったときだけ**走ります。

**やめた理由は「重かったから」ではありません。** 実測は 27 分 0 秒で、
毎日走らせても月の枠に収まる程度に軽いものでした。それでも要らないと判断しました。

深い門が答えるのは「**いま公開してよいか**」であって、「昨夜の時点でどうだったか」ではありません。
**誰も見ない緑が毎晩 1 つ増えるだけなら、それは記録であって門ではありません。**

同時に、公開／非公開を見て曜日を判定していた仕掛け（`PRIVATE_RUN_DOW`・「予算の門」）も
消しました。あれは「どの曜日に走らせるか」を決めるためだけのものなので、
定例が無くなれば守るものがありません。
**動かないまま残る仕掛けは、あとから読む人に「まだ走っている」と読まれます。**

### **代わりに、打つ場面を決めました**

定例をやめると、深い門は**誰も打たなければ一度も走らない検査**になります。
**場面を書かずに定例だけ外すのは、検査を消したのと同じです。** だから場面を書きます。

| いつ | 誰が | なぜ |
| --- | --- | --- |
| **本番へ公開すると判断する日**（必須） | 公開を決める人 | `docs/product/open-doors.md` を見る回と**同じ回**に含めます。公開の判断に要るものを 1 回で揃えるためで、日を分けると「今日はどっちを見る日か」を覚えている人が要ります |
| domain / application の**テストを大きく足した・消した直後** | 動かした本人 | 深い門はテストがコードの書き換えに気づくかを見るので、テストの側が動いた回にしか意味のある差が出ません |
| **3 段のテストを新しく足した回**（いまは 0 件） | 足した本人 | 打たないと、中身が 0 件のまま通っていた頃と区別が付きません |

打ち方は 1 つです。GitHub の Actions で「深い門」を選び、`Run workflow` を押します。

### 費用について（もう頻度の根拠ではありません）

実測は残しておきます。ただし**これは「何回走らせるか」を決めるための数字ではなくなりました**
（回数が決まっていないので、掛ける数がありません）。
3 段の対象を増やすときに、1 回あたりの重さとして使います。

| 何を | 実測 | 1 回あたりの目安 |
| --- | --- | --- |
| 速い門（保存のたび） | テスト 11 秒 | 準備を含めて約 2 分 |
| 広い門（確認依頼のたび） | テスト 31 秒 | 準備を含めて約 3 分 |
| 深い門（人が打ったとき） | **27 分 0 秒** | 約 27 分 |

非公開にすると月 2,000 分という枠が効き始めます。定例が無いので、
深い門がこの枠を食う量は**打った回数ぶんだけ**です
（月に 2〜3 回なら 54〜81 分で、ほかの検査と公開の約 1,050 分に足しても余裕があります）。
なお非公開の機械は性能が半分になるため、27 分はもう少し延びます。

### 「使いすぎ」の見張りについて

「月の使用量が 70% を超えたら警告」というご要望をいただいていました。
**見張りは置きました。ただし、いまは鳴りません。**鳴らない理由をそのまま表示します。

公開のあいだは実行時間が無制限なので、「上限の 70%」という数が作れません。
そこでこの見張りは、公開のあいだ **0% を報告しません。**
「対象がありません」とだけ出します。
0% と書くと「余裕がある」と読まれますが、それは余裕ではなく**測っていない**という意味だからです。

**非公開に切り替えた日から、この見張りが本番になります。**
そのとき鍵（トークン）が登録されていなければ、
「見張りは動いていません」という**警告が出ます**。黙って緑にはしません。
やることは §12 に書いてあります。

深い門を打つたびに出る「所要時間」は、**深い門 1 回分**の数字です。
§12 の見張りが見るのは**口座（ご本人のアカウント）全体の 1 か月の合計**で、別のものです。
1 回が軽くても、全部足すと枠に当たることがあります。

## 10. 検査を足す・外すときの手順

1. `quality-gates.config.mjs` を開く
2. `CHECKS` に 1 行足す（`id` / 実行する指示 / 止めるか警告どまりか / **入れた理由**）
3. `pnpm verify` を手元で走らせて、その 1 行が実際に動くことを確かめる
4. **わざと壊して、赤くなることを確かめる**

4 を飛ばさないでください。通ることだけを見ても、「本当に見ているか」は分かりません。
表示されているのに実際には使われていない設定、という不具合は現実によく起きます。

外すときも同じファイルの 1 行を消すだけです。
`.github/workflows/` を触る必要が出てきたら、それは「1 か所にまとめる」が崩れた合図です。

## 11. 検査の 3 つの段

検査は重さで 3 つに分けてあります。**重い検査を足す前に、置き場所を先に作りました。**
順番が逆だと、検査が終わらなくなってから「重い検査を消す」方向に流れます。

| 段 | いつ走るか | 目安の時間 | 反映を止めるか | 中身 |
| --- | --- | --- | --- | --- |
| 速い門 | 保存のたび・確認依頼のたび | 5 分 | **止めます** | 型・書き方・単体の検査 |
| 広い門 | 確認依頼のたび | 15 分 | **止めます** | 画面・つなぎ目・読み上げ・網羅率 |
| 深い門 | **人が打ったときだけ**（定例なし・場面は §9） | **27 分（実測）** | 止めません | 全体のミューテーション検査ほか |

深い門が止めない理由は、止めると手が止まる人が出て、
やがて**深い門そのものが外される**からです。外された検査は、落ちる検査より困ります
（あると思われているのに、実は無い状態になるため）。

**目安の時間を超えても、赤にはしません。**警告を出すだけです。
時間で赤くすると、時間を守るためにテストを減らす力が働くためです。

### 新しいテストを書くときにひとつだけお願いすること

テストのファイルの先頭に、どの段のものかを 1 行書いてください。

```
/** @tier 1 */
```

書き忘れると**自動チェックが赤くなります**。これはわざとそうしてあります。
段の指定が無いテストは、どの段でも走らないまま「緑」になってしまうためです。
実際に指定の無いテストを足して、赤くなることを確認してあります。

現況: 速い門 74 件 / 広い門 35 件 / 深い門 0 件（深い門の中身はこれから足します）。

## 12. 使いすぎの見張り（口座全体の月間使用量）

### 何を見ているか

GitHub Actions は、**非公開**のリポジトリでは月 2,000 分までが無料で、
それを超えると有料になります。使い切ると、**検査も公開も止まります。**
止まってから気づくと、その場の判断が「検査を減らす」に流れます。そうならないための見張りです。

| | 見ているもの | どこ |
| --- | --- | --- |
| 深い門の「所要時間」 | 深い門を打った**その 1 回**が何分かかったか | 深い門の実行結果 |
| **この見張り** | **口座全体の 1 か月の合計**が、枠 2,000 分の何%か | 「使用量の見張り」（毎週月曜＋手動） |

**どちらか片方では足りません。**1 回が軽くても合計では枠に当たりますし、
合計に余裕があっても 1 回 3 時間かかるなら、打つ回数の判断は別に必要です。

### いつ何が出るか

| 状況 | 出るもの |
| --- | --- |
| **公開のあいだ**（いまここ） | 「対象がありません」という案内だけ。**使用率は出しません** |
| 非公開＋鍵が未登録 | **警告**「見張りは動いていません」 |
| 非公開＋枠の 70% 以内 | 使用量と割合をそのまま表示 |
| 非公開＋**70% 超** | **警告**（今月の残り分数つき） |
| 非公開＋**90% 超** | **エラー表示** |

**どの場合も、この見張りが公開やマージを止めることはありません。**
止めると、赤を消す最短の道が「この見張りを外す」になるためです。

### 非公開に切り替えた日にやること（ご本人の作業です）

1. GitHub の画面で fine-grained token を作ります。個人口座なら **Plan (read)**、
   組織口座なら **Administration (read)** だけを許可します
2. そのリポジトリの Settings → Secrets → Actions に、
   名前 `ACTIONS_USAGE_TOKEN` で登録します
3. Actions から「使用量の見張り」を 1 度手で起動し、割合が表示されることを確かめます

**この 3 つを代わりにやることはできません。**鍵の値は、
AI が読める場所（ファイル・コマンドの履歴）に 1 度も置かない決まりだからです（§8）。
登録しないままでも構いませんが、その場合は毎週「動いていません」という警告が出ます。
**「登録していないこと」が見える状態のほうが、静かに見張っていない状態より安全です。**

### 警告が本当に出るかを確かめる方法

Actions から「使用量の見張り」を選び、`Run workflow` の
**「使用量を分で与える」** に `1500` と入れて起動します。
70%（1,400 分）を超えるので、警告が出ます。`1900` を入れればエラー表示になります。

このとき出力の先頭に
**「使用量を外から与えています（測定用）」**という断り書きが必ず付きます。
断り書きの出ない入口を作ると、そこが「実測のふりをする」入口になるためです。

### しきい値を変えるとき

枠（2,000 分）・警告（70%）・エラー（90%）の 3 つは
`quality-gates.config.mjs` の `ACTIONS_USAGE` **1 か所**にあります。
ワークフローの設定ファイルには数字を書きません（書くと、機械だけが古い基準で走ります）。
