規範は `docs/spec/10-テスト戦略仕様.md` §2。全体の下限は **80%**、層ごとの下限は
`quality-gates.config.mjs` の `LAYER_COVERAGE` が正本。

**この文書の数字を手で書き換えない。** 末尾の囲みは
`scripts/coverage-report.mjs` が実測から丸ごと差し替える。
手で書いた数字は、古くなっても古く見えないため、最も危険な形で残る。

---

## 1. 測り方（再現できる形で残す）

```bash
pnpm run test:coverage          # 測る（全体の閾値に届かなければここで落ちる）
node scripts/coverage-report.mjs  # 層別に割って、この文書を書き換える
```

`pnpm verify` はこの 2 つを含めて機械と同じ順で走らせる。
どちらの下限も `quality-gates.config.mjs` の 1 ファイルだけを見ている。

`.css` を測る対象から外してあるのは、v8 が解析できず PARSE_ERROR が並ぶため
（数字は変わらない。雑音が消えるだけ）。

## 3. 数字合わせの検出（スタブを除いた実質）

**スタブをカバレッジ計算から除外しない。** 除外すると、除外の線引きを動かすだけで
数字を作れてしまう。代わりに**併記する**（仕様 §2-1）。

見るべきは絶対値ではなく**差の動き**である。

- 実質が上がって差が縮む → 本物のコードのテストが増えている（正しい進み方）
- 全体だけ上がって差が開く → **数字合わせが起きている**

差の推移（手で追記する。ここだけは履歴なので自動生成しない）:

| 日付 | 全体（行） | 実質（行） | スタブ（行） | 差 | 何をした後か |
| --- | --- | --- | --- | --- | --- |
| 2026-08-17 | 53.03% | 51.92% | 63.47% | **+11.55pt** | 起点。テスト基盤の実装前 |
| 2026-08-17 | 75.0% | 75.0% | 75.7% | **+0.7pt** | 画面 50 枚の総当たり描画を追加 |
| 2026-08-17 | 76.1% | 76.0% | 77.4% | **+1.4pt** | 道具 95 個を 3 つの入口から総当たり（application が 87.6% で下限超え） |
| 2026-08-17 | 79.2% | 79.4% | 77.4% | **-2.0pt** | 境界値テスト 121 件（domain 74.6% → 85.9%）。差が負に転じた |

差が 11.55pt から -2.0pt まで動いた。
これは全体が上がったからではなく、**本物のコード側が追い越した**ことを示している
（スタブ側の数字は 63.47% → 77.4% で止まったまま、実質だけが上がっている）。

負の差は「スタブより本物のコードの方が厚く検査されている」状態であり、
数字合わせの逆である。ここが再び正に開き始めたら、その時点の追加分を疑う。

### なぜ片側しか見ないのか

判定（`quality-gates.config.mjs` の `judgeStubGap`）は
**スタブが実質を上限 3pt 超えて上回ったときだけ**落とす。差の絶対値では見ない。

見張りたいのは「スタブを厚くして全体の数字を作る」という 1 方向だけである。
逆向き（実質がスタブを上回る）は求めている姿そのもので、止める理由が無い。
絶対値で見ると、**望ましい方向へ大きく進んだときにも赤くなる**。
良くなったのに落ちる検査は、そのうち誰も読まなくなり、
本当に数字合わせが起きたときにも無視される。

現在の -10pt は違反ではない。画面に出る一言（「望ましい向き」）で
どちらの側にいるかが分かるようにしてある。数字だけを見て
「上限 3pt を超えている」と読み違えないための表示である。
判定そのものは `tests/architecture/quality-gates.test.ts` が両方向で固定している。

## 4. 判定の欄に「PASS」と書ける条件

- `pnpm verify` が通ること（＝閾値を満たしていること）
- その実行が**この文書と同じ日付**であること
- 閾値を下げていないこと（下げた場合は、下げた値と理由をこの節に書く。黙って下げない）

**閾値を下げて緑にするのは禁止。** 下げた記録が残らないと、
次に見る人は「元からこの水準だった」と受け取る。
