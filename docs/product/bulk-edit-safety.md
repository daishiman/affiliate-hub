# 共有の作業木で一括置換をする前に

最終更新: 2026-08-21

**このファイルは、壊したときに戻せるようにするための手順書である。**壊さないための心得ではない。
一括置換は壊れるものとして扱い、**壊れたあとに戻す先が在るか**だけを問題にする。

書いた理由は残課題 150 の事故である。17 ファイルの取り込み文を一括置換の巻き添えで壊し、
**戻す先が無いことに、壊してから気づいた。**取り決めが `git checkout --` と `git stash` を塞いでいて、
塞いだだけで代わりの控えを用意していなかった。

正本の関係: 事故そのものの記録は `backlog.md` 150、同じ根から出た測定側の症状は同 136。
このファイルは**再発を止める側**だけを書く。

---

## 1. `HEAD` は戻す先にならない

複数の担当が同じ作業木で同時に動いているとき、**`HEAD` が指すのは「自分の変更前」ではなく「全員の変更前」である。**

`git show HEAD:<file>` は読めるし `git checkout -- <file>` も動く。だから戻せるように見える。
実際に戻すと、**同じファイルに載っている他の担当の未コミット変更が一緒に消える。**
150 の事故では、17 ファイルに同じ日の別担当の変更が 60〜190 行ずつ載っていた。

**`git` を戻す手段として当てにできるのは、そのファイルを自分しか触っていないときだけである。**
そして「自分しか触っていない」は、**壊す前に確かめないと分からない。**壊した後では、
`git diff` に自分の壊れと他人の変更が混ざって出るので、もう分けられない。

## 2. 手順：置換の前に控えを作業木の外へ取る

控えの置き場は **scratchpad**（作業木の外）。作業木の中に置くと、次の一括置換が控えごと巻き込む。

```
node <scratchpad>/hold.mjs save <控えの名前> <ファイル...>   # 控える
node <scratchpad>/hold.mjs list <控えの名前>                 # 何を控えたか見る
node <scratchpad>/hold.mjs back <控えの名前>                 # 全部戻す
node <scratchpad>/hold.mjs back <控えの名前> <ファイル...>    # 一部だけ戻す
```

`hold.mjs` は 40 行程度の写しである。リポジトリに置いていないのは、
**控えは作業木の外に在ることが要件**で、道具だけ木の中に在っても意味が無いためである。
無ければ書き直す。`copyFileSync` と、控えた一覧を書いた `_files.json` があればよい。

**決まりは 3 つ。**

1. **控える一覧は、置換が使う一覧と同じ物にする。**別に `grep` し直して控えてはいけない。
   別に数えると、**控えた集合と書き換えた集合がずれる**——ずれた分は、壊れても戻せない。
   ずれていることは、戻そうとした時にしか分からない。
2. **控えるのは置換の直前。**間に他の担当の変更が入ると、控えが古くなり、
   戻した瞬間に**他人の変更を巻き戻す**。1 の禁止と同じ理由（控えが実物とずれる）。
3. **戻したら、控えの名前を使い回さない。**同じ名前で 2 回 `save` すると、
   1 回目の控えが黙って消える。

## 3. 正規表現の一括置換で `[\s\S]*?` を使わない

150 の直接の原因はこれである。

```
/import\s*\{([\s\S]*?)\}\s*from\s*"@\/presentation\/ui";/
```

**非貪欲は「短く取る」であって「近くから取る」ではない。**
マッチの起点はファイル先頭の最初の `import {` で、そこから `@/presentation/ui` の閉じまでを
1 つの取り込み文と読む。**間にある 2〜4 本の取り込み文が丸ごと中身に入る。**

括弧の中身を取りたいなら、**その括弧に入り得ない文字を明示して禁じる**（`[^{}]*` など）。
`*?` は「行き過ぎ」を防がない。

## 4. 型検査が全件を挙げたのは運である

150 は `tsc` が `TS2305 has no exported member` を 17 ファイル分挙げたので即座に分かった。
**これを再発検知の手段として当てにしてはいけない。**

取り込み元だけが変わって名前が変わらない壊れ方——**同じ名前を 2 つのモジュールが出している場合**——は、
型検査を素通りする。実行時に別の実装が入るだけで、赤は 1 件も出ない。

**「`tsc` が緑だから壊れていない」は言えない。**言えるのは「型に出る壊れ方はしていない」だけである。

## 5. 計測が仮説どおりの数を出したときは、数え方を先に疑う

これは控えの話ではないが、同じ「気づけない壊れ方」なのでここに置く。

残課題 147 の計測中、「`.linkNote` はリンクの注記だろう」という仮説に対して、
代理指標（近くの開きタグを親と見なす数え方）が **13 件**を返した。仮説にちょうど合う数だった。
祖先を正しく積んで数え直すと **0 件**で、13 は数え方が創作した数だった。

**代理指標は「在るものを取りこぼす」向きには外れない。「在りもしない役を創作する」向きに外れる。**
取りこぼしなら「該当なし」で気づけるが、**創作は気づけない**——仮説に合っているので、
確かめる動機がそこで消える。

**これは見張りにできない。**「仮説どおりの数が出た」は機械が判定できる形をしていない。
仮説はコードの中に無いからである。**だから手順の側に置く**:

> 計測の結果が、そのとき立てていた仮説にちょうど合ったときは、**数え方を疑ってから報告する。**
> 疑うのは結論ではなく、**数え方**である。

## 6. 記録した文が、次の計測で数えられる

過去の誤りを記録すると、**その記録の文自体が、誤りの形をしている。**

実例: `src/app/signin/page.tsx:136` のコメントは UX-03 の経緯を書いた文で、
中に `<button className={styles.linkNote}>` が出てくる。
素の `grep` で `.linkNote` を数えると、**この 1 件が実物として混ざる**（45 と 44 の差はこれだった）。
148 の記録にも同じ危険がある（`<label>` の中の誤用を書き残す文に、その形が出てくる）。

**計測する側が、コメントを落とせるかを毎回確かめること。**落とせないなら、
差分を分解して**何件がコメント由来かを言えるようにしてから**報告する。
「素の `grep` と一致しない」ことに気づけるのは、両方を数えたときだけである。
