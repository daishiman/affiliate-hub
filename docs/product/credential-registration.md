# 合言葉（鍵）の登録手順

**この作業はご本人が行ってください。** 私（AI）は代行しません。
鍵の値をこちらへ渡すと、渡した時点でファイルや実行履歴に残り、
消したつもりでも残り続けます。**値そのものは受け取りません。**
「登録が終わりました」の一言だけいただければ、続きを進められます。

登録するのは 3 組です。用途がまったく違うので、別々に説明します。

- **A. 公開の合言葉**（Cloudflare）— アプリをみんなが使える場所へ出すために要る
- **B. 生成 AI の合言葉** — 記事の下書きを AI に書かせるために要る
- **C. ログインの合言葉**（Google）— 管理画面を「あなただけ」に閉じるために要る

---

## いまお願いすること（この 1 件だけ）

> **C の 1〜3**（Google の画面でアプリを登録し、戻り先を 4 つ貼り、
> `node .better-auth-google/setup-secrets.mjs` を 1 回実行する）。所要 10 分ほど。
> 3 番目のコマンドは用意できました（2026-08-18）。

**この欄には常に 1 件だけを置きます。** お願いを足していくと、
済んだものと未着手のものが並んで、どれが「いま」なのか分からなくなるためです。
済んだお願いと、まだ順番が来ていないお願いは、各節の順番表の側にあります。

なぜ C が先かというと、**B（生成 AI の鍵）を貼っていただく画面そのものが、
いま誰でも開ける状態にあるから**です。順番を逆にすると、
「登録してください」とお願いした先が守られていないことになります。

## A. 公開の合言葉（Cloudflare の口座番号と鍵）

**この節は、いまお願いしていることではありません。** まだ登録されていませんが、
公開はいまも私の手元から実行できているので、止まってはいません。
**C（Google のログイン設定）が済んだあと**にお願いします。

### これが無いと何が起きているか

いま、アプリを公開する操作は私の手元から実行しています。
手元からの実行は**その場の作業中のファイルをそのまま公開してしまう**ため、
「まだ保存していない書きかけ」が本番に出る余地が残ります。

この 2 つを登録すると、公開は「確認済みのものをまとめる操作」からのみ
自動で走るようになり、その余地が仕組みとして消えます。

### 登録する場所

GitHub のこのリポジトリ → **Settings** → **Secrets and variables** → **Actions**
→ **New repository secret**

### 登録するもの（名前は下の表のとおり、1 文字も変えずに）

| 名前 | 中身 | どこで手に入るか |
| --- | --- | --- |
| `CLOUDFLARE_ACCOUNT_ID` | 口座番号（これ自体は秘密ではありません） | Cloudflare の管理画面 → Workers & Pages → 画面右側に表示されています |
| `CLOUDFLARE_API_TOKEN` | 公開する権限を持つ鍵 | 下の手順で新しく発行します |

### 鍵の発行手順

1. Cloudflare の管理画面にログイン
2. 右上のアイコン → **My Profile** → **API Tokens** → **Create Token**
3. テンプレートの一覧から **「Edit Cloudflare Workers」** を選ぶ
4. 表示された鍵を、その場で GitHub 側へ貼り付ける（**この画面を閉じると二度と表示されません**）

**「Global API Key」は使わないでください。** あれは口座の全権を持つ鍵で、
公開だけに用途を絞れません。万一漏れたときに、口座ごと作り直すことになります。
上の手順で作った鍵なら、**その鍵 1 本だけを無効にして作り直せます。**

### 登録できたことの確かめ方

GitHub の **Actions** の画面から `migrate.yml` を手動で 1 回実行し、
最後まで緑になることを見てください。落ちる場合は、
その画面に出ているメッセージだけをお知らせいただければ調べます
（**鍵の値は貼らないでください**）。

## B. 生成 AI の合言葉（画面から登録します）

### やっていただくのは 1 つだけです

**鍵を発行して、アプリの設定画面に貼り付ける。** これだけです。
ターミナルは使いません。私に鍵を渡す場面もありません。

対応するのは次の 4 社です。**全部そろえる必要はありません。**
1 社だけ登録すれば、その社で下書きが作れます。

| 提供元 | 鍵を発行する場所 |
| --- | --- |
| Anthropic（Claude） | https://console.anthropic.com/settings/keys |
| Google（Gemini） | https://aistudio.google.com/apikey |
| OpenAI | https://platform.openai.com/api-keys |
| xAI（Grok） | https://console.x.ai/ |

使うモデルは、登録のあとに**画面の一覧から選ぶ**形にしてあります。
提供元は新しいモデルをひんぱんに出すので、選べる中身は設定で差し替えられます
（新しいモデルが出るたびにアプリを作り直す、という形にはしていません）。

### いま、どこまでできているか（正直に）

登録の画面は作り終えていますが、**まだ本番には出していません**。
また、画面に並ぶ**モデルの一覧は空**です（モデル名と料金は私が設定します。
提供元が入れ替えるものなので、アプリの中に書き込まない形にしてあります）。

**この節には、いまお願いすることはありません。** 順番はこうなります。

| 順 | 誰が | やること | いまの状態 |
| --- | --- | --- | --- |
| 0 | ご本人 | C（Google のログイン設定）を済ませる | **いまお願いしていること** |
| 1 | ご本人 | 元締めの合言葉（`LLM_KEY_ENCRYPTION_SECRET`）を登録する | C のあと |
| 2 | 私 | 画面を本番へ出す | これから |
| 3 | 私 | モデルの一覧と料金を設定する | これから |
| 4 | 私 | 提供元を 1 社ずつつなぐ（Anthropic から） | これから |
| 5 | ご本人 | つないだ社の鍵を発行して貼る | 4 のあと |

1 番のやり方は下の「1 つだけ、私からお願いする設定があります」に書いてあります。
**鍵の登録より先に済ませる必要があります**（これが無いと、鍵を貼る欄そのものが出ません）。
ただし、いま着手していただく必要はありません。**私からお知らせしてから**で構いません。

**1 社できるたびにお知らせします。** 4 社そろうのを待つ必要はありません。
1 社つながれば、その社で下書きが作れます。

### 手順（上の表の 5 番。私からお知らせしてから始めてください）

1. 上の表のリンクから、使いたい会社の管理画面で API キーを発行する
2. アプリの **設定 → 生成 AI** を開く
3. 提供元の欄に鍵を貼り付けて保存する
4. その場に出る **「接続を確認する」** を押す（ごく短い問い合わせを 1 回だけ送ります）

確認が通れば、その提供元で下書きが作れる状態です。

### 登録した鍵がどう扱われるか（正直に書きます）

- **暗号化して保管します。** そのままの形ではどこにも保存しません
- **保存後は二度と表示しません。** 画面に出るのは末尾 4 文字だけです。
  「確認のためもう一度表示する」という口は**作っていません**
  （作れば、それが漏れる経路になります）
- **操作の記録にも鍵は残りません。** 残るのは
  「いつ・誰が・どの提供元の鍵を登録した／失効させた」までです
- **AI に渡す文には混ざりません。** 記事の下書きを作るとき、
  鍵は通信のときだけ使われ、AI が読む文（指示・資料・記事本文）には入りません
- **提供元からのエラーにも出しません。** 提供元は
  「api_key sk-… は無効です」のように**こちらが送った鍵を載せて**
  返してくることがあります。その文面は、鍵が混ざっていたら丸ごと捨てます
- **いつでも失効させられます。** 失効させると、保管していた値もその場で消えます

これらは書き置きではなく、**わざと破って検査が落ちることを毎回確かめています**
（`tests/architecture/llm-credential-leak.test.ts` /
`tests/infrastructure/llm-credential-vault.test.ts`）。

### 1 つだけ、私からお願いする設定があります

鍵を包むための**元締めの合言葉**が要ります。これは鍵そのものではなく、
「鍵をしまう金庫の合言葉」にあたるもので、**ご自身で作った長い文字列**で構いません
（32 文字以上。意味のある言葉である必要はありません）。

ご自身のターミナルで次を実行し、**聞かれてから**貼り付けてください。
本番と、試し用（dev）の 2 か所に要ります。同じ値で構いません。

```
pnpm exec wrangler secret put LLM_KEY_ENCRYPTION_SECRET --env production
pnpm exec wrangler secret put LLM_KEY_ENCRYPTION_SECRET --env dev
```

- **コマンドの後ろに値を書かないでください。** `secret put NAME 値` の形にすると
  そのまま実行履歴のファイルに残り、あとから消しても復元できることがあります。
  値は「Enter a secret value:」と聞かれてから貼ります
- 値は**ご自身だけが知っていれば十分**です。控えておく必要もありません
  （忘れても作り直せます。ただし作り直すと、それまでに登録した各社の鍵は
  開けなくなるので、登録し直しになります）
- **この設定が無いあいだ、鍵の登録欄は出ません。**
  「とりあえず暗号化せずに保存する」という逃げ道は作っていません
- 終わったら「登録しました」の一言だけお知らせください。**値は送らないでください**

### 費用について

呼ぶ前に見積もり、上限を超える依頼は**呼ばずに止めます**。
使った量（どの提供元・どのモデルを何回・おおよそいくら）も記録し、画面で見られます。
ただし**請求の正はいつでも提供元の管理画面**です。こちらの数字は概算です。

各社の管理画面で**支出の上限**も設定しておくことをおすすめします。
アプリ側の制御は不具合ですり抜けることがありますが、提供元側の上限はすり抜けません。

### Cloudflare Workers AI について

4 社とは別に枠だけ残してあります。**対応必須ではありません。**
同じ Cloudflare の口座の中で動くため鍵の登録が不要で、仕組みが他社と違います。
いま使う予定はありませんが、消すと「鍵の要らない提供元もありうる」という
前提ごと消えてしまうため、画面には出しつつ登録欄は出していません。

## C. ログインの合言葉（Google）

### いま何が開いているか（正直に）

**管理画面には、いま鍵がかかっていません。** アドレスを知っている人なら誰でも、
記事の一覧も、書き手の設定も、成果の数字も開けます。読むだけではありません。
**記事を公開する・配信の予約を入れる・提携先の接続を付け外しする**といった、
一度やったら取り消しがきかない操作も、ログインなしで実行できる状態です。
アドレスは推測しにくいので今日まで何も起きていませんが、それは
「守られている」ではなく「**まだ見つかっていない**」というだけです。
公開の場所（`https://affiliate-hub.daishimanju.workers.dev`）へ本格的に出す前に、
ここを閉じる必要があります。閉じ方が、この C 節のお願いです。

数え方と件数は `docs/product/open-doors.md` に機械が数えた形で置いてあります
（2026-08-18 時点で、入口 79 か所のうち **49 か所が誰でも入れる**。
そのうち取り消しがきかない操作は **6 つ**）。

### 何をする設定か

**「この Google アカウントの人だけが管理画面に入れる」**という札を作ります。
アプリは自前でパスワードを持ちません。「この人は本人です」の確認は Google に任せ、
アプリは Google からの返事だけを見ます。パスワードを預からないので、
**こちらから漏れるパスワードが存在しません**。

入れる人は**メールアドレスの名指し**で決めます
（`daishimanju@gmail.com` を許可、それ以外は全員お断り）。

> 会社のドメイン（`@example.co.jp` のような Google Workspace）をお使いなら、
> 「そのドメインの人は全員 OK」という決め方もできます。ただし個人の Gmail には
> ドメインという区切りが無く、`@gmail.com` 全員を許可することになってしまうため、
> **名指しの方を採りました。** あとで会社ドメインへ移るときは切り替えられます。
> 誰かを追加したいときは、その方のアドレスをお知らせいただければ足します
> （これは秘密の情報ではないので、チャットで送っていただいて構いません）。

### やっていただくこと（3 ステップ・10 分ほど）

**1. Google の画面でアプリを 1 つ登録する**

https://console.cloud.google.com/auth/clients を開きます。
初めての場合はプロジェクトの作成と、アプリ名・連絡先メールの入力を求められます。
アプリ名は画面に出る名前です（`Affiliate Hub` など、お好きなもので構いません）。

種類は **「ウェブ アプリケーション」** を選びます。

**2. 戻り先のアドレスを 4 つ貼る**

「承認済みのリダイレクト URI」という欄に、下の 4 つを**1 文字も変えずに**入れます。
末尾のスラッシュを足したり消したりすると、その場で弾かれます
（Google 側は「一致するか、しないか」しか見ません）。

```
https://affiliate-hub.daishimanju.workers.dev/api/auth/callback/google
https://affiliate-hub-dev.daishimanju.workers.dev/api/auth/callback/google
http://localhost:8788/api/auth/callback/google
http://localhost:3000/api/auth/callback/google
```

下の 2 つは、ご本人が手元で試すとき用です。公開の場所とは別扱いになります。

**3. できた 2 つの値を、ターミナルで 1 回だけ入れる**

登録が終わると「クライアント ID」と「クライアント シークレット」が表示されます。
**この 2 つをチャットに貼らないでください。** 代わりに、プロジェクトのフォルダで
次を実行し、**聞かれてから**貼り付けてください。

```
node .better-auth-google/setup-secrets.mjs
```

聞かれるのは 3 つです。

| 聞かれるもの | どこから持ってくるか | 画面への表示 |
| --- | --- | --- |
| Client ID | Google の画面（`.apps.googleusercontent.com` で終わる） | 出ません |
| Client Secret | Google の画面 | 出ません |
| 許可するアドレス | ご自身の Gmail。複数ならカンマ区切り | 出ます（秘密ではないため） |

上 2 つは入力中に画面へ文字が出ません（打てていないように見えますが、入っています）。
貼り付けたら Enter を押してください。やめたいときは Ctrl+C です。

このコマンドは、値を**手元の設定ファイル（`.dev.vars`）と Cloudflare の両方**へ登録し、
**画面にも、コマンドの履歴にも、git にも値を残しません**
（Cloudflare へは、コマンドの引数ではなく標準入力から渡しています）。
アプリが署名に使う値（`BETTER_AUTH_SECRET`）は自動で作るので、
ご自身で用意していただくものはありません。

> **先に `wrangler` へのログインが要ります。** まだなら
> `pnpm exec wrangler login` を一度だけ実行してください
> （ブラウザが開いて Cloudflare の確認画面が出ます）。
> 手元だけ先に試したいときは `node .better-auth-google/setup-secrets.mjs --local-only`
> で、Cloudflare へは触れずに手元の設定だけ作れます。

**登録先は 2 か所あります。** 既定はお試し用（dev）です。

```
node .better-auth-google/setup-secrets.mjs           … 手元 + お試し用（dev）
node .better-auth-google/setup-secrets.mjs --prod    … 手元 + 本番
```

まずお試し用だけで結構です。本番はこちらでの確認が済んでからお願いします。
同じ値を 2 回貼ることになりますが、Google の画面から何度でも見られます。

終わったら「登録しました」の一言だけお知らせください。**値は送らないでください。**

### そのあとどうなるか

管理画面（`/admin` 以下）を開くと、まずログインの画面が出るようになります。
Google のボタンを 1 回押せば入れます。以降しばらくは押さずに入れます。

**許可していないアカウントは、Google のログイン自体は通っても、
こちらで断ります。**「入れないアカウントに、中途半端に途中まで入られる」
という状態は作りません（入れた状態そのものを作りません）。

**断った試みは日時とアドレスだけ記録します**（パスワードや鍵にあたるものは
記録しません）。誰かが入ろうとしているかどうかを、後から見られるようにするためです。

読者向けのページ（公開した記事）は、これまでどおり誰でも読めます。
閉じるのは管理側だけです。

### うまくいかないときに多いもの

| 画面に出るもの | 原因 | 直し方 |
| --- | --- | --- |
| `redirect_uri_mismatch` | 戻り先のアドレスが 1 文字違う | 上の 4 行をコピーし直して貼る |
| ログインは通るのに弾かれる | 許可していないアドレスで入った | 使ったアドレスをお知らせください |
| ボタンを押しても何も起きない | 私の側の設定漏れ | 画面のメッセージだけお知らせください |

いずれの場合も、**画面に出ている文字だけ**をお知らせいただければ調べます
（クライアント ID とシークレットは貼らないでください）。

## やらないでいただきたいこと

- 鍵をチャットに貼る（私に渡す）
- 鍵をリポジトリの中のファイルに書く
- 鍵をコマンドの引数として打つ（`wrangler secret put NAME 値` の形。履歴に残ります）
- スクリーンショットに鍵が写った状態で共有する

うっかり渡してしまった場合は、**その鍵を失効させて作り直してください。**
「消したので大丈夫」とは考えないでください。責めるつもりはまったく無く、
作り直すのが唯一の確実な対処です。

#### `pricedOn` が主張していること（読み違えないように）

目録の各行が持つ `pricedOn` は、**その日に、その提供元のドメインから
返ってきた内容でその単価を読んだ**という意味である。
それ以上のことは言っていない。具体的には次のとおり。

| したこと | していないこと |
| --- | --- |
| 各社のドメインに絞って検索し、返ってきた価格ページの内容から単価を読んだ | **その URL を直接開いて（`curl` / ページ取得で）読んではいない** |
| 2026-08-18 に 6 行すべてを取り、同日に取り直して同じ値を確認した | 記憶から書いて URL を後付けする、はしていない |

直接開けなかったのは、この作業場所ではページ取得の手段が使えなかったためである
（`curl` は許可されず、ページ取得の道具が無い）。
**書いておかないと、`pricedOn` が「そのページを自分で開いた日」として読まれる。**
古さを見る仕組みはこの日付だけを基準に動くので、
日付が何を根拠にしているかが分からなくなると、仕組みごと当てにならなくなる。

取り直すときにページを直接開ける手段があるなら、そちらを使ってほしい。
検索の結果は提供元の内容を写したものであって、提供元のページそのものではない。

**単価は USD で持つ。** 円で持つには為替をこちらが決める必要があり、
その値は必ず古くなる。しかも請求の正である提供元の数字は USD なので、
円で持つと**照合できない概算**になる。円で見せたいときは、
表示の段で為替を掛ける（記録は USD のまま残す）。

長い文脈や優先処理で単価が変わる社があるが（xAI は 20 万トークン超で倍、
OpenAI と Anthropic にも同種の段がある）、目録は 1 モデル 1 単価しか持たない。
**安いほうを入れない。** 概算が実際より安く出ると、上限で止める仕組みが
効かないまま請求だけ増える。

### 4 社の呼び出しの形（2026-08-18 に各社の docs で確認）

アダプタが写しているのはこの 4 点だけ（それ以外の手順は 4 社共通で
`src/infrastructure/llm/providers/http-llm.ts` にある）。

| --- | --- | --- | --- | --- |
| Anthropic | `POST /v1/messages` | `x-api-key` | 道具呼び出し（`tools` + `tool_choice`） | `usage.input_tokens` / `output_tokens` |
| Google | `POST /v1beta/models/{model}:generateContent` | `x-goog-api-key` | `generationConfig.responseMimeType` + `responseSchema` | `usageMetadata.promptTokenCount` / `candidatesTokenCount` |
| OpenAI | `POST /v1/responses` | `authorization: Bearer` | `text.format = { type: "json_schema", strict: true }` | `usage.input_tokens` / `output_tokens` |
| xAI | `POST /v1/chat/completions` | `authorization: Bearer` | `response_format = { type: "json_schema", json_schema: { strict: true } }` | `usage.prompt_tokens` / `completion_tokens` |

| 提供元 | 確認日 | 構造化出力のページ |
| --- | --- | --- |

Google は鍵を `?key=` で経路に載せる書き方も受け付けるが、**使わない**。
経路は中継の記録に残りやすい。見出しだけに載せる。

OpenAI と xAI の `strict` は「すべての項目が `required`」「`additionalProperties: false`」を
要求するので、送る前に `toStrictSchema` で直す。**全部必須で困らない**のは、
指示（`assemblePrompt`）が「分からない項目は null」と伝えているため。
欄を落とすのではなく「分からなかった」と書かせるほうが、後から読む人に区別が付く。

Workers AI だけはこの手順に乗らない。鍵を預からず、実行環境の結び付けで呼ぶため。
繋ぐときは別の組み立てが要る（いまはスタブ）。

**ここまでで言えるのは「呼び出しの形が合っている」ことだけである。**
偽の応答での検査（`tests/infrastructure/llm-providers.test.ts`）が緑でも、
実際の鍵で受け入れられるかは分からない。それを見るのは設定画面の接続確認
（`llm-connectivity.ts`）で、鍵の登録は利用者ご本人の作業になる。

### 開発者が入れる秘密（`secret-resolver.ts` 経由）とは別物

ASP の接続情報などは従来どおり環境変数から解決する

### 赤の実測

「落ちない門は、無い門と見分けが付かない」ため、要件 1〜7 は
**わざと壊して検査が落ちることを実際に確かめた**（2026-08-18）。

| 要件 | わざと壊した内容 | 落ちた検査 |
| --- | --- | --- |
| 1 | `const sealed = input.apiKey`（包まずに保存） | vault「要件 1: 保管される値が平文でない」 |
| 2 | 条件から `eq(llmCredentials.workspaceId, …)` を外す | vault「要件 2: よその作業場所の鍵は取り出せない」＋ architecture「要件 2」 |
| 3 | ポートに `reveal(...)` を足す | architecture「要件 3: 鍵の値を返す口が無い」 |
| 4 | 監査の `after` に `apiKey` を足す | architecture「要件 4: 操作の記録へ鍵を詰める経路が無い」 |
| 5 | `const safe = raw`（提供元のエラー本文を素通し） | vault「要件 5」2 件 |
| 5 | `console.error` で鍵を書き出す | architecture「要件 5: ログへ出す文が無い」 |
| 6 | 保管庫に `LlmRequest` を import | architecture「要件 6」 |
| 7 | `prompt-assembly.ts` に `LlmCredentialVaultPort` を import | architecture「要件 7」 |
| 6 | ユースケースに `LlmKeyAccess` を import | architecture「要件 6: 応用層から鍵を使う口へ手が届かない」 |

最後の 1 行は、`useKey` を応用層から移したときに足した検査である。
一度目は説明文の中の `LlmKeyAccess` に当たって落ちた（自分の書いた注釈で
落ちる検査は、いずれ注釈のほうが消される）。注釈を落としてから見る形に直し、
**実際の import を足して測り直した**。

このうち 2 件は、**最初の測定では赤にならなかった**。

- 要件 2: 偽の接続の側が作業場所で絞っていたため、実装から条件を外しても
  緑のままだった。偽物から絞り込みを外して測り直した
- 要件 2（書き方の検査）: 引数名 `workspaceId` に当たって通っていた。
  条件式の中の `eq(llmCredentials.workspaceId` を見る形に書き直して測り直した

どちらも「守っているつもりで何も守っていない」検査だった。
**赤を測らなければ、この 2 つは最後まで緑のままだった。**

なお試験に使う鍵は、実在の提供元の接頭辞（`sk-ant-` など）を使わない。
秘密情報の持ち込みを見張る検査が形で拾って止まるためで、
これは見張りが効いている証拠なので、見張りではなく試験の値のほうを変える。
