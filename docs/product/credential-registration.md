# 合言葉（鍵）の登録手順

**この作業はご本人が行ってください。** 私（AI）は代行しません。
鍵の値をこちらへ渡すと、渡した時点でファイルや実行履歴に残り、
消したつもりでも残り続けます。**値そのものは受け取りません。**
「登録が終わりました」の一言だけいただければ、続きを進められます。

登録するのは 2 組です。用途がまったく違うので、別々に説明します。

- **A. 公開の合言葉**（Cloudflare）— アプリをみんなが使える場所へ出すために要る
- **B. 生成 AI の合言葉** — 記事の下書きを AI に書かせるために要る

A と B は独立しています。片方だけ先に登録しても構いません。

---

## A. 公開の合言葉（Cloudflare の口座番号と鍵）

### これが無いと何が起きているか

いま、アプリを公開する操作は私の手元から実行しています。
手元からの実行は**その場の作業中のファイルをそのまま公開してしまう**ため、
「まだ保存していない書きかけ」が本番に出る余地が残ります。

この 2 つを登録すると、公開は「確認済みのものをまとめる操作」からのみ
自動で走るようになり、その余地が仕組みとして消えます。

### 登録する場所

GitHub のこのリポジトリ → **Settings** → **Secrets and variables** → **Actions**
→ **New repository secret**

### 登録するもの（名前は下の表のとおり、1 文字も変えずに）

| 名前 | 中身 | どこで手に入るか |
| --- | --- | --- |
| `CLOUDFLARE_ACCOUNT_ID` | 口座番号（これ自体は秘密ではありません） | Cloudflare の管理画面 → Workers & Pages → 画面右側に表示されています |
| `CLOUDFLARE_API_TOKEN` | 公開する権限を持つ鍵 | 下の手順で新しく発行します |

### 鍵の発行手順

1. Cloudflare の管理画面にログイン
2. 右上のアイコン → **My Profile** → **API Tokens** → **Create Token**
3. テンプレートの一覧から **「Edit Cloudflare Workers」** を選ぶ
4. 表示された鍵を、その場で GitHub 側へ貼り付ける（**この画面を閉じると二度と表示されません**）

**「Global API Key」は使わないでください。** あれは口座の全権を持つ鍵で、
公開だけに用途を絞れません。万一漏れたときに、口座ごと作り直すことになります。
上の手順で作った鍵なら、**その鍵 1 本だけを無効にして作り直せます。**

### 登録できたことの確かめ方

GitHub の **Actions** の画面から `migrate.yml` を手動で 1 回実行し、
最後まで緑になることを見てください。落ちる場合は、
その画面に出ているメッセージだけをお知らせいただければ調べます
（**鍵の値は貼らないでください**）。

## B. 生成 AI の合言葉（画面から登録します）

### やっていただくのは 1 つだけです

**鍵を発行して、アプリの設定画面に貼り付ける。** これだけです。
ターミナルは使いません。私に鍵を渡す場面もありません。

対応するのは次の 4 社です。**全部そろえる必要はありません。**
1 社だけ登録すれば、その社で下書きが作れます。

| 提供元 | 鍵を発行する場所 |
| --- | --- |
| Anthropic（Claude） | https://console.anthropic.com/settings/keys |
| Google（Gemini） | https://aistudio.google.com/apikey |
| OpenAI | https://platform.openai.com/api-keys |
| xAI（Grok） | https://console.x.ai/ |

使うモデルは、登録のあとに**画面の一覧から選ぶ**形にしてあります。
提供元は新しいモデルをひんぱんに出すので、選べる中身は設定で差し替えられます
（新しいモデルが出るたびにアプリを作り直す、という形にはしていません）。

### 手順

1. 上の表のリンクから、使いたい会社の管理画面で API キーを発行する
2. アプリの **設定 → 生成 AI** を開く
3. 提供元の欄に鍵を貼り付けて保存する
4. その場に出る **「接続を確認する」** を押す（ごく短い問い合わせを 1 回だけ送ります）

確認が通れば、その提供元で下書きが作れる状態です。

### 登録した鍵がどう扱われるか（正直に書きます）

- **暗号化して保管します。** そのままの形ではどこにも保存しません
- **保存後は二度と表示しません。** 画面に出るのは末尾 4 文字だけです。
  「確認のためもう一度表示する」という口は**作っていません**
  （作れば、それが漏れる経路になります）
- **操作の記録にも鍵は残りません。** 残るのは
  「いつ・誰が・どの提供元の鍵を登録した／失効させた」までです
- **AI に渡す文には混ざりません。** 記事の下書きを作るとき、
  鍵は通信のときだけ使われ、AI が読む文（指示・資料・記事本文）には入りません
- **提供元からのエラーにも出しません。** 提供元は
  「api_key sk-… は無効です」のように**こちらが送った鍵を載せて**
  返してくることがあります。その文面は、鍵が混ざっていたら丸ごと捨てます
- **いつでも失効させられます。** 失効させると、保管していた値もその場で消えます

これらは書き置きではなく、**わざと破って検査が落ちることを毎回確かめています**
（`tests/architecture/llm-credential-leak.test.ts` /
`tests/infrastructure/llm-credential-vault.test.ts`）。

### 1 つだけ、私からお願いする設定があります

鍵を包むための**元締めの合言葉**が要ります。これは鍵そのものではなく、
「鍵をしまう金庫の合言葉」にあたるもので、**ご自身で作った長い文字列**で構いません
（32 文字以上。意味のある言葉である必要はありません）。

ご自身のターミナルで次を実行し、聞かれたところに貼り付けてください。

```
pnpm exec wrangler secret put LLM_KEY_ENCRYPTION_SECRET
```

- コマンドの後ろに値を書かないでください（実行履歴に残ります）
- **この設定が無いあいだ、鍵の登録欄は使えません。**
  「とりあえず暗号化せずに保存する」という逃げ道は作っていません

### 費用について

呼ぶ前に見積もり、上限を超える依頼は**呼ばずに止めます**。
使った量（どの提供元・どのモデルを何回・おおよそいくら）も記録し、画面で見られます。
ただし**請求の正はいつでも提供元の管理画面**です。こちらの数字は概算です。

各社の管理画面で**支出の上限**も設定しておくことをおすすめします。
アプリ側の制御は不具合ですり抜けることがありますが、提供元側の上限はすり抜けません。

### Cloudflare Workers AI について

4 社とは別に枠だけ残してあります。**対応必須ではありません。**
同じ Cloudflare の口座の中で動くため鍵の登録が不要で、仕組みが他社と違います。
いま使う予定はありませんが、消すと「鍵の要らない提供元もありうる」という
前提ごと消えてしまうため、画面には出しつつ登録欄は出していません。

## やらないでいただきたいこと

- 鍵をチャットに貼る（私に渡す）
- 鍵をリポジトリの中のファイルに書く
- 鍵をコマンドの引数として打つ（`wrangler secret put NAME 値` の形。履歴に残ります）
- スクリーンショットに鍵が写った状態で共有する

うっかり渡してしまった場合は、**その鍵を失効させて作り直してください。**
「消したので大丈夫」とは考えないでください。責めるつもりはまったく無く、
作り直すのが唯一の確実な対処です。

## 技術的な補足（開発者向け）

### 鍵の道すじ（利用者が画面から入れるもの）

| 段 | ファイル | 役目 |
| --- | --- | --- |
| domain | `src/domain/generation/llm-credential.ts` | 形の検査・末尾 4 文字・塗り潰し。**値を持つ型が無い** |
| port | `src/application/ports/llm-credential.ts` | 登録・一覧・失効・確認の記録。**値に触れる口が 1 つも無い** |
| infra | `src/infrastructure/llm/key-access.ts` | `useKey(fn)` と使用量の書き留め。**応用層からは型として届かない** |
| usecase | `src/application/usecases/generation/manage-llm-credentials.ts` | 権限・目録の照合・操作の記録 |
| usecase | `src/application/usecases/generation/read-llm-usage.ts` | 使った量の読み出し（通貨ごとに分けて合計する） |
| infra | `src/infrastructure/persistence/d1/llm-credential-repository.ts` | 包む／開ける。**ここだけが平文を作る** |
| infra | `src/infrastructure/platform/secret-box.ts` | AES-GCM。IV 12 バイトを毎回作り、`base64(iv‖暗号文)` で持つ |
| 目録 | `src/infrastructure/llm/llm-provider-catalog.ts` | 提供元は表、モデルと単価は `LLM_PROVIDER_CATALOG` |

保存先は `llm_credentials`（主キーは作業場所 + 提供元）と `llm_usages`。
`drizzle/0013_loose_mentor.sql`。

### 開発者が入れる秘密（`secret-resolver.ts` 経由）とは別物

ASP の接続情報などは従来どおり環境変数から解決する
（参照キーの形式は `<種別>/<接続ID>/<用途>`、写像は `refToEnvName()`）。
**生成 AI の鍵はもうそこを通らない。** 利用者が画面から入れ、D1 に包んで置く。
`SECRET_LLM__*` という名前の環境変数は使わない。

### 鍵を使う口を応用層に置かない（2026-08-18 に動かした）

最初は `useKey` も `src/application/ports/llm-credential.ts` に並べていた。
つなぎ目の検査が「`useKey` はユースケースから一度も呼ばれていない」と出し、
事実その通りだった。**応用層は鍵を使わない。** 並べてあると
「使ってよい口」に見えるだけで、守りは書く人の注意力に戻る。

そこで `src/infrastructure/llm/key-access.ts` へ移し、
応用層から `LlmKeyAccess` を参照したら落ちる検査を足した
（`tests/architecture/llm-credential-leak.test.ts` の「要件 6: 応用層から
鍵を使う口へ手が届かない」）。使用量を書き留める口も同じ理由で移してある。
実装（D1 の預かり所）は両方の面を satisfy する 1 つの物だが、
受け取る側は自分に必要な面しか型として持てない。

### 赤の実測

「落ちない門は、無い門と見分けが付かない」ため、要件 1〜7 は
**わざと壊して検査が落ちることを実際に確かめた**（2026-08-18）。

| 要件 | わざと壊した内容 | 落ちた検査 |
| --- | --- | --- |
| 1 | `const sealed = input.apiKey`（包まずに保存） | vault「要件 1: 保管される値が平文でない」 |
| 2 | 条件から `eq(llmCredentials.workspaceId, …)` を外す | vault「要件 2: よその作業場所の鍵は取り出せない」＋ architecture「要件 2」 |
| 3 | ポートに `reveal(...)` を足す | architecture「要件 3: 鍵の値を返す口が無い」 |
| 4 | 監査の `after` に `apiKey` を足す | architecture「要件 4: 操作の記録へ鍵を詰める経路が無い」 |
| 5 | `const safe = raw`（提供元のエラー本文を素通し） | vault「要件 5」2 件 |
| 5 | `console.error` で鍵を書き出す | architecture「要件 5: ログへ出す文が無い」 |
| 6 | 保管庫に `LlmRequest` を import | architecture「要件 6」 |
| 7 | `prompt-assembly.ts` に `LlmCredentialVaultPort` を import | architecture「要件 7」 |
| 6 | ユースケースに `LlmKeyAccess` を import | architecture「要件 6: 応用層から鍵を使う口へ手が届かない」 |

最後の 1 行は、`useKey` を応用層から移したときに足した検査である。
一度目は説明文の中の `LlmKeyAccess` に当たって落ちた（自分の書いた注釈で
落ちる検査は、いずれ注釈のほうが消される）。注釈を落としてから見る形に直し、
**実際の import を足して測り直した**。

このうち 2 件は、**最初の測定では赤にならなかった**。

- 要件 2: 偽の接続の側が作業場所で絞っていたため、実装から条件を外しても
  緑のままだった。偽物から絞り込みを外して測り直した
- 要件 2（書き方の検査）: 引数名 `workspaceId` に当たって通っていた。
  条件式の中の `eq(llmCredentials.workspaceId` を見る形に書き直して測り直した

どちらも「守っているつもりで何も守っていない」検査だった。
**赤を測らなければ、この 2 つは最後まで緑のままだった。**

なお試験に使う鍵は、実在の提供元の接頭辞（`sk-ant-` など）を使わない。
秘密情報の持ち込みを見張る検査が形で拾って止まるためで、
これは見張りが効いている証拠なので、見張りではなく試験の値のほうを変える。
