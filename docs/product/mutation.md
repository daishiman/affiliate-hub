# ミューテーションテストの実測（テストを騙せないようにする）

規範は `docs/spec/10-テスト戦略仕様.md` §10。下限は
`quality-gates.config.mjs` の `MUTATION_SCORE` が正本。

カバレッジは「その行を通ったか」しか見ない。
`return 42` に `expect(f()).toBe(42)` を当てれば **100% 緑で仕様はゼロ**である。
ここで測るのは別のことで、**コードをわざと書き換えたときテストが赤くなるか**を見る。
赤くなればそのテストは本当にその判断を見ている。緑のままなら、その判断は誰も見ていない。

## 2. 覆っていない場所（先に書く）

「ミューテーションを入れた」とだけ書くと、読んだ人は全体に当たっていると受け取る。
**それは事実ではない。** 当たっていない場所は次のとおり。

| 場所 | 状態 | 理由 |
| --- | --- | --- |
| `src/infrastructure` | **対象外** | スタブが多く、変異させても意味のある判断が少ない |
| `src/presentation` | **対象外** | 描画が主で、1 変異あたりの実行が重い |
| `src/app` | **対象外** | 同上 |
| **static な変異** | **対象外** | ↓ §2-1 |

### 2-1. static な変異を外している（実測に基づく判断）

**これは見落としを増やす設定なので、外した理由と、外した結果どこが見えないかを書く。**

`ignoreStatic: false`（＝全部見る）で 1 度測ったところ、こうだった。

| | 値 |
| --- | --- |
| 変異の総数 | 12,927 |
| うち static（モジュール読込み時に 1 回だけ動く＝トップレベル定数など） | **3,876（30%）** |
| Stryker の見積りで static が占める実行時間 | **98%** |
| 全体の見積り時間 | **20 時間超** |

static な変異はテストの絞り込みが効かず、1 個ごとに全テストを読み直すためである。
**20 時間かかる検査は誰も走らせない。** 走らないまま「やっています」になるので外した。
外すと 10,028 変異・16 分になる。

外した結果、見えなくなるのは主に**定数表そのもの**である。

| 見えなくなる例 | 代わりに何が守っているか |
| --- | --- |
| `ALLOWED_RANKING_CRITERIA` | `tests/domain/` の、表そのものを当てるテスト |
| `GATE_REQUIREMENT_LABEL` | 同上 |
| `OPTIMIZATION_DIMENSIONS` | `tests/property/variant-spec.property.test.ts`（登録表から入力を作る） |

全部見たいときは `STRYKER_STATIC=1 node scripts/mutation.mjs`（20 時間かかる）。

## 3. 生き残りの中身（何が見られていないのか）

生き残り 2,383 件の内訳。**上 2 つで 64% を占める。**

| 変異の種類 | 件数 | 生き残ると何が言えるか |
| --- | --- | --- |
| `StringLiteral`（文字列を空にする） | 940 | **利用者が読む文言を、誰も確かめていない** |
| `ConditionalExpression`（条件を真/偽に固定） | 582 | 分かれ道の片側しか通っていない |
| `MethodExpression` | 154 | `sort` や `filter` を消しても気づかない |
| `ObjectLiteral`（`{}` にする） | 149 | 返す中身が空でも通る |
| `LogicalOperator`（`&&`↔`\|\|`） | 141 | 「両方必要」が「片方でよい」になっても通る |
| `EqualityOperator`（`>`↔`>=` ほか） | 132 | **境界ちょうどの扱いが見られていない** |

`StringLiteral` が最大なのは、この製品の性質と関係がある。
「編集できない理由を 1 行出す」「断る理由を文で返す」を要件にしているため、
**文言そのものが機能**であり、変異の数も多い。
一方でテストは「空でないこと」までしか見ていないものが多く、そこが生き残っている。

`ConditionalExpression` と `EqualityOperator` は、要件で名指しした
`>`→`>=` / 条件の反転にあたる。ここは**足すべきテストが具体的に分かる**種類の生き残りである。

## 5. 性質テストを足して測り直した結果（実測の前後）

要件の「生き残った変異を見てテストを足す（下限を下げない）」に対して、
`tests/property/` に 5 ファイル・48 件の性質テストを足し、**同じ条件で測り直した**。

| | スコア |
| --- | --- |
| 性質テストを足す前 | 66.25% |
| 足した後 | **67.20%（+0.95 ポイント）** |

**全体では 1 ポイントしか動いていない。** 正直に書くと、これは小さい。
理由は §4-1 のとおりで、残りの穴の大半が「テストが無いモジュール」だからである。
一方、**狙ったモジュールでは大きく動いた**。

| モジュール | 前 | 後 | 倒した数 |
| --- | --- | --- | --- |
| `domain/authoring/appearance.ts` | 0.0% | **74.2%** | +23 |
| `domain/shared/tenancy.ts` | 26.1% | **60.9%** | +8 |
| `domain/compliance/publish-gate.ts` | 75.4% | **88.8%** | +18 |
| `domain/analytics/variant-spec.ts` | 57.5% | **68.7%** | +15 |
| `domain/ranking/scoring.ts` | 79.1% | **89.1%** | +11 |
| `domain/product/product-identity.ts` | 76.5% | 83.3% | +7 |
| `domain/monetization/link-ingestion.ts` | 70.8% | 76.6% | +11 |
| `domain/ranking/ranking-model.ts` | 65.9% | 68.2% | +2 |

**個別に確かめたこと。** 以前は `scoring.ts` の順位付けで、
`.sort(...)` を丸ごと消す・比較関数を `() => undefined` にする・
`b - a` を `b + a` にする、のいずれも**生き残っていた**（＝順位が総崩れでも緑）。
測り直した後、この 3 つを含む L205 付近の変異は**すべて倒されている**。
倒したのは「最強・最弱が重み付き点数の最大・最小と一致する」という性質テストである。

### 5-1. 副作用として測定が遅くなった

性質テストは 1 件あたり 100 通りの入力を試すので、変異 1 個ごとのテストが重くなる。

| | 実行時間 |
| --- | --- |
| 性質テストを足す前 | 12 分 34 秒 |
| 足した後 | **16 分 5 秒** |

3 段の目標 90 分には収まっている。**速さのためにこの性質テストを削らない。**
遅くなったのは確かめる量が増えたからで、それがここでやりたいことそのものである。

## 6. 実装で見つけた不具合（この作業の実利）

性質テストが、実際に動いているコードの欠陥を 1 件見つけた。

`normalizeAffiliateUrl` が URL を組み立て直すときに符号化していなかったため、

- `?x=b%26y%3Dz`（**x という 1 つの値**が `b&y=z`）
- `?x=b&y=z`（**x と y の 2 つ**）

が同じ正規形になっていた。**別の成果リンクが互いの重複として印を付けられる**状態で、
利用者から見ると「貼ったのに受信箱に出てこない」になる。

直したうえで、最小の反例を `tests/domain/link-ingestion.test.ts` に例として写してある。
性質テストは毎回違う入力を試すので、**同じ壊れ方の再現を保証しない**。
再現できない検出は、直したことを確かめられない。

## 7. 走らせる場所

| 段 | いつ | 対象 | マージを止めるか |
| --- | --- | --- | --- |
| 2 段 | PR | 変更したファイルだけ | **止める** |
| 3 段 | 夜間・週次 | 全体 | 止めない（落ちたら起票。`docs/product/nightly-triage.md`） |

2 段には変更ファイル数の上限がある（`MUTATION_MAX_CHANGED_FILES`）。
超えた PR では 2 段で測らず、3 段の全体実測へ回す。
**検査が消えるのではなく、測る場所が変わるだけ**である。見送ったことは必ず出力する。

機械の上で比較元（`MUTATION_BASE`）が取れない場合は**失敗させる**。
比較元が無いと変更範囲を計算できず、「走らなかったのに緑」になるためで、
これは検査が無いのと同じ状態にあたる。

## 9. 下限を動かすときの決まり

- **下げて緑にすることを禁じる。** 生き残った変異を見てテストを足す
- どうしても下げる場合は、**この文書に理由と日付を書いてから**下げる
- **ゼロにしない。** ゼロの門は門ではない
- 上げるのは自由（実測が上がったら追随させる）

| 日付 | 下限 | 実測 | 理由 |
| --- | --- | --- | --- |
| 2026-08-17 | 65% | 67.20% | 初回の実測に合わせて設定。実測の 2.2 ポイント下 |
