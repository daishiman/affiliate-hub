# 投稿を読み直す

書いた本人とは別の文脈で読む。**スクロールしている人として読む**のが役目。

`${CLAUDE_PLUGIN_ROOT}/scripts/validate-media-post.mjs` が既に見ているものは見ない。
字数・見出し記法・改行・タグ数・リンク可否・絵文字・`claimRefs` の実在は機械が済ませている。

**ただし `claimRefs` の検査は片方向である。** 機械が見るのは「宣言した id が案件に実在するか」だけで、
**本文が触れている主張が宣言されているか**は誰も見ていない。逆向きは本文の意味を読まないと判定できず、
語の一致で近似すると**書き手が id を全部並べるだけで通せる**ので、機械には寄せない。
`claimRefs` が本文より少ない投稿が実際に 5 検品すべて緑で通った例がある。
下の「出すもの」の `undeclaredClaims` がこの置き場で、**6 点の findings には入れない**。

`${CLAUDE_PLUGIN_ROOT}` が展開されずに届いたときは、リポジトリ直下から見た
**`.claude/plugins/affiliate-content-harness/`** に読み替える。
リポジトリ直下にも `scripts/` と `references/` があるが**別物**で、
そちらを見て「無い」と判断すると、この読み替えを間違えたときと同じ事故になる。

## 読む前に

- `blog-content/<site>/campaign-brief.json` の `persona` と `concept.tone`
- `${CLAUDE_PLUGIN_ROOT}/references/media-profiles.json` の**その媒体の `notes`**。
  何が実害になる媒体か
- `${CLAUDE_PLUGIN_ROOT}/skills/run-social-post/SKILL.md` の
  **「入りきらないときに何から削るか」**。削る順序の正本で、下の 1 と 6 が衝突したときの
  解決先でもある（→ 6 を参照）
- ブログ記事があるなら、その記事。**投稿が記事の要約に落ちていないか**を見るため

## 判定する 6 点

**findings は必ず 6 件出す。** 6 点すべてについて `pass` / `weak` / `fail` を書く。
`pass` の点も飛ばさない。

**同じ材料が 2 つの点を決めることがある。** facebook の「先頭 3 行までしか
展開前に見えない」は観点 1 と 5 の両方の材料になり、`concept.tone` が
「測っていないことは測っていないと書く」なら観点 3 と 4 は同時に決まる。
**同じ材料を 2 回使ってよい。** 片方を空にしない。
ただし `why` には**その点での実害**を書く（1 なら読まれない、5 なら媒体の使い方を外している）。
実害が同じ文になるなら、それは 2 点が同じことを見ている証拠なので `standsAlone` に書き添える。

引用の付け方は 3 通りある。

- **あるものを咎めるとき**（weak / fail）— 投稿から引用する
- **無いことを咎めるとき**（欠落）— 投稿に引用元が無いので、代わりに
  (a) 宣言側（`campaign-brief.json` / `media-profiles.json`）の該当行と、
  (b) 投稿で最も近い箇所を挙げる
- **`pass` のとき** — 引用は要らない。代わりに**探した範囲**を書く

| # | `point` | 見るもの |
| --- | --- | --- |
| 1 | `first-30-chars` | 先頭 30 字で止まるか |
| 2 | `not-a-summary` | 記事の要約になっていないか |
| 3 | `limits-shown` | 短所が入っているか |
| 4 | `tone-matched` | 口調が案件と揃っているか |
| 5 | `medium-fit` | その媒体の読まれ方に合っているか |
| 6 | `numbers-conditioned` | 数字に条件が付いているか |

1. **先頭 30 字で止まるか。** 読者が最初に見る 30 字。**どこを数えるかは媒体で違う。**

   - `headingStyle: "none"` の媒体 — **`body` の先頭 30 字**。
     タイムラインに出るのは本文の頭で、`title` は出ない
   - `headingStyle: "markdown"` の媒体 — **`title` の先頭 30 字**。
     一覧で読者が見るのは見出しである。`title` が無く本文が見出しで始まるなら、
     最初の見出しの**文言**（`## ` の記法は数えない）

   数字か、意外な事実か、条件付きの結論をそこへ置けているか。
   → 内容を予告するだけの入り（「在宅ワークについて書きます」）は `fail`。
   自分の経緯から入っているなら `weak`。
   **30 字の枠に入っていることと、先頭に置けていることは別**である。
   ただし**字数で線を引かない**。日本語は「〜したら」「〜すると」の条件節が主節の前に来るので、
   この観点が求める「条件付きの結論」を書くと、核は構造的に後ろへ行く。
   字数の閾値を置くと、正しく書いた投稿ほど落ちる。

   見るのは**核より前に何が置かれているか**である。

   - **読者が自分に当たるかを判断する材料**（何をした結果の数字か／どこで測った数字か）
     — 結論の一部なので `pass`。「洗濯機の下に防振マットを敷いて、階下で測ったら」
   - **読者が捨てる材料**（経緯・前置き）— `weak`。「在宅 3 年目で、」「ずっと悩んでいて、」

   **語形で見分けない。** 「〜したら」でも「〜して、」でも役割は同じである。
   見るのは、その句が無いと読者が判断できなくなるかどうか。

2. **記事の要約になっていないか。** その媒体だけで完結して読めるか。
   リンクを踏まなくても 1 つは持ち帰れるものがあるか。
   → ブログの見出しを並べ直しただけなら `fail`。
   記事と同じ順序・同じ役割で、短くしただけなら `weak`
   （媒体ごとに何を担うかは `run-social-post` の媒体ごとの役割を見る）。

   **`fix` に「1 点に絞れ」だけを書かない。** 下限のある媒体で絞ると、
   そのままでは下限を割る。絞ったあとに何を書くかまで書いて、はじめて実行できる指示になる。

   実測（2026-08-29・x-long、下限は実質 1200 字）:

   ```
   1 点に絞った状態                     665 字
   ＋「どう数えたか」を足す            1134 字
   ＋「数えなかったこと」を足す        1234 字
   ```

   足したのは**話題ではなく深さ**である。数え方の線引き（何を 1 回と数えたか）と、
   見なかったもの（なぜ比べなかったか）だけで下限に届いた。
   **記事の節を並べ直すのは、絞れていないから起きるのではなく、深める方向を持っていないから起きる。**
   だから `fix` は「絞れ」＋「そのぶん測り方と外した選択肢を書け」の 2 つで 1 組にする。

3. **短所が入っているか。** 褒めるだけの投稿は、媒体を問わず広告に見える。
   `persona.objection`（買う直前に何を疑うか）へ、この投稿のどこかが答えているか。
   → 短所も合わない条件も 1 つも無いなら `fail`。
   短所はあるが `objection` と噛み合っていないなら `weak`。

4. **口調が案件と揃っているか。** `concept.tone` と照らす。
   同じ書き手が書いたように見えるか。ブログでは言い切っているのに投稿だけ煽っている、
   のような差は `weak`。
   → `concept.tone` と正面から反する語（煽り・断定の強調）があるなら `fail`。

5. **その媒体の読まれ方に合っているか。**
   - `lineBreakRule: "context"` の媒体 — 折る位置が文節と句読点で、意味の切れ目に来ているか。
     字数だけ守って変な位置で折っていないか（機械は位置まで見ない）
   - `linkAllowed: false` の媒体 — 導線をどこへ送るつもりか、読者に分かるか。
     「リンクはこちら」は機械が弾くが、**書いていないせいで行き先が分からない**のはここで拾う
   - `hashtags` — 中身と関係ないタグで数を埋めていないか
   → 導線の行き先が読者に分からないなら `fail`（買えないので実害が出る）。
   折る位置とタグは `weak`。
   **3 項目とも該当規則が無い媒体では `n/a` を出す。** `lineBreakRule` が `"paragraph"` で
   `linkAllowed: true` で `hashtags.max` が 0 の媒体には、この点で見るものが存在しない。
   そこを `pass` と書くと「探したが問題なし」に見えるが、実際は探す対象が無い。
   `n/a` のときは `searched` に**どの規則が不適用なのか**を書く。
   `n/a` は `verdict` の集計に入れない（悪いほうにも良いほうにも数えない）。

6. **数字に条件が付いているか。** 「38kPa」だけが残って、測った状況が消えていないか。
   条件の無い数字は、どこかで見た数字と区別が付かない。

   実際に出てくるのは「条件がゼロ」ではなく「**条件が薄い**」である。線はここに引く —
   **最小要件は「その数字が何の状態を測ったものか」が読める**こと
   （「階下で測ったら」「脱水中に」）。回数・平均・暗騒音まで揃っているかは、この点では問わない。

   → 最小要件を満たさない数字が 1 つでもあれば `fail`（条件の無い数字は広告に見え、
   この harness がいちばん避けたい実害がそこにある）。
   最小要件は満たすが、**足せる余白があるのに足していない**なら `weak`
   （`maxChars` と本文長の差を見る）。余白が無いなら、その媒体で書ける限りの条件が
   付いている状態なので `pass`。

   **他の媒体と比べない。** 「x-long はもっと条件を付けている」を基準にすると、
   短い媒体は x-long が存在する限り永久に `weak` になり、
   **書き手が fix を実行しても判定が動かない**。
   媒体間の比較は `validate-cross-media-consistency.mjs` の担当である。

   **1 と衝突したときはこちらを優先する。** 「数字を先頭へ」（1）と
   「条件が書けないなら数字を落とす」（6）は**条件が長いときに**両立しない。
   短い媒体で必ず起きるわけではない。条件が 1 句で済むなら
   （「階下で測ったら」）、その 1 句が 1 の材料と 6 の最小要件を同時に満たす。
   解決は削る順序の 3 番にあり、**中途半端に数字だけ残すのが一番悪い**とされている。
   条件ごと入るなら数字を先頭へ、入らないなら数字ごと落として定性的に書く。

   **衝突したときは、削る順序 3 番の 3 段を順に見る。**

   1. **条件を数語で足して両立しないか。** 「42dB が 36dB に」に「脱水中に階下で測ったら」を
      足して 8 字。多くの場合ここで終わる。**先に落とすことを考えない**
   2. 足しても入らないときだけ、数字ごと落として定性的に書く
   3. ただし、その数字が `persona.objection` への回答そのものなら**落とせない**。
      「どのくらい下がったのか書いていない」を疑いに挙げている読者に対して、
      数字を落とした投稿は、その疑いが名指ししている失敗例そのものになる

   **2 で落とした投稿の判定はこうなる。** 観点 1 は `pass`（条件付きの結論が先頭にあるので、
   1 が求めるものは満たしている）。`why` に「6 に従って数字を落とした結果」と書く。
   上の「核より前に何が置かれているか」もここでは当てない。

   **ただし観点 3 と 4 が代わりに `weak` になることがある。** 数字を落とす操作は、
   objection への回答を落とす操作と、測ったことを定性で書く操作を兼ねる。
   **`weak` が減らないなら、それは 1 で解けたはずの衝突である。**
   その場合は fix に「条件を数語足して数字を戻す」と書く。
   実際にこの経路をたどった検証があり、数字を落とした版は元の版より悪くなった。

## 出すもの

`--output` が渡されたらそこへ JSON で書く。渡されなければ本文で返す。

```json
{
  "medium": "x-long",
  "campaignId": "ergoone-pro-2026h2",
  "verdict": "weak",
  "standsAlone": "この媒体だけが、測り方の手順そのものを運んでいる。記事は結論から入るので、順序が逆になっている。",
  "findings": [
    {
      "point": "first-30-chars",
      "verdict": "weak",
      "quote": "在宅3年目で、夕方の腰の張りが当たり前になっていました。",
      "why": "自分の経緯から入っているので、スクロールを止める理由がありません。",
      "fix": "「10万円の椅子で腰の張りは減った。ただし部屋を選ぶ」のような、条件付きの結論を先頭へ。"
    },
    {
      "point": "medium-fit",
      "verdict": "n/a",
      "searched": "media-profiles.json のこの媒体の規則を確認。lineBreakRule は paragraph、linkAllowed は true、hashtags.max は 0。3 項目とも該当規則が無い。"
    }
  ]
}
```

`findings` は 6 件（上の例は 2 件だけ抜き出したもの）。
`verdict` は 6 点のうち最も悪いものを取る（`pass` < `weak` < `fail`。`n/a` は数えない）。

**キーは verdict で決まる。**

- `weak` / `fail` — `quote`（無いことを咎めるときは宣言側と最も近い箇所）/ `why` / `fix`
- `pass` — `quote` も `fix` も持たず、`searched` に**探した範囲**を書く
  （見た宣言側のフィールド / 投稿のどこを走査したか / 見つからなかったもの）
- `n/a` — `searched` に**どの規則が不適用なのか**を書く（観点 5 のみ）

`undeclaredClaims` は、**本文が触れているのに `claimRefs` に無い主張の id** を並べる。
無ければ省く（空配列も書かない）。判定には数えない — `verdict` は 6 点だけで決まる。
6 点のどれでもないので findings に入れる場所が無く、かつ機械も見ていない。
**置き場を作らないと、気づいた人が黙って通すことになる。**

```json
"undeclaredClaims": ["c3", "c4", "c5"]
```

id を挙げるには本文と `campaign-brief.json` の `claims` を突き合わせる必要がある。
**先に `claimRefs` を読まないこと** — 宣言を先に見ると「この投稿は c3 を運んでいない」と
読めてしまい、本文にある c3 が見えなくなる。本文を読んでから宣言を見る。

**6 点すべてが `pass` の投稿では、6 件の findings は読む側にほぼ何も残さない。**
そこで `standsAlone` を必ず 1 行書く — **この媒体だけが運んでいるもの**は何か。
6 件の「探して何も無かった」より、この 1 行のほうが次に読む人の役に立つ。
書けないなら、それは観点 2（要約落ち）が `pass` でないということである。

## やらないこと

- 直さない。指摘して返すだけ
- **`blog-content/` 配下へ書き込まない。** `Write` は `--output` の JSON を出すためだけに使う
- 媒体間の数値の食い違いは見ない（`validate-cross-media-consistency.mjs` の担当）
- 字数を数え直さない（機械が済ませている）
- 「もっと親しみやすく」のような、`concept.tone` に書いていない好みを持ち込まない
