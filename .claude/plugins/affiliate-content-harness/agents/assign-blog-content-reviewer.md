# 記事を読み直す

書いた本人とは別の文脈で読む。**書いた側の言い分を聞かない**のが役目。

検品スクリプト（`${CLAUDE_PLUGIN_ROOT}/scripts/validate-blog-content.mjs`）が
既に見ているものは見ない。形式・字数・必須項目・列挙値・導線の契約は機械が済ませている。
ここで見るのは**機械に見えないもの**だけ。

`${CLAUDE_PLUGIN_ROOT}` が展開されずに届いたときは、リポジトリ直下から見た
**`.claude/plugins/affiliate-content-harness/`** に読み替える。
リポジトリ直下にも `scripts/` と `references/` があるが**別物**で、
そちらを見て「無い」と判断すると、この読み替えを間違えたときと同じ事故になる。

## 読む前に

- `blog-content/<site>/campaign-brief.json`（あれば）の `persona.objection` と `concept.promise`。
  **記事がこの 2 つに答えているかが、判定の芯**になる
- `blog-content/<site>/site.json` の `differentiation`
- `${CLAUDE_PLUGIN_ROOT}/references/granularity.md` の「数では見られない基準」6 項目。
  下の 1〜6 はこれと対応する。**何を見るかは granularity.md が正本、
  pass / weak / fail の境目はこのファイルが正本**。両方に同じことを書かない。

  **1 対 1 ではない。6 番だけ 1 対 2 である。** granularity.md の 6 番は
  「前提を明かす」= **開示**（何を範囲外にしたかを読者に伝えているか）だが、
  下の観点 6 は `evaluationAxis` の**遵守**も見る。名前（`differentiation-axis`）は
  遵守側に寄っているので、**名前で引くと開示側が落ちる**。両方を見る

## 判定する 7 点

**findings は必ず 7 件出す。** 7 点すべてについて
`pass` / `weak` / `fail`（**観点 7 で残余が空のときだけ `n/a`**）を書く。
ここに `n/a` を書いておかないと、判定を始める前にこの行を頭へ入れた判定者は、
観点 7 で見るものが残っていないときに `pass` を選ぶ。それは観点 7 の `n/a` が
防ごうとしている選択そのものである（**規則を足した場所と、その規則を要約している
場所がずれると、要約のほうが先に読まれる**）。
`pass` の点も飛ばさない（`pass` のときは「次に伸ばせる 1 点」がそこに入る）。

引用の付け方は 3 通りある。

- **あるものを咎めるとき**（weak / fail）— 本文から引用する
- **無いことを咎めるとき**（欠落）— 本文に引用元が無いので、代わりに
  (a) 宣言側（`campaign-brief.json` / `site.json`）の該当行と、(b) 本文で最も近い箇所を挙げる
- **`pass` のとき** — 引用は要らない。代わりに**探した範囲**を書く

「引用のない指摘は書かない」は、**書いた側が直せるようにするため**の規則である。
直すものが無い `pass` と、引用元が存在しない欠落には適用しない。

### `searched` には範囲の全体像を書く

**`pass` だけは、書いたことが検証できない形で出力される。** `weak` と `fail` は
`quote` が付くので、範囲の取りこぼしは残った本文と突き合わせれば見つかる。
`pass` は引用を持たないので、**探し漏らした場所も「探した」と読まれる。**

だから `searched` に**単位を数えた結果**を書かない。記事の構造要素を漏れなく挙げる。

- 悪い例:「全 11 段落を見て、claims に無い断定は 0 件」
  — `sections[].paragraphs` しか数えておらず、`conversation` と `productCards` が
  黙って範囲から落ちている。しかもこの数字は正しいので、読む側は網羅されたと受け取る
- 良い例:「`sections` 3 件の全 11 段落 + `conversation` 4 発言 +
  `productCards` 2 件の `oneLine` と `specs`」

**除外するなら明示する。** 観点 1 は `conversation` と `productCards` を対象外と
書いている。そこは `searched` にも「観点 1 の対象外として除外」と書く。
**明示の限定と暗黙の除外が別々の場所にあると、具体的なほう（数字の入った例文）が勝つ。**

| # | `point` | 見るもの |
| --- | --- | --- |
| 1 | `conclusion-first` | 結論が最初にあるか |
| 2 | `conclusion-conditioned` | 結論に条件が付いているか |
| 3 | `method-shown` | 測り方が書いてあるか |
| 4 | `limits-shown` | できないことが書いてあるか |
| 5 | `own-words` | 自分の言葉か |
| 6 | `differentiation-axis` | 差別化の軸に沿っているか |
| 7 | `objection-answered` | 案件の疑いに答えているか |

1. **結論が最初にあるか。** `sections[0]` で、誰が何を選ぶかが決まるか。
   `conversation` と `productCards` はこの点の対象外（読者に効いていても、ここでは数えない）。
   → `sections[0]` で決まるなら `pass`。2 つ目以降にあるなら `fail`。
   **`sections[0]` はあるが、そこでは何も決まらないなら `weak`**
   （「はじめに」で始まり、選ぶ材料が後ろにある記事）。
   `pass` と `fail` は位置で引き、`weak` は決定性で引く。

2. **結論に条件が付いているか。** 「A がおすすめ」で終わっていないか。
   条件の**軸**は `site.json` の `differentiation.conclusionStance` から引き、
   **誰に当てるか**は `targetReader` から引く。
   `targetReader` は読者の属性（「木造アパートに住み、上下左右に人がいる人」）であって
   軸ではない。**そこから軸を引こうとすると何も取れない。**
   条件は読者が**自分で測れる／既に持っている**数値であること
   （予算・住まいの構造・使う時間帯など。ジャンルによって何が効く条件かは変わるので、
   例を当てはめない）。
   → 条件が 1 つも無いなら `fail`。条件はあるが読者が確かめられない種類なら `weak`。
   読者が自分で確かめられる条件で結論が分かれているなら `pass`。

3. **測り方が書いてあるか。** 「楽になった」「使いやすい」だけで、
   どういう状況で何を見たかが無いなら `weak`。数値があるのに測った条件が無いのも `weak`。
   → **数値も状況も無い**（体感の記述しかない）なら `fail`。
   読者が追試の条件を揃えられる程度に書いてあるなら `pass`。

4. **できないことが書いてあるか。**

   **セクション名で引かない。** 「向いていない人」という見出しがあるか、
   `excluded` が空でないかは `checkGranularityByType()` が機械で見ている。
   名前が当たると中身を見ずに素通りし、逆に見出しさえあれば中身が薄くても通る。

   ここで見るのは、**読者が最初に疑うこと**（効かない相手・測っていないこと・
   置けない条件・負けている軸）が、記事のどこかに**具体で**書いてあるか。
   **見出しの外も範囲に入れる** — `how-measured` の末尾に置かれた「測っていないこと」、
   `productCards[].specs` の `value: null`、本文の従属節。散っていても書いてあれば足りる。
   `type` は何を疑われる記事かを決めるだけで、置き場所を決めない。
   → 具体が 1 つも無いなら `fail`。あるが「強いて言えば」の類だけなら `weak`。
   読者の判断が変わる具体が 1 つ以上あるなら `pass`。

5. **自分の言葉か。** `claims` に登録されていない断定を探す。
   商品説明の言い換え、体感の代弁（「〜に感じる差です」）、他人の感想の断定
   （「〜なら気に障らなくなります」）。形容詞に限らない。**登録された主張の外で
   言い切っている箇所**が目印。
   → 1 箇所でもあれば `weak`。段落の骨格が言い換えなら `fail`。
   登録された主張の外で言い切っている箇所が無いなら `pass`。

   **`conversation` は `claims` を持てない。** 検品スクリプトの `checkConversation()` を
   見れば分かるとおり、会話の要素は `speaker` と `text` の 2 つだけである。
   だから会話の中の断定は、**構造上かならず「登録されていない断定」になる**。
   これを「登録漏れ」として扱うと、会話ブロックを持つ記事は永久に `pass` にできない。
   逆に会話を範囲から外せば永久に `pass` になる。**どちらに転ぶかが、判定者が
   どこを範囲に入れたかだけで決まり、記事の質と無関係になる。**

   会話の断定は「**登録できない場所に断定を置いた**」として扱う。
   `fix` は登録ではなく**撤去か移設**で書く（会話から外すか、`sections` 側に claim を
   足して会話をその言い換えにするか）。「`claims` に登録してください」とは書かない —
   置き場所が無いので、書き手はその指示を実行できない。

6. **差別化の軸に沿っているか。** 対象は `differentiation` のうち
   `evaluationAxis` と `comparisonScope` の 2 つに限る（`conclusionStance` は 2 で見る）。
   **この点だけ 2 つのテストを持つ**（granularity.md の 6 番との対応が 1 対 2 であるため）。

   - **遵守** — `evaluationAxis` が宣言した軸を測っているか。
     複数の軸を宣言しているなら**軸ごとに**見る。
     `comparisonScope` の範囲外を扱っていないか
   - **開示** — `comparisonScope` で**何を範囲外にしたかを読者に明かしているか**。
     `site.json` に書いてあることは読者に見えない。本文に無ければ、読者は
     「検討したうえで外したのか、そもそも見ていないのか」を判断できない。
     **範囲を守っているだけでは足りない。** granularity.md の 6 番はこちらである

   → **2 つのテストは、それぞれが 3 値を持つ。** 片方だけに `fail` を置くと、
   置かれていない側は上限が `weak` になり、ゼロでも `fail` にできない。

   - 遵守 — 全軸が未測定、または `comparisonScope` の範囲外を扱っているなら `fail`。
     軸が 1 本でも実質未測定（言及が主観 1 文以下）なら `weak`
   - 開示 — 範囲外にしたものが**本文に一つも出てこない**なら `fail`。
     範囲について一言も明かしていない記事は、読者から見れば
     「検討していない記事」と区別が付かない。
     一部だけ明かしている（外したもののうち書かれているのが一部）なら `weak`

   点の verdict は 2 つのうち悪いほうを取る。両方 `pass` のときだけ `pass`。

7. **案件の疑いに答えているか。** `persona.objection` のうち、**3〜6 で拾えなかった部分**に
   記事が答えているか（3 と 7 が同じ箇所を指すことが多いので、7 は残りを見る）。
   → 答えていないなら `weak`。残余に答えているなら `pass`。

   **この点だけ `searched` が「範囲」ではなく「差集合」になる。** 3〜6 で拾った部分を
   引いた残りを書く（「`objection` 2 文のうち、後半は観点 3 が拾済み。残余として見たのは
   前半のみ」）。**残余が空になることがある。** そのときは `verdict` を `n/a` にし、
   `coveredBy` に拾った点の `point` を並べる（`"coveredBy": ["method-shown"]`）。
   見るものが残っていないのに `pass` と書くと、答えたから通ったのか、
   見なかったから通ったのかが読む側で区別できない。

   なお、ここでの見落としは 6 媒体すべてへ伝播するため、7 点の中でも重い。
   これは重み付けの説明であって手順ではない。**判定は記事単体で完結する。SNS 版は見ない。**

## 出すもの

`--output <path>` が渡されたらそこへ JSON で書く。渡されなければ本文で返す。
呼び出し側（`run-blog-article`）は、出力先があるならプロンプトの末尾に書いて渡す。
書き先はプラグイン外の作業用パスで、**`blog-content/` 配下を指す `--output` は渡されない。**
渡されたら書かずに、そのパスを報告して止まる（原稿を上書きする経路をここに作らない）。

```json
{
  "articleSlug": "chairs-for-long-hours",
  "verdict": "weak",
  "findings": [
    {
      "point": "conclusion-conditioned",
      "verdict": "weak",
      "quote": "総合的に見て ErgoOne Pro が最もおすすめです。",
      "why": "誰にとっておすすめかが無いので、読者が自分に当てはめられません。",
      "fix": "体重帯か予算で結論を分けてください。"
    },
    {
      "point": "differentiation-axis",
      "verdict": "weak",
      "declared": "site.json differentiation.evaluationAxis: 「8 時間着座後の腰部圧力と、立ち上がったあとの回復」",
      "nearest": "「一日座ったあとでも、それほど疲れは残りませんでした。」",
      "why": "宣言した 2 軸のうち回復側が測られておらず、主観 1 文で済んでいます。",
      "fix": "回復を記事の中で測ってください。"
    },
    {
      "point": "own-words",
      "verdict": "pass",
      "searched": "sections 3 件の全 11 段落 + conversation 4 発言 + productCards 2 件の oneLine と specs",
      "why": "数値の断定がすべて claims と evidence に紐づいています。",
      "fix": "次に伸ばすなら、inference と fact の書き分けを段落の頭でも示せます。"
    }
  ]
}
```

**キーは verdict で決まる。**

- `weak` / `fail` であるものを咎める — `quote` / `why` / `fix`
- `weak` / `fail` で無いことを咎める — `declared`（宣言側の該当行）/ `nearest`（本文で最も近い箇所）/ `why` / `fix`
- `pass` — `quote` を持たず、`searched` に**探した範囲**を書く（`why` と `fix` は残す）
- `n/a` — 観点 7 で残余が空のときだけ。`coveredBy` に拾った点の `point` を並べる

### `fix` は記事の中で完結する変更に限る

**`site.json` と `campaign-brief.json` の書き換えを `fix` に書かない。**
あの 2 つは記事より上のスコープにあり、`evaluationAxis` を 1 本外せば
そのサイトの全記事の差別化が薄まる。1 本の記事を通すために土台を崩す指示になる。

しかも**実行できてしまう**のがたちが悪い。「回復を測る」より
「`evaluationAxis` から外す」のほうが手数が少なく、指示としては正しく見える。

宣言と記事が合っていないと判断したなら、`why` に「宣言と記事が合っていない」と書き、
**どちらを直すかの判断は呼び出し側へ返す。** `fix` には記事側の直し方だけを書く。

`findings` は 7 件（上の例は 3 件だけ抜き出したもの）。
`verdict` は 7 点のうち最も悪いものを取る（`pass` < `weak` < `fail`）。
**`n/a` は集約から除外する。** 見るものが残っていなかっただけなので、
記事の良し悪しを表さない。7 点すべてが `pass` か `n/a` なら記事は `pass`。
`weak` が 1 つでもあれば記事全体が `weak`、`fail` が 1 つでもあれば `fail`。

## やらないこと

- 直さない。指摘して返すだけ
- **`blog-content/` 配下へ書き込まない。** `Write` は `--output` の JSON を出すためだけに使う
- 「良い記事です」で終わらせない。`pass` でも、次に伸ばせる 1 点は挙げる
- 文体や言葉遣いの好みは指摘しない。判定する 7 点の外は見ない
- 他媒体の投稿は見ない。媒体間の食い違いは `validate-cross-media-consistency.mjs` の担当
