# affiliate-content-harness

1 つのアフィリエイト案件から、ブログ記事と 5 媒体ぶんの投稿を、
**主張が食い違わない状態で**出すための道具一式。

ここは「何があるか」と「規則をどこに書くか」。
**詰まったときに何をするかは [RUNBOOK.md](RUNBOOK.md)** — 公開前の入口、
検品が緑なのに壊れているとき、判定を外部に依頼するとき、定義を直したあとの洗い直し、
回すのをやめて人に上げる線。

## 解こうとしている問題

媒体ごとに原稿を書き下ろすと、こうなる。

> ブログ: 「8 時間着座後の腰部圧力は平均 38kPa」
> X 長文: 「平均 38kPa」
> Instagram: 「約 40kPa」

3 つとも単体では正しく見える。根拠も付いているし、どの検品も通る。
気づけるのは 2 つ以上を並べて読んだ人だけ — つまり読者だけ。

この harness は、主張・根拠・買う導線を**案件ブリーフ 1 箇所**に集め、
各媒体はそこから継ぐ形にする。そのうえで、媒体をまたいだ突合を機械でやる。

## 使う順

```
/create-campaign            案件を立ち上げ、最初のブログ記事まで書く
  ├ run-campaign-brief      読者・約束・主張・根拠・導線・展開先を決める
  ├ run-blog-create         （ブログがまだ無いとき）設計図を作る
  └ run-blog-article        記事を 1 本書く

run-social-post             各媒体へ展開する（媒体の数だけ繰り返す）

/publish-content-set        公開前に一式をまとめて確かめる
```

**ブログを先に書く。** Instagram は本文にリンクを置けないので、導線をブログへ送る。

## 中身

### skills（4）

| | 役目 |
| --- | --- |
| `run-campaign-brief` | 案件ブリーフを作る。全媒体の正本 |
| `run-blog-create` | ブログの設計図を作る |
| `run-blog-article` | 記事を 1 本書く。最初の媒体 |
| `run-social-post` | X 長文 / X 短文 / Instagram / note / Facebook へ展開する |

### agents（4）

| | 役目 |
| --- | --- |
| `assign-blog-content-reviewer` | 記事を別の文脈で読み直す（7 点） |
| `assign-social-post-reviewer` | 投稿を「スクロールしている人」として読む（6 点） |
| `apply-style-genome` | 6 媒体が同じ書き手に見えるか揃える |
| `optimize-media-length` | 入りきらない／届かないときに、何を削り何を足すか決める |

4 本とも `isolation: fork`。frontmatter の `fork` は**独立コンテキスト**で、
会話履歴を継ぐのは `inherit` のほう。Agent ツールの `subagent_type: "fork"`
（親の context を継承する）と**意味が逆**なので注意する。
レビュアー 2 本はこの独立性が存在理由なので、`inherit` へ変えない。

### commands（2）

`/create-campaign` — 案件を立ち上げる
`/publish-content-set` — 公開前に一式を確かめる

### hook（1）

`guard-blocked-affiliate-link`（PreToolUse / Write・Edit）。保存される前に 3 つを止める。

- 導線があるのに `blockedReason` が同居している（理由は画面に出ない）
- `affiliateUrl` が https でない
- ASP 発行 URL にパラメータを足している（規約違反。リンクは動くので気づけない）

### scripts（5検品 + content-set入口）

```bash
P=.claude/plugins/affiliate-content-harness

node $P/scripts/validate-content-set.mjs             --content-set blog-content/<site>

# 以下は、執筆途中に対象を絞って直すときの個別入口
node $P/scripts/validate-campaign-brief.mjs          --campaign C [--site S]
node $P/scripts/validate-blog-content.mjs            [--site S] [--article A ...] [--campaign C] [--all]
node $P/scripts/validate-media-post.mjs              --post P [--post P ...] [--campaign C]
node $P/scripts/validate-affiliate-disclosure.mjs    --campaign C [--article A ...] [--post P ...]
node $P/scripts/validate-cross-media-consistency.mjs --campaign C [--article A ...] [--post P ...]
```

公開前は `validate-content-set.mjs` を使う。案件の `media` と実ファイルを突き合わせ、
不足・予定外・同一媒体の重複を止めたうえで、下の 5 検品へ同じファイル一覧を渡す。
個別入口は、案件や原稿を作っている途中に短いフィードバックを得るために残してある。

終了コード: `0` 通過（`△` は残っていてもよい）／ `1` 止めるものがある／ `2` そもそも読めなかった。
1 と 2 を分けているのは、「直せば通る」のか「渡すファイルを間違えた」のかを呼ぶ側が
見分けられるようにするため。

共有の判定（日付・slug・根拠の要求・導線の契約・言い換え禁止）は
`scripts/lib/harness.mjs` に集約してある。各 script へ書き写すと、片方だけ直した日に
**同じものを別の場所へ入れたら怒られた**という、理由の見えない壊れ方になる。

### templates（11）

`site.json`（設計図）／`campaign-brief.json`（案件）／記事 4 種（`article.ranking` `article.review`
`article.comparison` `article.guide`）／投稿 5 媒体（`post.x-long` `post.x-short` `post.instagram`
`post.note` `post.facebook`）。

投稿 5 件は**同じ案件を 5 通りに書いた例**。並べて読むと、何を書き直し（文章・順番・入口）、
何を揃えたか（数値・条件・導線）が分かる。`_` で始まるキーは注記なので写さない。

### そのほか

`plugin-composition.yaml` — このプラグインの自己記述（不変条件・呼び出しの向き・規則の正本）
`EVALS.json` — 実際に動かして確かめた記録。設計の言い分ではなく実行の結果だけを書く

## 規則をどこに書くか

| 規則 | 正本 |
| --- | --- |
| 媒体ごとの長さ・見出し・改行・タグ・リンク可否・表記 | `references/media-profiles.json` |
| ブログパターン・収益モデル・固定ページ・テーマ | `src/domain/authoring/site-blueprint.ts`（実行時に読む） |
| 言い切りの印（fact / inference / opinion） | `src/application/read-models/published-article.ts`（実行時に読む） |
| ASP 発行 URL へ足してはいけないもの | `src/domain/monetization/affiliate-link.ts`（実行時に読む） |
| 画面で使う言葉 | `src/presentation/ui/copy.ts` |
| 削る順序 | `skills/run-social-post/SKILL.md` の「入りきらないときに何から削るか」 |

**列挙値をこのプラグインへ書き写さない。** 書き写すと、コード側に選択肢を足した日に
ここだけ古くなり、「正しい入力を弾く検品」という最も質の悪い壊れ方になる。

媒体を足すときは `references/media-profiles.json` へ 1 エントリ足す。
生成側と検品側が同じファイルを読むので、両方が追随する。

## 検査を足すときにやること

新しく「この形は止める」という検査を script へ足したら、**その検査が落とす形の文字列を
harness 全体に grep する。** 落とす形は、たいてい**それを説明している場所**に例として残っている。

```bash
grep -rn '<落とす形>' templates/ references/ agents/ skills/ README.md
```

例と本文の両方を直す。例だけ直すと、本文が古い形を明示的に肯定したまま残り、
書き手は検品が落ちたときに **skill が間違っているのか検品が間違っているのかを判断できない**。

**見出しに数を書くのは、数えられる先があるときだけにする。** 「### skills（4）」は
`skills/` の中身が答えなので、ずれたら誰でも確かめられる。散文の項目数には答えになる先が無く、
項目を足した人が見出しを直さないと古くなるだけなので、**数を書かない**
（実際に「見つけにくい壊れ方（3 つ）」の下に 5 件ある状態で見つかった）。

## 歯止めを書くときにやること

資料（`notes` や役割記述、agent の定義）へ「これはこう読むな」と書き足す前に、
**資格の側で切れないかを一度見る。**

| | 形 | 次に似たものが来たら |
| --- | --- | --- |
| 資格 | そもそも成立しない形にする | 何も書き足さなくても効く |
| 例外 | 使ってよいものへ「ただしこれは除く」と足す | もう一度書く必要がある |

この harness の実例で言うと、記事の claim id を `a1..aN` にしたのは資格側（名前空間が違うので
名前での照合が成立しない）、`checkedAgainst` に「出典は指摘と同じ軸を扱っているものに限る」と
書いたのも資格側（軸が違う行は出典の資格を持たない）。`media-profiles.json` の `notes` へ足した
「呼びかけを増やす理由にはならない」は例外側で、**似た行を足すたびに歯止めも足すことになる。**

例外が悪いわけではない。資格で切れないものは例外で書く。順序の話である。

## 項目を足したときにやること

数を書いた宣言（「判定する 7 点」「findings は必ず 6 件出す」「出典として使えるのは 4 つある」）は
**足した項目が属するものだけ数え直す。**

**まず、その数が要るか見る。** 数が内容の一部として働いている宣言（「判定する 7 点」は
7 という約束が判定の中身）は残す。目次以上の働きをしていない数（この README の
「見つけにくい壊れ方」の見出しに書いてあった数がそれで、いまは消してある）は
**消すほうが強い。** 直すと次に足す人が数え直す作業を引き継ぐが、消せばその作業ごと消える。

**この段落で数を書かないのも同じ理由。** 消した数をここへ例として引き写すと、
項目が増えた日にこの説明文のほうが古くなる。実際そうなった。

残すと決めたものを探す。

```bash
grep -rnE '^#{1,6} .*[0-9０-９]+ ?(つ|件|点|項目|種|通り)' . --include=*.md
grep -rnE '[0-9０-９]+ ?(つ|件|点|通り)(ある|です|に限る|書く|出す)' . --include=*.md
grep -rnE '[0-9０-９]+ ?(回|度)(起き|出|あっ|ある)' . --include=*.md
```

**この 3 行は出発点であって、当たり判定そのものではない。** 数を書く言い方は他にもあり、
実際 3 行目は後から足したものである（最初の 2 行は `つ / 件 / 点 / 通り` しか見ておらず、
「4 回起きている」を落としていた）。**当たらない言い方があると思って読む。**
パターンを足していく形では、同じ穴をくり返す。

**前の節の grep とは、当たったものの意味が違う。** 混ぜると「11 件当たった」を
11 件の欠陥と読む人が出る。

| | 当たったものは | 当たり判定 |
| --- | --- | --- |
| 禁止する形を足したとき | **即、欠陥**。全部直す | 機械 |
| 項目を足したとき | **数え直す対象**。合っていることのほうが多い | 目視 |

**律速は grep ではなく目視のほう。** 実測で、この 2 行は 11 件挙げたが、
挙がった行を数え上げる側が 2 件落とした（`commands/publish-content-set.md:19` と
`skills/run-blog-article/SKILL.md:113`。どちらも「2 つある」で、正規表現には当たっていた）。
**挙がった行は全部表に書き出してから数える。**読みながら数えると落ちる。

数え直した結果を報告するときは、**走らせたコマンドも一緒に書く。** 結論だけだと読む側は
数え直せない。上の 2 件が見つかったのも、報告にコマンドが付いていて再実行できたからである。
**数え上げの結論は、それ単体では検証できない形をしている**（判定の `pass` に引用が無いのと同じ）。

**この形はくり返し起きている。** 実例は `EVALS.json` に同型の defect として記録してある
（数えるならそこで数える。ここに件数を書くと、次に起きるたびに直す数がもう一つ増える）。
共通しているのは、**規則を足した場所と、それを要約・例示している場所が
別のファイルにあり、読む人は要約・例示のほうを先に読む**こと。
規則の側だけ新しくしても、先に読まれるのは古いほうである。

## 見つけにくい壊れ方

1. **`blockedReason` が黙って消える。** 買う導線を出さない理由は、
   `affiliateUrl` と `trackingCode` が**両方とも無いとき**にしか表示されない。
   URL を残したまま理由を書くと、理由は消え、購入ボタンが出る

2. **広告表記の向きが媒体で反転する。** ブログは本文に書かない（画面が自動で出す）。
   SNS は本文に書く（誰も出してくれない）。移し替えるときに落ちる

3. **媒体間の数値の食い違い。** 単体検品を何回通しても出てこない。
   `validate-cross-media-consistency.mjs` を回さないかぎり見つからない

4. **参照を書かないと、その突き合わせ自体が効かない。** 記事は claim の
   `sourceClaimId`、投稿は `claimRefs` で案件の主張を指す。書いていない成果物は
   検査の対象から外れ、**通ったのではなく見ていない**状態になる。
   5 番の検品は「何も参照していない成果物」を `△` で出すので、そこを読む

5. **前後の値のうち、後ろだけがずれる。** 「42dB から 36dB へ」のような主張は、
   前の値が合っていると食い違いに見えない。しかし読者の判断材料は後ろの値のほう。
   5 番の検品は「案件が言っている値のうち、ここに無いもの」を `△` で出す。
   要約で片方だけ運んだのなら、そのままでよい

6. **検品に何も渡さないのが、いちばん簡単な通し方だった。** 検品は「渡されたものを
   見る」形なので、フラグ名を打ち間違えると**何も渡されなかった状態と区別がつかない**。
   実際に `--posts`（正しくは `--post`）で横断検品を呼んだら
   「0 件の食い違いを見ました。止めるもの 0 件」と `exit 0` が返った。
   `lib/harness.mjs` の `checkFlags` が知らないフラグを `exit 2` で止めるようにしたが、
   **これは名前の打ち間違いしか見ていない。** zsh は変数展開で単語分割をしないので、
   `node … $args` は `--post a.json --post b.json` を 1 個の引数として渡す。
   配列（`POSTS=(); POSTS+=(--post "$f")`）かコマンド置換で組み立てる。
   4 番と同じ形で、**通ったのではなく見ていない**

**`exit 0` は「全部見て問題なかった」ではなく「見たものに問題がなかった」。**
何件見たかは最後のまとめ行（「6 件の成果物を突き合わせました。」）に出る。
`止めるもの 0 件` の前に、**その数を読む**。

## 旧 blog-authoring との関係

かつて `.claude/plugins/blog-authoring/` にあったものを統合した（`supersedes`）。
承継したのは `validate-blog-content.mjs`・記事テンプレート 4 種・設計図テンプレート・
`references/` 3 種・記事レビュアー。**旧プラグインは 2026-08-29 に削除済みで、もう存在しない。**

`plugin.json` と `plugin-composition.yaml` の `supersedes` は残してある。あれは
「どこから来たか」の記録で、**現在そこにあるという意味ではない**。消すと、
承継物を旧プラグインの版と見比べたい人が辿る先を失う。
